# Runbook — деплой и откат

> **Кто выполняет:** владелец / дежурный. **Когда:** плановый релиз; откат неудачного релиза.
> **Источник правды:** [`.github/workflows/deploy.yml`](../../.github/workflows/deploy.yml). Изменил workflow — обнови этот документ в том же PR (rule 55).
> **Production gate:** мерж и зелёный CI не запускают деплой. Workflow запускается вручную на текущем Docker-verified SHA `master` только после локального Docker evidence и выполнения `FA-06/PG-03`, CTO sign-off и явного подтверждения `confirm_production`.
> **Главное правило отката:** если после деплоя стало хуже — **сначала откатывай, потом разбирайся**. Дебаг на горящем проде дороже отката.

---

## 1. Как устроен деплой (факты из workflow)

```
локальный Docker evidence → merge/push в master → отдельный ручной запуск workflow "Build & Deploy"
   ├─ build+push образов в GHCR:
   │     ghcr.io/valerijkk/hub/backend :latest и :<SHA>
   │     ghcr.io/valerijkk/hub/frontend:latest и :<SHA>
   └─ SSH на прод-хост:
         docker pull обоих образов по <SHA>
         cd /opt/hub/deployments
         IMAGE_BACKEND=... IMAGE_FRONTEND=... \
           docker compose -f docker-compose.prod.yml --env-file .env -p hub \
           up -d --force-recreate backend hub-mail livekit
         docker rm -f frontend && docker run -d --name frontend <FRONTEND_IMAGE>
         docker start/restart hub-caddy-1
         docker image prune -af --filter "until=72h"
```

Существенные следствия, которые надо держать в голове:

| Факт | Следствие |
|------|-----------|
| Образы тегируются **коммитным SHA** | Откат = передеплой предыдущего SHA. Возможен **только пока образ не вычищен**. |
| `docker image prune -af --filter "until=72h"` | **Окно отката ≈ 72 часа.** Старше — образа на хосте нет, нужно тянуть из GHCR заново. |
| `--force-recreate backend hub-mail livekit` | Эти три сервиса пересоздаются каждый деплой. ⚠️ `livekit` пересоздаётся → **активные звонки рвутся**. |
| `frontend` пересоздаётся через `docker rm -f` + `docker run` | Frontend вне compose-оркестрации; при ручных операциях его тоже надо поднимать вручную. |
| БД/Redis/NATS/SeaweedFS **не трогаются** деплоем | Данные переживают деплой; откат кода не откатывает схему БД (см. §5). |
| Compose-проект `-p hub` | Все ручные `docker compose` команды на проде **обязаны** включать `-p hub`, иначе создадут второй набор контейнеров. |

## 3. Деплой

Штатный путь — **ручной GitHub Actions gate**: после локального Docker evidence для текущего SHA открыть workflow `Build & Deploy` на ветке `master`, включить `confirm_production` и запустить его. Запуск с другой ветки или без подтверждения будет пропущен. Если `master` продвинется после dispatch, deploy job сравнит remote `master` с выбранным SHA и завершится ошибкой до `git reset` и перезапуска контейнеров; запустите workflow заново на новом Docker-verified SHA.

☐ Убедиться, что выбран текущий Docker-verified SHA `master`, и вручную запустить workflow «Build & Deploy».
☐ Дождаться завершения build и deploy jobs в GitHub Actions.
☐ Проверить, что задеплоился ожидаемый SHA (workflow печатает в конце `Deployed <SHA> <git log>`).
☐ Пост-деплой проверка (§4.1) — **обязательна**, деплой без проверки не считается завершённым.

### Ручной деплой (если workflow недоступен)

⚠️ Только когда GitHub Actions не работает, а деплой необходим.

```bash
ssh <prod-host>
SHA=<нужный-коммит-sha>
BACKEND_IMAGE="ghcr.io/valerijkk/hub/backend:${SHA}"
FRONTEND_IMAGE="ghcr.io/valerijkk/hub/frontend:${SHA}"

docker pull "${BACKEND_IMAGE}"
docker pull "${FRONTEND_IMAGE}"

cd /opt/hub/deployments
IMAGE_BACKEND="${BACKEND_IMAGE}" IMAGE_FRONTEND="${FRONTEND_IMAGE}" \
  docker compose -f docker-compose.prod.yml --env-file .env -p hub \
  up -d --force-recreate backend hub-mail livekit

docker rm -f frontend 2>/dev/null || true
docker run -d --name frontend "${FRONTEND_IMAGE}"    # TODO(ops): сверить остальные флаги run с workflow
docker restart hub-caddy-1 2>/dev/null || true
```

> `TODO(ops)`: в workflow у `docker run frontend` есть дополнительные флаги (сеть/порты/labels), обрезанные в этом конспекте. Перед первым прямым SSH-деплоем — выписать полную команду из `deploy.yml` сюда, чтобы fallback-путь не расходился с workflow.

## 4. Проверка после деплоя

### 4.1 Обязательный минимум (первые 5 минут)

☐ Контейнеры подняты:

```bash
docker compose -f docker-compose.prod.yml -p hub ps
```

☐ Health:

```bash
curl -sf http://127.0.0.1:3000/api/health | head -c 300; echo
```

☐ Логи backend без паник и повторяющихся ошибок:

```bash
docker compose -f docker-compose.prod.yml -p hub logs --tail=100 --timestamps backend
```

☐ Реальный пользовательский сценарий (не только curl): открыть UI, залогиниться, выполнить одно действие в ключевом модуле.

### 4.2 Наблюдение (следующие 30 минут)

☐ Метрики не деградировали: 5xx-rate и p95 — [monitoring-and-alerts.md](monitoring-and-alerts.md) §3.1–3.3.
☐ Не сыпятся алерты. Помни: `HubBackendMetricsDown` может кратковременно сработать на рестарте — это ожидаемо.
☐ При росте 5xx/p95 в течение 10–15 минут после деплоя → §5 «Откат», не «подождём, может само».

## 5. Откат

### 5.1 Решение об откате

Откатывай **сразу**, без длительного анализа, если после деплоя:

- сервис недоступен или в цикле рестарта;
- массовые 5xx (алерт `HubHighHTTP5xxRate`);
- сломан ключевой пользовательский сценарий (логин, создание задачи, отправка сообщения);
- p95 вырос кратно.

Разбор причины — после восстановления, по сохранённым логам.

### 5.2 Процедура отката (передеплой предыдущего SHA)

☐ Взять SHA, зафиксированный в §2 (или `git log` предыдущего успешного релиза).
☐ Проверить, что образ ещё есть на хосте (окно 72 часа) либо тянется из GHCR:

```bash
docker images | grep -E 'hub/(backend|frontend)' | head
docker pull ghcr.io/valerijkk/hub/backend:<PREV_SHA>     # если локально нет
```

☐ Выполнить ручной деплой (§3, «Ручной деплой») с `SHA=<PREV_SHA>`.
☐ Проверка по §4.1 — полностью, как при обычном деплое.
☐ Зафиксировать в журнале: что откатили, с какого на какой SHA, во сколько.

### 5.3 Если образа предыдущей версии уже нет

Причина: `prune --until=72h` вычистил, и в GHCR тега тоже нет (`TODO(ops)`: подтвердить retention-политику GHCR).

Тогда — пересборка из нужного коммита:

☐ Если для этого точного SHA уже существует исторический запуск production workflow — выполнить его re-run. Новый `workflow_dispatch` запускается только с текущего `master` и произвольный старый SHA не принимает.
☐ Надёжный fallback: собрать образ вручную из нужного тега/коммита, запушить SHA-тег в GHCR и выполнить ручной откат по §5.2.

Это долго (минуты сборки). **Вывод для профилактики:** держать «последний известно-хороший» SHA записанным, а критичные релизы делать в начале рабочего дня, а не перед выходными.

## 6. Опасные релизы (нужен план заранее)

### 6.1 Миграции схемы БД

Схема управляется **Ent** (`backend/ent/migrate/`), миграция применяется приложением при старте.

⚠️ Ключевое следствие: **откат кода не откатывает схему**. Если релиз добавил/изменил колонку, откат backend на предыдущий SHA оставит схему новой.

☐ Перед релизом с миграцией — **бэкап БД** ([backup-restore.md](backup-restore.md) §2), не «потом».
☐ Предпочитать аддитивные миграции (добавить колонку/таблицу), а не разрушительные (удалить/переименовать) — аддитивные совместимы со старым кодом, значит откат безопасен.
☐ Разрушительное изменение — разбивать на два релиза: (1) код перестаёт использовать поле, (2) следующим релизом поле удаляется. Между релизами откат безопасен.
☐ После релиза с миграцией проверить, что схема применилась и приложение стартовало без ошибок миграции (логи backend при старте).

### 6.2 Изменения auth / контрактов API

☐ Проверить обратную совместимость: старые клиенты (открытые вкладки пользователей) продолжат работать?
☐ Изменение auth — держать наготове план отзыва сессий, если что-то пошло не так.

### 6.3 Изменения LiveKit / звонков

☐ Помнить: каждый деплой и так пересоздаёт `livekit` (рвёт звонки). Релиз с изменением конфигурации звонков — тем более.
☐ Деплоить вне пика созвонов.
