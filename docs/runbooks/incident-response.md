# Runbook — реагирование на инцидент

> **Кто выполняет:** дежурный / владелец. **Когда:** прод недоступен, деградирует или есть подозрение на инцидент.
> **Главное правило:** сначала **восстановить сервис**, потом искать причину. Диагностика ради полноты картины при лежащем проде — ошибка приоритета.
> **Второе правило:** фиксируй время и действия по ходу, а не после. Постмортем без таймлайна бесполезен.

---

## 0. Первые 5 минут (не пропускать)

☐ Засеки время начала — оно понадобится в постмортеме.
☐ Открой блокнот/тикет и пиши туда каждое действие с временем (`14:32 перезапустил backend`).
☐ Определи severity по §1 — от этого зависит, звать ли владельца немедленно.
☐ Не делай ⚠️-действий (рестарт БД, откат миграции, удаление данных) до §2 — сначала снять картину.

---

## 1. Классификация severity

| Sev | Критерий | Реакция | Кого звать |
|-----|----------|---------|------------|
| **SEV-1** | Прод полностью недоступен; потеря/повреждение данных; утечка секретов | Немедленно, любое время суток | Владелец сразу |
| **SEV-2** | Ключевой модуль не работает (auth, tracker, messenger); массовые 5xx; данные не сохраняются | В течение часа | Владелец уведомляется |
| **SEV-3** | Деградация (медленно, частичные ошибки); один некритичный модуль | В рабочее время | По итогу — тикет |
| **SEV-4** | Косметика, единичные жалобы, неудобство | Плановый бэклог | Тикет |

Правило эскалации: **сомневаешься между уровнями — бери выше**. Понизить severity позже дёшево, поднять поздно — дорого.

Утечка секрета — всегда SEV-1 независимо от видимого эффекта → сразу [fa06-secret-rotation.md](fa06-secret-rotation.md).

## 2. Снять картину (5–10 минут, до любых изменений)

☐ Состояние контейнеров:

```bash
ssh <prod-host>            # TODO(ops): зафиксировать хост/алиас
cd /opt/hub/deployments
docker compose -f docker-compose.prod.yml ps
docker ps --format 'table {{.Names}}\t{{.Status}}\t{{.RunningFor}}'
```

☐ Health backend:

```bash
curl -sf http://127.0.0.1:3000/api/health | head -c 400; echo
```

☐ Свежие логи упавшего/подозрительного сервиса (последние 200 строк, с временем):

```bash
docker compose -f docker-compose.prod.yml logs --tail=200 --timestamps backend
docker compose -f docker-compose.prod.yml logs --tail=100 --timestamps caddy
```

☐ Ресурсы хоста (частая причина «всё сломалось» — кончилось место):

```bash
df -h            # диск: >90% на разделе с docker volumes = вероятная причина
free -m          # память
docker stats --no-stream
```

☐ Что менялось последним (деплой? миграция? ротация секретов?):

```bash
cd /opt/hub && git log -1 --oneline
docker compose -f docker-compose.prod.yml images
```

**Вывод этого шага** — одна фраза в журнал: «backend рестартует в цикле, в логах X, диск 45%, последний деплой 20 минут назад». С ней идёшь в §3.

## 3. Маршрутизация по картине

| Что видишь | Наиболее вероятная причина | Куда идти |
|------------|----------------------------|-----------|
| Контейнер `backend` в `Restarting` | Падение на старте: конфиг/миграция/зависимость | §4.1 |
| Все контейнеры `Up`, но 5xx | Ошибка приложения / отказ зависимости | §4.2 |
| Диск >90% | Логи/volumes/образы съели место | §5.1 |
| БД не принимает соединения | Postgres/Mongo упал или исчерпал соединения | [database-operations.md](database-operations.md) §4 |
| Проблема началась сразу после деплоя | Плохой релиз | [deploy-and-rollback.md](deploy-and-rollback.md) §4 — **откат в первую очередь** |
| Сертификат/домен/502 от Caddy | Reverse proxy или TLS | §5.2 |
| Нет писем/уведомлений | Внешние ключи (Resend/Telegram) | §5.3 |

---

## 4. Типовые сценарии восстановления

### 4.1 Backend не стартует (цикл рестарта)

☐ Прочитать причину в логах — она почти всегда в первых строках после старта:

```bash
docker compose -f docker-compose.prod.yml logs --tail=100 backend | head -60
```

☐ Проверить, на месте ли `.env`:

```bash
test -f /opt/hub/deployments/.env && echo '.env present' || echo 'MISSING .env'
```

☐ Проверить доступность зависимостей изнутри сети (backend стартует после них, но мог не дождаться):

```bash
docker compose -f docker-compose.prod.yml ps postgres mongo redis nats
```

☐ Если причина — недоступная зависимость: поднять её, затем `restart backend`.
☐ Если причина — конфиг/миграция после деплоя: ⚠️ откат релиза ([deploy-and-rollback.md](deploy-and-rollback.md) §4), разбор потом.
☐ Если причина непонятна из логов: сохранить полный лог в файл до рестарта (рестарт затрёт картину):

```bash
docker compose -f docker-compose.prod.yml logs --no-color backend > /tmp/backend-incident-$(date +%F-%H%M).log
```

### 4.2 Сервисы `Up`, но массовые 5xx

☐ Локализовать: все эндпоинты или конкретный модуль? (по логам/метрикам — [monitoring-and-alerts.md](monitoring-and-alerts.md)).
☐ Проверить внешние зависимости приложения (БД, Redis, NATS, S3/SeaweedFS, LiveKit) — отказ одной даёт 5xx в её домене.
☐ Проверить, не деградировала ли БД (медленные запросы, блокировки) — [database-operations.md](database-operations.md) §3.
☐ Если 5xx начались после деплоя — откат, не героический дебаг на проде.

### 4.3 Перезапуск сервиса (когда причина ясна и локальна)

⚠️ Перезапуск стирает состояние в памяти и рвёт активные соединения (WS-сессии, звонки). Для `livekit` это означает разрыв текущих звонков — предупредить, если возможно.

```bash
docker compose -f docker-compose.prod.yml restart backend
sleep 5 && curl -sf http://127.0.0.1:3000/api/health | head -c 200; echo
```

Полный пересоздать (когда рестарт не помог и нужен чистый контейнер):

```bash
docker compose -f docker-compose.prod.yml up -d --force-recreate backend
```

## 5. Инфраструктурные причины

### 5.1 Кончилось место

☐ Найти, что съело:

```bash
df -h
du -sh /var/lib/docker/* 2>/dev/null | sort -h | tail -5
docker system df
```

☐ Безопасная очистка (не трогает работающие контейнеры и именованные volumes):

```bash
docker image prune -f            # висячие образы
docker builder prune -f          # кэш сборки
```

⚠️ `docker system prune -a --volumes` **не выполнять** без явного решения — снесёт volumes с данными (`pgdata`, `mongodata`, `seaweeddata`).

☐ Логи Docker раздуваются при отсутствии ротации — проверить настройку `TODO(ops)`: подтвердить `log-driver`/`max-size` в `/etc/docker/daemon.json`.

### 5.2 Caddy: 502 / проблемы TLS

☐ Логи и конфиг:

```bash
docker compose -f docker-compose.prod.yml logs --tail=100 caddy
docker compose -f docker-compose.prod.yml exec caddy caddy validate --config /etc/caddy/Caddyfile
```

☐ 502 обычно означает, что upstream (`backend`/`frontend`) не отвечает — вернуться в §4.1.
☐ Проблема сертификата: проверить, что домен резолвится на этот хост и порты 80/443 доступны снаружи (ACME-челлендж). `TODO(ops)`: зафиксировать домен и регистратора.

### 5.3 Не уходят письма / Telegram-уведомления

☐ Логи `hub-mail` и backend-домена нотификаций.
☐ Проверить валидность внешних ключей — истёкший/отозванный ключ даёт именно такую картину: [fa06-secret-rotation.md](fa06-secret-rotation.md).
☐ Проверить, не упёрлись ли в лимиты провайдера (`TODO(ops)`: зафиксировать план/лимиты Resend).

## 6. Коммуникация

| Кому | Когда | Что сообщить |
|------|-------|--------------|
| Владелец | SEV-1 сразу, SEV-2 в течение часа | Что не работает, с какого времени, что уже сделано, нужна ли помощь |
| Пользователи | SEV-1/SEV-2 дольше 30 минут | Факт проблемы + ожидание, **без** внутренних деталей и обвинений |

Шаблон сообщения пользователям:

```
Наблюдаем проблему с доступом к <модуль/сервис> с <время>.
Работаем над восстановлением, следующее обновление в <время +30 мин>.
```

Правило: не обещать конкретный срок починки, пока причина неизвестна. Обещать **время следующего обновления** — это выполнимо.

## 7. Постмортем (обязателен для SEV-1 и SEV-2)

Заводится в тот же или следующий рабочий день, пока помнятся детали. Шаблон и требования — [`docs/TROUBLESHOOTING.md`](../TROUBLESHOOTING.md) §5 и `prompt-engineering/prompts/12-documentation-reporting.md` #14.

Обязательные разделы:

1. **Таймлайн** — когда внесено, когда проявилось, когда заметили, когда починили (из твоего журнала §0).
2. **Влияние** — кто и что не мог делать, сколько времени.
3. **Root cause** — механизм от причины до симптома, а не «упал backend».
4. **Почему не поймали раньше** — какой тест/алерт должен был сработать и почему не сработал.
5. **Системные действия** — конкретные, с владельцем и сроком. «Быть внимательнее» — не действие.
6. **Регрессия на класс** — тест/алерт, который поймает **класс** проблемы, а не конкретный инстанс.

☐ Записать инцидент в `.planning/ops/production/` (файл по дате).
☐ Обновить `.planning/STATE.md` — session note с итогом.
☐ Если выявлен пробел мониторинга — завести правило в `deployments/monitoring/prometheus/alerts/hub.yml` и описать в [monitoring-and-alerts.md](monitoring-and-alerts.md).

## 8. Чек-лист закрытия инцидента

- [ ] Сервис восстановлен, health зелёный, проверено не только curl-ом, но и реальным сценарием.
- [ ] Причина понята (или явно записано «причина не установлена», с планом доработки наблюдаемости).
- [ ] Временные костыли (ручные правки, отключённые фичи) — записаны как долг с тикетом, не забыты.
- [ ] Журнал инцидента сохранён.
- [ ] Постмортем заведён (SEV-1/SEV-2).
- [ ] Пользователи уведомлены о восстановлении (если уведомлялись о проблеме).
