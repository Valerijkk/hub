# Hub — Бизнес-документация

## Описание продукта

Hub — единая платформа для команд разработки и тестирования (10-50 человек), объединяющая трекер задач (Kanban + Scrum), мессенджер с каналами и тредами, систему управления тестированием (TMS) с Allure-интеграцией и голосовые созвоны с демонстрацией экрана. Все модули связаны между собой: задачи привязаны к тест-кейсам, результаты прогонов автотестов из CI попадают в TMS, уведомления о событиях приходят в мессенджер и Telegram.

## Целевая аудитория

- **Средние команды разработки** (10-50 человек)
- **Роли в команде**: разработчики, тестировщики, тимлиды, менеджеры проектов
- **Организации**, которым нужен self-hosted инструмент без зависимости от SaaS-вендоров
- **Команды**, уставшие от переключения между Jira + Slack + TestRail + Google Meet

## Бизнес-ценность и проблема

### Проблема

Типичная команда разработки использует 4-6 разрозненных инструментов: Jira (трекер), Slack (мессенджер), TestRail/Allure TestOps (TMS), Google Meet (созвоны), GitHub (код). Переключение между ними:
- Теряется контекст при переходе между инструментами
- Нет единого места для traceability (задача -> тест -> баг -> PR)
- Информация размазана по десятку интерфейсов
- Высокая стоимость ($30k+/год только за Allure TestOps)
- Нет контроля над данными (SaaS lock-in)

### Решение

Hub объединяет все инструменты в одном интерфейсе с глубокой интеграцией:
- **Traceability**: задача связана с фичей, фича покрыта тест-кейсами, тест-кейсы привязаны к автотестам в GitHub, результаты прогонов из CI попадают в TMS, уведомления приходят в мессенджер
- **Self-hosted**: полный контроль над данными, развёртывание на своих серверах
- **Бесплатно**: все компоненты open-source, минимальный бюджет на инфраструктуру
- **Единый UX**: единый дизайн, горячие клавиши, глобальный поиск, единая система меток

## Функциональные модули

### 1. Авторизация и пользователи

**Безпарольная аутентификация** — современный подход без необходимости запоминать пароли.

| Фича | Описание поведения |
|------|-------------------|
| Magic Link (email) | Пользователь вводит email, получает одноразовую ссылку через Resend API. Ссылка валидна 15 минут. При клике — авторизация и выдача JWT |
| Telegram авторизация | Пользователь отправляет команду Telegram-боту, получает 6-значный код. Вводит код в Hub — авторизация |
| Refresh-токен | Access Token (JWT, 15 мин) + Refresh Token (Redis, 30 дней). При истечении access — автоматический refresh |
| Множественные сессии | Пользователь может быть авторизован одновременно на нескольких устройствах. Список сессий с device/IP. Отзыв отдельных сессий |
| Уведомление о новом входе | При авторизации с нового устройства — push-уведомление через WebSocket на все активные сессии |
| Профиль | Имя, аватар, email, Telegram ID, должность, отдел, телефон, часовой пояс, язык (ru/en), дата рождения, кастомные поля (JSONB) |
| Системные роли | Admin — полный доступ, управление настройками, пользователями, бэкапами. Member — стандартный доступ |
| Режим регистрации | Admin выбирает: открытая (любой может зарегистрироваться) или только по инвайтам |
| Онбординг | Трёхшаговый flow: заполнение профиля -> обзорный тур (6 карточек фич) -> выбор темы/accent color -> создание/присоединение к проекту |
| Quiet hours | Пользователь задаёт «тихие часы» (HH:MM - HH:MM). В это время обычные уведомления не приходят. Срочные — пробивают |
| Деактивация | Admin деактивирует пользователя: доступ блокируется, задачи переназначаются, данные сохраняются. GDPR-удаление — полное удаление данных |

### 2. Проекты

**Контейнер для всех рабочих процессов** — создание проекта автоматически создаёт трекер, TMS, чат, канал, дашборд.

| Фича | Описание поведения |
|------|-------------------|
| Создание проекта | Admin или Member создаёт проект с именем и ключом (HUB, MOBILE). Ключ уникальный, используется в нумерации задач (HUB-1, HUB-2). Автоматически создаётся начальный workflow (To Do, In Progress, Done), дефолтная Kanban-доска, канал мессенджера |
| Участники | Добавление по email или по invite-ссылке. Каждому участнику назначается роль. Команды (Team) — группа людей добавляется целиком |
| Роли в проекте | Фиксированные: Owner (создатель, полные права), Developer, Tester, Viewer. Кастомные: RBAC с гранулярными permissions (task.create, task.edit, testcase.create и т.д.) |
| Invite-ссылки | Генерация ссылки с указанием роли, max uses, expiration. Любой с ссылкой может присоединиться |
| Шаблоны | Встроенные: пустой, Software Dev (с начальным workflow и метками), QA, Kanban Simple. Кастомные: сохранение проекта как шаблон |
| Архивирование | Проект переводится в read-only: просмотр разрешён, изменения заблокированы. Альтернатива удалению |
| Удаление | Мягкое удаление: проект в корзине 30 дней. Полное удаление — Admin подтверждает. Экспорт бэкапа перед удалением |
| Команды (Team) | Группа пользователей. Создание команды, добавление/удаление участников. Добавление команды в проект — все участники получают доступ |

### 3. Трекер задач

**Полнофункциональный трекер** с 9 типами задач, настраиваемым workflow и глубокой интеграцией с остальными модулями.

| Фича | Описание поведения |
|------|-------------------|
| Типы задач | Bug, Task, Story, Epic, Sub-task, Improvement, Tech Debt, Spike, Release. Каждый тип имеет свой набор обязательных полей |
| Нумерация | Префикс проекта + автоинкремент: HUB-1, HUB-2. Уникальный ключ задачи (issue_key) |
| Фиксированные поля | Заголовок, описание (rich-text Plate JSON + plain text для поиска), тип, приоритет (critical/high/medium/low/trivial), статус, исполнитель, reporter, due date, story points, estimate/time spent |
| Кастомные поля | Project Owner создаёт поля: текст, число, дата, чекбокс, select, multi-select, user, URL. Значения хранятся в JSONB |
| Вложенность | Свободная иерархия parent/child любой глубины. Задача может быть дочерней для любой другой задачи |
| Связи между задачами | blocks/blocked_by, relates_to, duplicates/duplicated_by, clones/cloned_from, causes/caused_by, parent/child + кастомные типы связей |
| Workflow | Project Owner создаёт статусы (категория: todo/in_progress/done), задаёт переходы между ними. Каждый статус с цветом и sort order |
| Комментарии | Rich-text (Plate JSON), @упоминания (нотифицируют упомянутых), внутренние комментарии (видны только определённым ролям), реакции (emoji) |
| Лог изменений | Каждое изменение логируется: кто, когда, что изменилось (field-level diff: old_value -> new_value) |
| Таймтрекинг | Ручной ввод (минуты + описание) + таймер Start/Stop (автоматическое логирование). Estimate vs actual |
| Метки | На уровне проекта, с цветами, группы меток (Label Groups). Единая система — метки используются в задачах и тест-кейсах |
| Чеклисты | JSONB массив [{id, text, checked}] внутри задачи. Визуальный прогресс |
| Оптимистичная блокировка | Поле version: при сохранении проверяется совпадение версии. Конфликт — уведомление пользователю |
| LexoRank | Позиционирование задач на доске через rank-строку. Drag & drop без пересчёта всех позиций |

### 4. Kanban

**Визуализация workflow** — колонки соответствуют статусам, задачи перемещаются drag & drop.

| Фича | Описание поведения |
|------|-------------------|
| Колонки | Каждая колонка = статус workflow. Порядок определяется sort_order |
| WIP-лимиты | Для каждого статуса задаётся максимальное количество задач. При превышении — визуальный индикатор |
| Swimlanes | Группировка задач: по исполнителю, приоритету, типу. Режим хранится в настройках доски |
| Несколько досок | В одном проекте можно создать несколько досок с разными фильтрами (только баги, только мои задачи) |
| Фильтры | На доске: мои задачи, только баги, по приоритету, по исполнителю. Фильтры сохраняются в JSON-конфигурации доски |
| Drag & Drop | Перемещение задач между колонками = смена статуса. Перемещение внутри колонки = изменение rank (LexoRank) |

### 5. Scrum / Спринты

**Полный Scrum-процесс** — спринты, burndown, velocity, ретроспективы, planning poker.

| Фича | Описание поведения |
|------|-------------------|
| Создание спринта | Имя, цель (goal), даты начала и окончания. Статус: planning -> active -> completed |
| Управление задачами | Drag & drop задач из бэклога в спринт. Привязка issue -> sprint через связь |
| Запуск спринта | Меняет статус на active. Только один спринт может быть active в проекте |
| Завершение | Незавершённые задачи автоматически переносятся в следующий спринт или возвращаются в бэклог |
| Burndown Chart | График выполнения задач по дням спринта. Идеальная линия vs фактическое выполнение |
| Velocity Chart | История story points: сколько запланировано vs выполнено в каждом спринте |
| Ретроспектива | JSONB заметки: went_well, to_improve, actions. Привязаны к спринту |
| Planning Poker | Создание сессии, голосование по Фибоначчи (1, 2, 3, 5, 8, 13, 21). Голоса скрыты до раскрытия. Real-time через WebSocket |

### 6. Мессенджер

**Полноценный корпоративный мессенджер** с каналами, тредами, реакциями, голосовыми сообщениями, поллами.

| Фича | Описание поведения |
|------|-------------------|
| Личные чаты (DM) | 1 на 1. Дедупликация через dm_key (отсортированные user IDs). Создание через CreateOrGetDM |
| Групповые чаты | Несколько участников, название, описание |
| Публичные каналы | Любой участник проекта может присоединиться. Видны в списке каналов |
| Приватные каналы | Только по приглашению. Не видны в общем списке |
| Автоканалы | При создании проекта автоматически создаётся канал #project-{key} |
| Read-only каналы | Флаг is_readonly: только создатель/admin могут писать. Для CI-уведомлений (#hub-ci) |
| Треды | Ответ на сообщение создаёт ветку (reply_to). Отдельный endpoint для загрузки тредовых сообщений |
| Реакции | Любые emoji, toggle (повторный клик убирает). Хранятся в MongoDB |
| Форматирование | Bold, italic, code, списки, ссылки через Plate editor |
| Редактирование/удаление | Своё сообщение — edit/delete. Owner/Admin канала — delete любого |
| Пересылка | Forward сообщения в другой канал с указанием оригинала |
| Pin/Bookmark | Pin — закрепление сообщения в канале (видно всем). Bookmark — личная закладка (saved) |
| Голосовые сообщения | Запись и отправка голосового сообщения (файл в SeaweedFS) |
| Поллы | Создание опроса в канале: вопрос, варианты, голосование, закрытие. Real-time результаты |
| Превью ссылок | Упоминание задачи (HUB-123) или PR — карточка превью. Внешние URL — OG meta |
| Поиск | Глобальный + локальный (по каналу). Полнотекстовый поиск по MongoDB text index |
| Статусы присутствия | Онлайн/оффлайн/отошёл (автоматически по heartbeat) + кастомный текстовый статус |
| Unread counts | Количество непрочитанных сообщений по каналам. Mark as read |
| Starred | Пользователь помечает каналы звёздочкой для быстрого доступа |
| Mute | Mute канала до указанного времени. Три режима уведомлений: all, mentions, nothing |
| Invite-ссылки | Генерация ссылки для приглашения в канал с expiration и max uses |
| Typing indicator | Real-time через WebSocket. Показывает «набирает...» в канале |
| Блокировка | Блокировка пользователя: скрытие сообщений от заблокированного |

### 7. TMS (Управление тестированием)

**Полнофункциональная система управления тестированием** уровня Allure TestOps.

| Фича | Описание поведения |
|------|-------------------|
| Тест-кейсы | Два формата: классический (шаги + ожидаемый результат) и BDD (Given/When/Then). Шаги хранятся в JSONB |
| Ключ тест-кейса | Формат: HUB-TC-42. Автоинкремент через project.test_case_counter |
| Структура | Папки (TestSuite) с вложенностью (parent/child). Теги через Labels. Компоненты (Component) для категоризации |
| Версионирование | При каждом изменении создаётся снимок (TestCaseVersion). Откат на любую версию. История изменений |
| Связь с GitHub | По ID аннотации (@TestCase("HUB-TC-42")), по full_name, по class+method. Статус синхронизации: synced/outdated/unlinked |
| Прогоны (Test Runs) | Типы: manual (ручной), automatic (Allure), mixed. Статусы: created -> in_progress -> completed/aborted |
| Назначение тестировщиков | Назначение пользователей на прогон. Каждый тестировщик выполняет свою часть |
| Результаты (Test Results) | Статус: passed/failed/broken/skipped/unknown. Комментарий, скриншоты, длительность. Step-level результаты |
| Allure-интеграция | Парсер читает allure-results JSON, отправляет POST в TMS API. Matching по annotation/fullname/classmethod. Import через webhook или API |
| JUnit webhook | Приём JUnit XML результатов через webhook |
| Создание бага | Из failed результата автоматически создаётся задача типа Bug в трекере с привязкой |
| Связь с трекером | Двусторонняя привязка test_case <-> issue. Покрытие требований. Матрица трассируемости |
| Окружения | Метка (dev/staging/prod), конфигурации (браузер, ОС). Привязка прогонов к окружению. Сравнение между окружениями |
| Отчёты | Тренды (pass rate по прогонам), flaky-тесты, категории дефектов, сравнение прогонов, матрица трассируемости, сравнение окружений |
| Импорт | CSV, JSON, XML, Excel. Универсальный маппинг полей через API |
| Экспорт | CSV, JSON, XML (тест-кейсы), PDF (отчёт прогона) |
| Flaky detection | Поле is_flaky на результате. Отчёт по нестабильным тестам |

### 8. Созвоны

**Голосовые звонки + screen share** через LiveKit (self-hosted WebRTC).

| Фича | Описание поведения |
|------|-------------------|
| Создание звонка | Привязка к каналу мессенджера: нажатие "Позвонить" создаёт звонок в канале |
| Instant-звонки | Быстрый звонок без канала: генерируется invite-код (hub-abc123), ссылка для присоединения |
| Присоединение | По ID звонка или по invite-коду. LiveKit выдаёт токен для WebRTC-соединения |
| Голос | Только аудио (без вебкамер — осознанное решение). До 50 участников |
| Screen share | Демонстрация экрана или окна. Несколько участников могут шарить одновременно |
| Mute/unmute | Toggle микрофона. Статус виден всем участникам |
| Поднять руку | Индикатор "Хочу сказать". Видно всем участникам |
| Запись | По кнопке: LiveKit Egress записывает голос + screen share. Уведомление всем участникам. Сохранение в SeaweedFS. Ссылка на запись в канале |
| Записи проекта | Раздел "Записи" в проекте. Список всех записей с download URL |
| Эфемерный чат | Чат звонка: сообщения доступны только во время звонка, real-time через NATS -> WebSocket |
| Запланированные звонки | Создание звонка на будущее с привязкой к каналу. Повторяющиеся (ежедневный стендап) |
| Проверка конфликтов | При создании запланированного звонка — проверка пересечений с другими звонками |
| Webhook LiveKit | Обработка событий: room_started, room_finished, participant_joined, participant_left, egress_ended |

### 9. Дашборды

**Настраиваемые панели** с drag & drop виджетами.

| Фича | Описание поведения |
|------|-------------------|
| Личный дашборд | Мои задачи, непрочитанные, звонки, прогоны, дедлайны, активность, quick actions. Виджеты с drag & drop, настраиваемые размеры |
| Проектный дашборд | Статусы задач, burndown, velocity, баги, активность команды, тесты, тренды. Шаблоны: Dev/QA/Manager |
| Админский дашборд | Пользователи, проекты, задачи, DAU/WAU/MAU, хранилище, здоровье сервисов, топ проектов. Только для Admin |
| Раскладка | JSON-массив виджетов с позицией (x, y) и размерами (w, h). Сохранение на сервере |
| Шаблоны | Предустановленные раскладки. Apply — применяет шаблон к текущему дашборду |

### 10. Уведомления

**Многоканальные уведомления** с гранулярной настройкой.

| Фича | Описание поведения |
|------|-------------------|
| Триггеры | Назначение задачи, @упоминание, смена статуса, новое сообщение, звонок, завершение прогона, приближение дедлайна, блокировка задачи |
| Каналы доставки | Внутри Hub (колокольчик + WebSocket push) + Telegram бот + Web Push (VAPID) |
| Настройка | По типам: отключить отдельные типы уведомлений. По каналам: in_app/telegram для каждого типа. По проектам: per-project override |
| Quiet hours | Тихие часы: обычные уведомления заглушаются. Срочные (is_urgent=true) пробивают |
| Web Push | Браузерные push-уведомления через VAPID. Подписка/отписка через API |
| Unread count | Количество непрочитанных уведомлений. Mark read (одиночное) / Mark all read |

### 11. Интеграции

#### GitHub

| Фича | Описание поведения |
|------|-------------------|
| Подключение | Настройка интеграции: repo owner, repo name, access token, webhook secret. Per-project |
| Webhook | Обработка push (коммиты) и pull_request событий. Автоматическое создание GitHubLink |
| Автопривязка | «HUB-123» в коммит-сообщении или PR-заголовке -> задача получает ссылку |

| Link Preview | Карточка превью PR/коммита в мессенджере и задаче |
| GitHub Workflows | Просмотр workflow runs и их деталей через API |

#### GitLab

| Фича | Описание поведения |
|------|-------------------|
| Подключение | Настройка интеграции: project URL, access token, webhook token |

| Автопривязка | Аналогично GitHub: по issue key в сообщении |
| Pipelines | Просмотр pipeline runs, запуск pipeline через API |
| Создание ветки | Из задачи через GitLab API |

## Роли и права доступа

### Системные роли

| Роль | Описание |
|------|----------|
| **Admin** | Полный доступ. Управление пользователями, настройками регистрации, бэкапами, аудит-логами, системными лимитами, корзиной. Просмотр админ-дашборда |
| **Member** | Стандартный доступ. Создание проектов, участие в проектах. Не имеет доступа к админ-панели |

### Проектные роли (фиксированные)

| Роль | Описание |
|------|----------|
| **Owner** | Создатель проекта. Управление настройками, workflow, участниками, ролями, удаление проекта |
| **Developer** | Создание/редактирование задач, комментариев, вложений. Создание тест-кейсов и прогонов |
| **Tester** | Аналогично Developer, с акцентом на TMS. Создание/выполнение прогонов, создание тест-кейсов |
| **Viewer** | Только чтение. Просмотр задач, тест-кейсов, дашбордов. Участие в чатах и звонках |

### Кастомные роли (RBAC)

Project Owner создаёт кастомные роли с гранулярными permissions:
- `project.view` — просмотр проекта
- `task.create`, `task.edit`, `task.delete` — управление задачами
- `task.comment` — комментирование
- `testcase.create`, `testcase.edit` — управление тест-кейсами
- `testrun.create`, `testrun.execute` — управление прогонами
- `file.upload`, `file.delete` — управление файлами
- `project.manage_workflow` — настройка workflow и кастомных полей
- `project.manage_roles` — управление ролями

Permissions хранятся как bitmask (uint64) в поле `permissions` роли.

## Пользовательские сценарии

### Сценарий 1: Разработчик начинает рабочий день

1. Открывает Hub -> Личный дашборд
2. Видит назначенные задачи с приоритетами и дедлайнами
3. Проверяет непрочитанные сообщения в мессенджере
4. Открывает задачу HUB-42, нажимает Start Timer
5. Работает. Коммитит с «HUB-42 fix login bug» -> задача автоматически получает ссылку на PR
6. Останавливает таймер. Логируется время

### Сценарий 2: Тестировщик проводит ручное тестирование

1. Открывает TMS -> Прогоны
2. Создаёт новый прогон «Release 1.5 Smoke», выбирает окружение «staging», добавляет тест-кейсы
3. Выполняет каждый кейс: passed/failed + комментарий + скриншот
4. При failed — нажимает «Create Bug» -> автоматически создаётся задача Bug с привязкой к кейсу
5. Завершает прогон. Видит отчёт: 45/50 passed, 3 failed, 2 skipped

### Сценарий 3: CI прогоняет автотесты

1. GitHub Actions запускает тесты, генерирует allure-results
2. `hub-cli push-results` отправляет JSON в TMS API
3. Hub парсит результаты, матчит с тест-кейсами по annotation/fullname
4. Создаёт прогон типа «automatic» с результатами
5. Уведомление в Telegram: «Прогон #15: 120 passed, 2 failed»

### Сценарий 4: Команда проводит ежедневный стендап

1. Запланированный звонок автоматически создаётся в канале #dev-standup
2. Участники присоединяются, обсуждают статус задач
3. Один из разработчиков шарит экран с Kanban-доской
4. Тимлид записывает звонок по кнопке
5. Запись сохраняется в проекте, ссылка публикуется в канал

### Сценарий 5: Project Owner настраивает новый проект

1. Создаёт проект «Mobile App», ключ «MOB»
2. Настраивает workflow: To Do -> In Progress -> Code Review -> QA -> Done
3. Создаёт метки: backend, frontend, bug-fix, feature
4. Генерирует invite-ссылку, отправляет команде
5. Настраивает GitHub-интеграцию для автопривязки PR
6. Подключает Allure webhook для CI/CD

## Out of Scope

| Что НЕ входит | Почему |
|----------------|--------|
| Видеозвонки с вебкамерами | Осознанное ограничение — голос + screen share достаточно для рабочих созвонов |
| Мобильные нативные приложения | PWA покрывает потребность для мобильного доступа |
| Email уведомления | Telegram бот покрывает потребность в внешних уведомлениях |
| Биллинг/подписки | Внутренний инструмент, не SaaS-продукт |
| SSO/LDAP/OAuth | Magic Link + Telegram достаточно для v1 |
| Gantt-диаграммы | Kanban + Scrum покрывают потребности в управлении задачами |
| Видео/аудио сообщения (кроме голосовых) | Избыточно для v1 |
| Remote control (управление чужим экраном) | Сложная фича, не критична для команды |
| Route-level page transitions | Layout shift bugs, productivity tool не маркетинговый сайт |
| Multi-tenant | Single-tenant: один инстанс = одна команда |
