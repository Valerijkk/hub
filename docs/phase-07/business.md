# Фаза 7: Доработка и расширенные возможности -- Бизнес-документация

## Обзор фазы

Фаза 7 завершает разработку платформы Hub, добавляя расширенные возможности поверх базовых модулей (трекер, мессенджер, TMS, звонки, дашборды). Пять функциональных областей фазы:

1. **Scrum и Kanban-расширения** -- спринты, burndown/velocity, Planning Poker, WIP-лимиты, swimlanes
2. **Интеграция с GitHub** -- webhook-приемник, автопривязка PR/коммитов, автосмена статуса, создание ветки, превью ссылок
3. **Запись и планирование звонков** -- запись через LiveKit Egress, запланированные и повторяющиеся звонки (RRULE)
4. **i18n, темы, мобилка, PWA** -- русский/английский, темная/светлая тема, мобильная навигация, установка как приложение
5. **API Gateway, бэкапы, импорт/экспорт, CLI** -- API-ключи, вебхуки, JQL-поиск, резервное копирование, hub-cli

Фаза покрывает **32 требования**: PROJ-05, KANB-02, KANB-03, SCRM-01..05, MSG-11, TMS-07, CALL-02, CALL-04, CALL-05, GHUB-01..05, SRCH-03, API-01..04, IMEX-01, IMEX-03, BKUP-01..03, UI-02..04, UI-06.

## 1. Scrum и Kanban-расширения

### Покрытые требования

| ID | Требование | Реализация |
|----|-----------|------------|
| SCRM-01 | Спринты: создать, задать даты, перетащить из бэклога, запустить | SprintService с lifecycle planning -> active -> completed |
| SCRM-02 | Burndown chart + Velocity chart | Recharts AreaChart (burndown) и BarChart (velocity) |
| SCRM-03 | Sprint retrospective (заметки привязаны к спринту) | JSONB retro_notes: went_well, to_improve, actions |
| SCRM-04 | Автоперенос незавершенных задач в следующий спринт | CompleteSprint автоматически переносит issue в next planning sprint |
| SCRM-05 | Planning Poker: Фибоначчи, голоса скрыты до раскрытия | Redis hashes + NATS broadcast, значения Фибоначчи |
| KANB-02 | WIP-лимиты на колонку | wip_limit поле в WorkflowStatus, проверка через WIPChecker |
| KANB-03 | Swimlanes (по исполнителю, приоритету, типу) | swimlane_mode enum на Board, группировка на фронтенде |

### Описание функциональности

**Спринты** -- полный жизненный цикл от планирования до завершения. Пользователь создает спринт с именем, целью и датами, перетаскивает задачи из бэклога. При запуске спринта проверяется отсутствие другого активного спринта. При завершении незакрытые задачи автоматически переносятся в следующий спринт (или создается новый со статусом planning).

**Burndown/Velocity** -- burndown chart показывает идеальную линию (dashed) и фактический остаток story points по дням спринта. Velocity chart отображает committed vs completed story points по спринтам проекта.

**Planning Poker** -- сессия привязана к задаче внутри спринта. Участники голосуют значениями Фибоначчи (1, 2, 3, 5, 8, 13, 21). Голоса скрыты до момента reveal. После раскрытия отображается среднее и медиана. Данные хранятся в Redis (TTL 5 мин), события транслируются через NATS.

**WIP-лимиты** -- каждый статус workflow имеет опциональный wip_limit. При перемещении задачи в статус с лимитом проверяется текущее количество задач. Превышение блокирует перемещение с ошибкой. На Kanban-доске колонки с достигнутым лимитом подсвечиваются красной рамкой.

**Swimlanes** -- горизонтальные полосы на Kanban-доске группируют задачи по исполнителю, приоритету или типу. Режим задается на уровне доски и переключается через UI.

### Пользовательские сценарии

**Сценарий: Scrum-мастер запускает спринт**
1. Scrum-мастер создает спринт "Sprint 5" с датами 18-29 марта
2. Из бэклога выбирает 8 задач и перетаскивает в спринт
3. Запускает Planning Poker для оценки каждой задачи
4. Команда голосует значениями Фибоначчи, после reveal фиксируют оценку
5. Scrum-мастер нажимает "Запустить спринт"
6. Burndown chart начинает отслеживать прогресс

**Сценарий: Завершение спринта с автопереносом**
1. Спринт завершается, 2 задачи не закрыты
2. Система автоматически создает "Sprint 6" (planning) и переносит задачи
3. Scrum-мастер заполняет ретроспективу (что получилось, что улучшить, действия)
4. Velocity chart обновляется с данными нового завершенного спринта

## 2. Интеграция с GitHub

### Покрытые требования

| ID | Требование | Реализация |
|----|-----------|------------|
| GHUB-01 | Ссылки на PR/коммиты в задачах (карточка превью) | GitHubLink Ent-схема с автопривязкой |
| GHUB-02 | Автопривязка: "HUB-123" в коммите -> задача получает ссылку | Regex `\b([A-Z]+-\d+)\b` в push/PR событиях |
| GHUB-03 | Статус PR в задаче (open/merged/closed) | GitHubLink.status обновляется через webhook |
| GHUB-04 | Автосмена статуса при мерже PR | merge_status_id в GitHubIntegration, срабатывает при merge |
| GHUB-05 | Создание ветки из задачи (hub-123-fix-login) | CreateBranch через go-github API с slugify |
| MSG-11 | Превью ссылок: задачи, тест-кейсы, GitHub PR/Issue + внешние URL (OG meta) | LinkPreviewService с Redis-кешем 1ч TTL |

### Описание функциональности

**Webhook-приемник** -- POST /api/github/webhook принимает push и pull_request события от GitHub. Подпись валидируется HMAC-SHA256 (X-Hub-Signature-256). Из тела события извлекаются упоминания ключей задач через regex `\b([A-Z]+-\d+)\b` в сообщениях коммитов, заголовках и телах PR.

**Автопривязка** -- при обнаружении ключа задачи (например, "HUB-42") в коммите или PR автоматически создается GitHubLink с типом (commit/pull_request), URL, статусом и автором. Связь отображается в секции задачи с бейджами статуса PR.

**Автосмена статуса** -- при мерже PR задача автоматически переводится в целевой статус, заданный в настройках интеграции (merge_status_id). Это позволяет настроить автоматическое закрытие задач при мерже.

**Создание ветки** -- из карточки задачи пользователь может создать ветку в GitHub. Имя ветки генерируется автоматически: `hub-123-fix-login` (ключ задачи + slugified заголовок, max 50 символов). Используется go-github API.

**Превью ссылок** -- при отправке сообщения со ссылками в мессенджере отображаются карточки превью. Для внутренних сущностей (задачи, тест-кейсы) данные берутся из БД. Для внешних URL используется otiai10/opengraph для извлечения OG-метаданных. Превью кешируются в Redis (1ч TTL), максимум 3 превью на сообщение.

### Пользовательские сценарии

**Сценарий: Разработчик работает с GitHub**
1. Разработчик создает ветку из задачи HUB-42 -> создается `hub-42-add-user-search`
2. Делает коммит с сообщением "fix: resolve HUB-42 search pagination"
3. GitHub отправляет push webhook -> в задаче HUB-42 появляется ссылка на коммит
4. Разработчик создает PR -> в задаче отображается PR со статусом "open"
5. При мерже PR -> задача автоматически переходит в статус "Done"

**Сценарий: Превью ссылок в чате**
1. Пользователь отправляет сообщение "Посмотри задачу HUB-42 и https://github.com/org/repo/pull/15"
2. Под сообщением отображаются 2 карточки превью: задача из Hub и PR из GitHub
3. При повторной отправке той же ссылки превью загружается из Redis-кеша

## 3. Запись и планирование звонков

### Покрытые требования

| ID | Требование | Реализация |
|----|-----------|------------|
| CALL-02 | Запланированные + повторяющиеся звонки (ежедневный стендап) | ScheduledCallService с RFC 5545 RRULE |
| CALL-04 | Запись по кнопке (голос + screen share), уведомление всем | RecordingService через LiveKit Egress |
| CALL-05 | Записи привязаны к проекту (раздел "Записи") | Recording edge к Project, ListProjectRecordings |

### Описание функциональности

**Запись звонков** -- участник нажимает кнопку "Запись" во время звонка. RecordingService создает RoomCompositeEgress через LiveKit, который записывает аудио в MP4 и загружает в SeaweedFS (S3). Максимум 2 одновременные записи на звонок. При завершении Egress отправляет webhook, сервис обновляет метаданные (размер, длительность, статус "ready"). Все участники видят индикатор REC с таймером.

**Запланированные звонки** -- пользователь создает запланированный звонок с названием, датой/временем и привязкой к каналу. Поддерживаются повторяющиеся звонки через RFC 5545 RRULE (ежедневный стендап, еженедельное демо). Cron-задача каждые 60 секунд проверяет наступившие звонки и публикует NATS-событие для уведомления через WebSocket. Для повторяющихся звонков автоматически вычисляется следующее вхождение.

**Раздел записей** -- в проекте доступен раздел "Записи" со списком всех записей проекта. Поддерживается пагинация, фильтрация по дате, скачивание через presigned S3 URL (действителен 1 час).

### Пользовательские сценарии

**Сценарий: Запись стендапа**
1. Тимлид создает повторяющийся звонок "Daily Standup" (RRULE: каждый будний день в 10:00)
2. Каждый день в 10:00 участники канала получают уведомление
3. Во время звонка тимлид нажимает "Запись" -> все видят индикатор REC
4. После завершения запись появляется в разделе "Записи" проекта
5. Любой участник может скачать запись по ссылке

## 4. Интернационализация, темы, мобильная версия, PWA

### Покрытые требования

| ID | Требование | Реализация |
|----|-----------|------------|
| UI-02 | Мобилка: bottom navigation + упрощенный Kanban + мобильные дашборды | Mobile bottom nav, responsive layout |
| UI-03 | Темная + светлая тема + системная + кастомный accent color | next-themes + 5 accent colors (oklch CSS variables) |
| UI-04 | Русский + английский (переключатель в профиле) | i18next с 7 namespaces, LanguageDetector |
| UI-06 | PWA: установка на телефон, offline кеш, Web Push | VitePWA + manifest.webmanifest + service worker |

### Описание функциональности

**Интернационализация** -- i18next с 14 файлами локализации (7 namespaces x 2 языка: RU/EN). Namespaces: common, tracker, messenger, tms, calls, dashboard, settings. Компоненты используют хук `useTranslation('namespace')`. Язык определяется автоматически из браузера или переключается в профиле.

**Темная тема** -- next-themes с attribute="class" для совместимости с Tailwind. Три режима: темная, светлая, системная. Пять акцентных цветов (red, blue, green, purple, orange) через CSS-переменные oklch и data-accent HTML-атрибут.

**Мобильная версия** -- на экранах < 768px отображается bottom navigation с 5 вкладками (Дашборд, Трекер, Мессенджер, Звонки, Ещё). Сайдбар работает как slide-over overlay. Хук `useIsMobile()` определяет breakpoint.

**PWA** -- VitePWA генерирует service worker для кеширования статических ресурсов. manifest.webmanifest описывает приложение для установки. Поддерживается standalone-режим на мобильных устройствах.

2. Выбирает темную тему и фиолетовый акцентный цвет
3. Переключает язык на English
4. Все компоненты мгновенно обновляются

**Сценарий: Работа с мобильного**

## 5. API Gateway, бэкапы, импорт/экспорт, CLI

### Покрытые требования

| ID | Требование | Реализация |
|----|-----------|------------|
| API-01 | REST API + Swagger документация | REST API реализован, Swagger подготовлен |
| API-02 | API-ключи (генерация в профиле) | APIKeyService с SHA-256 хешем, X-API-Key header |
| API-03 | Webhook'и (POST на внешний URL при событии) | WebhookDispatcher с HMAC-SHA256 подписью |
| API-04 | hub-cli (CLI утилита для CI/CD) | cobra CLI: push-results, create-bug, update-task |
| SRCH-03 | JQL-подобный язык запросов | Recursive descent parser с AND/OR/ORDER BY |
| IMEX-01 | Универсальный CSV/JSON импорт задач + маппинг полей | ImportService с preview mode |
| IMEX-03 | Экспорт: задачи (CSV/Excel), прогоны (PDF), полный бэкап (ZIP) | ExportService + ZIP export |
| BKUP-01 | Еженедельный автоматический бэкап (PG + Mongo + S3) | BackupService с pg_dump + mongodump + S3 |
| BKUP-02 | Хранить последние N бэкапов | Ротация: по умолчанию 4 бэкапа |
| BKUP-03 | Восстановление через Admin панель | RestoreBackup с pre-backup safety net |
| PROJ-05 | Шаблоны проектов | 4 системных + кастомные, save-as-template |
| TMS-07 | Окружения (dev/staging/prod) | Environment CRUD с config JSON |

### Описание функциональности

**API-ключи** -- пользователь генерирует ключ в профиле. Полный ключ показывается только при создании. В БД хранится SHA-256 хеш. Middleware APIKeyAuth проверяет заголовок X-API-Key параллельно с JWT -- если ключ присутствует, используется он, иначе проверяется JWT. Поддерживается срок действия (expires_at) и отзыв.

**Вебхуки** -- пользователь создает webhook-эндпоинт с URL, секретом и списком событий. WebhookDispatcher подписывается на JetStream и при получении события отправляет POST на все активные эндпоинты с HMAC-SHA256 подписью payload. Повторы с exponential backoff (1с, 5с, 30с). История доставок сохраняется в WebhookDelivery.

**JQL-поиск** -- recursive descent parser поддерживает синтаксис: `status = "In Progress" AND priority IN (high, critical) ORDER BY created DESC`. Поля: status, priority, type, assignee, created, updated. Операторы: =, !=, IN, NOT IN, >, <, >=, <=. Функция `currentUser()` для текущего пользователя.

**Бэкапы** -- pg_dump (--format=custom) + mongodump (--archive) + архивирование в ZIP + загрузка в SeaweedFS. Автоматический еженедельный бэкап через ticker-горутину. Ротация: по умолчанию хранятся последние 4 бэкапа. Восстановление через Admin панель с автоматическим pre-backup текущего состояния.

**hub-cli** -- Go CLI на cobra для CI/CD интеграции:
- `push-results --project HUB --file ./allure-results` -- загрузить результаты Allure
- `create-bug --project HUB --title "Login broken" --priority high` -- создать баг
- `update-task --key HUB-42 --status done` -- обновить задачу
Авторизация через `--api-key` или `HUB_API_KEY`.

**Шаблоны проектов** -- 4 системных шаблона (Пустой, Разработка ПО, QA, Kanban Simple) создаются при запуске. Пользователь может сохранить существующий проект как шаблон. При создании проекта из шаблона копируются: статусы workflow, метки, доски, кастомные поля.

**Окружения** -- CRUD для test environments (dev/staging/prod/custom) с конфигурацией (браузер, ОС, версия). Окружения привязаны к проекту и тестовым прогонам.

**Импорт/Экспорт** -- CSV/JSON импорт задач с preview mode для маппинга полей перед подтверждением. CSV/Excel экспорт задач. ZIP-экспорт полного проекта.

### Пользовательские сценарии

**Сценарий: CI/CD интеграция**
1. DevOps генерирует API-ключ в профиле Hub
2. В GitHub Actions добавляет секрет `HUB_API_KEY`
3. После прогона тестов: `hub-cli push-results --project HUB --file ./allure-results`
4. При обнаружении бага: `hub-cli create-bug --project HUB --title "Test failure"`
5. При мерже: `hub-cli update-task --key HUB-42 --status done`

**Сценарий: Настройка вебхуков**
1. Admin создает webhook с URL `https://slack.com/webhook/...` и событиями ["task.created", "task.status_changed"]
2. При создании задачи Hub отправляет POST с payload и HMAC подписью
3. Admin просматривает историю доставок: статус-коды, время, ошибки

**Сценарий: Резервное копирование**
1. Каждую неделю автоматически создается бэкап (PG + Mongo -> ZIP -> S3)
2. Admin видит список бэкапов в Admin панели (статус, размер, дата)
3. При необходимости восстановления: система сначала делает бэкап текущего состояния, затем восстанавливает выбранный
4. Старые бэкапы автоматически ротируются (хранятся последние 4)
