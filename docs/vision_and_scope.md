# Hub — Видение и границы (Vision and Scope)

> Единая база знаний. Обновляется BA при изменении бизнес-требований.
> Детальная документация: `docs/BUSINESS.md`, планирование: `.planning/PROJECT.md`

---

## Проблема и ценность

**Проблема:** типичная команда 10–50 человек использует 4–6 разрозненных инструментов (Jira, Slack, TestRail/Allure TestOps, Google Meet, GitHub). Контекст теряется при переключении, traceability размазана, Allure TestOps стоит $30k+/год, SaaS создаёт vendor lock-in.

**Решение:** Hub — self-hosted единая платформа с глубокой интеграцией модулей, единым UX и сквозной трассируемостью задача → тест → баг → PR → уведомление.

**Целевая аудитория:** средние команды разработки и тестирования, организации с требованием контроля данных и минимального бюджета инфраструктуры.

#### US-INTR-01 — Опрос-в-посте ленты

Ограничение scope (GZ-V4-01): опрос существует **только внутри поста ленты**; отдельные company-wide опросы/анкеты — вне scope.

```gherkin
Scenario: Автор добавляет опрос к посту (позитивный)
  Given Игорь создаёт пост в ленте intranet
  When он прикрепляет опрос с вопросом и 2–10 вариантами ответа и публикует пост
  Then пост отображается в ленте с опросом
  And читатели поста могут выбрать ровно один вариант
  And после голосования пользователь видит распределение голосов в процентах

Scenario: Повторное голосование запрещено (негативный)
  Given Игорь уже проголосовал в опросе поста
  When он отправляет второй голос в тот же опрос
  Then система отвечает 422 {"error","request_id"}
  And счётчики голосов не изменяются

Scenario: Опрос без вариантов не публикуется (негативный)
  Given Игорь заполнил вопрос опроса, но добавил менее 2 вариантов
  When он пытается опубликовать пост
  Then система отвечает 400 {"error","request_id"} с указанием минимума вариантов
```

Edge-cases: удаление поста каскадно скрывает опрос и его голоса (корзина 30 дней, NFR-11); голос анонимен для коллег, но автор опроса видит только агрегаты (не список проголосовавших); редактирование вариантов после первого голоса запрещено (422).

#### US-INTR-02 — Onboarding-шаблоны с чекбоксами

Ограничение scope (GZ-V4-02): ровно 1–2 системных шаблона (dev / не-dev) с чекбокс-списками; конструктор произвольных шаблонов — вне scope.

```gherkin
Scenario: Назначение шаблона новичку (позитивный)
  Given Елена (Admin) открывает профиль нового пользователя
  When она назначает ему onboarding-шаблон "Developer"
  Then пользователь видит чеклист шаблона на своей интранет-странице
  And может отмечать пункты выполненными; прогресс (N из M) сохраняется

Scenario: Прогресс виден администратору (позитивный, альтернативный)
  Given новичку назначен шаблон и он отметил часть пунктов
  When Елена открывает список onboarding-статусов
  Then она видит процент выполнения чеклиста по каждому новичку

Scenario: Чужой чеклист недоступен для правки (негативный)
  Given Игорь (Member) открывает чеклист другого сотрудника
  When он пытается отметить пункт выполненным
  Then система отвечает 403 {"error","request_id"}
  And состояние чеклиста не меняется
```

Edge-cases: повторное назначение шаблона тому же пользователю сбрасывает прогресс только после явного подтверждения; деактивация пользователя замораживает чеклист (не удаляет); шаблон применяется копией — правка системного шаблона не меняет уже назначенные чеклисты.

#### US-INTR-03 — Постмодерация ленты

Ограничение scope (GZ-V4-03): модель — только постмодерация (удаление админом после публикации); премодерация и очередь одобрения — вне scope.

```gherkin
Scenario: Админ удаляет пост (позитивный)
  Given в ленте опубликован пост, нарушающий правила
  When Елена (Admin) удаляет пост
  Then пост исчезает из ленты у всех пользователей
  And пост попадает в корзину (30 дней, восстановим), действие фиксируется в audit log с actor и post_id

Scenario: Member не может удалить чужой пост (негативный)
  Given Игорь (Member) видит чужой пост в ленте
  When он вызывает удаление этого поста
  Then система отвечает 403 {"error","request_id"}
  And пост остаётся в ленте
```

Edge-cases: автор может удалить свой пост сам (та же корзина); удаление поста с опросом скрывает опрос и голоса (см. US-INTR-01); восстановление из корзины возвращает пост с опросом и счётчиками.

#### US-INTR-04 — Kudos-лидерборд

Ограничение scope (GZ-V4-03): простой лидерборд по количеству полученных kudos; без внутренней валюты, магазина наград и геймификации-экономики.

```gherkin
Scenario: Просмотр лидерборда (позитивный)
  Given за текущий месяц пользователи отправляли kudos
  When Игорь открывает вкладку лидерборда kudos
  Then он видит топ получателей kudos за выбранный период (месяц/квартал/всё время)
  And для каждого — имя, аватар и число полученных kudos

Scenario: Пустой период (негативный/граничный)
  Given за выбранный период не отправлено ни одного kudos
  When Игорь открывает лидерборд за этот период
  Then отображается пустое состояние с пояснением, без ошибки (200)
```

Edge-cases: kudos удалённого (деактивированного) пользователя остаются в агрегате, имя отображается как деактивированное; равенство очков — стабильная сортировка (по дате первого kudos); лидерборд считается по received, не по sent.

#### US-INTR-05 — Random Coffee: авто-матчинг + авто-DM

Ограничение scope (GZ-V4-03): матчинг автоматический раз в неделю; DM пары создаётся автоматически через messenger; ручной запуск матчей и настройки частоты — вне scope.

```gherkin
Scenario: Еженедельный матчинг с авто-DM (позитивный)
  Given Игорь и ещё N сотрудников включили участие в Random Coffee
  When наступает еженедельный запуск матчинга (cron)
  Then каждый opt-in участник получает пару (при нечётном числе — одна тройка)
  And для каждой пары автоматически создаётся DM в messenger с приветственным сообщением
  And участники получают уведомление о новой паре

Scenario: Отключившийся участник не матчится (негативный)
  Given Игорь выключил участие в Random Coffee до запуска матчинга
  When выполняется еженедельный матчинг
  Then Игорь не получает пару и DM
  And его отсутствие не ломает матчинг остальных

Scenario: Недостаточно участников (граничный)
  Given участие включено только у одного пользователя
  When выполняется матчинг
  Then матчей не создаётся, пользователь получает уведомление «в этот раз пары нет»
```

Edge-cases: повторение прошлой пары допускается только если иных комбинаций нет (история последних матчей учитывается); существующий DM пары переиспользуется (новое сообщение, не новый канал); деактивация пользователя между матчингом и встречей — DM остаётся, следующий матчинг его исключает.

```gherkin
Scenario: Бронирование свободного ресурса (позитивный)
  Given Елена (Admin) создала ресурс «Переговорка 1»

Scenario: Конфликт бронирования (негативный)

```

Edge-cases: удаление события освобождает бронь; перенос события переносит бронь с повторной проверкой конфликта (409 при занятости на новом интервале); деактивированный ресурс не предлагается для новых броней, существующие брони сохраняются; смежные интервалы (15:00–16:00 после 14:00–15:00) конфликтом не считаются.

#### US-CAL-02 — Recurring события (daily/weekly/monthly, until/count)

Ограничение scope (GZ-V4-06): частоты daily/weekly/monthly с окончанием по дате (until) или числу повторений (count); правка **серии целиком** — правка отдельного вхождения (exceptions) вне scope.

```gherkin
Scenario: Создание weekly-серии (позитивный)
  Given Дмитрий создаёт событие «Стендап» на понедельник 10:00
  When он включает повторение weekly с count = 10
  Then в календаре отображаются 10 вхождений по понедельникам 10:00
  And все вхождения ссылаются на одну серию

Scenario: Правка серии применяется ко всем вхождениям (позитивный, альтернативный)
  Given существует weekly-серия из 10 вхождений
  When Дмитрий меняет время серии на 11:00
  Then все будущие вхождения серии отображаются в 11:00
  And участники получают одно уведомление об изменении серии

Scenario: Некорректное правило повторения (негативный)
  Given Дмитрий настраивает повторение
  When он указывает одновременно until в прошлом или count = 0
  Then система отвечает 400 {"error","request_id"}
  And серия не создаётся
```

Edge-cases: monthly для 29/30/31 числа — вхождение в короткий месяц ставится на последний день месяца; удаление серии удаляет все вхождения (корзина 30 дней); ресурс, прикреплённый к серии, проверяется на конфликт по каждому вхождению — при частичном конфликте создание отклоняется (409 со списком конфликтных дат); хранение времени в UTC, отображение в TZ пользователя (NFR-12).

#### US-CAL-03 — iCal export + подписка на внешние iCal-фиды

Ограничение scope (GZ-V4-05): «двусторонне-упрощённо» = export по секретной ссылке + read-only подписка на внешние фиды по URL; OAuth-интеграции (Google/Outlook API) и запись во внешние календари — вне scope.

```gherkin
Scenario: Подписка на внешний фид (позитивный)
  Given у Игоря есть URL внешнего iCal-фида (https)
  When он добавляет подписку на этот фид в настройках календаря
  Then события фида отображаются в его календаре как read-only
  And фид периодически обновляется автоматически (не реже раза в час)

Scenario: Экспорт собственного календаря (позитивный, альтернативный)
  Given Игорь открывает настройки календаря
  When он копирует персональную iCal-ссылку и подключает её во внешнем клиенте
  Then внешний клиент видит события Игоря в формате iCal
  And ссылка содержит непереборный секретный токен, отзыв ссылки генерирует новый токен

Scenario: Недоступный или невалидный фид (негативный)
  Given Игорь добавляет URL, который не отвечает или отдаёт не-iCal контент
  When система выполняет первичную загрузку фида
  Then пользователь видит ошибку валидации фида {"error","request_id"}
  And подписка помечается как «ошибка», ранее загруженные события не дублируются
```

Edge-cases: URL фида проходит `ValidateOutboundURL` (SSRF, NF-07) и загружается через SafeHTTPClient с `io.LimitReader`; события read-only фида нельзя редактировать в Hub (403); удаление подписки убирает её события из календаря; лимит подписок на пользователя (например, 10) — превышение 422.

Ограничение scope (GZ-V4-07): режим busy/free — участник видит только занят/свободен по чужим календарям; детали (название, описание, участники) видны только для своих событий. Отпуска из модуля hr отображаются как busy.

```gherkin
  And утверждённые отпуска из hr отображаются как busy на весь день

Scenario: Детали чужого события скрыты (негативный)
  Given у Игоря есть событие «1:1 с Еленой» в 15:00
  When Дмитрий смотрит доступность Игоря
  Then он видит busy-интервал 15:00 без названия и описания события
  And прямой запрос деталей чужого события возвращает 403 {"error","request_id"}

Scenario: Свои события с деталями (позитивный, альтернативный)
  Given Дмитрий — участник события «Планирование спринта»
  When он смотрит сетку доступности, включающую его самого

```

Edge-cases: неутверждённая заявка на отпуск (pending) не показывается как busy; события внешних iCal-подписок участвуют в busy/free владельца; пользователь без событий отображается как full free (не ошибка); интервалы конвертируются в TZ смотрящего (хранение UTC, NFR-12).

#### US-WIKI-02 — RBAC: space-level (read/write/admin) + наследование + restrict-флаг

```gherkin
Scenario: Не-участник space не имеет доступа (негативный)

  When он запрашивает любую страницу этого space по прямой ссылке
  Then система отвечает 403 {"error","request_id"}
```

Edge-cases: restrict-флаг может только сужать круг (подмножество имеющих доступ к space), расширить доступ за пределы space он не может; снятие restrict возвращает наследование; у space всегда ≥ 1 admin — снятие последнего admin отклоняется (422); Елена (system Admin) имеет служебный доступ для восстановления/GDPR, действия фиксируются в audit log.

```gherkin
  Given страница отредактирована несколько раз разными пользователями
  When Игорь открывает историю страницы
  Then он видит список версий: автор, дата (UTC → локальный TZ), номер версии
  And может открыть любую версию и увидеть diff с текущей

Scenario: Откат к прежней версии (позитивный, альтернативный)
  Given в истории страницы есть версия N-2
  When Игорь (write) выполняет «Восстановить эту версию»
  Then контент версии N-2 становится новой версией N+1 (история не переписывается)
  And в истории зафиксирован откат с автором

Scenario: Откат без прав записи (негативный)
  Given у пользователя роль read в space
  When он пытается восстановить старую версию страницы
  Then система отвечает 403 {"error","request_id"}
```

Edge-cases: версия создаётся на каждый save (не на каждый keystroke — autosave-черновик не версионируется); история восстановленной из корзины страницы сохраняется; restrict-флаг распространяется и на историю версий (403 на историю закрытой страницы).

#### US-WIKI-04 — Связь страниц с задачами (issue-link)

```gherkin
Scenario: Привязка страницы к задаче (позитивный)
  Given Алексей открыл страницу «Дизайн API уведомлений»
  When он связывает её с задачей HUB-123
  Then в карточке задачи HUB-123 появляется ссылка на страницу
  And на странице отображается обратная ссылка на HUB-123 со статусом задачи

Scenario: Привязка к недоступной задаче (негативный)
  Given у Алексея нет доступа к проекту задачи SEC-77
  When он пытается связать страницу с SEC-77
  Then система отвечает 403 {"error","request_id"}
  And связь не создаётся
```

Edge-cases: связь многие-ко-многим (страница ↔ несколько задач и наоборот); удаление задачи или страницы убирает связь без битых ссылок (tombstone в UI); пользователь видит ссылку на страницу из задачи, только если имеет доступ к странице (иначе ссылка скрыта — не «403 при клике из списка»).

#### US-WIKI-05 — Поиск user-scoped (NF-03)

```gherkin
Scenario: Поиск в границах прав (позитивный)
  Given Игорь имеет доступ к space A и не имеет к space B
  When он ищет термин через Ctrl+K, встречающийся в страницах обоих space
  Then в результатах только страницы space A
  And restrict-страницы space A, куда Игорь не входит, отсутствуют в результатах

Scenario: Права проверяются на момент запроса (негативный)
  Given Игоря удалили из space A после индексации страниц
  When он повторяет тот же поисковый запрос
  Then страницы space A более не появляются в результатах (0 результатов ≠ ошибка)
```

Edge-cases: сниппет результата не раскрывает контент сверх права read (заголовок + фрагмент только доступных страниц); поиск не выдаёт страницы из корзины; фильтрация по правам — на сервере (инвариант NF-03: search без user-scope фильтра запрещён), не на клиенте.

## Сценарии использования

### Основной: создание бага из failed тест-кейса

1. CI запускает автотесты → Allure JSON → `hub-cli push-results` в TMS API
2. Парсер матчит результат с тест-кейсом HUB-TC-42
3. QA видит failed в прогоне → «Создать баг»
4. Создаётся задача HUB-123 типа Bug, связь с кейсом
5. Уведомление в канал #hub-bugs и Telegram ответственному

### Основной: рабочий день разработчика

1. Личный дашборд → назначенные задачи и дедлайны
2. Открывает HUB-42, Start Timer
3. Коммит «HUB-42 fix login» → автопривязка PR
4. Stop Timer → время в логе задачи

### Альтернативный: вход через Magic Link

1. Пользователь открывает /login → вводит email
2. Получает код (Resend / hub-mail) → verify → JWT
3. При необходимости — привязка Telegram в Settings для notify

*(Telegram login removed — ADR-AUTH-01)*

### Альтернативный: настройка нового проекта (Project Owner)

1. Создаёт проект «Mobile App», ключ MOB
2. Настраивает workflow: To Do → In Progress → Code Review → QA → Done
3. Генерирует invite-ссылку, подключает GitHub и Allure webhook

### Альтернативный: ежедневный стендап

1. Recurring звонок в #dev-standup
2. Screen share Kanban-доски
3. Запись по кнопке → ссылка в канал и раздел «Записи» проекта

### Исключительный: конфликт optimistic lock

1. Два пользователя редактируют задачу одновременно
2. Второй save получает 409 Conflict (version mismatch)
3. UI показывает diff и предлагает перезагрузить или перезаписать
