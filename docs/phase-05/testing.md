# Фаза 5: Голосовые звонки -- Тестовая документация

## Обзор

Тестовая документация для модуля голосовых звонков покрывает три требования: CALL-01 (аудиозвонки и демонстрация экрана), CALL-03 (управление звонком) и CALL-06 (эфемерный чат). Тест-кейсы следуют конвенции именования `TC-CALL-{REQ_ID}-{NN}`, принятой в предыдущих фазах.

## Тест-кейсы для CALL-01: Аудиозвонки и демонстрация экрана

### TC-CALL-01-01: Создание звонка из канала

**Предусловия:**
- Пользователь аутентифицирован и находится в канале мессенджера
- В канале нет активного звонка
- Сервер LiveKit запущен и доступен

**Шаги:**
1. Пользователь нажимает кнопку "Начать звонок" в заголовке канала
2. Система отправляет POST /api/calls с `channel_id`
3. Бэкенд создает комнату в LiveKit через RoomServiceClient.CreateRoom
4. Бэкенд сохраняет запись звонка в PostgreSQL (статус: active)
5. Бэкенд добавляет создателя как участника (CallParticipant)
6. Бэкенд генерирует JWT-токен LiveKit для создателя
7. Бэкенд публикует событие `calls.channel.{channelID}.started` в NATS

**Ожидаемый результат:**
- HTTP 201 с CallResponse (id, room_name, channel_id, status=active, token)
- Комната создана на сервере LiveKit с MaxParticipants=50
- Запись Call в БД со статусом "active"
- Запись CallParticipant для создателя
- Событие started доставлено в канал через WebSocket

---

### TC-CALL-01-02: Присоединение к активному звонку

**Предусловия:**
- Активный звонок существует в канале
- Пользователь аутентифицирован и не является участником звонка

**Шаги:**
1. Пользователь нажимает "Присоединиться" на индикаторе активного звонка
2. Система отправляет POST /api/calls/:callId/join
3. Бэкенд проверяет статус звонка (должен быть "active")
4. Бэкенд добавляет участника в БД
5. Бэкенд генерирует JWT-токен для нового участника
6. Бэкенд публикует событие `calls.channel.{channelID}.joined` в NATS

**Ожидаемый результат:**
- HTTP 200 с CallResponse (включает token)
- Новая запись CallParticipant в БД
- Счетчик participant_count увеличен на 1
- Событие joined доставлено в канал через WebSocket
- Пользователь подключается к LiveKit и слышит аудио других участников

---

### TC-CALL-01-03: Выход из звонка

**Предусловия:**
- Пользователь является участником активного звонка

**Шаги:**
1. Пользователь нажимает кнопку "Покинуть звонок" на панели управления
2. Система отправляет POST /api/calls/:callId/leave
3. Бэкенд устанавливает left_at для записи CallParticipant
4. Бэкенд декрементирует participant_count
5. Бэкенд публикует событие `calls.channel.{channelID}.left` в NATS
6. Клиент отключается от LiveKit

**Ожидаемый результат:**
- HTTP 200
- CallParticipant.left_at заполнен текущей датой
- participant_count уменьшен на 1
- Событие left доставлено в канал через WebSocket
- Браузер отключен от комнаты LiveKit

---

### TC-CALL-01-04: Завершение звонка создателем

**Предусловия:**
- Активный звонок существует
- Пользователь имеет доступ к завершению звонка

**Шаги:**
1. Пользователь нажимает кнопку "Завершить звонок"
2. Система отправляет POST /api/calls/:callId/end
3. Бэкенд удаляет комнату в LiveKit через RoomServiceClient.DeleteRoom
4. Бэкенд обновляет статус звонка на "ended" и устанавливает ended_at
5. Бэкенд публикует событие `calls.channel.{channelID}.ended` в NATS
6. Все участники автоматически отключаются

**Ожидаемый результат:**
- HTTP 200
- Call.status = "ended", Call.ended_at заполнен
- Комната удалена из LiveKit
- Событие ended доставлено в канал через WebSocket
- Все подключённые клиенты получают onDisconnect

---

### TC-CALL-01-05: Демонстрация экрана

**Предусловия:**
- Пользователь является участником активного звонка
- Браузер поддерживает getDisplayMedia API

**Шаги:**
1. Пользователь нажимает кнопку "Демонстрация экрана" на панели управления
2. Браузер показывает системный диалог выбора экрана/окна/вкладки
3. Пользователь выбирает источник и подтверждает
4. LiveKit публикует screen share track в комнату
5. Все участники видят демонстрацию в области ScreenShareView

**Ожидаемый результат:**
- Screen share track опубликован через LiveKit
- Все участники видят демонстрацию экрана в VideoTrack компоненте
- Кнопка "Демонстрация экрана" меняется на "Остановить демонстрацию"
- При остановке track удаляется и демонстрация прекращается

---

### TC-CALL-01-06: Множественные screen share одновременно

**Предусловия:**
- Активный звонок с 3+ участниками
- Минимум 2 участника могут демонстрировать экран

**Шаги:**
1. Участник A начинает демонстрацию экрана
2. Участник B также начинает демонстрацию экрана
3. Оба screen share отображаются у всех участников
4. Участник A останавливает демонстрацию
5. Screen share участника B продолжает отображаться

**Ожидаемый результат:**
- ScreenShareView отображает сетку из нескольких демонстраций
- Каждый VideoTrack показывает отдельный экран
- Остановка одной демонстрации не влияет на другие
- Layout адаптируется к количеству активных screen share

---

## Тест-кейсы для CALL-03: Управление звонком

### TC-CALL-03-01: Включение/выключение микрофона

**Предусловия:**
- Пользователь является участником активного звонка
- Микрофон включён по умолчанию при подключении

**Шаги:**
1. Пользователь нажимает кнопку микрофона на панели управления
2. Система вызывает LiveKit toggleMicrophone (localParticipant)
3. Аудио track отключается
4. Индикатор mute появляется у участника в ParticipantList
5. Пользователь повторно нажимает кнопку микрофона
6. Аудио track включается обратно

**Ожидаемый результат:**
- При mute: иконка микрофона зачёркнута, аудио не транслируется другим участникам
- При unmute: иконка микрофона активна, аудио возобновляется
- Индикатор mute виден всем участникам в списке
- Переключение происходит мгновенно через LiveKit SDK

---

### TC-CALL-03-02: Поднятие руки

**Предусловия:**
- Пользователь является участником активного звонка

**Шаги:**
1. Пользователь нажимает кнопку "Поднять руку"
2. Система отправляет POST /api/calls/:callId/raise-hand с `{raised: true}`
3. Бэкенд вызывает RoomServiceClient.UpdateParticipant с метаданными `{hand_raised: true, raised_at: "..."}`
4. LiveKit рассылает обновление метаданных всем участникам
5. ParticipantList отображает иконку поднятой руки у пользователя
6. Пользователь повторно нажимает кнопку для опускания руки
7. Система отправляет POST /api/calls/:callId/raise-hand с `{raised: false}`

**Ожидаемый результат:**
- При поднятии: иконка руки рядом с именем участника, кнопка меняет состояние
- При опускании: иконка руки исчезает
- Обновление видно всем участникам в реальном времени
- Метаданные содержат raised_at timestamp для упорядочивания

---

### TC-CALL-03-03: Выбор экрана/окна для демонстрации

**Предусловия:**
- Пользователь является участником активного звонка
- У пользователя открыто несколько окон/приложений

**Шаги:**
1. Пользователь нажимает "Демонстрация экрана"
2. Браузер показывает диалог с вкладками: "Весь экран", "Окно", "Вкладка браузера"
3. Пользователь выбирает конкретное окно приложения
4. Демонстрация начинается только для выбранного окна
5. Другие участники видят содержимое этого окна

**Ожидаемый результат:**
- Системный диалог выбора отображается корректно
- Демонстрация показывает только выбранный источник
- При переключении окна содержимое обновляется в реальном времени
- При отклонении диалога (Cancel) демонстрация не начинается

---

## Тест-кейсы для CALL-06: Эфемерный чат звонка

### TC-CALL-06-01: Отправка сообщения в чат звонка

**Предусловия:**
- Пользователь является участником активного звонка
- MongoDB сконфигурирован (chatRepo != nil)

**Шаги:**
1. Пользователь открывает панель чата звонка
2. Вводит текстовое сообщение (например, "Ссылка на задачу: HUB-42")
3. Нажимает "Отправить"
4. Система отправляет POST /api/calls/:callId/chat с `{text: "..."}`
5. Бэкенд проверяет что звонок активен (status == "active")
6. Бэкенд сохраняет сообщение в MongoDB (коллекция call_chat_messages)
7. Бэкенд публикует событие `calls.chat.{callID}` в NATS

**Ожидаемый результат:**
- HTTP 201 с CallChatMessage (id, call_id, user_id, user_name, text, created_at)
- Сообщение сохранено в MongoDB с ObjectID
- Событие содержит все поля сообщения для real-time доставки
- Текст ограничен 2000 символами (при превышении -- ошибка)

---

### TC-CALL-06-02: Real-time доставка сообщений чата

**Предусловия:**
- Два+ участника в активном звонке
- Оба подключены к WebSocket и подписаны на WS room `call:{callID}`

**Шаги:**
1. Участник A отправляет сообщение в чат звонка
2. Бэкенд публикует событие в NATS subject `calls.chat.{callID}`
3. WS bridge получает событие и маршрутизирует в room `call:{callID}`
4. Участник B получает сообщение через WebSocket с типом `chat.message`

**Ожидаемый результат:**
- Сообщение доставлено всем участникам звонка в реальном времени
- Задержка доставки минимальна (< 100ms в локальной сети)
- Формат WS-сообщения содержит: id, user_id, user_name, text, created_at
- Сообщения отображаются в хронологическом порядке

---

### TC-CALL-06-03: Удаление чата после завершения звонка

**Предусловия:**
- Активный звонок с несколькими сообщениями в чате
- MongoDB содержит записи в коллекции call_chat_messages для данного callID

**Шаги:**
1. Звонок завершается (все участники покинули или создатель завершил)
2. LiveKit отправляет webhook `room_finished`
3. Бэкенд обрабатывает webhook в HandleWebhook -> OnRoomFinished
4. OnRoomFinished вызывает chatRepo.DeleteCallChat(callID)
5. ChatRepository выполняет DeleteMany({call_id: callID}) в MongoDB

**Ожидаемый результат:**
- Все сообщения чата удалены из MongoDB
- Попытка получить сообщения (GET /api/calls/:callId/chat) возвращает пустой массив
- Попытка отправить новое сообщение возвращает ошибку "звонок уже завершён"
- Если chatRepo == nil, удаление пропускается с логированием

## Дополнительные сценарии

### TC-CALL-01-07: Получение активного звонка канала

**Предусловия:**
- В канале есть активный звонок

**Шаги:**
1. Пользователь открывает канал
2. Система отправляет GET /api/calls/channel/:channelId
3. Бэкенд ищет звонок со статусом "active" для данного канала

**Ожидаемый результат:**
- HTTP 200 с CallResponse (без token -- токен выдаётся только при join/create)
- Если активного звонка нет -- HTTP 200 с `{call: null}`

---

### TC-CALL-01-08: Webhook room_started от LiveKit

**Предусловия:**
- Звонок создан через API
- LiveKit сервер запущен и отправляет webhooks

**Шаги:**
1. LiveKit отправляет POST /api/calls/webhook с событием room_started
2. Бэкенд верифицирует JWT подпись в Authorization header
3. Бэкенд проверяет SHA256 hash тела запроса
4. Бэкенд вызывает OnRoomStarted -- устанавливает started_at

**Ожидаемый результат:**
- HTTP 200
- Call.started_at заполнен текущим временем
- Невалидный JWT -- HTTP 401

---

### TC-CALL-06-04: Получение истории сообщений чата

**Предусловия:**
- Активный звонок с 10+ сообщениями в чате

**Шаги:**
1. Пользователь запрашивает GET /api/calls/:callId/chat?limit=5
2. Бэкенд запрашивает MongoDB с сортировкой по created_at DESC, limit=5
3. Результат реверсируется для хронологического порядка

**Ожидаемый результат:**
- HTTP 200 с массивом из 5 последних сообщений
- Сообщения отсортированы от старого к новому
- limit по умолчанию = 50, максимум = 200
- Пустой массив если сообщений нет
