# Глоссарий Hub

> Единый словарь терминов, ID-конвенций и модулей. Нужен, чтобы «ECC-AI-001», «GZ-SEC-02» и «bases» означали для всех одно и то же.
>
> Правило: вводишь новый префикс ID или доменный термин — добавляй сюда в том же PR (`.cursor/rules/55-docs-sync.mdc`).

*Создано: 2026-07-19. Префиксы и модули извлечены из фактического содержимого `docs/`, `.planning/`, `backend/internal/`.*

---

## 1. ID-конвенции

> Порядок — по фактической частоте употребления в репозитории.

| Префикс | Расшифровка | Что обозначает | Где живёт | Пример |
|---------|-------------|-----------------|-----------|--------|
| `ECC-` | Edge/Corner Case | Краевой/угловой сценарий из каталога покрытия | `.planning/july-2026/EDGE-CORNER-CATALOG.md`, `.planning/edge-expansions/` | `ECC-AI-001` |
| `TC-` | Test Case | Тест-кейс (ручной или автоматизированный) | `docs/TESTING.md` | `TC-AUTH-03` |
| `US-` | User Story | Пользовательская история | `docs/vision_and_scope.md` | `US-C01` |
| `NFR-` | Non-Functional Requirement | Нефункциональное требование (производительность, безопасность, надёжность) | `docs/system_specification.md` | `NFR-02` |
| `FR-` | Functional Requirement | Функциональное требование | `docs/system_specification.md` | `FR-CAL-01` |
| `GZ-` | Gray Zone | Серая зона — вопрос, требовавший решения; после решения фиксируется как принятое | `.planning/gray-zones/` | `GZ-SEC-02` |
| `FA-` | Final Audit | Задача финального аудита волны | `.planning/audits/` | `FA-06` |
| `SEC-` | Security finding | Находка безопасности | `docs/security_guidelines.md`, аудиты | `SEC-01` |
| `ADR-` | Architecture Decision Record | Зафиксированное архитектурное решение с контекстом и последствиями | `.planning/decisions/` | `ADR-AUTH-01-magic-link-only` |
| `PG-` | Production Gate | Задача-ворота перед выпуском в прод | `.planning/production/` | `PG-03` |
| `ME-` | (Module/Engineering issue) | Инженерная находка по модулю | аудиты, agent-файлы | `ME-13` |
| `TF-` | Test Framework | Задача по тестовому фреймворку | `.planning/`, `testframework/` | `TF-CLEANUP-01` |
| `UX-` | UX task | Задача пользовательского опыта | `.planning/` | `UX-1` |
| `V4-` | Milestone v4 | Задача milestone v4 (Super-app) | `.planning/milestones/v4-super-app/` | `V4-04` |
| `PROD-` | Production task | Задача продакшн-эксплуатации | `.planning/production/` | `PROD-01` |
| `INF-` | Infrastructure finding | Инфраструктурная находка | аудиты, `docs/security_guidelines.md` | `INF-03` |

**Правила именования:** префикс заглавными, разделитель `-`, номер с ведущими нулями там, где так уже принято в конкретном каталоге (`ECC-AI-001`). Домен в середине — для сквозных каталогов (`TC-AUTH-03`, `FR-CAL-01`).

**Трассируемость:** цепочка `US → FR/NFR → TC → автотест` — обязательна для проверяемых требований; матрица покрытия — `.planning/COVERAGE.md`. Обрыв цепочки в любом звене — находка ревью (`.cursor/playbooks/prompt-contract.md` §8, роль `qa-manual`).

## 2. Модули backend (`backend/internal/`)

> Фактический список пакетов. Домен = граница ответственности и, как правило, граница задач между агентами (`be1`/`be2`).

### Ядро платформы

| Модуль | Назначение |
|--------|-----------|

| `search` | Поиск по сущностям |
| `notification` | Уведомления (in-app, внешние каналы) |

## 3. Инфраструктурные термины

| Термин | Что это в Hub |
|--------|----------------|
| **Ent** | ORM/кодогенератор схемы для Go. Схема — `backend/ent/`, миграции применяются при старте приложения (`ent/migrate/`) |
| **Fiber** | HTTP-фреймворк backend |
| **NATS / JetStream** | Шина событий между модулями; JetStream — персистентные стримы |
| **SeaweedFS** | S3-совместимое файловое хранилище |
| **LiveKit** | Медиасервер для звонков (канон; альтернатива mediasoup отклонена — `SEED-001`) |
| **Caddy** | Reverse proxy + автоматический TLS |
| **GHCR** | GitHub Container Registry — где лежат образы `ghcr.io/valerijkk/hub/*` |
| **K3s** | Лёгкий Kubernetes; манифесты — `deployments/k3s/` |
| **Promtail / Loki / Grafana / Prometheus / Alertmanager** | Стек наблюдаемости (`deployments/docker-compose.monitoring.yml`) |

## 4. Тестирование

| Термин | Значение |
|--------|----------|
| **testframework** | Каталог `testframework/` — карта тестов по стадиям CI (`PIPELINE.md`); Go-тесты физически в `backend/testframework/` |
| **hubtest** | Build-тег Go для интеграционных тестов: `go test -tags hubtest` |
| **e2e-smoke / e2e-full** | CI-джобы: smoke — 3 спеки (быстрый гейт на PR); full — все домены (перед релизом/волной) |
| **coverage-gate** | Джоба-гейт по порогу покрытия |
| **Test triage** | Обязательный протокол при падении теста: сверить функционал с докой → решить `ROOT=code` или `ROOT=test` → чинить минимальный слой (`.cursor/skills/test-triage/`) |
| **Flaky** | Недетерминированный тест (проходит/падает без изменений кода). Ретрай — не фикс |
| **Allure** | Формат отчётности тестов |

## 5. Процесс AI-команды

| Термин | Значение |
|--------|----------|
| **Агент** | Роль AI-команды, файл `.cursor/agents/<role>.md` (32 файла) |
| **Верификатор (`*-ver`)** | Независимая роль приёмки артефакта; readonly, выдаёт вердикт, не правит |
| **Playbook** | Глубокая практика ремесла, `.cursor/playbooks/*.md`; агенты ссылаются, не дублируют |
| **Rule** | Краткая always-applied карточка ограничений, `.cursor/rules/*.mdc` |
| **Волна (wave)** | Пакет параллельных задач, выполняемых агентами одновременно с разделением по файлам |
| **Handoff** | Передача артефакта следующему звену по шаблону промпта (§5.2) |
| **Шаблон §5.2** | Канонический формат делегирования: роль/задача, контекст с границами, формат ответа, условия (`.cursor/agents/team-lead.md` §5.2) |
| **Контракт промпта** | Обязательный контракт приёма/ответа/верификации для всех агентов (`.cursor/playbooks/prompt-contract.md`) |
| **10-этапная верификация** | Протокол самопроверки перед handoff (`prompt-engineering/rules/40-verification-protocol.md`) |
| **GSD** | Get-Shit-Done — набор skills для планирования/исполнения фаз (`~/.claude/skills/gsd-*`), маршрутизация в `.cursor/GSD-INTEGRATION.md` |
| **Prompt Engineering Toolkit** | Переносимый набор агентов/скилов/1000 промптов для тестового фреймворка (`prompt-engineering/`) |

## 6. Статусы и решения

| Термин | Значение |
|--------|----------|
| **Milestone** | Крупный этап продукта (v1.0 … v4 Super-app); архив — `.planning/milestones/` |
| **Gray zone (серая зона)** | Нерешённый вопрос, требующий явного решения владельца; реестр решений — `.planning/gray-zones/` |
| **Seed** | Идея «на будущее» с условиями активации (`.planning/seeds/`); статусы: active / rejected |
| **Baseline** | Состояние, принятое как эталонное после верификации |
| **DoD (Definition of Done)** | Критерии готовности артефакта; у каждого агента свой в agent-файле |
| **TZ-инвариант** | Жёсткое ограничение техзадания (mandatory/forbidden), `docs/tz_constraints.md` |

## 7. Как пользоваться глоссарием

- **Не знаешь префикс в тикете** — §1, там же где искать сам объект.
- **Не знаешь, чей это модуль** — §2, оттуда же понятно, какой playbook грузить.
- **Новый термин в команде** — добавь строку сюда, иначе через месяц он будет означать разное у разных участников.
- **Термин устарел** (модуль удалён, префикс не используется) — удалить строку, а не оставлять «на всякий случай»: глоссарий с мёртвыми терминами вводит в заблуждение.
