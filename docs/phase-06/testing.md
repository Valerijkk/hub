# Фаза 6: Уведомления, поиск, дашборды и аудит -- Тестовая документация

## Обзор

Тестовая документация покрывает все 14 требований фазы 6. Тест-кейсы следуют конвенции именования `TC-{REQ_ID}-{NN}`, принятой в предыдущих фазах проекта.

Всего: **44 тест-кейса** для подсистем уведомлений, поиска, дашбордов и аудита.

---

## Тест-кейсы для NOTF-01: Триггеры уведомлений

### TC-NOTF-01-01: Уведомление при назначении задачи (assigned)

**Предусловия:**
- Пользователь A аутентифицирован и является участником проекта
- Пользователь B является участником того же проекта
- NATS JetStream запущен, consumer `notification-dispatcher` активен

**Шаги:**
1. Пользователь A назначает задачу HUB-42 на пользователя B
2. Трекер публикует событие `project.{projectID}.assigned` в NATS
3. Consumer обрабатывает событие и создает уведомление

**Ожидаемый результат:**
- В таблице notifications создана запись с type="assigned", user_id=B, entity_type="issue", entity_id=HUB-42
- Уведомление доставлено через WebSocket (событие notification.new)
- GET /api/notifications/unread-count для пользователя B возвращает count >= 1

---

### TC-NOTF-01-02: Уведомление при @упоминании в комментарии (mentioned)

**Предусловия:**
- Пользователь A и B -- участники проекта
- Задача HUB-10 существует в проекте

**Шаги:**
1. Пользователь A добавляет комментарий к HUB-10 с текстом "Посмотри @B"
2. Трекер публикует событие `project.{projectID}.comment_added` с mentions=[B]
3. Consumer извлекает @mentions и создает уведомление типа "mentioned"

**Ожидаемый результат:**
- Уведомление с type="mentioned" создано для пользователя B
- Заголовок содержит ссылку на задачу и комментарий
- Пользователь A НЕ получает уведомление о своем же комментарии

---

### TC-NOTF-01-03: Уведомление при смене статуса задачи (status_changed)

**Предусловия:**
- Задача HUB-15 назначена на пользователя B
- Пользователь A (не assignee) меняет статус

**Шаги:**
1. Пользователь A переводит HUB-15 из "In Progress" в "Done"
2. Трекер публикует событие `project.{projectID}.status_changed`
3. Consumer создает уведомление для assignee (пользователь B)

**Ожидаемый результат:**
- Уведомление с type="status_changed" создано для пользователя B
- Тело уведомления содержит старый и новый статус
- GET /api/notifications для B содержит это уведомление

---

### TC-NOTF-01-04: Debounce предотвращает дублирование

**Предусловия:**
- Consumer активен с 2-секундным debounce окном

**Шаги:**
1. За 1 секунду приходят 3 события assigned для одной и той же задачи + пользователя
2. Consumer проверяет debounce ключ `userID:assigned:entityID`

**Ожидаемый результат:**
- Создано только 1 уведомление (первое)
- Последующие 2 события отброшены debounce-фильтром
- В логах slog отражен пропуск дублей

## Тест-кейсы для NOTF-02: Каналы доставки

### TC-NOTF-02-01: Доставка In-App через WebSocket

**Предусловия:**
- Пользователь B подключен через WebSocket
- WS bridge подписан на `notification.user.{userID}`

**Шаги:**
1. Создается уведомление для пользователя B
2. Service публикует событие в NATS-субъект `notification.user.{B.ID}`
3. WS bridge маршрутизирует через WebSocket

**Ожидаемый результат:**
- Пользователь B получает WS-сообщение с event="notification.new"
- Payload содержит id, type, title, body, entity_type, entity_id, is_urgent
- Zustand store обновляет unreadCount

---

### TC-NOTF-02-02: Доставка через Telegram

**Предусловия:**
- У пользователя B указан telegram_chat_id в профиле
- TelegramSender инициализирован с корректным botToken
- Предпочтение telegram включено для данного типа уведомления

**Шаги:**
1. Создается уведомление типа "assigned" для пользователя B
2. Service ставит сообщение в очередь TelegramSender (buffered channel)
3. Worker-горутина извлекает сообщение и отправляет через telego.SendMessage()

**Ожидаемый результат:**
- Сообщение отправлено в Telegram в формате MarkdownV2
- Между отправками соблюдается rate limit 35мс
- При ошибке отправки логируется warning, но процесс не останавливается

---

### TC-NOTF-02-03: Nil-safe TelegramSender (botToken пустой)

**Предусловия:**
- Переменная окружения TELEGRAM_BOT_TOKEN не задана

**Шаги:**
1. Сервер запускается, NewTelegramSender возвращает nil
2. Создается уведомление, service пытается вызвать telegram.Send()

**Ожидаемый результат:**
- Send() на nil sender -- no-op, ошибки нет
- Сервер не падает, уведомление сохранено в БД
- In-App доставка работает нормально

## Тест-кейсы для NOTF-04: Тихие часы

### TC-NOTF-04-01: Блокировка несрочного уведомления в тихие часы

**Предусловия:**
- Пользователь B установил quiet_hours: 22:00 - 08:00
- Часовой пояс пользователя: Europe/Moscow
- Текущее время в Москве: 23:30

**Шаги:**
1. Создается несрочное (is_urgent=false) уведомление для B
2. Service проверяет текущее время vs quiet_hours с учетом timezone

**Ожидаемый результат:**
- Уведомление сохранено в БД (is_read=false)
- Telegram-доставка заблокирована
- WS-доставка заблокирована
- При GET /api/notifications уведомление отображается

---

### TC-NOTF-04-02: Срочное уведомление пробивает тихие часы

**Предусловия:**
- Те же, что в TC-NOTF-04-01 (тихие часы активны)

**Шаги:**
1. Создается срочное (is_urgent=true) уведомление (blocker_added)
2. Service проверяет is_urgent=true

**Ожидаемый результат:**
- Уведомление доставлено через In-App и Telegram несмотря на тихие часы
- В теле Telegram-сообщения есть метка "Срочное"

---

### TC-NOTF-04-03: Тихие часы с переносом через полночь

**Предусловия:**
- quiet_hours_start=23:00, quiet_hours_end=07:00
- Текущее время: 01:00 (после полуночи, но до end)

**Шаги:**
1. Алгоритм проверяет: start(23:00) > end(07:00) -> перенос через полночь
2. Проверка: now(01:00) >= start(23:00) ИЛИ now(01:00) < end(07:00) -> true

**Ожидаемый результат:**
- Тихие часы активны в 01:00 (корректная обработка переноса через полночь)
- Несрочные уведомления заблокированы

## Тест-кейсы для AUDT-04: Управление пользователями

### TC-AUDT-04-01: Деактивация пользователя

**Предусловия:**
- Администратор аутентифицирован
- Пользователь B активен (status="active")

**Шаги:**
1. POST /api/admin/users/{B.id}/deactivate
2. Пользователь B пытается сделать запрос к API

**Ожидаемый результат:**
- User.status обновлен на "deactivated"
- Ответ: `{"success":true, "message":"Пользователь деактивирован"}`
- Auth middleware проверяет user.Status и возвращает 401 для деактивированных
- Пользователь B не может войти в систему

---

### TC-AUDT-04-02: Переназначение задач деактивированного пользователя

**Предусловия:**
- Пользователь B деактивирован, имеет 5 назначенных задач
- Пользователь C активен

**Шаги:**
1. POST /api/admin/users/{B.id}/reassign с body: `{"to_user_id":"{C.id}"}`

**Ожидаемый результат:**
- Все незакрытые задачи B переназначены на C
- Ответ: `{"success":true, "reassigned_count":5}`
- Задачи C теперь включают переназначенные

---

### TC-AUDT-04-03: GDPR-удаление данных пользователя

**Предусловия:**
- Пользователь B деактивирован

**Шаги:**
1. DELETE /api/admin/users/{B.id}/gdpr
2. Система выполняет каскадное удаление

**Ожидаемый результат:**
- Assignee очищен у всех задач B
- Сессии B удалены из таблицы sessions
- Запись пользователя B удалена из таблицы users
- Данные B анонимизированы в MongoDB
- Ответ: `{"success":true, "message":"Данные пользователя удалены (GDPR)"}`

---

### TC-AUDT-04-04: Мульти-шаговое подтверждение GDPR в UI

**Предусловия:**
- Администратор на странице управления пользователями

**Шаги:**
1. Нажимает "GDPR-удаление" для пользователя B
2. Первый шаг: предупреждение о необратимости
3. Второй шаг: ввод подтверждающего текста
4. Третий шаг: финальное подтверждение

**Ожидаемый результат:**
- Каждый шаг требует явного подтверждения
- DELETE-запрос отправляется только после всех шагов
- При отмене на любом шаге операция прерывается
