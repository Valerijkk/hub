# Трекер задач -- Бизнес-документация

## Обзор модуля

Трекер задач -- центральный модуль платформы Hub, предназначенный для управления рабочими процессами команд разработки и тестирования. Модуль обеспечивает полный цикл работы с задачами: от создания и назначения до выполнения и закрытия, с поддержкой гибких рабочих процессов, Kanban-досок, иерархии задач и учета времени.

Трекер задач интегрирован с остальными модулями Hub:
- **Мессенджер**: уведомления о событиях трекера приходят в каналы проекта
- **TMS**: задачи привязываются к тест-кейсам, баги создаются из упавших тестов
- **Файловое хранилище**: вложения к задачам хранятся в SeaweedFS

## 1. Типы задач (TASK-01)

Трекер поддерживает 9 типов задач, каждый из которых предназначен для определенного класса работ:

| Тип | Назначение | Пример использования |
|-----|-----------|---------------------|
| **Bug** | Дефект, ошибка в работе системы | "Кнопка 'Сохранить' не работает на мобильной версии" |
| **Task** | Обычная задача, единица работы | "Добавить валидацию email на форме регистрации" |
| **Story** | Пользовательская история | "Как пользователь, я хочу фильтровать задачи по приоритету" |
| **Epic** | Большая функциональность, группирует Stories | "Модуль управления тестированием" |
| **Sub-task** | Подзадача, часть более крупной задачи | "Написать unit-тесты для API авторизации" |
| **Improvement** | Улучшение существующей функциональности | "Ускорить загрузку списка задач на 30%" |
| **Tech Debt** | Технический долг | "Рефакторинг модуля аутентификации" |
| **Spike** | Исследовательская задача | "Оценить возможность интеграции с Jira API" |
| **Release** | Релиз, объединяет задачи версии | "Релиз v1.2.0" |

Тип задачи задается при создании и не может быть изменен после.

## 2. Жизненный цикл задачи

Каждая задача проходит через следующие этапы:

### Создание
Пользователь с правом `PermTaskCreate` создает задачу, указывая:
- **Обязательно**: заголовок, тип задачи
- **Опционально**: описание (rich-text через Plate editor), приоритет, исполнитель, родительская задача, статус, метки, кастомные поля, оценка времени, дедлайн

При создании задача автоматически получает:
- Уникальный номер в проекте (атомарный счетчик)
- Ключ в формате `ПРЕФИКС-НОМЕР` (например, HUB-1)
- Статус по умолчанию ("To Do")
- Версию 1 (для оптимистичной блокировки)
- Запись в журнале активности ("created")

### Назначение
Задачу можно назначить на исполнителя при создании или позже через обновление. Изменение исполнителя фиксируется в журнале активности.

### Работа
В процессе работы над задачей:
- Исполнитель перемещает задачу по статусам workflow (например, "To Do" -> "In Progress")
- Команда оставляет комментарии с @упоминаниями
- Ведется учет времени (ручной ввод или таймер)
- Добавляются метки и вложения

### Ревью
Задача переводится в статус ревью ("In Review"), где проверяется качество выполненной работы.

### Закрытие
После успешного ревью задача переводится в финальный статус ("Done"). Все переходы между статусами контролируются движком workflow.

## 3. Рабочий процесс (Workflow) (TASK-06)

### Статусы по умолчанию

При создании проекта автоматически создается рабочий процесс с четырьмя статусами:

| Статус | Категория | Цвет | Описание |
|--------|-----------|------|----------|
| To Do | `todo` | серый (#6B7280) | Задача создана, ожидает начала работы |
| In Progress | `in_progress` | синий (#3B82F6) | Задача в работе |
| In Review | `in_progress` | желтый (#F59E0B) | Задача на проверке |
| Done | `done` | зеленый (#10B981) | Задача завершена |

### Категории статусов

Каждый статус принадлежит одной из трех категорий:
- **todo** -- задача еще не начата
- **in_progress** -- задача в работе
- **done** -- задача завершена

Категории используются для аналитики и визуализации на дашбордах.

### Настройка workflow

Владелец проекта (роль Owner) может настраивать рабочий процесс:

1. **Создание статусов**: добавление новых статусов с именем, категорией, цветом и порядком сортировки
2. **Редактирование статусов**: изменение имени, цвета и порядка сортировки
3. **Удаление статусов**: удаление неиспользуемых статусов
4. **Создание переходов**: определение разрешенных переходов между статусами
5. **Удаление переходов**: удаление разрешенных переходов

Для управления workflow требуется право `PermProjectManageWorkflow`.

### Диаграмма переходов (по умолчанию)

```
  To Do -----> In Progress -----> In Review -----> Done
    ^               |                  |
    |               v                  v
    +---- (обратные переходы настраиваются владельцем) ----+
```

Переходы проверяются движком `WorkflowEngine.ValidateTransition()`. При попытке выполнить неразрешенный переход возвращается ошибка 400.

## 4. Kanban-доска (KANB-01, KANB-04, KANB-05)

### Колонки = статусы workflow

Каждая колонка Kanban-доски соответствует статусу рабочего процесса. Задачи автоматически группируются по текущему статусу. Порядок колонок определяется полем `sort_order` статуса.

### Перетаскивание карточек

Перетаскивание карточки из одной колонки в другую:
1. Проверяется разрешенность перехода через `WorkflowEngine`
2. Обновляется статус задачи
3. Обновляется ранг (позиция) задачи в колонке через LexoRank
4. Записывается событие в журнал активности

### Множественные доски

В одном проекте может быть несколько досок с разными сохраненными фильтрами:
- **Основная доска** -- все задачи проекта (создается по умолчанию)
- **Sprint Board** -- задачи текущего спринта
- **My Tasks** -- задачи, назначенные на текущего пользователя
- Любые пользовательские доски с сохраненными фильтрами

### Фильтры на доске

Доступные фильтры:
- **Мои задачи**: показывает только задачи, назначенные на текущего пользователя
- **По приоритету**: critical, high, medium, low, trivial
- **По типу задачи**: bug, task, story и др.
- **Текстовый поиск**: по заголовку и описанию задачи
- **По статусу**: фильтрация по одному или нескольким статусам
- **По исполнителю**: задачи конкретного участника

Фильтры сохраняются в JSON-формате при создании доски и применяются при загрузке данных.

## 5. Иерархия задач (TASK-03)

Трекер поддерживает неограниченную вложенность задач через связь parent/child:

```
Epic: Модуль авторизации (HUB-1)
  |
  +-- Story: Magic Link авторизация (HUB-2)
  |     |
  |     +-- Task: API отправки magic link (HUB-5)
  |     +-- Task: Верификация magic link (HUB-6)
  |     +-- Sub-task: Unit-тесты (HUB-7)
  |
  +-- Story: Telegram авторизация (HUB-3)
  |     |
  |     +-- Task: Telegram Bot webhook (HUB-8)
  |     +-- Task: Привязка аккаунта (HUB-9)
  |
  +-- Task: RBAC-система (HUB-4)
```

При создании задачи можно указать `parent_id` для установки связи. Каждая задача хранит:
- Ссылку на родителя (`parent` edge)
- Список дочерних задач (`children` edge)
- Количество дочерних задач в ответе API (`children_count`)

## 6. Связи между задачами (TASK-04)

### Встроенные типы связей

| Тип связи | Обратный тип | Описание |
|-----------|-------------|----------|
| `blocks` | `blocked_by` | Задача блокирует другую задачу |
| `relates_to` | `relates_to` | Задачи связаны (симметричная связь) |
| `duplicates` | `duplicated_by` | Задача дублирует другую |
| `clones` | `cloned_from` | Задача является клоном |
| `causes` | `caused_by` | Задача является причиной другой |
| `parent` | `child` | Родительская/дочерняя связь |

### Пользовательские типы связей

Помимо встроенных типов, можно создавать связи с пользовательским типом через поле `custom_type`. Это позволяет определять специфичные для проекта типы связей.

### Управление связями

- **Создание**: POST на `/issues/:issueKey/links` с указанием целевой задачи и типа связи
- **Просмотр**: GET на `/issues/:issueKey/links` возвращает все связи задачи (входящие и исходящие)
- **Удаление**: DELETE на `/issues/:issueKey/links/:linkId`

Уникальный индекс по паре (source, target) предотвращает дублирование связей.

## 7. Нумерация задач (TASK-05)

### Формат ключа

Каждая задача получает уникальный ключ вида `ПРЕФИКС-НОМЕР`:
- **Префикс**: ключ проекта, задается при создании проекта (например, HUB, MOBILE, QA)
- **Номер**: последовательный номер внутри проекта (1, 2, 3, ...)

### Примеры
- `HUB-1`, `HUB-2`, `HUB-42` -- задачи проекта Hub
- `MOBILE-1`, `MOBILE-15` -- задачи мобильного проекта

### Атомарная генерация

Номер задачи генерируется атомарно через `AddTaskCounter(1)` в транзакции Ent. Это гарантирует уникальность номеров даже при конкурентном создании задач несколькими пользователями.

Ключ задачи (`issue_key`) является иммутабельным и уникальным в БД.

## 8. Пользовательские поля (TASK-02)

### Определение полей

Владелец проекта создает определения кастомных полей с указанием:
- **Имя**: название поля (уникальное в рамках проекта)
- **Тип**: один из 8 поддерживаемых типов
- **Опции**: список допустимых значений (для select/multi_select)
- **Обязательность**: является ли поле обязательным

### Поддерживаемые типы

| Тип | Описание | Пример |
|-----|----------|--------|
| `text` | Текстовое поле | Комментарий к сборке |
| `number` | Числовое значение | Story points |
| `date` | Дата | Дата демо |
| `checkbox` | Булево значение | Требует code review |
| `select` | Выбор из списка | Спринт (Sprint 1, Sprint 2) |
| `multi_select` | Множественный выбор | Компоненты (Backend, Frontend) |
| `user` | Ссылка на пользователя | Ревьюер |
| `url` | URL-ссылка | Ссылка на дизайн в Figma |

### Хранение значений

Значения кастомных полей хранятся в JSONB-поле `custom_fields` задачи в формате `{field_id: value}`. Это обеспечивает:
- Гибкость без миграций схемы при добавлении полей
- Нативную фильтрацию PostgreSQL по JSONB
- Отсутствие оверхеда EAV-паттерна

## 9. Комментарии (TASK-07)

### Возможности комментариев

- **Rich-text**: содержимое комментария хранится в формате Plate editor JSON (`body_json`) с дублированием в plain text (`body_text`) для поиска и уведомлений
- **@Упоминания**: при написании комментария можно упомянуть участников проекта через @. Список упомянутых сохраняется в поле `mentions`
- **Внутренние комментарии**: флаг `is_internal` ограничивает видимость комментария определенными ролями (например, только разработчики)
- **Редактирование**: автор может изменить текст комментария
- **Удаление**: автор или администратор может удалить комментарий

### Реакции

На каждый комментарий можно добавить эмодзи-реакцию:
- Один пользователь может добавить одну реакцию одного типа (уникальный индекс: comment + user + emoji)
- Повторное добавление той же реакции удаляет её (toggle)
- В ответе API реакции агрегируются: количество, список пользователей, поставил ли текущий пользователь

## 10. Журнал активности (TASK-08)

Все изменения задачи автоматически фиксируются в журнале активности:

| Действие | Что записывается |
|----------|-----------------|
| `created` | Задача создана |
| `updated` | Изменены поля (title, priority, status, assignee) |
| `status_changed` | Изменен статус (old -> new) |
| `commented` | Добавлен комментарий |
| `linked` | Создана связь с другой задачей |
| `time_logged` | Записано время |

Каждая запись содержит:
- **Кто**: пользователь, совершивший действие
- **Что**: тип действия и список изменений полей (field, old_value, new_value)
- **Когда**: timestamp

Журнал доступен через `GET /issues/:issueKey/activity`.

## 11. Учет времени (TASK-09)

### Оценка

При создании или обновлении задачи можно указать `estimate_minutes` -- предполагаемое время на выполнение.

### Ручной ввод

Через `POST /issues/:issueKey/time` можно записать фактическое время:
- `minutes` -- количество минут (обязательное, минимум 1)
- `description` -- описание работы (опционально, до 500 символов)

### Таймер

Для точного учета доступен таймер Start/Stop:
1. **Старт**: `POST /issues/:issueKey/timer/start` -- создает запись с `started_at`, без `ended_at`
2. **Стоп**: `POST /issues/:issueKey/timer/stop` -- находит активный таймер, устанавливает `ended_at`, вычисляет `minutes`

Если у пользователя уже есть активный таймер на этой задаче, при попытке запустить новый возвращается ошибка.

### Суммарное время

Поле `time_spent_minutes` в задаче хранит суммарное фактическое время. Обновляется при каждой записи времени.

## 12. Метки (TASK-10)

### Создание меток

Метки создаются на уровне проекта с указанием:
- **Имя**: уникальное в рамках проекта
- **Цвет**: HEX-код (по умолчанию #3B82F6)
- **Группа**: опциональная принадлежность к группе меток

### Группы меток

Метки можно организовать в группы для удобства:
- Группа "Приоритет": urgent, important, low-priority
- Группа "Компоненты": backend, frontend, database, infra
- Группа "Платформа": web, mobile, desktop

Имя группы уникально в рамках проекта.

### Назначение на задачу

При создании или обновлении задачи можно указать массив ID меток. Метки привязываются через M2M-связь (edge `labels` в схеме Issue).

## 13. Вложения (TASK-11)

Задачи поддерживают прикрепление файлов через связь с сущностью FileMetadata (реализованной в Phase 1):
- Любые типы файлов
- Предпросмотр изображений, PDF, видео
- Вставка через Ctrl+V и перетаскивание (drag & drop)
- Файлы хранятся в SeaweedFS (S3-compatible хранилище)

Связь реализована через edge `files` в схеме Issue.

## 14. Пагинация (UI-09)

### Курсорная пагинация

Список задач использует курсорную пагинацию:
- `cursor` -- ключ задачи, после которой начинать выборку
- `limit` -- количество элементов на странице (от 1 до 100, по умолчанию 50)

Ответ содержит:
```json
{
  "items": [...],
  "next_cursor": "HUB-50",
  "has_more": true,
  "total": 142
}
```

### Серверная фильтрация

Фильтры применяются на стороне сервера до пагинации:
- `status` -- фильтр по статусам (массив)
- `priority` -- фильтр по приоритетам (массив)
- `assignee` -- UUID исполнителя
- `issue_type` -- тип задачи
- `search` -- текстовый поиск
- `order_by` -- сортировка (created_at, priority, updated_at)

## 15. Оптимистичная блокировка

Для предотвращения потери данных при одновременном редактировании используется оптимистичная блокировка:

1. При получении задачи клиент получает текущую `version`
2. При обновлении клиент передает `version` в запросе
3. Сервер проверяет: `WHERE version = expected`
4. Если версии совпадают -- обновление выполняется, `version` увеличивается на 1
5. Если не совпадают -- возвращается **409 Conflict**

Клиент при получении 409 должен перезагрузить задачу и повторить редактирование.

## 16. Приоритеты задач

Каждая задача имеет приоритет:

| Приоритет | Описание |
|-----------|----------|
| `critical` | Критический -- блокирует работу, требует немедленного исправления |
| `high` | Высокий -- важная задача, выполнить в первую очередь |
| `medium` | Средний (по умолчанию) -- обычная задача |
| `low` | Низкий -- можно отложить |
| `trivial` | Тривиальный -- незначительная задача |
