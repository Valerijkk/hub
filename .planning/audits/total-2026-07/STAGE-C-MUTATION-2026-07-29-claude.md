## 1. Поправка к STAGE-C-GAP-2026-07-29

Предыдущий разбор занизил масштаб проблемы. Счётчик ловил **упоминание слова**
«мутация», а не спецификацию.

Точный пересчёт по признаку «указано что ломать **и** какой тест обязан упасть»:

| Признак | Задач из 110 |
|---|---:|
| **Конкретная мутация** (что ломать + имя теста) | **9** |
| Только слово «мутация» без спецификации | 65 |
| Нет вовсе | 36 |

Механически проверяемы **9 задач из 110**, а не 71. Прежняя цифра неверна,
исправляется этим документом.

Пример недостаточной формулировки — P1-задачи TASK-134 и TASK-171: слово
«мутация» стоит только в строке `Responsibility` («закрыть finding ID + тесты
и мутация»). Что ломать и какой тест обязан упасть — не сказано.

### TASK-152 — apigateway rune guard · **PROVEN** ✅

| | |
|---|---|
| Что ломали | порог `utf8.RuneCountInString(req.Name) > 255` → `> 999999`, `internal/apigateway/handler.go` |
| Слой | handler |

**Замечание по методу.** Первая формулировка мутации — заменить условие на

в ТЗ Touchstone предусмотрен вердикт `mutation_failed_to_build` с требованием
переформулировать (FR-MUT-2, шаг 3).

### TASK-170 — sprint partial unique · **MUTATION_FAILED_TO_BUILD** ⚠️

| | |
|---|---|
| Что ломали | `entsql.IndexWhere("status = 'active' AND deleted_at IS NULL")` из `ent/schema/sprint.go` |
| Результат | сборка пакета тестов упала после `go generate` |
| Вердикт | мутация невалидна, нужна другая формулировка |

Задача **не признана доказанной**: отсутствие красного из-за несобравшейся
мутации доказательством не является.

**Отдельное наблюдение.** Функция `task170ApplyActiveUnique`, применяющая
DDL индекса, объявлена **внутри тестового файла**
`testframework/ent/schema_sprint_task170_test.go`. Тест сам создаёт объект,
который проверяет.

Продакшн-часть при этом на месте: аннотация в схеме (строка 83) и миграция
`migrations/20260729_task170_sprint_active_unique_setnull.sql` существуют.
Но тест их не использует — он воспроизводит DDL самостоятельно. Значит
расхождение схемы с миграцией тест не поймает.

Это класс `layer_mismatch`: guard объявлен в схеме, тест проверяет свою копию.

## 4. Что это значит для TASK-008

Условие «каждая закрытая задача имеет мутацию» **не может быть выполнено**
для 101 задачи из 110, пока в них не дописан критерий.

Порядок остаётся тот же, но первый шаг оказался объёмнее, чем считалось:
дописать спецификацию мутации нужно не в 39 задач, а в **101**.

Для каждой требуется указать:

```
что ломать      конкретный файл, строка, фрагмент кода
какой тест      имя теста, который обязан упасть
на каком слое   handler | service | repository | schema | frontend
```

Без этих трёх полей задача не проверяема, и статус «Закрыта» на ней означает
доверие к отчёту исполнителя, а не доказательство.

## 5. Метод, подтверждённый на практике

Три прогона показали, что мутационный контур работает и ловит именно то,
для чего задуман:

- **TASK-136** — защита реальна, тест её ловит
- **TASK-152** — первая формулировка мутации оказалась невалидной, потребовалась
  вторая; вердикт `mutation_failed_to_build` в ТЗ Touchstone предусмотрен не зря
- **TASK-170** — тест проверяет собственную копию guard'а вместо продакшн-объекта;
  без мутации это не видно ни при чтении диффа, ни при чтении теста
