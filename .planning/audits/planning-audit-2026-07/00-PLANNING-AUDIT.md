## 4. Сквозные требования выполнены на 18–20%

Источник формулировок — `docs/system_specification.md`.

### 4.1 NFR-24 — optimistic locking

`docs/system_specification.md:70`:

> | NFR-24 | Optimistic locking | `version` int **на каждой изменяемой** Ent |

| Замер | Значение |
|---|---|
| Схем в `backend/ent/schema/` | **83** |
| Из них с полем `version` | **17** |
| Доля | **20%** |

Оговорка в пользу кода: часть схем append-only (`auditlog`, `activitylog`,
`outboxevent`) или неизменяемые связки (`pollvote`, `reaction`) — для них
`version` бессмыслен. Точная доля «изменяемых» требует ручной классификации,
но разрыв слишком велик, чтобы объясняться только этим.

### 4.2 NFR-11 — soft delete и корзина 30 дней

`docs/system_specification.md:57`:

> | NFR-11 | Soft delete retention | 30 дней |

| Замер | Значение |
|---|---|
| Схем с `deleted_at` | **15 из 83** (18%) |
| Типов, поддержанных корзиной в API | **4** |

Корзина реализована в `backend/internal/audit/service.go`
(`ListTrash` ≈ строки 196–206, `RestoreItem` ≈ 225–238, `SoftDelete` ≈ 241+)
и знает ровно четыре типа:

```go
case "issue":     ...
case "test_case": ...
case "file":      ...
case "project":   ...
default:          // пусто / ошибка
```

Роуты: `internal/audit/handler.go:33-34` — `GET /admin/trash`,
`POST /admin/trash/:type/:id/restore`.

### 4.3 Следствие — два невыполненных FR

**FR-INTR-08** (`system_specification.md:231`):

> Восстановление поста из корзины возвращает пост вместе с опросом и счётчиками голосов

Факт: `ent/schema/newspost.go` содержит `deleted_at` **и** `version`, `pinned`,
`published` — схема сделана правильно. Но `newspost` **отсутствует в списке типов
корзины**. Результат: пост удаляется мягко, данные остаются в БД, а
**штатного способа восстановить его не существует**. Худший из возможных исходов —
данные лежат и недоступны.

**FR-CAL-05** (`system_specification.md:393`):

> Удаление серии удаляет все вхождения (корзина 30 дней)

Факт: `ent/schema/scheduledcall.go` содержит `rrule` (строка 41) — серии реальны.
Поле `deleted_at` — **отсутствует полностью** (`grep -c deleted_at` = 0).
Ни soft delete, ни корзины. Требование не выполнено ни в одной части.

## 5. Модуль Wiki: спецификация есть, реализации и планов нет

`docs/system_specification.md:515-529` определяет **новый модуль Wiki**
с четырьмя требованиями:

| ID | Суть | NFR |
|---|---|---|
| FR-WIKI-01 | Space CRUD, иерархия `parent_id`, перемещение, цикл → 422, глубина >10 → 422 | NFR-37 |
| FR-WIKI-02 | Optimistic lock `version`, второй save → 409; изображения через presigned upload | NFR-24 |
| FR-WIKI-03 | Удаление страницы с детьми — каскад **поддерева** в корзину 30 дней | NFR-11 |
| FR-WIKI-04 | Роли space `read`/`write`/`admin`, наследование, ≥1 admin | NFR-38 |

**Факт в коде:**

- В `backend/internal/` модуля wiki / page / doc **нет**
- В `backend/ent/schema/` схем wiki / page / space **нет**
- Проверено отдельно: `bases` — **не** wiki, а Airtable-подобные структурированные
  таблицы (`hubbase.go`, `hubtable.go`, `hubrecord.go`)

**Факт в планировании:**

- `system_specification.md:41` помечает модуль как «**spec (Волны 5/8)**»
- В `.planning/ROADMAP.md` и `.planning/PROJECT.md` слово «wiki» **не встречается вообще**

**Вывод.** Спецификация содержит модуль, который роадмап никогда не подобрал.
Формально это не сорванное обещание — модуль помечен как спека будущих волн.
Но `STATE.md` рапортует **100%**, и эти 100% считаются от числа заведённых фаз,
а не от спецификации. Величины разные, STATE их не различает.

Дополнительно: решение по серым зонам GZ-SEC-17/18/19 (см. §6) описывает
«единая корзина 30д, **wiki каскадит**» — то есть принятое решение опирается
на несуществующий модуль.
