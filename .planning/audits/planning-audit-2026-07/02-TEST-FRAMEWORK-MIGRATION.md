## Решение

Тестовый фреймворк выносится **целиком в отдельную папку в корне репозитория**
и переписывается **полностью на Python**. Каталоги `testframework/` внутри
`backend/` и `frontend/` ликвидируются. Юнит-тесты переезжают **к функционалу**,
рядом с кодом, и пишутся на языке своего слоя.

### Разделение ответственности

| Уровень | Где живёт | На чём | Кто пишет | Кто проверяет |
|---|---|---|---|---|
| **Юнит** | рядом с кодом | Go (бэк) / TS (фронт) | **разработчики** | тестировщики |
| **Интеграционные, E2E, нагрузка** | корневая папка фреймворка | **Python** | тестировщики | — |

Ключевой принцип: юниты — обязанность разработчика и часть кода, а не отдельного
фреймворка. Всё, что выше юнитов, — отдельный Python-проект.

### Целевой стек

| Слой | Инструмент |
|---|---|
| Тест-раннер | **pytest** |
| E2E / браузер | **Playwright (Python)** |
| Нагрузка | **Locust** |

## Целевая структура

```
/tests/                          # новый корневой Python-проект
    pyproject.toml               # pytest, playwright, locust
    conftest.py                  # общие фикстуры: БД, авторизация, клиенты
    integration/                 # интеграционные, по доменам
    e2e/                         # Playwright (Python), перенос с 20 *.spec.ts
    load/                        # Locust-сценарии
    fixtures/                    # данные и фабрики
    README.md

/backend/internal/<домен>/
    *_test.go                    # юниты рядом с кодом, пишут разработчики

/frontend/src/<модуль>/
    *.test.ts(x)                 # юниты рядом с кодом, пишут разработчики

# удаляется:
/backend/testframework/          # 508 файлов раскидываются по доменам
/frontend/e2e/                   # уезжает в /tests/e2e на Python
/testframework/                  # заменяется на /tests
```

## Этапы

### Э1. Каркас Python-проекта
Поднять `/tests` — pyproject, pytest, conftest с фикстурами БД и авторизации,
подключение к Docker-стеку (`docker-compose.local.yml`). Критерий: один
интеграционный тест проходит end-to-end.

### Э2. Перенос E2E на Python
20 `*.spec.ts` → Playwright Python. Критерий: паритет сценариев, старый
`node_modules` в `testframework/e2e` удалён.

### Э3. Возврат юнитов к коду — бэкенд
508 Go-файлов из `backend/testframework/**` раскидать по
`backend/internal/<домен>/`. Учесть: тесты используют build-тег `hubtest`
и экспорт-хелперы (`export_hooks.go`) — при переезде в тот же пакет часть
этих костылей становится не нужна и удаляется.
Критерий: `go test ./internal/...` зелёный, `testframework/` в бэке пуст.

### Э4. Возврат юнитов к коду — фронтенд
Сейчас юнитов рядом с кодом ноль. Завести Vitest-юниты в `frontend/src/**`
по мере переноса из `testframework/stages/unit/frontend-test`.

### Э5. Интеграционные на Python
Перенести то, что по смыслу интеграционное, а не юнит (сценарии с БД, NATS,
Mongo, внешними интеграциями) в `/tests/integration`.

### Э6. Нагрузочные — Locust
Новый слой, сейчас отсутствует. Сценарии на горячие пути: логин, лента,
поиск, создание задач.

### Э7. CI и удаление старого
Перевести `.github/workflows/ci.yml` на новую схему: юниты языком слоя,
Python-фреймворк отдельной job. Удалить `testframework/` из корня,
`backend/testframework/`, `frontend/e2e/`.

## Риски

| Риск | Почему важен |
|---|---|
| **Потеря покрытия при переезде 508 файлов** | Основной. Нужен замер до и после; текущий baseline протух (см. [`01-PLANNING-FIXES.md`](01-PLANNING-FIXES.md) §A3) — **сначала прогнать coverage, потом начинать миграцию** |
| Build-тег `hubtest` и `export_hooks.go` | При переезде в родной пакет экспорт-хелперы теряют смысл; выкидывать аккуратно, не потеряв проверки |
| Два языка в CI одновременно | На время миграции пайплайн держит и Go-тесты, и Python — усложняется |
| Playwright TS → Python | Не механический перенос: другой API, фикстуры, авторизация |
| Дублирование в переходный период | Старый и новый фреймворк живут параллельно — риск, что правят только один |

## Зависимость от аудита планирования

**Этап Э1 не начинать до выполнения A3** из [`01-PLANNING-FIXES.md`](01-PLANNING-FIXES.md):
прогнать coverage gate и зафиксировать честный baseline. Иначе после миграции
не с чем будет сравнить, и потеря покрытия пройдёт незамеченной — а это главный
риск всей затеи.
