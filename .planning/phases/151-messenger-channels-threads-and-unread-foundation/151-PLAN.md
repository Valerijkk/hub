# Phase 151 — Messenger Channels, Threads, and Unread Foundation Implementation Plan

> One task has one current writer. A task touching a shared file starts only after its numbered predecessor. The original channel/thread/unread feature work retains four unconditional unit gates plus conditional integration Task 160. The 2026-08-30 recovery amendment adds one focused RED/GREEN gate per recovery atom, beginning with mandatory MPR-01; every gate runs strictly sequentially.

**Goal:** Safe workplace channels, one-level native threads, durable unread/follow state, and recipient-only invalidation. Redis and client arithmetic are never unread authority.

**Architecture:** Ent/PostgreSQL is authority for singleton tenant, active account, channel role/membership, project eligibility, and event audience. Fresh `ChannelAccess.CanRead` precedes every ordinary message Mongo use: timeline, parent, thread, edit, forward source/target, pin. `AuthorizedUnreadScope` is only for unread/read-state/follow/count/cutover. `AuthorizedMessageSearchScope` is a distinct PG-only visible-channel proof reused by both Messenger and global Search; it is never unread authority. Mongo stores data and grants nothing.

**Spec:** `.planning/phases/151-messenger-channels-threads-and-unread-foundation/151-SPEC.md`, `151-CONTEXT.md`, `151-RESEARCH.md`.

## Frozen contracts

- No Ent schema/codegen/migration in the original feature tasks. The only exceptions are the separately frozen recovery sub-atoms MPR-03A/B and MPR-05A below; no other task may use that exception. Do not touch `pro-qa-ai/**`, Mail/Calendar, Jitsi, or `frontend/src/modules/calls/create-call-dialog.tsx`. Docker-only QA; no Jitsi pull/build/render/start.
- `ResolveInstanceOrganizationID(ctx)` is the singleton Ent proof; zero/multiple fails closed. Tenant never derives from HTTP, WS, cache, Mongo, or a DTO. Active account is fresh immediately before Mongo/NATS/bridge use; after status commit and before revoker hook, disabled actor has zero Mongo (test race).
- `ChannelAccess{TenantID,Channel,IsMember,Role,HasActiveProjectMembership,CanRead,CanPost,CanReply,CanJoin,CanFollow,CanUnfollow,CanViewUnread,CanDeleteMessage,CanPin,CanListPins}` in `backend/internal/messenger/channel_access.go`. Actions: `ReadTimeline`, `ReadThread`, `ReadParent`, `Send`, `Reply`, `Typing`, `EditMessage`, `ForwardSource`, `ForwardTarget`, `DeleteMessage`, `Pin`, `ListPins`, `React`, `Bookmark`, `Promote`, `ReceiveEvent`.
- `MessengerService` receives a mandatory production PG `ChannelAccessResolver` before any consumer is constructed; tests pass an explicit fail-closed fixture and no constructor permits nil fallback. `AuthorizedBotChannelScope{TenantID,BotKind,ChannelID,IntegrationID,IsProjectChannel}` is fresh singleton/active-bot/channel/project/integration proof, emitted only for an allowlisted system `BotKind`; it grants only one stated bot operation and never becomes a generic Mongo bypass.
- `ListMessages` has fresh `ReadTimeline`; legacy replies and exact thread authorize route `channelID` using `ReadParent`/`ReadThread` before parent Mongo. `ChannelActionTyping` proves fresh singleton/active sender/current member/project eligibility immediately before NATS; stale presence, disabled users, and bot callers get no generic bypass. No proof means zero Mongo/resource fields. Public prejoin may see only public metadata/history; no post/follow/receipt/state/unread/follow mode. Project needs current `ProjectMember`; read-only ordinary members cannot post/reply.
- `AuthorizedUnreadScope{TenantID,UserID,Targets[]AuthorizedUnreadTarget{ChannelID,Kind}}` authorizes only state/follow/count/unread/cutover; empty/denied returns four empty maps and zero Mongo. `AuthorizedMessageSearchScope{TenantID,UserID,Targets[]AuthorizedMessageSearchTarget{ChannelID,Kind,IsProjectChannel}}` is recomputed only from current singleton/active-account PG proof: public `CanRead` channels, active member channels/DMs, and project channels with current `ProjectMember`; Messenger `service_search.go` and global `backend/internal/search/service.go` consume only that scope-bound Mongo search and cannot widen it from Mongo. Global Search resolves the scope before `searchMessages` enters Mongo or schedules a goroutine; empty/denied returns no message results and zero Mongo.
- Dashboard receives mandatory fail-closed server-authoritative `UnreadSummaryProvider` from the Messenger durable unread coordinator. It resolves the same fresh `AuthorizedUnreadScope` and returns only `UnreadSummary{UniqueMessageCount int64, HasUnread bool}` from a server-side deduplicated union of accessible message IDs across the four categories; Dashboard never sums category maps or reads Redis `HGETALL unread:{user}`, so Redis loss is irrelevant.
- `AuthorizedGrantBaselineScope{TenantID,ActorID,TargetID,ChannelID,Kind,TargetKind,IsProjectChannel}` is immutable; only a method with it may reset pre-membership data/read protected head/write baseline. The final PG transaction rechecks active actor/target, tenant, target, project cap, actor authority.
- `ChannelDTO` is transport only. `RecipientChannelProjection` is a separate fresh `ChannelAccess` projection. `is_readonly` remains; additive capabilities never duplicate it. Every channel/DM/invite/discovery response projects from ChannelAccess, never role/cache. Public prejoin exposes only `can_read`,`can_join`.
- One live root plus direct same-channel replies only; `also_send_to_channel` only for a direct reply and appears as that same canonical record in root timeline + thread. Nested/cross-channel/deleted root fails closed. Categories exactly `channel`,`dm`,`mention`,`followed_thread`; `(created_at,message_id)` is forward-only and categories overlap.
- Mongo: `read_states` unique `(tenant_id,user_id,category,target_kind,target_id)`; `thread_follows` unique `(tenant_id,user_id,channel_id,root_message_id)`, cleanup `(tenant_id,user_id,channel_id)`, list `(tenant_id,user_id,mode,channel_id)`; message indexes `(channel_id,created_at,_id)`, `(channel_id,thread_id,created_at,_id)`, `(channel_id,resolved_mention_user_ids,created_at,_id)`, `(channel_id,post_create_effects_state,created_at,_id)`. Equal/stale cursor is no-op; equal UTC compares string ID. Manual unfollow persists/suppresses auto.
- GDPR after successful Ent deletion calls one idempotent `MessengerDataEraser`: delete that user's messages, `read_states`, and `thread_follows`, pull the deleted user from remaining `resolved_mention_user_ids`, and use the same operation for retry. Partial retry is safe; no cross-collection atomicity is claimed. Stale follows owned by other users whose roots were deleted are filtered from unread/follow/thread output and leak no metadata.
- All canonical root/reply writers insert `pending`, immutable resolved mentions, and execute effects through `pending -> complete` CAS. Missing legacy state is complete; `Created=false` repeats no effect. Pipeline explicit allowlist `TrustedMessageProducer` covers only user send, forward, a separately authorized allowlisted `BotKind`, poll wrapper, promotion backlink—never generic bypass; user source retains PG authorization. CAS re-derives reply count, auto-follow, recipient invalidation. No outbox/exactly-once claim; reconnect/refetch repairs CAS-before-NATS loss.
- Six grants: CreateChannel owner/initial, JoinChannel, AddMembers, AddMembersInternal, AcceptInvite, CreateOrGetDM do proof -> reset state plus auto/manual follows retaining manual_unfollow -> protected head -> baseline -> final PG CAS -> event. Retry no rebaseline/event. Revoke PG-first then best-effort cleanup retaining manual_unfollow then recipient `channel_removed`.
- Delete has fresh Stage 1 `CanDeleteMessage`; Stage 2 exactly one authorized lookup then author or owner/admin/moderator. Authority denial is zero Mongo; no message ownership Ent migration. Promotion replaces the message-ID-only top-level route with `POST /messenger/channels/:channelId/messages/:messageId/promote-to-issue`; missing/mismatched route channel is denied before Mongo. Planning scan found no frontend caller, so docs record an additive backend route replacement. `AddBookmark` proves route `channelID` with fresh `Bookmark` before Ent write; `ListBookmarks` reads PG bookmark records first, groups distinct `channel_id`, then proves fresh active/project `ReadTimeline` per target before every Mongo enrichment, omitting denied targets without identifiers or Mongo. Reactions, promotion, pin and list-pin retain distinct fresh ChannelAccess gates.
- OpenAPI sources `backend/docs/docs.go`, `backend/docs/swagger.json`, and `backend/docs/swagger.yaml` are synchronized atomically: legacy `/messages/{messageId}/promote-to-issue` is absent, `/messenger/channels/{channelId}/messages/{messageId}/promote-to-issue` is present, and the unread schema exposes exactly `channels`, `dms`, `mentions`, `threads` maps with `int64` values.
- Generic receipt accepts only `channel|dm|mention`; followed_thread/unknown/mismatch is 400 before Mongo. Thread receipt accepts `followed_thread` only; each advances one category. Missing/deleted root or message is non-disclosive: thread/follow/unread outputs omit it and a receipt cannot advance. `UnreadResponse` fields are `map[string]int64`: `channels[channel_id]`, `dms[dm_conversation_id]`, `mentions[target_id]`, `threads[root_message_id]`; physical cleanup delivery remains deferred. The global Messenger nav dot is one server-snapshot boolean (`has any positive category`), never a numeric sum; overlapping categories still produce one dot.
- `ListPendingRecoveryTargets` is PG-only unique `(tenant_id,channel_id,kind)`, globally tuple-paged/max-pages/max-targets/min-interval; `AuthorizePendingRecoveryTarget` runs immediately before bounded Mongo recovery. Denial/deletion is zero Mongo.
- `backend/internal/ws/bridge.go` receives mandatory fail-closed `UserChannelEventAuthorizer` and `ChannelEventAudienceResolver`; shared interfaces live in `backend/internal/ws/authorizer.go` only if bridge+room need them. Its user-event parser allows only the typed `unread_changed` identifier payload (`channel_id`,`target_kind`,`category`, optional string `root_message_id`), rejects unknown event/type and all content/count fields, and makes a fresh auth check before publish/delivery; `channel_removed{channel_id}` is the sole post-revoke exception. The audience resolver rechecks active/project/channel eligibility for typing and omits disabled or removed recipients. `backend/cmd/server/wiring_ws.go` injects PG adapters from messenger channel-access/Ent.
- Runtime Mongo/NATS/WS/browser/cutover/Phase149 remains `NOT_RUN` without exact Docker evidence; `python-integration` begins `NOT_BOUND/NOT_RUN`.

## 2026-08-30 recovery-runtime execution amendment

This amendment is additive to the channel/thread/unread feature plan above and supersedes only conflicting recovery-runtime assumptions. The tracked 2026-08-30 communications ADR amendment is canonical authority and this section is self-contained.

### Evidence and fixed boundary

- Current status remains `IN_PROGRESS_PARTIAL_UNIT_EVIDENCE`; runtime, live PostgreSQL/Mongo, NATS, WebSocket, browser, canary and rollback are `UNBOUND/NOT_RUN`.
- Phase 149 unit/static acceptance is an allowed dependency. Its Mongo/NATS/WebSocket/browser and cross-store residuals are not inherited as PASS and must close here or in Phase 155.
- Recovery is a dedicated self-hosted process in the existing backend image. It is not a server goroutine and it does not publish NATS.
- One global PostgreSQL leader lease/fence owns the process loop and target checkpoint. The existing Mongo owner/fence/lease remains the independent per-message guard.
- Mongo completion writes a replayable delivery intent. A materializer writes one deterministic delivery ledger row and one platform `OutboxEvent` in a single PostgreSQL transaction. For canonical/recovery delivery types, the existing outbox worker is the only NATS publisher and current audience is re-resolved before fanout. The isolated legacy publisher may coexist only before tenant cutover and never for the same request.
- Semantics are at-least-once. Exactly-once, cross-store atomicity and dual-write are forbidden claims.
- Frozen launch values are `run_timeout=20s`, `leader_lease=90s`, `leader_renew=30s`, `message_lease=30s`, `message_renew_before=10s`, `max_pages=5`, `max_targets=100`, `pending_scan_limit=25`. Validation rejects non-positive bounds, `leader_renew >= leader_lease`, and `run_timeout + 5s >= message_lease`; the selected values are valid.
