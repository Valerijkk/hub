## Technical defaults frozen for planning

1. `call.RoomName` is the single provider room identity; `Call.ID` remains the Hub audit key. The Jitsi issuer must stop signing a different UUID-only room.
2. Provider control URLs and browser connection URLs are distinct. Existing `LIVEKIT_URL` stays server-side; Phase 152 introduces an explicit validated browser URL. Jitsi continues to use configured `JITSI_PUBLIC_URL`, never ambient browser origin.
3. Credential issuance becomes a typed, call-aware provider request built only after Hub authz. The request carries call ID, canonical room, server-resolved participant identity/name, and member/guest kind; providers do not authorize users.
4. Join credentials gain a truthful expiry. Jitsi remains five minutes; refresh is a separately reauthorized, non-participant-mutating credential operation after pinned-runtime behavior is proven.
5. Guest access preserves the current narrow product: active instant-call invite only, server-generated guest identity, no channel membership or arbitrary Jitsi room. Moderator/lobby semantics remain a security/product gate.

Additive public join DTO, call-aware provider conversion, and conference shell must preserve every legacy field/route and keep LiveKit active. Jitsi activation still requires the separately authorized deployment, TLS, JWT, UDP media, refresh, guest/lobby, browser, rollback, and recording gates.
