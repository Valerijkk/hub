## Goal
Снять потолок 64-бит для `rbac.Permission`. Сейчас все 25 битов используются (см.
`PermTeamManage` = 33_554_432 = 1<<25), остаётся 39 свободных бит — но при следующих
итерациях (file-versioning, knowledge-base, calls-recording-share, etc.) хвост быстро
закончится. Готовим **аддитивный, обратно-совместимый** переход на безразмерное
представление через `[]string` (имена разрешений), **сохранив `Permission uint64` как fast
in-memory cache** для текущих 25 разрешений.

## Strategy: dual representation, additive migration

**Ключевая идея:** `Permission` уровня application остаётся `uint64` (быстрая битовая
арифметика, ноль аллокаций для middleware). Storage layer **дополнительно** хранит
полный набор имён разрешений в новой колонке `permission_names []string` (jsonb).
Reads делают reconciliation: имена → биты при загрузке. Когда 64 бит будет не хватать,
разрешения с index>=64 хранятся **только** в `permission_names`, а application-layer
расширит `Permission` до `type Permission struct { bits uint64; extra []string }` —
это будет followup плана.

В этом плане:

1. **Schema additive change** — добавить колонку `Role.permission_names []string`
   (Ent: `field.JSON("permission_names", []string{}).Optional().Default([]string{})`).
   Это nullable, default `[]` — `go run ./ent/entc.go generate ...` создаст миграцию,
   которая просто `ALTER TABLE roles ADD COLUMN permission_names JSONB DEFAULT '[]'`.
   **Никаких breaking-изменений в существующих строках.**

2. **Dual-write** — в `CreateCustomRole` / `UpdateCustomRole`:
   - вычислить `perm := permissionsFromNames(req.Permissions)` (как было) → запись в `permissions` uint64
   - **дополнительно** записать `req.Permissions` (валидированный список имён) в `permission_names`
   - validation: имена ДОЛЖНЫ быть в `permissionNameMap` (отвергаем неизвестные имена → 400)

3. **Read path** — в `toCustomRoleResponse`:
   - если `r.PermissionNames` непустой → `permList = r.PermissionNames` (источник правды)
   - иначе → fallback `permList = permissionNames(Permission(r.Permissions))` (legacy)
   - `Permissions uint64` поле в response сохраняется (back-compat для UI), но фронтенду
     даём указание мигрировать на `PermissionNames` (отметить в SUMMARY).

4. **Permission registry** — превратить `permissionNameMap` в **реестр**:
   ```go
   type permissionDef struct {
       Name    string
       Bit     Permission  // 0 для разрешений без bit-allocation (когда исчерпаем 64)
       Display string      // человекочитаемое описание для UI
   }
   var permissionRegistry = []permissionDef{
       {Name: "project.view", Bit: PermProjectView, Display: "View project"},
       // ...
   }
   var permissionNameMap = func() map[string]Permission { ... }()
   ```
   Тогда расширение в будущем (`{Name: "kb.publish", Bit: 0, Display: "..."}` для permission
   №65) не ломает существующий код — оно работает через `permission_names` storage path.

5. **Validation helper** — `func ValidPermissionName(name string) bool`. Возвращает true
   для имён в registry. Используется в `CreateCustomRole`/`UpdateCustomRole` для отказа от
   тайпо.

**Не меняем:**
- `RequirePermission` middleware (rbac/middleware.go) — продолжает использовать `Permission.Has()` через `GetEffectivePermissions`. Bit-арифметика быстрая, не тратим время на string-сравнение в hot path.
- `DefaultRolePermissions` map (для owner/developer/tester/viewer) — остаётся `Permission` (uint64) — system roles.
- `ProjectMember.permissions_override` (если есть как поле) — тот же подход.

### `backend/internal/rbac/permissions.go` (extend)
```go
// permissionDef описывает одно разрешение.
type permissionDef struct {
    Name    string
    Bit     Permission // 0 = разрешение хранится только по имени (для permissions index >= 64)
    Display string
}

// permissionRegistry — единый реестр всех известных разрешений. Source of truth.
var permissionRegistry = []permissionDef{
    {Name: "project.view", Bit: PermProjectView, Display: "View project"},
    {Name: "project.edit", Bit: PermProjectEdit, Display: "Edit project"},
    {Name: "project.delete", Bit: PermProjectDelete, Display: "Delete project"},
    // ... все 25 текущих ...
    {Name: "team.manage", Bit: PermTeamManage, Display: "Manage teams"},
}

// permissionNameMap построен из реестра.
var permissionNameMap = buildPermissionNameMap()

func buildPermissionNameMap() map[string]Permission {
    m := make(map[string]Permission, len(permissionRegistry))
    for _, p := range permissionRegistry {
        m[p.Name] = p.Bit
    }
    return m
}

// ValidPermissionName возвращает true если имя зарегистрировано в реестре.
func ValidPermissionName(name string) bool {
    _, ok := permissionNameMap[name]
    return ok
}

// ListAllPermissionDefs возвращает копию реестра (для UI / документации).
func ListAllPermissionDefs() []permissionDef {
    out := make([]permissionDef, len(permissionRegistry))
    copy(out, permissionRegistry)
    return out
}
```

## Risk + Rollback
- **Risk:** Ent code-gen может потребовать обновлённой версии `entgo.io/ent`. Если ошибка — фиксировать версию в SUMMARY.
- **Risk:** Существующие роли в БД имеют `permission_names = []` (default). После деплоя — UI продолжит читать через legacy fallback (uint64 → имена). Это **корректно**; новые роли получают полный список имён.
- **Migration backfill (не обязательно для этого плана):** для уже существующих кастомных ролей можно вручную бэкфилить `permission_names` через одноразовый скрипт `UPDATE roles SET permission_names = ... WHERE permission_names = '[]'::jsonb`. **Не требуется** — legacy fallback покрывает их.
- **Rollback:** Один коммит `feat(rbac): additive permission_names column + registry (SC-14-4)`. Откат через `git revert` — миграция `ADD COLUMN` обратима автогенерированным `DROP COLUMN` в downgrade-direction (или ручным SQL `ALTER TABLE roles DROP COLUMN permission_names;`).
