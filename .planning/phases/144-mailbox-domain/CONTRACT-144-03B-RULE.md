## Bounds, identities and ordering

- Rules: `0..100`; conditions per rule: `1..20`; actions: `1..10`; priority: `0..10000`.
- Rule name: `1..120` Unicode code points and `1..480` UTF-8 bytes. Condition strings:
  `1..500` code points and `1..2000` bytes. Public raw HTTP JSON stays independently capped
  at `65,536` UTF-8 bytes; compiler never reserializes JSON.
- Folder and label resolver inventories are each `0..100`. Opaque engine folder IDs are
  valid UTF-8, control-free, `1..1024` bytes.
- Folders and labels are complete all-and-only live non-deleted same-account snapshots under
  the same account lock. Stale, deleted or partial inventory is a 04M service invariant; no
  compiler lifecycle field is added.
- Every account ID, rule ID and target Hub UUID is non-zero; every resolver row has the same
  account. Rules are copied then sorted by ascending `(priority, unsigned lexicographic raw
  16 RFC-4122 UUID bytes)`.
- Condition order is preserved. Input action order remains hash-v1 material, but output is a
  canonical semantic projection: optional one move, optional one mark-read, then unique
  add-label targets in first stored order. A repeated move, mark-read or add-label target
  rejects; multiple distinct labels are allowed. Maps may be bounded lookup only; map
  iteration never determines output. Outputs and all nested slices are concrete deep copies
  and never mutate or alias input.

Engine label keywords are exactly `hubk-` plus the canonical lower-case, unpadded RFC-4648
base32 encoding of 32 cryptographically random bytes: 52 encoded characters and 57 ASCII bytes.
Validation decodes exactly 32 bytes then re-encodes to the identical lower-case suffix; regex
`[a-z2-7]{52}` alone is insufficient. They are server-generated, immutable and unique per
account; no Hub/account/user/label ID or name is embedded.

Rule names must be valid UTF-8, non-empty and within their rune/byte caps; reject Unicode
control, format, surrogate, private-use or unassigned characters, CR, LF, NUL, U+2028 and
U+2029. Preserve exact accepted bytes: no trim, NFC/NFKC, case fold or whitespace collapse.
Persistence, OpenAPI and QA text must stay synchronized; generation is outside compiler.

Strings must be valid UTF-8, non-empty and within rune/byte caps; reject Unicode control,
format, surrogate, private-use or unassigned characters, CR, LF, NUL, U+2028 and U+2029.
There is no trim, NFC/NFKC, case fold or whitespace collapse for `contains`/subject values.
Quotes, backslashes, semicolons, braces, comment markers and `${...}` are opaque IR data: no
Sieve escaping happens here. `to` means only visible structured `To`, not Cc/Bcc/envelope,
display name/body/arbitrary header. `matches_domain` is exact equality, never suffix/wildcard.
Phase 145 applies `i;ascii-casemap` unless an independently accepted extension changes it;
non-ASCII bytes otherwise compare literally.

`has_attachment` is accepted IR but not a base-Sieve promise. A ruleset using it is
Phase-145 capability-blocked until a separately accepted MIME/attachment mapping and
capability profile exists; absence returns safe `MAIL_RULE_CAPABILITY_UNAVAILABLE` without
upload. Evaluation is flat conjunction and first-match-wins in priority/UUID order: a matched
IR applies labels, flags and optional move then terminates. Phase 145 must render equivalent
termination and cannot reinterpret IR as run-all.

`move` needs exactly one live same-account folder resolver row and emits only opaque engine
folder ID; `add_label` needs exactly one live same-account label resolver row and emits only
its private keyword; `mark_read` has `uuid.Nil`, while move/add-label need non-zero target.
Missing target is `target_unavailable`; multiple live target rows are `target_ambiguous`;
cross-account rows are `account_mismatch`; wrong kind/malformed resolver is `invalid`.
Output retains Hub rule `ID` for deterministic identity/order, but never includes a target Hub
folder UUID or target Hub label UUID, display name, public label value, rule name or raw target
name.

## Phase-145 obligations and hash boundary

An engine folder ID is not a Sieve mailbox name. Phase 145 separately resolves it to an
unambiguous `fileinto` destination; no name-only fallback. It requires only capabilities used
by IR (`fileinto`, `imap4flags`, plus separately frozen attachment capability), compares RFC
9661 capability strings case-sensitively, and enforces canonical rendered bytes
`<= min(65,536, account maxSizeScript when non-null)` before upload. It must prove opaque
punctuation stays in exactly one quoted Sieve string and must not enable `encoded-character`.

Compiler neither calculates nor returns persistence canonical hash v1. Phase 145 additionally
needs a separately frozen canonical rendered-payload digest and content-verification carrier:
marker-only Get/compare is insufficient for tamper detection. No hash-version rewrite or new
persistence field is authorized here. Raw script bytes are never persisted, logged, included
in safe errors or returned publicly.

`RuleCompilerErrorKind`, six sentinels and `RuleCompilerError{Kind ...}` follow accepted
nil-safe `FolderPolicyError` `Error()`/`Unwrap()` shape. Nil/unknown is exactly
`mail rule compiler error` and unwraps nil; `errors.Is` matches only its exact sentinel.
No error includes a name, value, address, UUID, engine ID, keyword, script fragment, provider
response, hash or secret. Validate complete bounded input before output using global precedence:
`too_large`, `invalid`, `account_mismatch`, `duplicate`, `target_ambiguous`,
`target_unavailable`. Every failure returns zero `CompiledRuleSet` with no partial slices.
Compiler errors are internal only and never cross HTTP. 04M performs account-scoped lookup,
masks foreign and missing targets identically, and never exposes mismatch/ambiguity as an
existence oracle.
