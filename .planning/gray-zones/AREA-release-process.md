## Релизы и версии

### GZ-REL-01: Момент тега v2.5.0
- Контекст: пользователь решил «релиз не гейтим», но FA-06/PG-03 (ротация секретов) остаётся единственным prod-блокером; roadmap кладёт тег в фоновый ops-трек devops-engineer вместе с BFG purge.
- Вопрос: тегать v2.5.0 строго после завершения FA-06 + BFG purge, или тег можно ставить раньше (код готов), а ротацию закрыть отдельным hotfix-тегом?
- Варианты: A) Тег только после FA-06 + purge — тег означает «безопасно деплоить» [Рекомендую] B) Тег сейчас по готовности кода, FA-06 отдельно C) Отложить тег до конца Волны 1 (захватить quick tech-debt фиксы)
- Влияние: смысл тега для деплоя, порядок работ devops-engineer, история git после BFG (purge переписывает историю — тег до purge станет невалидным).

### GZ-REL-02: Каденс релизов на ~12–17 волн вперёд
- Контекст: впереди ~2.5 месяца двух треков (F+P). Правило тегов (`50-git.mdc`) знает только milestone-теги и hotfix; про волны ничего не сказано.
- Вопрос: что считается релизной единицей дальше — каждая волна, группа волн, milestone (v2.6/v3.x/v4.x), или «по готовности значимой фичи»?
- Варианты: A) Тег на milestone + промежуточные теги по завершении крупной фичи/фазы Track P [Рекомендую] B) Тег на каждую волну (частые мелкие релизы) C) Только milestone-теги, между ними untagged master
- Влияние: частота деплоев, откатываемость, объём release notes, нагрузка на devops.

### GZ-REL-03: Semver при появлении микросервисов
- Контекст: Track P выносит hub-notification, hub-ai, hub-realtime; уже есть hub-mail и meilisearch-indexer. Сейчас версия одна на платформу.
- Вопрос: сохраняем единую версию платформы (все сервисы релизятся вместе под vX.Y.Z), или переходим на per-service версии + манифест совместимости?
- Варианты: A) Единая платформенная версия, пока сервисов ≤6 и деплой из одного репо [Рекомендую] B) Per-service semver + compatibility-матрица C) Гибрид: платформенная версия + независимые patch-версии выделенных сервисов
- Влияние: тегирование, docker-теги образов, K3s-манифесты, отладка «какая комбинация сервисов в prod».

### GZ-REL-04: Деплой в прод во время больших волн
- Контекст: Track P Фаза 1 (Hardening: `*ent.Client` за интерфейсы) и strangler-fig выносы — долгие инвазивные изменения; параллельно Track F пилит фичи. Политики «деплоим ли master в это время» нет.
- Вопрос: продолжаем деплоить master в прод по ходу волн или замораживаем прод-деплой на время инвазивных фаз Track P?
- Варианты: A) Деплоим непрерывно — master всегда releasable, инвазивные фазы дробятся на атомарные безопасные шаги [Рекомендую] B) Freeze на время фаз M1/M2+ Track P, деплой только stable-тегов C) Два контура: staging получает всё, prod — только теги
- Влияние: риск регрессий у живых пользователей, ценность непрерывной обратной связи, дисциплина атомарности Track P.

### GZ-REL-05: Blue-green / canary
- Контекст: prod — K3s + Caddy, single-instance self-hosted. При выносе сервисов (пилот hub-notification) появляется место для canary, но это инфраструктурная работа.
- Вопрос: нужны ли blue-green/canary деплои сейчас, или до реального внешнего трафика достаточно rolling restart + быстрый rollback по тегу?
- Варианты: A) Пока нет — rolling update K3s + rollback по тегу; canary отложить до пилота hub-notification [Рекомендую] B) Blue-green сразу для hub-core C) Canary только для выносимых сервисов с первого дня Track P M2
- Влияние: сложность deployments/, время devops-engineer, риск-профиль деплоев во время Track P.

## Ветки, мерж, коммиты

### GZ-REL-06: Гранулярность PR в фича-ветках
- Контекст: пользователь хочет «пилить в фича-ветках». Playbook требует атомарных планов ≤200–300 строк = 1 коммит, но не говорит, что является единицей PR.
- Вопрос: один PR = один атомарный план (много мелких PR на фичу) или один PR = фича целиком (ветка живёт всю фазу, внутри атомарные коммиты)?
- Варианты: A) PR = фича/фаза, внутри атомарные коммиты по планам; ревью на PR целиком [Рекомендую] B) PR = атомарный план (макс. изоляция, но десятки PR и очереди мержа) C) Гибрид: фундамент (schema/контракты) отдельными мелкими PR, остальное фича-PR
- Влияние: скорость волн, нагрузка на code-reviewer и пользователя, разрешение конфликтов между потоками.

### GZ-REL-07: Кто нажимает merge в master
- Контекст: цепочка приёмки заканчивается на team-lead («финальная инстанция»), но Прил. J говорит «коммит/пуш только по явному запросу пользователя». Кто фактически мержит фича-ветку — не зафиксировано.
- Вопрос: team-lead мержит в master сам после green gate + code-reviewer, или каждый мерж в master требует явной команды пользователя?
- Варианты: A) Мерж в master — только по команде пользователя; team-lead готовит ветку до состояния «merge-ready» [Рекомендую — совпадает с «потом проверю и закоммитишь»] B) team-lead мержит автономно после всех ворот, пользователь смотрит постфактум C) Дифференцированно: рутинные фичи — автономно, критичные категории (GZ-REL-10) — по команде
- Влияние: скорость волн (ожидание пользователя = боттлнек при варианте A), контроль над prod-веткой.

### GZ-REL-08: Squash-политика и имя ветки
- Контекст: `50-git.mdc` требует squash merge в «main», фактическая ветка — `master`. Squash схлопнет атомарные коммиты планов в один коммит на PR — при PR=фича теряется атомарная откатываемость (gsd-undo, revert по плану).
- Вопрос: подтверждаем squash для всех PR, или при фича-PR переходим на merge-commit/rebase, чтобы сохранить атомарные коммиты? Заодно — починить «main» → «master» в правиле?
- Варианты: A) Rebase-merge (fast-forward): линейная история + атомарные коммиты сохранены [Рекомендую при PR=фича] B) Squash всегда (чистая история, но крупные неделимые коммиты) C) Squash для мелких PR, merge-commit для фича-PR
- Влияние: возможность точечного revert, читаемость истории, консистентность правила 50-git с реальностью.

### GZ-REL-09: Политика коммитов агентов в фича-ветках
- Контекст: правило «коммит только по явному запросу пользователя» писалось для эпохи работы прямо в master. С фича-ветками буквальное чтение парализует волны: агент не может даже зафиксировать атомарный шаг.
- Вопрос: подтверждаем двухуровневую политику — агент свободно коммитит в свою фича-ветку (атомарно, с воротами), а запрос пользователя нужен только для merge/push в master?
- Варианты: A) Да: авто-коммиты в фича-ветки, master — по команде [Рекомендую] B) Нет: любой коммит по команде (текущее буквальное правило) C) Авто-коммиты в ветки + авто-push веток на remote, master locally по команде
- Влияние: пропускная способность волн, формулировка `50-git.mdc` Прил. J, безопасность master.

## Командный процесс

### GZ-REL-10: Категории PR для личного ревью пользователя
- Контекст: цепочка агентов (кросс-ревью be1↔be2 + *-ver + code-reviewer + team-lead) закрывает качество, но пользователь сказал «потом проверю» — неясно, что именно он хочет видеть сам.
- Вопрос: какие категории PR пользователь ревьюит лично, а какие доверяет цепочке агентов полностью?
- Варианты: A) Только критичные: security/auth, миграции БД, деплой/CI, ADR-изменения; остальное — агентам [Рекомендую] B) Все PR лично (боттлнек ~12–17 волн) C) Ничего лично — доверие цепочке, выборочный аудит постфактум
- Влияние: скорость мержа, риск пропуска критичных изменений, формат «merge-ready» отчёта team-lead.

### GZ-REL-11: Лимит ≤4 параллельных агентов — жёсткий?
- Контекст: playbook §4 и GSD-INTEGRATION фиксируют «≤4 агента на волну» (антипаттерн №15). Roadmap подтверждает «волны ≤4». Но при жёстко разделённых модулях (Track F intranet + Track P notification + qa + docs) конфликтов файлов нет и при 6–8.
- Вопрос: лимит 4 — жёсткое правило, или его можно поднимать до 6–8 при доказанном непересечении файлов (карта владения модулями из PLAN-schedule)?
- Варианты: A) Мягкий: дефолт 4, до 6–8 по решению team-lead при явной карте файлов без пересечений [Рекомендую] B) Жёсткий 4 всегда (управляемость контекста оркестратора) C) Лимит на трек: ≤4 на Track F + ≤4 на Track P одновременно
- Влияние: длительность roadmap (~12–17 волн можно сжать), риск конфликтов и потери контроля team-lead, стоимость параллельных сессий.

### GZ-REL-12: Владение cross-cutting кодом
- Контекст: playbook решает конфликт `cmd/server/main.go` («wiring одному агенту»), но не назначает постоянных владельцев для `internal/platform/`, будущего `contracts/` (schema-per-service, NATS-события), общих типов фронта (`types.ts`, `api/`). При двух треках эти файлы — главная точка коллизий.
- Вопрос: назначаем ли постоянных владельцев cross-cutting зон (например platform/ → be1, contracts/ → arch+be2, общие FE-типы → fe1), или владелец назначается per-волна в PLAN?
- Варианты: A) Per-волна в PLAN tech-lead: колонка «файлы» уже есть, добавить обязательную строку для cross-cutting зон [Рекомендую] B) Постоянные владельцы в team-workflow.md C) Cross-cutting меняет только team-lead лично
- Влияние: частота конфликтов be1/be2 и fe1/fe2, скорость волн, качество границ в планах.

### GZ-REL-13: Протокол при конфликте потоков (be1 vs be2 задели общий файл)
- Контекст: playbook §4.4: «team-lead решает, чей коммит базовый, второй перебазируется». С фича-ветками появляется новый случай: две долгоживущие ветки задели один файл, конфликт всплывает на merge, а не в волне.
- Вопрос: подтверждаем протокол «первый смёрженный побеждает, вторая ветка обязана rebase на master до ревью», и кто выполняет rebase — автор-агент или team-lead?
- Варианты: A) Автор-агент ребейзит свою ветку + повторная регрессия, team-lead только арбитр порядка мержа [Рекомендую] B) team-lead ребейзит сам все ветки перед мержем C) Запретить долгоживущие ветки, задевающие общие файлы (ловить на этапе PLAN)
- Влияние: чистота master, повторные прогоны регрессии, нагрузка на team-lead.

## Лицензирование и дистрибуция

### GZ-REL-14: Статус проекта — внутренний, коммерческий или open-source
- Контекст: рыночный анализ (MARKET-AND-NEEDS) позиционирует Hub против Bitrix24 On-Premise / Lark для RU-корпоратов, что намекает на дистрибуцию третьим лицам. Файла LICENSE и решения о модели нет.
- Вопрос: Hub — внутренний инструмент, коммерческий self-hosted продукт (продажа лицензий/поддержки) или open-source (возможно open-core)?
- Варианты: A) Пока проприетарный/закрытый, решение о дистрибуции отдельным ADR при первом внешнем клиенте [Рекомендую] B) Open-core: ядро под пермиссивной лицензией, enterprise-модули (SSO/accounting) закрыты C) Полный open-source (MIT/Apache-2.0) для роста комьюнити
- Влияние: аудит лицензий зависимостей (Go modules, npm, Ent, LiveKit SDK), срочность BFG purge секретов из истории (критично ДО любой публикации), пункт GZ-REL-15.

### GZ-REL-15: Выбор лицензии и совместимость зависимостей (если публичный)
- Контекст: если по GZ-REL-14 выбран любой публичный вариант — нужна конкретная лицензия и проверка стека: LiveKit (Apache-2.0), Ent (Apache-2.0), Fiber (MIT) пермиссивны, но полный аудит транзитивных зависимостей не проводился; секреты в git-истории делают публикацию невозможной до purge.
- Вопрос: какая лицензия при публикации (MIT / Apache-2.0 / BSL с переходом / проприетарная EULA) и заказываем ли license-аудит зависимостей отдельной задачей devops/security?
- Варианты: A) Отложить до решения GZ-REL-14, но BFG purge и запрет секретов выполнить безусловно уже сейчас [Рекомендую] B) Apache-2.0 (патентная защита, совместим со стеком) + аудит сразу C) BSL 1.1 (защита от SaaS-конкурентов, конверсия в Apache через 4 года)
- Влияние: юридическая чистота дистрибуции, порядок работ devops (purge из GZ-REL-01), возможность принимать внешние контрибуции.

### GZ-REL-16: Changelog и release notes
- Контекст: Conventional Commits дают сырьё для автогенерации changelog, RACI релиза назначает docs-writer на «Docs/changelog», но самого файла CHANGELOG.md и формата release notes не существует.
- Вопрос: вести ли CHANGELOG.md (автогенерация из conventional commits + ручная выжимка) и писать ли человекочитаемые release notes на каждый тег?
- Варианты: A) CHANGELOG.md автогенерация по тегам + короткие release notes только на milestone-теги, владелец docs-writer [Рекомендую] B) Полные release notes на каждый тег C) Не вести до первого внешнего пользователя
- Влияние: прозрачность для будущих пользователей/клиентов, нагрузка docs-writer, зависит от каденса (GZ-REL-02) и дистрибуции (GZ-REL-14).

## Сводка

16 серых зон. Топ-3 критичных для немедленного решения:

1. **GZ-REL-09 / GZ-REL-07** (коммиты и мерж) — без явной двухуровневой политики «агент коммитит в фича-ветку, master по команде» Волна 1 либо парализована буквальным правилом, либо агенты трактуют его вразнобой.
2. **GZ-REL-01** (тег v2.5.0 vs BFG purge) — purge переписывает историю; тег, поставленный до purge, станет невалидным. Порядок работ devops-engineer в Волне 1 зависит от этого решения.
3. **GZ-REL-14** (статус дистрибуции) — определяет срочность license-аудита и делает BFG purge безусловным блокером любой публикации; влияет на GZ-REL-15/16.
