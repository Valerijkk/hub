## Границы сервисов

### GZ-ARCH-01: Состав hub-realtime — один юнит или три
- Контекст: ADR §3 объединяет ws+messenger+calls в один юнит `hub-realtime`; план Fable (§3.1) режет их на три: hub-ws (edge), hub-messenger, hub-calls с разными фазами (M4/M5).
- Вопрос: hub-realtime — единый деплой-юнит или ws/messenger/calls выносятся отдельно?
- Варианты: A) Один юнит hub-realtime — меньше деплоев, проще presence [Рекомендую] B) Три сервиса по плану Fable — независимое масштабирование calls (LiveKit-egress) C) ws+messenger вместе, calls отдельно.
- Влияние: фазы M4/M5 roadmap, число схем PG, K3s-манифесты, contract-тесты.

### GZ-ARCH-02: tms — в ядре или выносить
- Контекст: ADR §3 держит tms в hub-core, но порядок выноса заканчивается «…→ tms» (M6). Fable называет tms «самый крупный и автономный домен» (6834 строки, Mongo Allure).
- Вопрос: hub-tms — подтверждённая фаза M6 или остаётся в ядре до отдельного решения?
- Варианты: A) M6 подтверждён условно — исполняется только после Go по пилоту [Рекомендую] B) tms остаётся в ядре, M6 вычеркнуть C) поднять приоритет (вынос №3) как самого автономного.
- Влияние: длина Track P (~8–12 недель), загрузка be1/be2 vs Track F.

### GZ-ARCH-03: tracker — трогаем ли вообще
- Контекст: оба плана: tracker глубоко вплетён в rbac/project/search/dashboard/github, вынос «последним/опционально» (M7). Явного критерия «когда трогаем» нет.
- Вопрос: зафиксировать «tracker не выносим в этом горизонте» или оставить M7 висящей опцией?
- Варианты: A) Явно исключить из горизонта, вернуться отдельным ADR при доказанном драйвере [Рекомендую] B) Оставить M7 опциональной фазой C) Планировать после M6 по умолчанию.
- Влияние: скоуп Ent-распила, ожидания команды, оценки сроков.

### GZ-ARCH-04: search — агрегатор в ядре или сервис
- Контекст: ADR-порядок содержит «…→ ai → search → …», но каталог §3 держит search-agg в hub-core (meilisearch-indexer уже вынесен). Противоречие внутри одного документа.
- Вопрос: что означает «search» в порядке выноса — вынос агрегатора из ядра или только доводка indexer?
- Варианты: A) Search-agg остаётся в ядре, шаг «search» = стандартизация indexer [Рекомендую] B) Полноценный hub-search сервис C) Убрать шаг из порядка.
- Влияние: NF-03 (user-scope фильтр), число сервисов, roadmap-фазы.

## Go/No-Go и мотивация

### GZ-ARCH-05: Метрика Go/No-Go после пилота notification
- Контекст: ADR требует ретроспективу «если независимый деплой/изоляция не дали измеримой пользы — остановиться», но измеримый критерий не задан. Opus §11.1 прямо спрашивает про триггер.
- Вопрос: какая конкретная метрика решает Go после M2 (пилот notification)?
- Варианты: A) Композит: lead-time деплоя домена ↓, p95 API не хуже +10%, 0 инцидентов из-за split за 2 недели [Рекомендую] B) Только субъективная ретроспектива team-lead+product C) Числовой триггер нагрузки (>500 concurrent WS / p95 > X мс).
- Влияние: судьба M3–M6, критерии приёмки M2.

### GZ-ARCH-06: Драйвер split — что болит сейчас
- Контекст: Fable §10.1 и Opus §11.1: без названного драйвера (изоляция сбоев / релиз-каденс / масштабирование WS-AI) split — преждевременная оптимизация; «M0+M1+ws/ai закрывает 80% ценности за 30% стоимости».
- Вопрос: какова первичная мотивация — изоляция BYOK/сбоев, независимый деплой, масштабирование, или архитектурная гигиена?
- Варианты: A) Изоляция AI/BYOK + независимый деплой → полный порядок ADR оправдан B) Только масштабирование → ограничиться hub-ai+hub-realtime [Рекомендую уточнить] C) Гигиена → остановиться на M0/M1.
- Влияние: сколько фаз реально исполняется, Go/No-Go критерий (GZ-ARCH-05).

## БД: schema-per-service

### GZ-ARCH-07: Бэкапы при N схемах
- Контекст: `internal/backup` рассчитан на 1×PG+1×Mongo+S3 (Fable §2). Schema-per-service с per-service DB-user ломает предположение «один дамп одним юзером».
- Вопрос: как эволюционирует бэкап — единый pg_dump суперюзером всех схем или per-service бэкапы?
- Варианты: A) Единый кластерный бэкап (pg_dump/basebackup) отдельным backup-user с read-грантами на все схемы [Рекомендую] B) Per-service дампы своей схемы C) Отложить до M2 и решить на пилоте.
- Влияние: `internal/backup` рефакторинг, RPO/restore-процедура, K3s CronJob.

### GZ-ARCH-08: Порядок Atlas-миграций per-schema
- Контекст: Каждый сервис получает свой Ent-проект и свой versioned migration dir (Fable §2.3). Не определено, кто и в каком порядке применяет миграции при деплое нескольких сервисов и при общем restore.
- Вопрос: миграции применяет каждый сервис на старте (initContainer) независимо, или единый migration-job с порядком?
- Варианты: A) Per-service initContainer, схемы независимы по определению — порядок не нужен [Рекомендую] B) Центральный migration-job в CI/CD C) Ручной gate devops на каждую миграцию.
- Влияние: deploy pipeline, expand-contract переносы таблиц (M2-01), риск гонок.

### GZ-ARCH-09: Осиротевшие UUID-ссылки без cross-schema FK
- Контекст: Запрет cross-schema FK грантами означает: `notification.user_id` больше не защищён FK на `core.users`. Удаление user/project оставляет сироты в чужих схемах.
- Вопрос: чистить осиротевшие ссылки фоновым consumer'ом по событиям удаления или принять мусор как норму?
- Варианты: A) Идемпотентный consumer на `user.deleted`/`project.deleted` + периодический reconcile-job [Рекомендую] B) Только event-driven очистка без reconcile C) Забить — soft-delete 30 дней и малые объёмы делают проблему теоретической.
- Влияние: GDPR/hard-delete процедура, объём кода в каждом сервисе, консистентность отчётов.

## Deployment

### GZ-ARCH-10: K3s — одна нода или несколько (HA)
- Контекст: Fable §10.2: прод сейчас — один хост/одна нода; вся аргументация «против DB-per-service» строится на этом. HA-планов не заявлено.
- Вопрос: остаёмся на одной K3s-ноде на весь горизонт M0–M6 или закладываем мультинодность?
- Варианты: A) Одна нода, HPA/реплики не приоритет [Рекомендую при 10–50 юзерах] B) 2–3 ноды для HA критичных сервисов (realtime, core) C) Решить после пилота по метрикам.
- Влияние: storage-class (GZ-ARCH-11), ценность реплик/anti-affinity, стоимость железа.

### GZ-ARCH-11: PVC / storage-class для stateful-инфры
- Контекст: План: `hub-infra` namespace со StatefulSets + PVC local-path (Fable §6). Local-path привязывает PG/Mongo/NATS к ноде и исключает миграцию подов.
- Вопрос: остаёмся на local-path или вводим реплицируемый storage (Longhorn/NFS)?
- Варианты: A) Local-path пока одна нода, пересмотр при HA [Рекомендую] B) Longhorn сразу — готовность к мультинодности C) Внешние managed БД вне K3s.
- Влияние: TD-04 K3s-манифесты, restore-процедура, зависимость от GZ-ARCH-10.

### GZ-ARCH-12: Dev-режим — дефолт compose-профиля для агентов
- Контекст: Fable §6: compose `--profile split` поднимает вынесенные сервисы отдельно, «по умолчанию — монолит». После выноса notification dev-окружение агентов по умолчанию перестаёт соответствовать проду.
- Вопрос: когда дефолт для агентов/CI переключается на `--profile split` — сразу после M2 или монолит-дефолт до конца горизонта?
- Варианты: A) После приёмки каждого выноса дефолт = split для этого сервиса (dev ≈ prod) [Рекомендую] B) Монолит-дефолт всегда, split только для интеграционных прогонов C) Два канонических профиля с обязательным прогоном обоих в CI.
- Влияние: dev-петля всех агентов, полнота регрессии, расход CI-минут.

## Auth / сквозное

### GZ-ARCH-13: JWKS-миграция HS256→EdDSA — до пилота или после
- Контекст: Fable §5.1 допускает переходный общий HS256-секрет для пилота M2, JWKS — до выноса ai; §10.5 прямо спрашивает, не блокер ли это. ADR фиксирует целевое состояние без срока.
- Вопрос: допустим ли переходный HS256 через K8s Secret для notification, или JWKS — предусловие первого же выноса?
- Варианты: A) HS256 допустим для пилота, JWKS обязателен до hub-ai (BYOK-контур) [Рекомендую] B) JWKS до любого выноса — секрет в 2 местах уже неприемлем C) JWKS параллельно пилоту, без жёсткого gate.
- Влияние: скоуп M0/M1 vs M2, security-аудит FA-02, ротация ключей.

### GZ-ARCH-14: OTel tracing через NATS — жёсткий gate пилота?
- Контекст: ADR §6: trace-context через NATS-headers — «предусловие, не потом». Но не сказано, блокирует ли отсутствие сквозного трейса старт M2 или допускается доделка параллельно.
- Вопрос: сквозной trace (REST→outbox→NATS→consumer) — обязательный exit-критерий M0 до пилота, или M2 может стартовать параллельно?
- Варианты: A) Жёсткий gate: без сквозного трейса пилот не стартует — иначе отладка split вслепую [Рекомендую] B) Параллельно: HTTP-трейсы есть, NATS-headers доделываем в M2 C) Только для ai/realtime, пилоту достаточно логов с request_id.
- Влияние: длительность M0, качество ретроспективы Go/No-Go, debug-стоимость инцидентов.

### GZ-ARCH-15: Rate limits при split — edge или per-service
- Контекст: Fable §7: «уточнить в ADR: лимиты на edge (Caddy/hub-core) vs per-service»; рекомендация в плане — auth-лимиты в hub-core, доменные в сервисе. ADR это не зафиксировал. TZ: API 100/с, файлы 10/мин, сообщения 60/мин.
- Вопрос: где живут TZ-лимиты после выноса — централизованно на edge или в каждом сервисе?
- Варианты: A) Auth-лимиты в hub-core, доменные (60/мин сообщения) в своём сервисе, общий 100/с на Caddy [Рекомендую] B) Всё на Caddy edge — одна точка правды C) Всё per-service — Caddy без логики.
- Влияние: TZ-инвариант rate limiting, общий middleware в `platform/`, поведение при обходе edge.

## CI / процесс

### GZ-ARCH-16: Path-filtered CI — обязательность и бюджет минут
- Контекст: Fable §5.5: path-filter в M0 даёт экономию (~8–12 мин на PR вместо 25–30); без него матрица сервисов взорвёт студенческий пакет 3000 мин/мес. Fable §10.6 и Opus §11.6 спрашивают про готовность к платному тарифу.
- Вопрос: path-filtered jobs — блокирующее exit-условие M0, и есть ли готовность к платному тарифу GitHub Actions как fallback?
- Варианты: A) Path-filter обязателен в M0, остаёмся в 3000 мин, платный тариф — только по факту превышения [Рекомендую] B) Сразу заложить платный тариф C) Self-hosted runner на прод-хосте.
- Влияние: скорость PR-циклов всех агентов, риск блокировки CI в конце месяца.

### GZ-ARCH-17: Feature flags для strangler-переключений
- Контекст: Стратегия переключения — route-flip в Caddy (грубый рубильник на весь префикс). Fable §10.7 спрашивает про SLA: допустимы ли минутные окна при flip или нужен бесшовный переход. Redis-backed флаги дали бы канареечное/частичное переключение, но это новый механизм в стеке.
- Вопрос: вводить ли feature flags (Redis-backed) для постепенных strangler-переключений, или Caddy route-flip с коротким окном достаточен?
- Варианты: A) Только Caddy flip, окно в минуты допустимо при 10–50 юзерах [Рекомендую] B) Redis-флаги для канареечного % трафика на новый сервис C) Флаги только для рискованных доменов (messenger/realtime), пилот — flip.
- Влияние: сложность M2-04 и последующих flip'ов, rollback-процедура, новый механизм в `platform/`.
