## Секреты и ротация (FA-06 / PG-03)

### GZ-SEC-01: Исполнитель ручной ротации секретов
- Контекст: FA-06/PG-03 — единственный prod-блокер; Resend/Telegram токены скомпрометированы в git-истории (INF-03). Roadmap отдаёт задачу `devops-engineer`, но выпуск новых токенов требует доступа к внешним кабинетам (Resend, BotFather).
- Вопрос: кто физически выпускает новые токены — пользователь вручную, или агент с переданными credentials от кабинетов?
- Варианты: A) Пользователь выпускает токены сам, агент готовит чек-лист и обновляет env/Secrets [Рекомендую] B) Агенту передаются доступы к кабинетам C) Отложить до первого prod-деплоя.
- Влияние: срок снятия единственного prod-блокера, объём доверия агенту.

### GZ-SEC-02: BFG git-purge — переписывание истории
- Контекст: токены остаются в git-истории даже после ротации. BFG-purge переписывает историю → инвалидация всех клонов, force-push в protected main/master.
- Вопрос: делаем ли переписывание истории, или считаем ротацию достаточной (старые токены мертвы)?
- Варианты: A) Только ротация, history-purge не делаем — токены отозваны, репо приватный [Рекомендую] B) BFG-purge + скоординированный force-push C) Purge при переходе repo в public/open-source.
- Влияние: целостность истории, PR-refs, риск при будущем открытии репо.

### GZ-SEC-03: Момент и порядок ротации
- Контекст: Roadmap: ротация «не гейтит» разработку и идёт фоном в Волне 1 вместе с SSH deploy и tag v2.5.0.
- Вопрос: ротация строго до первого prod-деплоя (v2.5.0 tag) или допускается деплой со старыми секретами с ротацией после?
- Варианты: A) Ротация — precondition деплоя, tag только после [Рекомендую] B) Деплой сразу, ротация в первую неделю C) Ротация только скомпрометированных, остальные по расписанию.
- Влияние: окно эксплуатации утёкших токенов в prod.

### GZ-SEC-04: Политика регулярной ротации
- Контекст: сейчас rotation «Manual via Admin panel для API keys»; JWT signing key, NATS/Redis/PG пароли, LiveKit keys не имеют расписания ротации.
- Вопрос: вводим ли регулярную ротацию (например, 90 дней) и для каких классов секретов?
- Варианты: A) Только API keys + внешние токены по 90д, инфраструктурные — при инцидентах [Рекомендую] B) Все секреты по расписанию с автоматизацией C) Без расписания, только реактивно.
- Влияние: ops-нагрузка, окно компрометации.

### GZ-SEC-05: Хранилище секретов при переходе на микросервисы
- Контекст: при выносе 5–6 сервисов каждому нужны свои секреты (PG schema creds, NATS creds, S3 keys); ротация умножается ×N. Prod — K3s.
- Вопрос: что используем — plain K8s Secrets, sealed-secrets в git, или внешний Vault/SOPS?
- Варианты: A) K8s Secrets + SOPS/age-шифрованные манифесты в репо [Рекомендую] B) sealed-secrets controller C) HashiCorp Vault (оверкилл для 1 ноды) D) Plain K8s Secrets, вручную.
- Влияние: GitOps-воспроизводимость, сложность инфры, безопасность at-rest.

### GZ-SEC-06: Per-service DB-credentials и границы schema-per-service
- Контекст: ADR фиксирует schema-per-service в одном PostgreSQL, cross-schema запрещён грантами. Не решено, кто владеет выдачей грантов и как проверяется их дрейф.
- Вопрос: как enforce'им запрет cross-schema — только грантами при провижининге, или ещё CI-проверкой миграций?
- Варианты: A) Отдельный PG-роль на сервис + smoke-тест грантов в CI [Рекомендую] B) Только гранты при setup C) Row-level security поверх.
- Влияние: реальная изоляция данных между сервисами, blast radius при компрометации одного сервиса.

## SSO / LDAP / AD (ADR-AUTH-SSO proposed)

### GZ-SEC-07: Набор протоколов SSO
- Контекст: пользователь одобрил SSO/LDAP/AD в scope; ADR-AUTH-SSO ещё не написан. Целевая аудитория — RU-корпораты on-prem (AD/LDAP чаще, чем SAML).
- Вопрос: какие протоколы входят в первую итерацию — OIDC, SAML 2.0, LDAP bind, или всё сразу?
- Варианты: A) OIDC + LDAP(S) bind в v1; SAML отложить [Рекомендую] B) Только OIDC (Keycloak как прослойка к AD) C) Все три сразу.
- Влияние: объём auth-модуля, поверхность атаки, сроки ADR и реализации.

### GZ-SEC-08: Сосуществование SSO и Magic Link
- Контекст: Magic Link — единственный метод (ADR-AUTH-01, MANDATORY). Roadmap: «Magic Link остаётся дефолтным, SSO — дополнительный». Не решено поведение при конфликте.
- Вопрос: может ли админ *принудить* SSO-only для org (отключить Magic Link), и что происходит с пользователем, заведённым через SSO, при недоступности IdP?
- Варианты: A) Org-политика: magic-link / sso / both; при sso-only Magic Link остаётся break-glass для founder [Рекомендую] B) Всегда both, приоритетов нет C) SSO-only без fallback.
- Влияние: ADR-AUTH-SSO, ревизия MANDATORY-раздела tz_constraints, lockout-риски.

### GZ-SEC-09: Провижининг и деактивация пользователей из IdP
- Контекст: сейчас регистрация по invite + admin Pending queue (7 дней). SSO предполагает автосоздание аккаунтов; увольнение в AD должно закрывать доступ в Hub.
- Вопрос: JIT-провижининг при первом SSO-входе (минуя invite/Pending) и как выполняется деактивация — SCIM, периодический LDAP-sync, или вручную?
- Варианты: A) JIT + периодический LDAP-sync деактиваций (15 мин), SCIM позже [Рекомендую] B) SCIM 2.0 сразу C) Только JIT, деактивация вручную админом.
- Влияние: конфликт с invite-моделью (MANDATORY), скорость закрытия доступа уволенным, ERD user.

### GZ-SEC-10: Маппинг групп IdP на роли Hub
- Контекст: RBAC Hub: System (Admin/Member) → Project roles → Custom. AD/LDAP-группы нужно куда-то маппить.
- Вопрос: маппим ли AD-группы на system/project роли автоматически, и кто источник истины при расхождении?
- Варианты: A) Маппинг только на system role (Admin/Member), project-роли — внутри Hub [Рекомендую] B) Полный маппинг включая project-роли C) Без маппинга, роли только вручную.
- Влияние: сложность SSO-модуля, риск privilege escalation через группы IdP.

## RBAC новых модулей и межсервисный

### GZ-SEC-11: Модель доступа wiki
- Контекст: wiki — новый домен в hub-core, «крупнейший пробел vs Confluence». Спеки RBAC нет: наследование от project или собственные space/page-ACL.
- Вопрос: какая гранулярность — доступ на уровне space (проекта), или page-level ACL с приватными страницами?
- Варианты: A) Space-level наследует project RBAC, page-level restrict как флаг «только участники X» [Рекомендую] B) Полные page-ACL как Confluence C) Только project-уровень.
- Влияние: ERD wiki, search-скоуп (NF-03 распространяется на wiki), объём be-работ.

### GZ-SEC-12: Sharing в bases (no-code БД)
- Контекст: bases идут к Lark-паритету (formulas, relations, views). У Lark таблицы шарятся ссылкой/на пользователя; у Hub search обязан быть user-scoped.
- Вопрос: допускаем ли sharing базы за пределы project-membership (per-user grants, публичные read-only ссылки)?
- Варианты: A) Только project-membership в v1; per-user grants позже [Рекомендую] B) Per-user/per-view grants сразу C) + публичные ссылки (anonymous read).
- Влияние: RBAC-матрица, search/API-скоупы, поверхность утечки данных.

### GZ-SEC-13: Доступ к чувствительным HR/CRM-данным
- Контекст: HR (зарплаты? баланс отпусков, org chart) и CRM (сделки, суммы) появляются в v4. Текущий RBAC не различает «участник проекта» и «имеет право видеть зарплаты/суммы сделок».
- Вопрос: вводим ли отдельные data-роли (HR-manager, Finance, Sales-lead) и field-level скрытие (сумма сделки видна не всем участникам)?
- Варианты: A) Модульные роли (hr:admin, crm:manager) + field-level masking для зарплат/сумм [Рекомендую] B) Только module-level доступ (видишь модуль — видишь всё) C) Всё под system Admin.
- Влияние: RBAC-архитектура (третье измерение ролей), ERD hr/crm, аудит доступа.

### GZ-SEC-14: Хранение зарплат и персданных HR
- Контекст: encryption at rest сейчас только для GitHub/GitLab токенов (AES-GCM). Зарплаты и персданные сотрудников — иная категория чувствительности (и 152-ФЗ для RU on-prem).
- Вопрос: шифруем ли HR-поля (зарплата, паспортные данные) на уровне приложения, или полагаемся на диск/PG-уровень?
- Варианты: A) App-level AES-GCM для узкого списка полей (зарплата, документы) [Рекомендую] B) Полагаемся на full-disk encryption инстанса (ответственность self-hosted клиента) C) pgcrypto на уровне колонок.
- Влияние: производительность, поиск/сортировка по зашифрованным полям, комплаенс-позиционирование.

### GZ-SEC-15: Аутентификация сервис-к-сервису
- Контекст: при выносе hub-ai/hub-realtime/hub-notification появляются внутренние вызовы (HTTP + NATS). У hub-mail сейчас internal `POST /v1/send` — механизм защиты не зафиксирован в ADR.
- Вопрос: чем аутентифицируем межсервисные вызовы — статические internal API keys, JWT service tokens, mTLS, NATS subject-permissions?
- Варианты: A) Внутренняя сеть K3s + per-service NATS creds + internal API key на HTTP [Рекомендую] B) mTLS через service mesh (оверкилл) C) Подписанные service-JWT от hub-core.
- Влияние: ADR-MICROSERVICES §security, blast radius, сложность локальной разработки.

### GZ-SEC-16: Пропагация user-контекста между сервисами
- Контекст: RBAC-проверки живут в hub-core. hub-ai/hub-realtime должны знать «кто пользователь и что ему можно» — иначе повторение NF-02/NF-03 на новом уровне.
- Вопрос: сервисы валидируют user-JWT самостоятельно (shared public key) и дублируют RBAC-кэш, или каждый запрос ходит в hub-core за authz?
- Варианты: A) JWT-валидация локально + RBAC-проекция через NATS/CQRS с TTL [Рекомендую] B) Синхронный authz-вызов в hub-core C) Trust-by-network (запрещено — fail-open).
- Влияние: латентность, консистентность прав при отзыве, архитектура CQRS-проекций.

## GDPR / retention

### GZ-SEC-17: Корзина 30 дней для новых типов данных
- Контекст: MANDATORY: soft delete через корзину 30д. Для wiki-страниц (иерархия, версии), записей bases (relations) и HR-записей семантика «корзины» не определена.
- Вопрос: распространяем ли единый механизм trash+30д на wiki/bases/HR как есть, или для иерархичных/связанных данных нужны правила (что с child-страницами, битыми relations)?
- Варианты: A) Единый trash; удаление wiki-страницы каскадит на детей, relations в bases — tombstone [Рекомендую] B) Per-module политики C) HR-записи не удаляются в корзину (только hard по GDPR).
- Влияние: `audit/PurgeExpired`, ERD новых модулей, UX восстановления.

### GZ-SEC-18: Право на забвение для новых модулей
- Контекст: `DeleteUserGDPR` (BE-H6) каскадит по текущим модулям. Wiki-правки, записи bases, CRM-активности, HR-карточка — новые точки каскада; при микросервисах каскад станет распределённым.
- Вопрос: удаление или анонимизация авторства (wiki-правки терять нельзя — теряется история документа), и как оркестрируем каскад через сервисы?
- Варианты: A) Анонимизация авторства контента + hard-delete персональных записей; NATS-событие `user.gdpr_delete`, каждый сервис подписан [Рекомендую] B) Полный hard-delete везде C) Только hub-core, новые модули вручную.
- Влияние: целостность истории документов, распределённая согласованность, аудит выполнения GDPR-запроса.

### GZ-SEC-19: Сроки хранения HR/accounting-данных
- Контекст: бухгалтерия (своя, с НДФЛ) и HR-данные имеют законодательные сроки хранения (в РФ — годы), конфликтующие с «30 дней корзина» и правом на забвение.
- Вопрос: фиксируем ли legal-hold: accounting/HR-записи исключаются из GDPR-каскада на срок обязательного хранения?
- Варианты: A) Legal-hold флаг: анонимизация связей, финзаписи хранятся установленный срок [Рекомендую] B) Ответственность клиента (self-hosted), Hub удаляет всё C) Консультация с юристом до реализации accounting.
- Влияние: дизайн DeleteUserGDPR, позиционирование продукта для RU-компаний.

## Agent-native AI безопасность

### GZ-SEC-20: Границы автономии агента
- Контекст: agent-native AI + MCP-сервер — в scope (`hub-ai`). Агент потенциально может создавать/менять/удалять задачи, писать в каналы, править wiki. ADR-AI-agents ещё proposed.
- Вопрос: какие действия агенту разрешены автономно, а какие требуют подтверждения человека?
- Варианты: A) Autonomous: read + draft/create в своём scope; confirm: любые delete, изменения чужих задач, сообщения от имени пользователя, RBAC-изменения [Рекомендую] B) Всё автономно, откат через audit C) Всё через подтверждение (агент = только советчик).
- Влияние: ADR-AI-agents, ценность фичи vs риск, дизайн permission-модели агента.

### GZ-SEC-21: Идентичность и аудит действий агента
- Контекст: audit middleware пишет действия пользователей. Действия агента (по чьему поручению? какой промпт?) нуждаются в отдельной атрибуции — иначе не разобрать инцидент.
- Вопрос: агент действует как отдельный principal (service-account с собственным RBAC) или от имени пользователя с флагом `via_agent`?
- Варианты: A) Отдельный agent-principal, права = пересечение (агент ∩ пользователь), audit-запись содержит user + agent + task-id [Рекомендую] B) От имени пользователя с флагом C) Единый системный агент-аккаунт.
- Влияние: RBAC-модель, audit-схема, расследование инцидентов, отзыв прав агента.

### GZ-SEC-22: Лимиты стоимости BYOK и защита ключей
- Контекст: AI gateway BYOK + Ollama (Phase 17). Пользовательские API-ключи провайдеров — секреты; автономный агент может сжечь бюджет владельца ключа.
- Вопрос: вводим ли лимиты (запросов/токенов/$ в день на пользователя и на org) и где храним BYOK-ключи?
- Варианты: A) AES-GCM хранение (как GitHub-токены) + org-уровневые дневные лимиты токенов с hard-stop и алертом [Рекомендую] B) Только soft-warning без hard-stop C) Лимиты на стороне провайдера (ответственность пользователя).
- Влияние: схема ai-модуля, доверие к BYOK, поддержка Ollama (без затрат) как degraded-режим.

### GZ-SEC-23: Поверхность MCP-сервера
- Контекст: MCP-сервер открывает инструменты Hub внешним клиентам (Claude/Cursor и т.п.). Это новый входной канал в обход UI, с теми же данными.
- Вопрос: как аутентифицируем MCP-клиентов и ограничиваем ли toolset — полный API или курируемый безопасный список?
- Варианты: A) Personal Access Token с явными скоупами + курируемый read-heavy toolset в v1 [Рекомендую] B) OAuth-flow + полный toolset C) MCP только в локальной сети (on-prem default).
- Влияние: ADR-AI-agents, rate-limits для MCP-канала, повторное применение всех NF-инвариантов (search scope, RBAC) к MCP-инструментам.

## Прод-топология и эксплуатация

### GZ-SEC-24: Одна K3s-нода или кластер
- Контекст: prod — «K3s (planned)». Стек тяжёлый (PG, Mongo, Redis, NATS, SeaweedFS, LiveKit, Meilisearch + 5–6 сервисов). Одна нода = единая точка отказа, кластер = стоимость и сложность.
- Вопрос: целевая топология первого prod — single-node K3s или мини-кластер (2–3 ноды), и каков SLA-ориентир?
- Варианты: A) Single-node + строгие бэкапы + документированный restore (для 10–50 чел достаточно) [Рекомендую] B) 3 ноды с самого начала C) Single-node сейчас, кластер как условие v5/multi-org.
- Влияние: deployments/k3s-манифесты, стоимость, дизайн бэкапов, RTO/RPO.

### GZ-SEC-25: Стратегия бэкапов при schema-per-service
- Контекст: backup-модуль есть (S3, INF-04 закрыт). При schema-per-service + Mongo + SeaweedFS + Redis нужна согласованность: восстановление одной схемы может разъехаться с CQRS-проекциями соседей.
- Вопрос: бэкапим весь PG-инстанс атомарно или per-schema, и что с кросс-сторами (Mongo-сообщения vs PG-каналы)?
- Варианты: A) Полный pg_dump инстанса + Mongo dump в одном окне; restore только целиком; проекции перестраиваются из NATS/источника [Рекомендую] B) Per-schema бэкапы с ручной сверкой C) Снапшоты диска ноды целиком.
- Влияние: RPO, процедура restore, требование replay-able проекций в ADR-MICROSERVICES.

### GZ-SEC-26: Дежурства и получатели алертов
- Контекст: OTel заложен в Track P M0, но не решено, куда идут алерты (downtime, GDPR-cron FAIL, retention WARN, security-события) и кто реагирует — команда фактически «пользователь + AI-агенты».
- Вопрос: какие каналы алертинга (Telegram-бот Hub? email? внешний uptime-мониторинг) и какие события пейджат немедленно vs дайджест?
- Варианты: A) Telegram-канал админа: page = downtime/5xx-шторм/GDPR-FAIL; дайджест = retention/cert-expiry; внешний uptime-ping (healthchecks.io) [Рекомендую] B) Только email C) Полноценный Alertmanager+PagerDuty (оверкилл).
- Влияние: конфигурация OTel/алертинга в M0, MTTR, требования к notification-модулю.
