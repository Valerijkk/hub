### GZ-SEC-01: FA-06/PG-03 — исполнитель и срок ручной ротации секретов
- Контекст: единственный P0-блокер v2.5.0 — ручная ротация Resend/Telegram токенов (Phase 1–3, скрипты `scripts/fa06.sh` готовы). В roadmap назначен `devops-engineer`, но шаги требуют доступа к реальным аккаунтам Resend/Telegram и prod-хосту.
- Вопрос: кто физически выполняет ротацию (пользователь вручную / агент с предоставленными ключами) и к какому сроку, чтобы не гейтить tag v2.5.0 бесконечно?
- Варианты: A) Пользователь выполняет сам по runbook в ближайшие дни [Рекомендую — доступ к внешним аккаунтам есть только у него] B) Агент готовит всё, пользователь только вставляет новые ключи в env C) Отложить до первого реального prod-деплоя.
- Влияние: tag v2.5.0, SSH deploy, CTO sign-off, доверие к prod-инстансу.

### GZ-SEC-02: BFG git-purge истории — делать ли и когда
- Контекст: в истории до `859ecef` лежат `RESEND_API_KEY`, `TELEGRAM_BOT_TOKEN`, devkey LiveKit. Purge (BFG) — P1, ломает хэши коммитов и требует force-push + re-clone у всех.
- Вопрос: чистим историю BFG или считаем достаточным ротацию (старые ключи мертвы)?
- Варианты: A) Только ротация, историю не трогаем [Рекомендую — репо приватный, ключи после ротации бесполезны] B) BFG сразу после FA-06 C) BFG перед возможным open-source/передачей репо.
- Влияние: git-хэши, открытые PR, CI-кэши, ссылки в `.planning/` на коммиты.

### GZ-SEC-03: SSO — набор протоколов для ADR-AUTH-SSO
- Контекст: SSO/LDAP/AD одобрены пользователем (снимается FORBIDDEN), нужен ADR. SAML 2.0, OIDC и LDAP/AD-bind — разные затраты; RU-корпораты on-prem чаще просят AD/LDAP.
- Вопрос: какие протоколы входят в первую итерацию ADR-AUTH-SSO?
- Варианты: A) OIDC + LDAP/AD (покрывает Keycloak/ADFS-через-OIDC и legacy AD) [Рекомендую] B) Только OIDC (минимум) C) SAML + OIDC + LDAP сразу (максимум, дорого).
- Влияние: объём auth/identity-модуля, зависимости (go-ldap, oidc-lib), сроки Track F.

### GZ-SEC-04: Сосуществование SSO и Magic Link
- Контекст: Magic Link остаётся дефолтом (ADR-AUTH-01); SSO — «дополнительный корпоративный». Не решено, может ли org-админ отключить Magic Link целиком или принудить SSO для доменов.
- Вопрос: SSO — строго дополнительный метод, или админ может сделать его обязательным (Magic Link off / только как fallback-recovery)?
- Варианты: A) Оба метода активны, per-org toggle «enforce SSO» с break-glass Magic Link для founder [Рекомендую] B) Всегда оба, без enforce C) Полное отключение Magic Link при включённом SSO.
- Влияние: auth flow, rate-limit правила 3/10m, recovery-сценарии, ADR-AUTH-SSO.

### GZ-SEC-05: Провижининг/деprovisioning пользователей при SSO
- Контекст: сейчас регистрация только по invite + Pending queue (7 дней). SSO обычно означает JIT-создание учёток при первом входе и деактивацию при удалении из IdP/AD.
- Вопрос: как SSO-пользователи попадают в org — JIT-провижининг, SCIM, периодическая LDAP-синхронизация или всё равно через invite/Pending?
- Варианты: A) JIT + периодическая LDAP-sync деактивация, invite-модель остаётся для non-SSO [Рекомендую] B) SCIM 2.0 (стандартно, но дорого) C) SSO только для существующих invited-аккаунтов (matching по email).
- Влияние: инвариант «регистрация по invite» из tz_constraints, offboarding-безопасность, HR-модуль.

### GZ-SEC-06: MFA — вводить ли и в какой форме
- Контекст: паролей нет; Magic Link — одиночный фактор (email), 6-digit код принят с rate-limit (NF-10). При SSO MFA обычно живёт на стороне IdP.
- Вопрос: нужен ли собственный MFA (TOTP/WebAuthn) в Hub, или полагаемся на email-фактор + MFA IdP при SSO?
- Варианты: A) Без собственного MFA сейчас; делегировать IdP, зафиксировать в ADR-AUTH-SSO [Рекомендую] B) Опциональный TOTP для admin/founder C) WebAuthn/passkeys как второй фактор для всех.
- Влияние: scope ADR-AUTH-SSO, auth-таблицы, UX входа, NF-10 acceptance.

### GZ-SEC-07: Модель прав wiki (knowledge base)
- Контекст: RBAC сейчас: System (Admin/Member) → Project roles → Custom. Wiki — новый домен: пространства/страницы могут быть org-wide, командными и личными; Confluence-подобные системы имеют per-page permissions.
- Вопрос: какая гранулярность прав у wiki — на уровне пространства, страницы или наследование от проекта?
- Варианты: A) Права на уровне space (read/write/admin) + наследование страницами [Рекомендую — просто, покрывает 90%] B) Per-page ACL с наследованием и override C) Привязка wiki-space к project и переиспользование project roles.
- Влияние: схема Ent, search user-scope фильтр (NF-03 обязан покрыть wiki), объём фазы wiki.

### GZ-SEC-08: Sharing прав в bases (no-code БД) при Lark-паритете
- Контекст: bases углубляются до Lark-паритета (formula/relations/views). У Lark есть sharing таблиц/view наружу команды и права на уровне записей/полей.
- Вопрос: до какого уровня опускаем права в bases — база целиком, таблица, view, запись?
- Варианты: A) База + таблица (read/edit/manage), view наследует [Рекомендую] B) + row-level правила (owner-only записи) C) Полный field-level security (дорого, отложить).
- Влияние: производительность запросов, search-scope, API-контракты bases, сроки эпика B.

### GZ-SEC-09: Границы автономии AI-агентов (agent-native/MCP)
- Контекст: ADR-AI-agents (proposed). Hub-агент через MCP теоретически может создавать задачи, писать в каналы, менять данные CRM/bases. Сейчас есть только копилот `@hub-ai`.
- Вопрос: какие действия агент выполняет автономно, а какие требуют явного подтверждения человека?
- Варианты: A) Read + draft всё; mutation (создать задачу, отправить сообщение) — автономно в рамках прав вызвавшего пользователя; destructive (delete, права, admin) — только с подтверждением [Рекомендую] B) Всё через подтверждение (медленно, безопасно) C) Полная автономия в рамках RBAC-ролей агента.
- Влияние: ADR-AI-agents, дизайн MCP-инструментов, UX подтверждений, риск-профиль.

### GZ-SEC-10: Identity и аудит действий AI-агента
- Контекст: audit-middleware пишет действия по user_id. Действия агента от имени пользователя нужно отличать от действий самого пользователя; агенту нужен собственный principal и, вероятно, отдельные rate-limits.
- Вопрос: агент действует как отдельный service-account с делегированными правами (act-on-behalf-of) или напрямую под user_id?
- Варианты: A) Отдельный agent principal + поле `on_behalf_of` в audit log [Рекомендую] B) Просто user_id + флаг `via_agent` в audit C) Один общий системный агент-аккаунт на org.
- Влияние: audit-схема, RBAC, GDPR-выгрузки, отзыв доступа агента (kill-switch).

### GZ-SEC-11: GDPR/retention для новых типов данных (wiki, bases, CRM)
- Контекст: инвариант — soft delete через корзину 30 дней, hard delete только Admin/GDPR; `DeleteUserGDPR` каскад покрывает текущие модули. Wiki-страницы, записи bases и CRM-контакты — новые типы, причём CRM-контакты — персональные данные третьих лиц (не пользователей Hub).
- Вопрос: распространяем корзину 30д и GDPR-каскад (export + delete) на все новые типы без исключений, и как обрабатываем запросы субъектов-неюзеров (CRM-контакты)?
- Варианты: A) Единая политика: корзина 30д + включение в GDPR-каскад + admin-endpoint удаления CRM-контакта по запросу субъекта [Рекомендую] B) Корзина только для user-generated (wiki/bases), CRM — отдельная политика C) Решать per-module по мере реализации.
- Влияние: Ent-схемы новых модулей, `audit/retention.go`, `DeleteUserGDPR`, юридические риски.

### GZ-SEC-12: Секреты при переходе на микросервисы (Track P)
- Контекст: сейчас секреты — env через Docker Compose / GitHub Secrets. Track P выносит notification, ai, calls, ws+messenger, tms в сервисы на K3s; каждому нужны свои DB-креды, NATS-креды, межсервисные токены.
- Вопрос: какой механизм секретов для K3s выбираем — plain K8s Secrets, sealed-secrets или Vault?
- Варианты: A) K8s Secrets + sealed-secrets для GitOps (легковесно для 10–50 чел self-hosted) [Рекомендую] B) HashiCorp Vault (мощно, но лишний stateful-сервис) C) Оставить plain K8s Secrets + ручное управление.
- Влияние: M0/M1 Track P, deploy-манифесты, runbook ротации (следующая FA-06 станет проще/сложнее), порог входа self-hosted админов.

### GZ-SEC-13: Аутентификация межсервисных вызовов в микросервисах
- Контекст: монолит не имеет внутренних сетевых вызовов; после выноса сервисов появится трафик hub-core ↔ hub-ai/notification/calls. `hub-mail` уже слушает internal `POST /v1/send` — механизм его защиты не зафиксирован как стандарт.
- Вопрос: чем аутентифицируем service-to-service — shared static tokens, mTLS или JWT service-accounts?
- Варианты: A) Static bearer per service из K8s Secrets + network policy (просто, достаточно для одного кластера) [Рекомендую для M0–M2] B) mTLS через service mesh C) Внутренний JWT-issuer.
- Влияние: ADR-ARCH-MICROSERVICES детализация, платформенный код, сложность отладки.

### GZ-SEC-14: Внешняя поверхность — статус-страница, гости в звонках, marketplace
- Контекст: всё, что наружу без auth, расширяет attack surface. Потенциальные кандидаты: публичная status page, guest-доступ к звонкам по ссылке (стандарт у Zoom-конкурентов), публичный листинг marketplace, публичные wiki-страницы/формы bases.
- Вопрос: какие анонимные/гостевые поверхности одобряем в scope и с какими ограничениями?
- Варианты: A) Только guest-звонки по одноразовой ссылке с lobby-подтверждением; остальное — за auth [Рекомендую] B) + публичная status page (read-only, без версий/деталей) C) + публичные wiki-страницы и формы bases (нужен отдельный security-review каждой).
- Влияние: rate-limiting анонимного трафика, CORS/CSP, NF-02/NF-03 инварианты, объём security-audit перед каждым релизом.
