# Бизнес-документация: Phase 1 -- Фундамент и инфраструктура

## 1. Обзор

Phase 1 закладывает фундамент платформы Hub. Реализованы: система аутентификации без паролей (Magic Link + Telegram), управление проектами с гибкой ролевой моделью (RBAC), файловое хранилище на базе SeaweedFS, WebSocket-шлюз с NATS-мостом для событий реального времени и полноценная оболочка фронтенда (sidebar, topbar, страницы авторизации, проектов, профиля).

Все последующие модули (трекер задач, мессенджер, TMS, созвоны, дашборды) строятся поверх этой инфраструктуры.

**Целевая аудитория:** команды разработки и тестирования от 10 до 50 человек.

**Покрытые требования:** AUTH-01 -- AUTH-08, PROJ-01 -- PROJ-04, PROJ-06, PROJ-07, UI-01, UI-07, UI-08.

## 2. Аутентификация и пользователи

### 2.1. Вход через Magic Link (AUTH-01)

Беспарольная аутентификация через email:

1. Пользователь вводит email на странице входа `/login`.
2. Сервер генерирует 6-значный числовой код, сохраняет в Redis с TTL 5 минут.
3. Код отправляется через Resend API (в dev-режиме логируется в консоль).
4. Пользователь вводит код -- получает пару JWT access token + refresh token.
5. Если пользователь с таким email не существует, создается новый аккаунт.

**Ограничения:**
- Rate limit: 3 запроса за 10 минут на один email (HTTP 429 при превышении).
- Код действителен 5 минут.
- В режиме "только по приглашению" новые пользователи не могут зарегистрироваться через Magic Link (HTTP 403).

**API:**
- `POST /api/auth/magic-link` -- отправка кода. Тело: `{"email": "user@example.com"}`.
- `POST /api/auth/magic-link/verify` -- верификация кода. Тело: `{"email": "...", "code": "123456"}`. Ответ: `{"access_token": "...", "refresh_token": "...", "expires_in": 900}`.

### 2.2. Вход через Telegram (AUTH-02)

Аутентификация через Telegram Login Widget:

1. На странице входа пользователь нажимает "Войти через Telegram".
2. Telegram Widget передает `initData` (подписанные данные пользователя).
3. Сервер верифицирует HMAC-SHA256 подпись с использованием токена бота.
4. При первом входе создается пользователь с `telegram_id`; при повторном -- находится существующий.
5. Для Telegram-пользователей без email используется placeholder `tg_{telegram_id}@placeholder.hub`.

**API:**
- `POST /api/auth/telegram` -- вход через Telegram. Тело: `{"init_data": "..."}`. Ответ: `{"access_token": "...", "refresh_token": "...", "expires_in": 900}`.

### 2.3. Режим регистрации (AUTH-03)

Администратор управляет режимом регистрации новых пользователей:

- **Открытый режим (`open`):** любой может создать аккаунт через Magic Link или Telegram.
- **Только по приглашению (`invite_only`):** новые пользователи должны сначала получить invite-ссылку от участника проекта.

Режим хранится в таблице `SystemSetting` (ключ `registration_mode`).

**API (только Admin):**
- `GET /api/admin/registration-mode` -- получение текущего режима. Ответ: `{"mode": "open"}`.
- `PUT /api/admin/registration-mode` -- переключение режима. Тело: `{"mode": "invite_only"}`.

### 2.4. Профиль пользователя (AUTH-04)

Каждый пользователь имеет редактируемый профиль с полями:

| Поле | Тип | Описание |
|------|-----|----------|
| name | string | Имя пользователя |
| display_name | string | Отображаемое имя |
| avatar_url | string | URL аватара |
| email | string | Email (уникальный) |
| telegram_id | string | Telegram ID (уникальный) |
| phone | string | Телефон |
| position | string | Должность |
| department | string | Отдел |
| timezone | string | Часовой пояс (по умолчанию UTC) |
| language | string | Язык интерфейса (по умолчанию ru) |
| birthday | date | Дата рождения |

**Страница редактирования:** `/settings/profile` (фронтенд).

**API:**
- `GET /api/auth/me` -- получение профиля текущего пользователя.
- `PUT /api/auth/me` -- обновление профиля. Все поля опциональны (PATCH-семантика).

### 2.5. Системные роли (AUTH-05)

Два уровня системных ролей:

- **Admin:** полный доступ ко всем проектам и системным настройкам (режим регистрации, управление пользователями).
- **Member:** стандартный доступ, возможность создания проектов.

Роль хранится в поле `system_role` таблицы `User` (enum: `admin`, `member`). Первый зарегистрированный пользователь получает роль `member` (Admin назначается вручную).

### 2.6. Управление сессиями (AUTH-06)

Система поддерживает множественные одновременные сессии:

- Каждый вход создает новую запись в таблице `Session` с устройством (User-Agent) и IP-адресом.
- JWT access token (HS256, TTL 15 минут) содержит `userID` и `sessionID`.
- Refresh token (UUID, TTL 30 дней) хранится в сессии; при обновлении происходит ротация (старый refresh token инвалидируется).
- Пользователь может просматривать список активных сессий с пометкой текущей.
- Пользователь может завершить любую свою сессию (кроме текущей по желанию).

**API:**
- `POST /api/auth/refresh` -- обновление токенов. Тело: `{"refresh_token": "..."}`.
- `POST /api/auth/logout` -- завершение текущей сессии.
- `GET /api/auth/sessions` -- список активных сессий.
- `DELETE /api/auth/sessions/:sessionId` -- завершение конкретной сессии.

### 2.7. Уведомление о новой сессии (AUTH-07)

При каждом входе с нового устройства публикуется событие в NATS:
- Тема: `auth.session.{userID}.new_login`
- Данные: устройство, IP, время

Событие доставляется через WebSocket-мост текущим активным сессиям пользователя. В будущем (Phase 6) событие будет также отправляться в Telegram.

### 2.8. Онбординг (AUTH-08)

Новые пользователи проходят трёхшаговый процесс онбординга:

1. **Шаг 1: Заполнение профиля** -- имя, должность, аватар.
2. **Шаг 2: Обзорный тур** -- ознакомление с интерфейсом.
3. **Шаг 3: Создание или присоединение к проекту** -- создать новый или ввести invite-код.

После завершения онбординга поле `onboarding_completed` устанавливается в `true`. Фронтенд перенаправляет неонбоарженных пользователей на страницу `/onboarding`.

**API:**
- `POST /api/auth/me/onboarding` -- завершение онбординга. Тело: `{"profile": {"name": "...", ...}}`.

## 3. Проекты

### 3.1. Создание проекта (PROJ-01)

Любой аутентифицированный пользователь (Admin или Member) может создать проект:

- Задается имя (2--100 символов) и уникальный ключ (2--10 символов, uppercase, alphanumeric) -- ключ используется для нумерации задач (например, HUB-1, MOBILE-1).
- Опциональное описание (до 2000 символов).
- Создатель автоматически становится Owner проекта.
- При создании автоматически инициализируются заглушки: трекер задач, пространство TMS, чат проекта, канал, дашборд (реальное наполнение -- в следующих фазах).

**API:**
- `POST /api/projects` -- создание проекта. Тело: `{"name": "Hub", "key": "HUB", "description": "..."}`. Ответ: `ProjectResponse` со статусом 201.

### 3.2. Управление проектом (PROJ-02)

Владелец проекта (Owner) управляет:

- **Настройками:** редактирование названия, описания, аватара.
- **Участниками:** добавление, удаление, изменение ролей.
- **Приглашениями:** создание и отзыв invite-ссылок.
- **Командами:** добавление команд целиком в проект.

**API:**
- `GET /api/projects` -- список проектов пользователя (query: `include_archived=true`).
- `GET /api/projects/:projectId` -- детали проекта.
- `PUT /api/projects/:projectId` -- обновление проекта. Тело: `{"name": "...", "description": "...", "avatar_url": "..."}`.

### 3.3. Роли в проекте (PROJ-03)

#### Фиксированные роли

Четыре предопределённых роли с набором разрешений:

| Роль | Описание | Ключевые права |
|------|----------|----------------|
| **Owner** | Полный контроль | Все 26 разрешений (bitmap 0xFFFFFFFFFFFFFFFF) |
| **Developer** | Разработчик | Просмотр, создание/редактирование задач, назначение, комментарии, файлы, каналы, тесты, инвайты |
| **Tester** | Тестировщик | Просмотр, создание/редактирование задач, комментарии, файлы, тесты |
| **Viewer** | Наблюдатель | Только просмотр проекта |

#### Система RBAC

- **Bitmap-разрешения:** 26 прав (Permission uint64), каждое -- отдельный бит.
- **Кастомные роли:** можно создать роль с произвольной комбинацией разрешений через таблицу `Role`.
- **Redis-кеш:** эффективные разрешения кешируются с ключом `rbac:{userID}:{projectID}`, TTL 5 минут.
- **Middleware:** `RequirePermission(perm, rbacService)` проверяет разрешения на каждом запросе к защищённым эндпоинтам.
- **Инвалидация кеша:** автоматическая при любом изменении членства или ролей.

**Полный список разрешений:**
`ProjectView`, `ProjectEdit`, `ProjectDelete`, `ProjectManageMembers`, `ProjectManageRoles`, `ProjectManageWorkflow`, `TaskCreate`, `TaskEdit`, `TaskEditAny`, `TaskDelete`, `TaskAssign`, `TaskComment`, `FileUpload`, `FileDelete`, `FileDeleteAny`, `ChannelCreate`, `ChannelManage`, `MessageEdit`, `MessageDeleteAny`, `TestCaseCreate`, `TestCaseEdit`, `TestRunCreate`, `TestRunExecute`, `InviteCreate`, `InviteManage`, `TeamManage`.

**API:**
- `GET /api/projects/:projectId/members` -- список участников.
- `POST /api/projects/:projectId/members` -- добавление участника. Тело: `{"user_id": "...", "role": "developer"}`.
- `PUT /api/projects/:projectId/members/:userId` -- смена роли. Тело: `{"role": "tester"}`.
- `DELETE /api/projects/:projectId/members/:userId` -- удаление участника.

### 3.4. Приглашения и команды (PROJ-04)

#### Invite-ссылки

- Создаются участником с правом `InviteCreate`.
- Содержат: роль для присоединяющегося, лимит использований (0 = безлимит), срок действия.
- Генерируется уникальный код (8 символов).
- При присоединении по ссылке пользователь автоматически становится участником с указанной ролью.

**API:**
- `POST /api/projects/:projectId/invites` -- создание. Тело: `{"role": "developer", "max_uses": 10, "expires_at": "2026-04-01T00:00:00Z"}`.
- `GET /api/projects/:projectId/invites` -- список приглашений.
- `DELETE /api/projects/:projectId/invites/:inviteId` -- отзыв приглашения.
- `POST /api/invites/join` -- присоединение по коду. Тело: `{"code": "abc12345"}`.

#### Команды

Команды -- группы пользователей, которые можно добавлять в проект целиком. В Phase 1 реализованы маршруты и модели, но логика помечена как "coming soon" (HTTP 501).

**API (зарезервированы):**
- `POST /api/teams` -- создание команды.
- `GET /api/teams` -- список команд.
- `POST /api/teams/:teamId/members` -- добавление участника.
- `DELETE /api/teams/:teamId/members/:userId` -- удаление участника.
- `POST /api/teams/:teamId/projects/:projectId` -- добавление команды в проект.

### 3.5. Архивирование (PROJ-06)

Read-only альтернатива удалению:

- Архивированный проект (`status: archived`) доступен для просмотра, но не для редактирования.
- Проект можно разархивировать обратно в `active`.
- В списке проектов архивные не показываются по умолчанию (параметр `include_archived=true`).

**API:**
- `POST /api/projects/:projectId/archive` -- архивирование.
- `POST /api/projects/:projectId/unarchive` -- разархивирование.

### 3.6. Корзина (PROJ-07)

Soft delete с возможностью восстановления:

- При удалении проект получает `status: deleted` и `deleted_at` с текущим временем.
- Проект находится в корзине 30 дней, после чего подлежит окончательному удалению.
- Восстановление возвращает проект в активное состояние.
- Окончательное удаление доступно только Admin.

**API:**
- `DELETE /api/projects/:projectId` -- перемещение в корзину.
- `GET /api/projects/trash` -- список удалённых проектов.
- `POST /api/projects/:projectId/restore` -- восстановление из корзины.

## 4. UI/UX

### 4.1. Навигация и оболочка приложения (UI-01)

Структура интерфейса:

- **Сворачиваемый sidebar (левая панель):** список проектов, создание проекта, настройки, корзина.
- **Topbar (верхняя панель):** поиск (placeholder для Phase 6), уведомления (placeholder для Phase 6), аватар и меню профиля.
- **App Shell:** компонент `_authenticated` маршрута проверяет наличие JWT и онбординг, перенаправляя неавторизованных на `/login`.

**Маршруты фронтенда:**
- `/login` -- страница входа (Magic Link + Telegram).
- `/onboarding` -- трёхшаговый онбординг.
- `/` -- перенаправление на `/projects`.
- `/projects` -- список проектов.
- `/projects/new` -- создание проекта.
- `/projects/:id` -- детали проекта (вкладки).
- `/settings/profile` -- настройки профиля.
- `/trash` -- корзина.

**Стек фронтенда:**
- React 19 + TypeScript + Vite 6
- TanStack Router (file-based, type-safe маршрутизация)
- TanStack Query (серверный стейт)
- Shadcn/ui + Tailwind CSS 4 (UI-компоненты)
- Sonner (toast-уведомления)

### 4.2. Обработка ошибок (UI-07)

- **Toast-уведомления:** Sonner показывает ошибки API с request ID.
- **Error Boundary:** глобальный обработчик с кнопкой "Обновить".
- **Страница 404:** "Страница не найдена" с ссылкой на главную.
- **HTTP-ошибки бэкенда:** стандартизированный формат `{"message": "..."}` с соответствующими HTTP-кодами (400, 401, 403, 404, 429, 500).

### 4.3. Файлы (UI-08)

Загрузка файлов через presigned URL (прямая загрузка в SeaweedFS, без проксирования через бэкенд):

1. **Drag & Drop:** перетаскивание файлов в область загрузки.
2. **Ctrl+V:** вставка скриншотов из буфера обмена.
3. **Процесс:** фронтенд запрашивает presigned URL -> загружает файл напрямую в SeaweedFS -> подтверждает загрузку бэкенду.

**API:**
- `POST /api/files/upload-url` -- получение presigned URL. Тело: `{"filename": "...", "contentType": "...", "projectId": "..."}`.
- `POST /api/files/:fileId/confirm` -- подтверждение загрузки. Тело: `{"entityType": "task", "entityId": "..."}`.
- `GET /api/files/:fileId/url` -- получение presigned URL для скачивания.
- `DELETE /api/files/:fileId` -- удаление файла.

## 5. Инфраструктура

### 5.1. WebSocket Gateway

Единое WebSocket-соединение на клиента для событий реального времени:

- **Подключение:** `WS /ws?token={jwt}` -- JWT передается через query parameter (WebSocket handshake не поддерживает кастомные заголовки).
- **Комнаты:** клиент подписывается на комнаты (например, `project:{id}`).
- **NATS Bridge:** мост маршрутизирует события из NATS в WebSocket:
  - `project.{projectID}.{event}` -> комната `project:{projectID}` (broadcast всем участникам).
  - `auth.session.{userID}.{event}` -> конкретному пользователю (direct message).
- **Протокол:** JSON-сообщения с типами `subscribe`, `unsubscribe`, `event`, `ping`, `pong`.
- **Буфер:** 256 сообщений на клиента; при переполнении сообщения дропаются с логированием.

### 5.2. Outbox Pattern

Обеспечение консистентности между PostgreSQL и MongoDB:

- **Таблица `OutboxEvent`:** `event_type`, `payload` (bytes), `status` (pending/published/failed), `attempts`, `last_error`.
- **Worker:** поллит pending-события каждые 100ms.
- **Публикация:** NATS publish по `event_type`.
- **Retry:** до 10 попыток; при исчерпании статус переходит в `failed`.
- **Индекс:** `(status, created_at)` для эффективной выборки.

### 5.3. Файловое хранилище (SeaweedFS)

S3-совместимое хранилище для файлов:

- **SeaweedFS:** self-hosted, S3-compatible API (заменил MinIO после его архивации в Feb 2026).
- **SDK:** `aws-sdk-go-v2` со стандартным S3 API (UsePathStyle=true для совместимости).
- **Presigned URLs:** загрузка и скачивание без проксирования через бэкенд.
- **Метаданные:** таблица `FileMetadata` в PostgreSQL (filename, content_type, size, s3_key, s3_bucket, entity_type, entity_id, status).
- **Статусы файлов:** `pending` (создан, ожидает загрузки) -> `confirmed` (загружен и привязан) -> `deleted`.

### 5.4. Docker Compose

Среда разработки из 6 сервисов:

| Сервис | Образ | Порт | Назначение |
|--------|-------|------|------------|
| PostgreSQL | postgres:17 | 5432 | Основная БД (пользователи, проекты, задачи, TMS) |
| MongoDB | mongo:8 | 27017 | Документная БД (чаты, Allure-отчёты) |
| Redis | redis:7.4-alpine | 6379 | Кеш, сессии, Magic Link токены |
| NATS | nats:2.11 | 4222, 8222 | Pub/sub, фоновые задачи (JetStream) |
| SeaweedFS | chrislusf/seaweedfs:latest | 9333, 8333 | Файловое хранилище (S3 API) |
| Caddy | caddy:2-alpine | 80, 443 | Reverse proxy, авто-HTTPS, WebSocket |
