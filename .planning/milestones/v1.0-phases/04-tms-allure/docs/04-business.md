# Фаза 4: TMS и Allure -- Бизнес-документация

## 1. Обзор

Фаза 4 реализует модуль управления тестированием (TMS) и интеграцию с Allure для платформы Hub. Модуль позволяет командам создавать и вести тест-кейсы, выполнять ручные и автоматизированные прогоны, импортировать результаты из CI через Allure JSON, отслеживать покрытие требований и формировать отчёты.

TMS глубоко интегрирован с трекером задач (двусторонние связи тест-кейс <-> задача, создание багов из упавших тестов), мессенджером (NATS-события о завершении прогонов для уведомлений в Telegram) и CI-пайплайнами (приём allure-results JSON через REST API).

**Целевая аудитория:** команды разработки и тестирования от 10 до 50 человек.

**Покрытые требования:** TMS-01 -- TMS-06, TMS-08 -- TMS-10, ALLU-01 -- ALLU-03, IMEX-02.

## 2. Тест-кейсы

### 2.1. Два формата тест-кейсов (TMS-01)

Поддерживаются два типа тест-кейсов:

**Классический формат:**
- Каждый тест-кейс состоит из пронумерованных шагов.
- Каждый шаг содержит: действие (action) и ожидаемый результат (expected_result).
- Подходит для ручного тестирования с чётко определёнными сценариями.

**BDD формат (Given/When/Then):**
- Шаги размечены ключевыми словами: Given, When, Then.
- Формат позволяет описывать поведение системы на языке бизнес-требований.
- Используется та же структура шагов, но с полем `keyword`.

**Пользовательское взаимодействие:**
1. Пользователь создаёт тест-кейс, выбирая тип: `classic` или `bdd`.
2. Добавляет шаги с действиями и ожидаемыми результатами (для classic) или с Given/When/Then (для BDD).
3. Указывает приоритет (critical, high, medium, low, trivial) и статус (draft, active, deprecated).
4. Тип можно изменить в любой момент через обновление тест-кейса.

**Бизнес-ценность:** Поддержка обоих форматов позволяет использовать TMS как для традиционного QA, так и для команд, работающих по BDD-методологии.

**API:**
- `POST /api/projects/:projectId/tms/cases` -- создание тест-кейса. Тело включает `case_type` ("classic" | "bdd"), `title`, `steps`, `priority`.
- `PUT /api/projects/:projectId/tms/cases/:caseKey` -- обновление тест-кейса, включая смену типа.

**Компоненты:** handler.go (CreateTestCase, UpdateTestCase), service.go (CreateTestCase, UpdateTestCase), ent/schema/testcase.go.

### 2.2. Структурирование тест-кейсов (TMS-02)

#### Папки и секции

Тест-кейсы организуются в иерархическую структуру папок (TestSuite):
- Папки поддерживают неограниченную вложенность (parent -> children).
- Каждая папка принадлежит проекту.
- Тест-кейсы привязываются к папке через edge `suite`.
- Дерево папок строится в памяти из плоского списка (in-memory tree build).

**API:**
- `POST /api/projects/:projectId/tms/suites` -- создание папки.
- `GET /api/projects/:projectId/tms/suites` -- дерево папок проекта.
- `PUT /api/projects/:projectId/tms/suites/:suiteId` -- обновление.
- `DELETE /api/projects/:projectId/tms/suites/:suiteId` -- удаление.
- `POST /api/projects/:projectId/tms/suites/:suiteId/move` -- перемещение.

#### Теги и компоненты

- **Теги (Labels):** тест-кейсы привязываются к меткам проекта через M2M edge. Единая система с трекером задач.
- **Компоненты:** отдельная сущность Component с CRUD. Тест-кейсы привязываются к компонентам через M2M edge.

**API компонентов:**
- `POST /api/projects/:projectId/tms/components` -- создание.
- `GET /api/projects/:projectId/tms/components` -- список.
- `DELETE /api/projects/:projectId/tms/components/:componentId` -- удаление.

#### Версионирование

Каждое обновление тест-кейса автоматически создаёт версию-снимок (snapshot):
1. При вызове UpdateTestCase сервис сначала сохраняет текущее состояние как TestCaseVersion.
2. Снимок хранится как JSON map -- все поля тест-кейса на момент сохранения.
3. Пользователь может просмотреть историю версий и откатить тест-кейс к любой предыдущей версии.

**Пользовательское взаимодействие:**
1. Пользователь редактирует тест-кейс -- версия создаётся автоматически.
2. На странице тест-кейса отображается список версий с номером, датой и автором.
3. Кнопка "Откатить" восстанавливает тест-кейс из выбранного снимка.

**API:**
- `GET /api/projects/:projectId/tms/cases/:caseKey/versions` -- список версий.
- `POST /api/projects/:projectId/tms/cases/:caseKey/rollback/:versionId` -- откат к версии.

**Бизнес-ценность:** Версионирование защищает от случайных изменений и позволяет отслеживать эволюцию тест-кейсов.

### 2.3. Связь с GitHub (TMS-03)

Тест-кейсы поддерживают привязку к автотестам в репозитории через поле `external_id`:
- Аннотация `@TestCase("HUB-TC-42")` в коде автотеста задаёт связь.
- При импорте результатов Allure матчер ищет тест-кейс по external_id (наивысший приоритет).
- Поля `full_name`, `class_name`, `method_name` используются как fallback-стратегии.

**Пользовательское взаимодействие:**
1. Разработчик добавляет `@TestCase("HUB-TC-42")` в автотест.
2. При прогоне CI результат Allure автоматически привязывается к тест-кейсу.
3. На странице тест-кейса видно: external_id, стратегия последнего матчинга.

**Бизнес-ценность:** Автоматическая связь автотестов с тест-кейсами без ручной настройки. Единое представление ручных и автоматизированных тестов.

### 2.4. Тестовые прогоны (TMS-04)

Прогоны (TestRun) поддерживают три типа:
- **manual** -- ручной прогон, тестировщик выполняет кейсы пошагово.
- **automatic** -- автоматический прогон, результаты приходят из CI через Allure.
- **mixed** -- комбинация ручных и автоматизированных результатов.

**Жизненный цикл прогона:**
```
created -> in_progress -> completed
                       -> aborted
completed -> in_progress (переоткрытие)
```

**Пользовательское взаимодействие:**
1. Пользователь создаёт прогон, указывая название и тип.
2. Добавляет тест-кейсы в прогон (массовое добавление по ID).
3. Назначает тестировщиков (M2M связь через assignees).
4. Запускает прогон (статус -> in_progress).
5. Выполняет тесты пошагово, фиксируя результаты (passed/failed/broken/skipped).
6. Завершает прогон (статус -> completed) -- публикуется NATS-событие.
7. При необходимости переоткрывает завершённый прогон для доработки.

**API:**
- `POST /api/projects/:projectId/tms/runs` -- создание прогона.
- `POST /api/projects/:projectId/tms/runs/:runId/cases` -- добавление тест-кейсов.
- `POST /api/projects/:projectId/tms/runs/:runId/assignees` -- назначение тестировщиков.
- `POST /api/projects/:projectId/tms/runs/:runId/start` -- запуск.
- `POST /api/projects/:projectId/tms/runs/:runId/complete` -- завершение.
- `POST /api/projects/:projectId/tms/runs/:runId/reopen` -- переоткрытие.
- `PUT /api/projects/:projectId/tms/runs/:runId/results/:resultId` -- обновление результата.

**Статистика прогона:** При каждом обновлении результата автоматически пересчитываются счётчики (total, passed, failed, skipped, broken, unknown) через `recomputeRunStats`.

**Бизнес-ценность:** Единый интерфейс для управления ручными и автоматизированными тестами. Назначение тестировщиков обеспечивает распределение нагрузки.

---

### 2.5. Доказательства к результатам (TMS-05)

Каждый результат теста поддерживает прикрепление доказательств:

**Скриншоты:**
- К результату теста можно привязать файлы (скриншоты, логи) через M2M edge `files`.
- Файлы загружаются через модуль Storage (SeaweedFS) и привязываются по ID.

**Комментарии:**
- Каждый результат имеет поле `comment` для текстового описания.
- Для пошагового выполнения: каждый `StepResult` содержит свой `comment` и список `file_ids`.

**Пользовательское взаимодействие:**
1. При выполнении теста тестировщик отмечает статус каждого шага.
2. К каждому шагу можно добавить комментарий и прикрепить скриншоты.
3. К общему результату также можно добавить комментарий.

**API:**
- `PUT /api/projects/:projectId/tms/runs/:runId/results/:resultId` -- обновление с `step_results`, `comment`, `file_ids`.

**Бизнес-ценность:** Документирование результатов тестирования с визуальными доказательствами упрощает анализ дефектов и коммуникацию с разработчиками.

### 2.6. Связь с трекером задач (TMS-06)

#### Двусторонняя привязка

Тест-кейсы и задачи (Issues) связаны двусторонним edge:
- `TestCase.linked_issues` -> Issue (прямая связь).
- `Issue.linked_test_cases` -> TestCase (обратная связь через backref).

**Пользовательское взаимодействие:**
1. На странице тест-кейса пользователь видит список привязанных задач.
2. Можно добавить или удалить привязку к задаче.
3. На странице задачи в трекере видны связанные тест-кейсы.

**API:**
- `POST /api/projects/:projectId/tms/cases/:caseKey/links` -- привязка к задаче.
- `GET /api/projects/:projectId/tms/cases/:caseKey/links` -- список привязанных задач.
- `DELETE /api/projects/:projectId/tms/cases/:caseKey/links/:issueId` -- отвязка.

#### Создание бага из упавшего теста

Тестировщик может создать баг прямо из результата неуспешного теста:
1. Из экрана прогона нажимает "Создать баг" на упавшем тест-кейсе.
2. Сервис создаёт Issue с типом `bug` через общий Ent-клиент (без импорта трекера).
3. Заголовок бага автоматически формируется: "FAILED: {название тест-кейса}".
4. Баг автоматически привязывается к тест-кейсу.

**API:**
- `POST /api/projects/:projectId/tms/runs/:runId/results/:resultId/bug` -- создание бага.

#### Покрытие требований

Отчёт покрытия показывает матрицу трассируемости:
- Для каждой задачи проекта отображаются привязанные тест-кейсы.
- Для каждого тест-кейса показан последний статус выполнения.
- Визуально: раскрываемая таблица с процентами покрытия и цветовыми индикаторами.

**API:**
- `GET /api/projects/:projectId/tms/reports/coverage` -- отчёт покрытия.

**Бизнес-ценность:** Прямая связь тестов с требованиями. Мгновенное создание багов экономит время. Матрица трассируемости показывает, какие требования не покрыты тестами.

### 2.7. Отчёты (TMS-08)

#### Тренды прогонов

Отчёт трендов показывает динамику результатов по прогонам:
- Для последних N прогонов отображается: total, passed, failed, skipped, broken, pass_rate.
- Визуализация: горизонтальные стэковые бары по каждому прогону с процентом прохождения.

**API:**
- `GET /api/projects/:projectId/tms/reports/trends?limit=10` -- тренды.

#### Нестабильные тесты (Flaky)

Анализ нестабильности определяет тесты с непостоянными результатами:
- Для каждого тест-кейса анализируются последние 10 прогонов.
- Тест считается flaky, если статусы менялись (например, passed -> failed -> passed).
- Метрика: вариативность статусов (variance) по последним 10 запускам.

**API:**
- `GET /api/projects/:projectId/tms/reports/flaky` -- список нестабильных тестов.

#### Сравнение прогонов

Сравнение двух прогонов показывает разницу:
- Для каждого тест-кейса, присутствующего в обоих прогонах, отображаются статусы.
- Изменения (passed -> failed, failed -> passed) выделяются цветом.

**API:**
- `GET /api/projects/:projectId/tms/reports/comparison?run1=ID&run2=ID` -- сравнение.

**Бизнес-ценность:** Отчёты уровня Allure TestOps позволяют отслеживать качество продукта, выявлять нестабильные тесты и анализировать регрессии.

### 2.8. Импорт тест-кейсов (TMS-09)

Поддерживаемые форматы импорта:

| Формат | Библиотека | Особенности |
|--------|-----------|-------------|
| CSV | encoding/csv | Автоопределение маппинга по заголовкам |
| JSON | encoding/json | Массив объектов с полями тест-кейса |
| XML | encoding/xml | Корневой элемент `<testcases>`, дочерние `<testcase>` |
| Excel (XLSX) | excelize/v2 | Выбор листа, автоопределение заголовков |

**Автоопределение маппинга полей:**
- Поддерживает русские и английские названия столбцов.
- Примеры: "Title" / "Название", "Steps" / "Шаги", "Priority" / "Приоритет".
- Ручной маппинг передаётся через параметр `mapping` (JSON).

**Валидация:**
- Обязательное поле: `title` (название).
- Допустимые приоритеты: critical, high, medium, low, trivial.
- Ошибки валидации с указанием номера строки.

**Пользовательское взаимодействие:**
1. Пользователь открывает диалог импорта.
2. Перетаскивает файл (drag-and-drop) или выбирает через проводник.
3. Формат определяется автоматически по расширению.
4. Система показывает результат: создано N, пропущено M, ошибок K.

**API:**
- `POST /api/projects/:projectId/tms/import` -- multipart-загрузка файла с полями `file`, `format`, `mapping`.

**Бизнес-ценность:** Миграция тест-кейсов из других TMS (TestRail, TestLink) и документов (Excel) без ручного ввода.

### 2.9. Экспорт (TMS-10)

#### Экспорт тест-кейсов

Все тест-кейсы проекта экспортируются в выбранном формате:

| Формат | Файл | Особенности |
|--------|------|-------------|
| CSV | test-cases.csv | Стандартный CSV с заголовками |
| JSON | test-cases.json | Массив объектов с отступами |
| XML | test-cases.xml | XML с заголовком и корневым элементом |
| Excel | test-cases.xlsx | Жирные заголовки, автоширина, чередующийся цвет строк |

**API:**
- `GET /api/projects/:projectId/tms/export?format=csv` -- экспорт тест-кейсов.

#### Экспорт отчёта прогона

Отчёт прогона экспортируется в PDF:
- Заголовок с названием прогона и датой.
- Таблица статистики: всего, passed, failed, skipped, broken, pass rate.
- Таблица результатов: ключ тест-кейса, название, статус (с цветовой индикацией), время, комментарий.
- Генерация через maroto v2.

**API:**
- `GET /api/projects/:projectId/tms/runs/:runId/export?format=pdf` -- экспорт отчёта.

**Бизнес-ценность:** Экспорт позволяет делиться результатами тестирования с внешними стейкхолдерами и архивировать данные.

### 2.10. Импорт из Excel (IMEX-02)

Импорт тест-кейсов из Excel-файлов (XLSX):
1. Файл читается библиотекой excelize v2.
2. По умолчанию используется первый лист; можно указать имя листа.
3. Первая строка -- заголовки. Маппинг полей определяется автоматически или указывается вручную.
4. Каждая строка создаёт тест-кейс с валидацией.

Маппинг поддерживает двуязычные заголовки: "Title"/"Название", "Description"/"Описание", "Precondition"/"Предусловие", "Steps"/"Шаги", "Priority"/"Приоритет", "Status"/"Статус", "Type"/"Тип".

**Бизнес-ценность:** Excel -- наиболее распространённый формат для документирования тест-кейсов. Автоопределение колонок минимизирует ручную настройку.

## 3. Интеграция с Allure

### 3.1. Загрузка allure-results JSON (ALLU-01)

CI-пайплайн генерирует allure-results JSON. Hub предоставляет API для загрузки результатов:

1. CI запускает тесты и генерирует `allure-results/` директорию.
2. Скрипт или hub-cli собирает JSON-файлы и отправляет `POST /api/projects/:projectId/tms/allure/import`.
3. Парсер Hub читает JSON с защитной стратегией (все поля опциональны, невалидные данные не вызывают падения).
4. Автоматически создаётся прогон типа `automatic` с результатами.

**API:**
- `POST /api/projects/:projectId/tms/allure/import` -- импорт результатов Allure.
- `POST /api/projects/:projectId/tms/runs/:runId/allure` -- импорт в существующий прогон.

**Бизнес-ценность:** Замена Allure TestOps (стоимость $30k/год) собственным парсером. Данные хранятся в своей TMS.

### 3.2. Сопоставление результатов (ALLU-02)

Многостратегийный матчинг связывает результаты Allure с тест-кейсами Hub:

| Приоритет | Стратегия | Как работает |
|-----------|----------|--------------|
| 1 (высший) | Аннотация | Links с type="tms" или Labels "AS_ID"/"tms" -> поиск по external_id |
| 2 | FullName | Полное имя теста (пакет + класс + метод) -> поиск по full_name |
| 3 | Class+Method | Suite label + Name -> поиск по class_name + method_name |
| - | Unmapped | Ни одна стратегия не сработала -- результат помечается как несопоставленный |

**Пользовательское взаимодействие:**
- Несопоставленные результаты отображаются в прогоне с пометкой "unmapped".
- Пользователь может вручную привязать результат к тест-кейсу.

**Бизнес-ценность:** Гибкая стратегия покрывает разные фреймворки тестирования (JUnit, pytest, Jest). Приоритет аннотации гарантирует точное сопоставление.

### 3.3. История и статистика (ALLU-03)

**История прогонов:**
- Все прогоны проекта доступны в хронологическом порядке.
- Для каждого прогона: название, дата, total/passed/failed, pass rate.

**NATS-уведомления:**
- При завершении прогона публикуется событие `tms.testrun.completed`.
- Событие содержит: run_id, project_id, title, статистику (total, passed, failed, skipped, broken).
- Событие может быть перехвачено модулем уведомлений для отправки в Telegram.

**API:**
- `GET /api/projects/:projectId/tms/reports/history` -- история прогонов.

**Бизнес-ценность:** История прогонов с автоматическими уведомлениями позволяет команде отслеживать качество в реальном времени.

## 4. Пользовательские сценарии

### 4.1. Создание и управление тест-кейсами

1. Тестировщик открывает TMS проекта через боковое меню.
2. Создаёт структуру папок (Smoke, Regression, Integration).
3. Создаёт тест-кейсы в нужных папках, выбирая формат (classic/BDD).
4. Добавляет шаги, предусловия, приоритеты.
5. Привязывает компоненты и теги для организации.
6. При редактировании тест-кейса версия создаётся автоматически.
7. При необходимости откатывает к предыдущей версии.

### 4.2. Ручное тестирование

1. Тест-лид создаёт прогон "Regression v2.1".
2. Добавляет тест-кейсы из папки Regression.
3. Назначает тестировщиков.
4. Запускает прогон.
5. Тестировщик открывает прогон, видит назначенные кейсы.
6. Выполняет тесты пошагово, отмечая статус каждого шага.
7. Прикрепляет скриншоты к проблемным шагам.
8. При обнаружении бага -- создаёт баг прямо из результата.
9. Тест-лид завершает прогон, видит итоговую статистику.

### 4.3. CI интеграция с Allure

1. Разработчик добавляет `@TestCase("HUB-TC-42")` в автотесты.
2. CI запускает тесты, генерирует allure-results JSON.
3. Post-step в CI: `curl -X POST .../tms/allure/import -d @results.json`.
4. Hub парсит JSON, создаёт прогон, матчит результаты с тест-кейсами.
5. NATS-событие `tms.testrun.completed` уходит в систему уведомлений.
6. Команда видит результаты в TMS: проход, падения, нестабильные тесты.

### 4.4. Отчёты и анализ

1. QA-лид открывает раздел отчётов.
2. Просматривает тренды: процент прохождения растёт или падает.
3. Анализирует flaky-тесты: какие тесты нестабильны, нужно ли их чинить.
4. Сравнивает два прогона: что починили, что сломали.
5. Генерирует матрицу покрытия: какие задачи покрыты тестами.
6. Экспортирует отчёт прогона в PDF для стейкхолдеров.

### 4.5. Импорт/экспорт

1. Команда мигрирует с TestRail: экспортирует тест-кейсы в CSV.
2. Загружает CSV через диалог импорта в Hub TMS.
3. Маппинг определяется автоматически по заголовкам.
4. Результат: 150 создано, 3 пропущено (без названия), 0 ошибок.
5. При необходимости экспортирует тест-кейсы в Excel для внешнего аудита.

## 5. Интеграционные точки

### 5.1. TMS <-> Трекер

- **Edge:** TestCase.linked_issues <-> Issue.linked_test_cases (двусторонний Ent edge).
- **Создание бага:** TMSService.CreateBugFromFailedResult создаёт Issue через общий Ent-клиент (без импорта tracker).
- **NATS события:** `tms.testcase.linked`, `tms.coverage.updated` -- для обновления UI трекера.

### 5.2. TMS <-> Мессенджер

- **NATS события:** `tms.testrun.completed` содержит статистику прогона.
- **Назначение:** Модуль уведомлений (Phase 6) подписывается на событие и отправляет сообщение в Telegram / канал мессенджера.
- **Формат:** "Прогон 'Regression v2.1' завершён: 45/50 passed (90%)".

### 5.3. TMS <-> CI (Allure)

- **API:** POST-эндпоинт для приёма allure-results JSON.
- **Хранение:** Сырой JSON сохраняется в MongoDB (коллекция `allure_results`) для аудита.
- **Обработка:** Парсинг -> матчинг -> создание результатов -> пересчёт статистики -> NATS-событие.

## 6. Права доступа (RBAC)

| Действие | Требуемое разрешение |
|----------|---------------------|
| Просмотр тест-кейсов и прогонов | PermProjectView |
| Создание тест-кейса | PermTestCaseCreate |
| Редактирование/удаление тест-кейса | PermTestCaseEdit |
| Создание прогона | PermTestRunCreate |
| Выполнение теста (обновление результата) | PermTestRunExecute |
| Импорт Allure / тест-кейсов | PermTestCaseCreate |
| Экспорт | PermProjectView |

Разрешения проверяются через RBAC middleware на уровне маршрутов (handler.go RegisterRoutes).
