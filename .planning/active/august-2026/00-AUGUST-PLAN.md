## Трек 1 — Тестовый фреймворк на Python

**Документ:** [`audits/planning-audit-2026-07/02-TEST-FRAMEWORK-MIGRATION.md`](../../audits/planning-audit-2026-07/02-TEST-FRAMEWORK-MIGRATION.md)
**Фазы:** 128–136

Фреймворк выносится в корневую папку и переписывается целиком на Python:
**pytest + Playwright + Locust**. Каталоги `testframework/` в `backend/` и
`frontend/` ликвидируются, юнит-тесты возвращаются **к коду** и пишутся на языке
своего слоя разработчиками, проверяются тестировщиками.

| Фаза | Что |
|---|---|
| 128 | Каркас Python-проекта `testframework/` |
| 129–131 | Перенос E2E на Playwright Python (20 сценариев) |
| 132 | Go-юниты возвращаются в `backend/internal/**` |
| 133 | Фронт-юниты в `frontend/src/**` — **сейчас их ноль** |
| 134 | Интеграционные на Python |
| 135 | Нагрузочные на Locust — новый слой, сейчас отсутствует |
| 136 | CI и удаление старого фреймворка |

**Исходные замеры (2026-07-27):** 515 Go-файлов в `backend/testframework/`,
0 юнитов рядом с кодом, 0 юнитов во фронте, 20 `*.spec.ts` на Playwright TS,
покрытие 81.9%.

## Трек 2 — Вынос монолита в микросервисы

**Документ:** [`01-MICROSERVICES-SPLIT.md`](01-MICROSERVICES-SPLIT.md)
**Основание:** [`../ab-microservices/PLAN-team-lead-opus.md`](../../decisions/ab-microservices/PLAN-team-lead-opus.md)

У каждого сервиса — **свой бэкенд и свой фронтенд**. Раскладка по контейнерам и
схема БД — **решение архитектора** (§8 документа).

**Swagger остаётся единый** — не дробится на изолированные спеки, а делится на
**зоны по сервисам** (Identity, Tracker, Realtime, Notification, AI & Search,
Business, Integrations, Platform). Требование к детализации жёсткое: у каждой
ручки полные схемы запроса и ответа, все коды ошибок, единая форма `AppError`,
примеры, пагинация, требуемая роль. Ручка без описанной схемы ответа не проходит
ревью, расхождение спеки с реализацией валит CI.

34 домена группируются в **8 bounded contexts**: notification, ai, realtime,
tracker, identity, business, integrations, platform.

| Этап | Что |
|---|---|
| Э1 | Modular Monolith Hardening — запрет кросс-импортов |
| Э2 | Schema-per-service внутри текущего PostgreSQL |
| Э3 | `hub-shell` + Module Federation, первый фронт-модуль |
| Э4 | Пилот `hub-notification` — вертикальный срез целиком |
| **Э5** | **GATE Go/No-Go по результату пилота** |
| Э6–Э7 | `hub-ai`, затем `hub-realtime` |

## Трек 3 — доработка модулей до продукта

**Документ:** [`03-MODULES-ROADMAP.md`](03-MODULES-ROADMAP.md)

Шесть модулей помечены «MVP», два заявлены и не существуют в коде.
Трек снимает пометку MVP по единому критерию: покрытие ≥82% пакетным
замером, все FR закрыты или вынесены за скоуп, корзина и оптимистичная
блокировка там, где требует спека, ноль находок P0/P1 в свежем аудите.

| Группа | Модули | Работы |
|--------|--------|--------|
| A стабильные | tracker, sprint, messenger, tms, calls, dashboards, search, notifications | **нет**, только не просаживать гейт |
| B из MVP в продукт | calendar, intranet, accounting, crm, hr, bases | основной объём |
| C новые | wiki, sso, MCP для AI | заблокированы решениями владельца |

Начинать с календаря: шесть тестов на шесть файлов кода — вдвое хуже
соседей по группе.

Стартует **после** треков 1 и 2: дорабатывать модули значит писать
много тестов, а писать их в фреймворке, который переезжает на Python,
— работа дважды.

## Жёсткая зависимость между треками

```
Трек 1 (фазы 128-136)  ──────►  Трек 2 (Э1...)
                 фаза 133 обязательна
```

Во фронте сейчас **ноль юнит-тестов**. Резать единый SPA на микрофронтенды без
тестов — гарантированные регрессии без способа их заметить. Фаза 133 закрывает
это до Э3.

Аналогично по бэкенду: coverage baseline снят 2026-07-27 (81.9%), и после
переноса 515 файлов его надо сверить — иначе потеря покрытия при миграции
пройдёт незамеченной.
