## 1. Целевая форма сервиса

Требование заказчика: у каждой единицы — **свой бэкенд, свой фронтенд, свой Swagger**.

**Число контейнеров и схема БД — решение архитектора, не заказчика.** Ниже —
рабочая гипотеза для оценки объёма, а не утверждённая цифра. Финальную раскладку
определяет архитектор в ответах на §8.

```
hub-<сервис>/
    backend/          Go, свой go.mod, свои роуты
    frontend/         React-модуль, собирается независимо
    swagger/          OpenAPI-спека сервиса, своя /docs-ручка
    deploy/           Dockerfile ×2 + compose-фрагмент
```

Рабочая гипотеза раскладки (архитектор подтверждает или меняет):

| Контейнер | Назначение | Обязателен? |
|---|---|---|
| `<сервис>-api` | Go-бэкенд + отдача собственного Swagger UI | да |
| `<сервис>-web` | Собранный фронт-модуль (статика за Caddy) | да |
| `<сервис>-db` | Своя БД — только при варианте C (физически отдельная) | **решает архитектор** |

При schema-per-service своей БД у сервиса нет и он укладывается в два контейнера.
Третий появляется только там, где архитектор признает профиль нагрузки отличным
от остальных.

## 2. Сколько сервисов — группировка вместо дробления

В `backend/internal/` **34 домена**. Один сервис на домен = 68–102 контейнера,
что операционно неподъёмно для текущей команды.

Поэтому домены собираются в **bounded contexts** — 8 сервисов вместо 34:

| # | Сервис | Домены внутри | БД | Приоритет выноса |
|---|---|---|---|---|
| 1 | **hub-notification** | notification, mail | schema | **1-й, пилот** — почти не связан |
| 2 | **hub-ai** | ai, search | schema + Meili | 2-й |
| 3 | **hub-realtime** | ws, messenger, calls | schema + **Mongo** (уже отдельная) | 3-й, самый нагруженный |
| 4 | **hub-tracker** | tracker, sprint, project, tms | schema | 4-й, ядро |
| 5 | **hub-identity** | auth, rbac, audit | schema | 5-й, критичен — выносить осторожно |
| 6 | **hub-business** | crm, hr, accounting, calendar, intranet | schema | 6-й |
| 7 | **hub-integrations** | github, gitlab, integrations/onec, imex, marketplace, webhooks | schema | 7-й |
| 8 | **hub-platform** | apigateway, storage, backup, status, dashboard, dev | schema | остаётся ядром/edge |

`platform/` (общий код: errors, nats, outbox, observability, crypto) —
не сервис, а **общая библиотека**, публикуемая как внутренний Go-модуль.

**Итого контейнеров:** 8 API + 8 web + 1–3 отдельных БД ≈ **17–19**, а не 100.

## 3. База данных — решение архитектора

Вопрос закрыт в [`PLAN-team-lead-opus.md §2`](../../decisions/ab-microservices/PLAN-team-lead-opus.md).
Краткая выжимка, чтобы не расходиться:

| Вариант | Вердикт |
|---|---|
| A. Общая БД, общие таблицы | ❌ **Запрещено** — распределённый монолит, худший из миров |
| B. **Schema-per-service** (один PG-кластер, своя схема, кросс-доступ запрещён) | ✅ **Первый шаг** |
| C. Database-per-service (физически раздельные) | ✅ Точечно — messenger→Mongo, search→Meili, calls |
| D. CQRS + проекции через события | ✅ Целевое состояние для «нужен чужой домен на чтение» |

**Правило data ownership:** ни один сервис не делает SQL/Ent-запрос в чужие таблицы.
Только через gRPC или через события.

## 4. Фронтенд — чего нет в существующем плане

Сейчас фронт — **единый SPA** (React + TanStack Router, `frontend/src/modules/*`).
Требование «свой фронт у каждого сервиса» означает переход на **микрофронтенды**.

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| **Module Federation** (Vite) | Независимый деплой, общий рантайм, шаринг зависимостей | Сложность сборки, версионирование общих либ | ✅ **Рекомендуется** |
| Отдельные SPA + маршрутизация на Caddy | Максимальная независимость | Перезагрузка страницы между модулями, дублирование бандла | ⚠️ Запасной |
| iframe-композиция | Полная изоляция | Плохой UX, боль с авторизацией и высотой | ❌ |

**Что остаётся общим (shell):** авторизация, дизайн-система, layout, сайдбар,
i18n, WS-соединение. Выносится в `hub-shell` — хост-приложение.

**Риск:** сейчас юнит-тестов во фронте `frontend/src/**/*.test.ts` — **ноль**
(замер 2026-07-27). Резать SPA без тестов на модули опасно. Поэтому §6 ставит
жёсткую зависимость от миграции тестфреймворка.

## 5. Swagger на сервис

Сейчас Swagger генерируется на весь монолит (`backend/docs/`).

**Решение заказчика: единый общий Swagger сохраняется.** Он не дробится на
изолированные спеки — вместо этого делится **на зоны по сервисам**, чтобы всё
логически связанное лежало в одной группе.

### 5.1 Структура

```
/docs                          ← одна точка входа, весь API целиком
    ├── Identity        (auth, rbac, audit)
    ├── Tracker         (tracker, sprint, project, tms)
    ├── Realtime        (ws, messenger, calls)
    ├── Notification    (notification, mail)
    ├── AI & Search     (ai, search)
    ├── Business        (crm, hr, accounting, calendar, intranet)
    ├── Integrations    (github, gitlab, onec, imex, marketplace)
    └── Platform        (apigateway, storage, backup, status, dashboard)
```

Группировка — через `@Tag` с префиксом сервиса. Каждая зона имеет собственное
описание: назначение сервиса, владелец данных, базовый путь.

Дополнительно у каждого сервиса остаётся **свой `/docs`** со своей частью —
для команды, которая работает только с ним. Общий — источник правды и точка
входа для интеграторов; сервисный — подмножество, генерируемое из тех же
аннотаций. Расхождение между ними невозможно по построению.

### 5.2 Требование к детализации

Ориентир заказчика — Swagger, в котором **всё расписано и подписано**: схемы,
разделение по зонам, примеры, и ответы ручек проработаны **по корнер-кейсам и
эдж-кейсам**, а не только happy path.

Для **каждой** ручки обязательно:

| Элемент | Требование |
|---|---|
| Схема запроса | все поля, типы, обязательность, границы, формат |
| Схема ответа 200/201 | полная модель, никаких `object` без описания |
| Коды ошибок | 400 / 401 / 403 / 404 / 409 / 422 — каждый со своим смыслом и **своим условием** |
| Форма ошибки | единая `AppError`: `code`, `message`, `request_id` |
| Примеры | запрос и ответ на **каждый** значимый исход, не один на ручку |
| Пагинация | параметры, дефолты, верхний предел, поведение на границе |
| Авторизация | требуемая роль и скоуп ресурса |

### Корнер- и эдж-кейсы — обязательная часть описания

Недостаточно перечислить коды. Для каждого должно быть сказано **когда именно**
он возвращается. Минимальный набор вопросов, на которые спека обязана отвечать:

| Класс | Что должно быть описано |
|---|---|
| Пустой результат | `200` с пустым списком или `404` — и почему именно так |
| Чужой ресурс | `403` или `404` — маскируем ли существование объекта |
| Конкурентная правка | `409` по optimistic lock `version`, что делать клиенту |
| Повторный вызов | идемпотентна ли ручка; повтор оплаты/отправки/импорта |
| Границы пагинации | `limit=0`, `limit=-1`, превышение максимума, курсор в конце |
| Мягко удалённый объект | виден ли, `404` или `410`, восстановим ли |
| Частичный успех | импорт с ошибками в части строк — код и форма отчёта |
| Валидация | `400` (формат) против `422` (семантика) — граница между ними |
| Лимиты | rate limit `429`, размер файла `413` — пороги в описании |
| Внешняя зависимость | недоступен S3 / LiveKit / Resend — `502`/`503` и деградация |

Источник материала — `Edge-cases`-секции в `docs/vision_and_scope.md`: они уже
написаны для большинства модулей, но в Swagger не перенесены. Эта работа —
в основном перенос и сверка, а не сочинение с нуля.

**Известное расхождение к закрытию:** ТЗ описывает форму ошибки как
`{"error", "request_id"}`, фактически отдаётся `code` + `message` + `request_id`.

Текущее состояние по прошлому аудиту: форма ошибки в ТЗ описана как
`{"error", "request_id"}`, а фактически отдаётся `code` + `message` +
`request_id`. Расхождение закрывается в рамках этой работы.

### 5.3 Контроль

- Спека — источник правды; расхождение с реализацией **валит CI**
- Ручка без описанной схемы ответа не проходит ревью
- Контрактные тесты гоняются против общей спеки, а не против кода

                                      всё общение через интерфейсы и события
  Э2. Схемы БД по сервисам            schema-per-service внутри текущего PG,
                                      отдельные роли и grants, кросс-доступ закрыт
  Э3. hub-shell + Module Federation    каркас микрофронтендов, один модуль вынесен
                                      **BLOCKED until phase 133 VERIFIED** (TASK-005)
  Э4. Пилот hub-notification           полный вертикальный срез: бэк + фронт +
                                      swagger + контейнеры. Strangler Fig.
  Э5. GATE Go/No-Go                    решение по результату пилота

**Э5 — обязательные врата.** Если пилот показал, что операционная сложность
не окупается, остановиться на укреплённом монолите со schema-per-service:
существующий план прямо отмечает, что так достигается 80% ценности без разнесения
по процессам.

## 7. Честный флаг

`PLAN-team-lead-opus.md §0` рекомендует **не начинать split сейчас**, а
`EXPANSION-ANALYSIS-2026-07-02.md` помечает микросервисы как **F2 / P3 / v4.5,
«только по нагрузке»**.

Заказчик запросил план на август — план дан. Но зафиксировано: решение принимается
вопреки предыдущей рекомендации архитектора, и Э5 существует именно затем, чтобы
это решение можно было пересмотреть по факту пилота, а не по ожиданиям.

**Что стоит проверить до Э1:** есть ли реальная нагрузка, которая требует
независимого масштабирования. Если нет — Э1 и Э2 (укрепление границ +
schema-per-service) дают почти всю пользу и остаются полезными в любом случае.

5. **Фронт:** Module Federation, или отдельные SPA с маршрутизацией на edge?
6. **Identity:** `hub-identity` выносить вообще, или auth остаётся в ядре навсегда?
7. **Оркестрация:** K3s сразу или docker compose до GATE Э5?
