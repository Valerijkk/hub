# tf-cases — проектирование тест-кейсов

## Когда запускать

- Есть требование, спека или описание ручки — нужен набор кейсов
- Готовится ручное тестирование либо будущая автоматизация
- Надо оценить, сколько работы в покрытии, до написания кода

**Не для этого:** сразу писать автотесты — `tf-cover` (он вызывает этот
шаг внутри себя). Проверить готовые кейсы против документации —
`tf-verify`.

## Вход

Обязательно фиксируется **источник** каждого ожидания: путь к документу,
раздел, версия. Кейс без источника не трассируется — при изменении
требования никто не узнает, что его пора менять.

### Откуда берутся ожидания и что сильнее

| Источник | Что даёт | Сила |
|----------|----------|------|
| Бизнес-документация: спека, требования, описание процесса | Что система **обязана** делать | Высшая: расхождение с ней — дефект продукта |
| Контракт: схема API, типы, миграция | Форма и границы данных | Высокая, но описывает форму, а не смысл |
| Контекст от человека: «здесь важнее всего…», «этим пользуются так» | Риск и приоритет | Задаёт, что проверять в первую очередь |
| Код продукта | Как сделано сейчас | **Не источник ожиданий** |

Последняя строка — жёсткая. Кейс, выведенный из кода, проверяет, что код
делает, а не что он должен делать: баг, живущий в коде, становится
эталоном и закрепляется тестом навсегда.

**Контекст от человека не заменяет документацию, но меняет приоритеты.**
«Оплата важнее профиля» не говорит, каким должно быть поведение, — оно
берётся из спеки. Зато говорит, где сначала разворачивать углы и негатив,
а где хватит основного пути.

Расхождение бизнес-документации с контрактом — **стоп-условие**, а не
повод выбрать удобное. Выбранная агентом трактовка станет каноном,
которого никто не утверждал.

### Правила фреймворка — раньше общих практик

Как именно оформляется кейс — формат ID, уровни, обязательные поля,
конвенция имён — берётся **из профиля проекта**, а не из этого пакета.
Общие практики применяются там, где профиль молчит.

Порядок: решения команды → факты профиля → практики пакета → общие
представления. Полная лестница —
[`standards/README.md`](../standards/README.md); здесь она не
пересказывается.

Причина такого порядка: общие практики модель знает и так. Чего она не
знает — как принято здесь, и именно в этом расхождении рождается набор,
который формально правильный и на ревью разворачивается целиком.

## Шаги
### 1. Разбить на атомарные требования

Одно требование — одно проверяемое утверждение. Формулировка «система
должна корректно обрабатывать заказы» не атомарна: непонятно, что
считать корректным.

```
R1  Заказ с суммой в допустимом диапазоне создаётся со статусом «новый»
R2  Заказ с суммой выше лимита отклоняется с указанием лимита
R3  Повторный заказ с тем же ключом идемпотентности не создаёт второй
```

Каждое — с дословной цитатой и путём. Неоднозначное требование
фиксируется вопросом владельцу, а не догадкой.

### 2. Применить техники тест-дизайна

Не «придумать кейсы», а пройти по техникам — тогда пропуск виден:

| Техника | Когда применима | Что даёт |
|---|---|---|
| Классы эквивалентности | Есть диапазоны или категории входа | По одному представителю на класс вместо перебора |
| Граничные значения | Есть числовой или размерный предел | Обе стороны каждой границы плюс сама граница |
| Таблица решений | Несколько условий влияют на результат совместно | Комбинации, о которых забывают |
| Переходы состояний | У объекта есть жизненный цикл | Недопустимые переходы, которые никто не проверяет |
| Попарное тестирование | Много независимых параметров | Сокращает перебор, сохраняя покрытие пар |

Техника, признанная неприменимой, помечается с причиной. Молчание
неотличимо от забывчивости.

### 3. Развернуть обязательные классы

По [`rules/20`](../standards/rules/20-test-quality.md) и
[`standards/practices/negative-cases.md`](../standards/practices/negative-cases.md):
валидация, авторизация и denial, состояние (несуществующее и удалённое —
разные случаи), идемпотентность, ограничения, границы.

Код, работающий с вводом, файлами, диском или внешними программами,
разворачивается по двенадцати классам вместо шести — там же.

Неприменимый класс — строка `N/A: причина`, не пропуск.

### 4. Найти углы — сочетания предельных условий

Шаг отдельный, потому что углы **не выводятся из границ перебором**.
Граница проверяет один предел; угол — совпадение двух и более. Разбор
зон — [`standards/code/test-design.md`](../standards/code/test-design.md).

Вопрос, которым они находятся:

```
Какие два условия здесь могут совпасть — во времени или в данных?
```

Четыре источника совпадений, где углы живут чаще всего:

| Где искать | Пример совпадения |
|------------|-------------------|
| Предел и предел | Максимальная сумма **и** последний остаток на складе |
| Предел и время | Истечение срока **ровно** в момент операции; полночь, смена суток, переход тарифа |
| Предел и конкурентность | Два запроса на последний экземпляр одновременно |
| Предел и отказ | Внешний сервис отвечает ошибкой **на границе** ретрая |

**Углы берутся по риску, а не все.** Их немного — обычно три-четыре пары
на ручку, — но каждый дорог в написании и в поддержке. Правило отбора:

```
берём      совпадение даёт потерю денег, данных или доступ мимо правил
не берём   совпадение даёт неудобное сообщение об ошибке
```

Отобранный угол получает пометку `угол` и краткую запись, **какие именно**
условия совпали. Без этой записи через месяц кейс выглядит дублем
граничного и его удаляют как лишний.

Углов не нашлось — так и пишется: `углы: нет, условия независимы`.
Пустота здесь неотличима от невнимательности, а её цена — тот самый класс
дефектов, который проходит все зелёные тесты границ.

### 5. Оформить кейс

```
ID:              по конвенции профиля
Требование:      R1 (цитата + путь)
Приоритет:       P0 | P1 | P2
Уровень:         unit | integration | api | e2e
Предусловия:     что должно быть верно до начала
Данные:          что подаём, с обоснованием выбора значения
Шаги:            что делаем
Ожидание:        ОДИН наблюдаемый результат
```

Ожидание одно. Два ожидания в кейсе — два кейса: иначе при падении
неясно, что именно не сработало.

### 6. Свести матрицу и вычесть дубли

Матрица `требование × кейс × класс покрытия`. Дубль — кейс с тем же
входом, состоянием и ожиданием, что у существующего. Разные ID и разные
формулировки дублем быть не мешают.

### 7. Разметить исполнимость

| Метка | Смысл |
|---|---|
| автоматизируемый | Можно писать автотест |
| ручной | Автоматизация нецелесообразна, причина указана |
| заблокирован | Нужен доступ, стенд или данные, которых нет |

**Заблокированные не считаются покрытием.** Кейс, который невозможно
выполнить, покрывает требование только на бумаге.

## Формат отчёта
```
ТРЕБОВАНИЙ: <n> атомарных, источник: <путь, раздел, версия>
КОНТЕКСТ ОТ ЧЕЛОВЕКА: <что названо важным> | не задан
КЕЙСОВ: <n>, из них P0 <n>
ЗОНЫ: основной путь <n>, границы <n>, углы <n>, отказы <n>
ТЕХНИКИ: <применённые> / <неприменимые с причиной>
УГЛЫ: <какие условия совпали в каждом> | нет, условия независимы
МАТРИЦА: <n> ячеек, покрыто <n>, N/A <n>, вопросов <n>
ИСПОЛНИМОСТЬ: автоматизируемых <n>, ручных <n>, заблокированных <n>
GAP: <требование без единого кейса, если есть>
ВОПРОСЫ: <неоднозначности требований>
```

## Стоп-условия

- Требование неоднозначно и не разрешается доступными источниками
- Требования противоречат друг другу
- Источник требования не найден — кейсы без источника не проектируются

## Границы
- Не пишу код автотестов — это `tf-cover`
- Не придумываю требования за владельца
- Не считаю заблокированные кейсы покрытием
- Не оформляю кейс с двумя ожиданиями

## Критерий готовности

- [ ] Ожидания взяты из документации, а не из кода продукта
- [ ] Формат кейса взят из профиля проекта, общие практики — где профиль молчит
- [ ] Требования разбиты на атомарные, каждое с цитатой, путём и версией
- [ ] Контекст человека учтён в приоритетах либо отмечено, что он не задан
- [ ] По каждой технике вынесено решение: применена либо `N/A: причина`
- [ ] Обязательные классы развёрнуты либо помечены `N/A: причина`
- [ ] Углы найдены и отобраны по риску либо записано «условия независимы»
- [ ] У каждого кейса ровно одно наблюдаемое ожидание
- [ ] Матрица сведена, дубли вычтены
- [ ] Исполнимость размечена, заблокированные не засчитаны покрытием
- [ ] Неоднозначности вынесены в вопросы, а не разрешены догадкой

## Вердикт

| Вердикт | Условие |
|---------|---------|
| PASS | Все требования покрыты кейсами либо имеют явную `N/A: причина` |
| PARTIAL | Часть требований ждёт ответа владельца; вопросы перечислены |
| FAIL | Есть требование без единого кейса и без причины |
| NOT_RUN | Источник требований не найден — проектирование не начиналось |

## Что дальше

`tf-verify` — гейт кейсов против документации. Не пройден — код не пишется
([цикл](../workflows/playbooks/phase-loop.md), ворота шага 2).

`tf-cover` — реализация автоматизируемых кейсов, после гейта.
