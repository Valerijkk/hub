# tf-cases — проектирование тест-кейсов

## Когда

- Есть требование, спека или описание ручки — нужен набор кейсов
- Готовится ручное тестирование либо будущая автоматизация
- Надо оценить, сколько работы в покрытии, до написания кода

**Не для этого:** сразу писать автотесты — `tf-cover` (он вызывает этот
шаг внутри себя). Проверить готовые кейсы против документации —
`tf-verify`.

## Вход

Требование в любом виде. Обязательно фиксируется **источник**: путь к
документу, раздел, версия. Кейс без источника не трассируется, а значит
при изменении требования никто не узнает, что его пора менять.

## Процедура

### 1. Разбить на атомарные требования

Одно требование — одно проверяемое утверждение. Формулировка «система
должна корректно обрабатывать заказы» не атомарна: непонятно, что
считать корректным.

```
R1  Заказ с суммой в допустимом диапазоне создаётся со статусом «новый»
R2  Заказ с суммой выше лимита отклоняется с указанием лимита
R3  Повторный заказ с тем же ключом идемпотентности не создаёт второй
```

Каждое — с дословной цитатой и путём. Неоднозначное требование
фиксируется вопросом владельцу, а не догадкой.

### 2. Применить техники тест-дизайна

Не «придумать кейсы», а пройти по техникам — тогда пропуск виден:

| Техника | Когда применима | Что даёт |
|---|---|---|
| Классы эквивалентности | Есть диапазоны или категории входа | По одному представителю на класс вместо перебора |
| Граничные значения | Есть числовой или размерный предел | Обе стороны каждой границы плюс сама граница |
| Таблица решений | Несколько условий влияют на результат совместно | Комбинации, о которых забывают |
| Переходы состояний | У объекта есть жизненный цикл | Недопустимые переходы, которые никто не проверяет |
| Попарное тестирование | Много независимых параметров | Сокращает перебор, сохраняя покрытие пар |

Техника, признанная неприменимой, помечается с причиной. Молчание
неотличимо от забывчивости.

### 3. Развернуть обязательные классы

По [`rules/20`](../../rules/20-test-quality.md) и
[`practices/negative-cases.md`](../../practices/negative-cases.md):
валидация, авторизация и denial, состояние (несуществующее и удалённое —
разные случаи), идемпотентность, ограничения, границы.

Неприменимый класс — строка `N/A: причина`, не пропуск.

### 4. Оформить кейс

```
ID:              по конвенции профиля
Требование:      R1 (цитата + путь)
Приоритет:       P0 | P1 | P2
Уровень:         unit | integration | api | e2e
Предусловия:     что должно быть верно до начала
Данные:          что подаём, с обоснованием выбора значения
Шаги:            что делаем
Ожидание:        ОДИН наблюдаемый результат
```

Ожидание одно. Два ожидания в кейсе — два кейса: иначе при падении
неясно, что именно не сработало.

### 5. Свести матрицу и вычесть дубли

Матрица `требование × кейс × класс покрытия`. Дубль — кейс с тем же
входом, состоянием и ожиданием, что у существующего. Разные ID и разные
формулировки дублем быть не мешают.

### 6. Разметить исполнимость

| Метка | Смысл |
|---|---|
| автоматизируемый | Можно писать автотест |
| ручной | Автоматизация нецелесообразна, причина указана |
| заблокирован | Нужен доступ, стенд или данные, которых нет |

**Заблокированные не считаются покрытием.** Кейс, который невозможно
выполнить, покрывает требование только на бумаге.

## Отчёт

```
ТРЕБОВАНИЙ: <n> атомарных, источник: <путь>
КЕЙСОВ: <n>, из них P0 <n>
ТЕХНИКИ: <применённые> / <неприменимые с причиной>
МАТРИЦА: <n> ячеек, покрыто <n>, N/A <n>, вопросов <n>
ИСПОЛНИМОСТЬ: автоматизируемых <n>, ручных <n>, заблокированных <n>
GAP: <требование без единого кейса, если есть>
ВОПРОСЫ: <неоднозначности требований>
```

## Стоп-условия

- Требование неоднозначно и не разрешается доступными источниками
- Требования противоречат друг другу
- Источник требования не найден — кейсы без источника не проектируются

## Что НЕ делаю

- Не пишу код автотестов — это `tf-cover`
- Не придумываю требования за владельца
- Не считаю заблокированные кейсы покрытием
- Не оформляю кейс с двумя ожиданиями

## Что дальше

`tf-verify` — гейт кейсов против документации.
`tf-cover` — реализация автоматизируемых кейсов.
