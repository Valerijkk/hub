# SOLID в автотестах — вопросы, не scorecard

Пять принципов разобраны как design questions для code review. Они не требуют
пяти интерфейсов, класса на каждую ветку или абстракции вокруг любого клиента.
Completion bar — локальность и безопасность изменения, не SOLID score.

## S — единственная ответственность

Плохо:

```python
class OrderHelper:
    def create_order(self): ...        # создаёт
    def check_order(self): ...         # проверяет
    def cleanup_orders(self): ...      # убирает
    def send_order_report(self): ...   # отчитывается
```

Хорошо: фабрика создаёт, тест проверяет, фикстура убирает, репортер
отчитывается.

**Что сломается:** у класса четыре причины измениться. Правка отчётности
задевает создание заказов, и падает то, что не трогали.

Признак: в имени класса есть «и» либо суффикс `Helper`, `Manager`,
`Utils` — они обычно означают «сюда складываем всё подряд».

## O — открыт для расширения, закрыт для изменения

Плохо:

```python
def create_notification(kind):
    if kind == "email": ...
    elif kind == "sms": ...
    elif kind == "push": ...      # каждый новый канал правит эту функцию
```

Хорошо:

```python
NOTIFIERS = {"email": EmailNotifier, "sms": SmsNotifier}

def create_notification(kind):
    return NOTIFIERS[kind]()
```

**Что сломается:** ветвление растёт, и каждая правка рискует задеть
существующие ветки. В тестах это особенно неприятно: сломается канал,
который никто не менял.

Оговорка: три ветки — ещё не повод для абстракции. Правило действует,
когда ветки **добавляются регулярно**.

## L — подстановка не ломает поведение

Плохо:

```python
class BasePage:
    def open(self, url): ...

class ModalPage(BasePage):
    def open(self, url):
        raise NotImplementedError("модалка не открывается по URL")
```

Хорошо: модалка не наследует страницу — у неё другой контракт.

**Что сломается:** код, работающий с `BasePage`, падает на конкретном
наследнике. Тип обещает одно, объект делает другое, и обнаруживается это
в рантайме.

Признак нарушения: наследник, выбрасывающий «не поддерживается», или
сужающий допустимые аргументы родителя.

## I — интерфейс не заставляет реализовывать лишнее

Плохо:

```python
class Client(Protocol):
    def get(self): ...
    def post(self): ...
    def upload_file(self): ...
    def subscribe_to_events(self): ...
```

Хорошо: три узких протокола — чтение, запись, подписка. Клиент реализует
те, что ему нужны.

**Что сломается:** клиент очереди вынужден реализовать `upload_file`
заглушкой. Заглушка однажды будет вызвана, и падение окажется
непонятным.

## D — зависимость от абстракции, а не от конкретики

Плохо:

```python
class OrderScenario:
    def __init__(self):
        self.api = ApiClient("https://staging.example.com")  # создаёт сам
```

Хорошо:

```python
class OrderScenario:
    def __init__(self, api: Client):
        self.api = api
```

**Что сломается:** сценарий нельзя прогнать против другого стенда и
нельзя подменить клиент на стаб. Зависимость, созданная внутри, не
управляется снаружи — а тест только этим и живёт.

Это же принцип за фикстурами: они передают готовые зависимости, а не
дают объекту создавать их самому.

## Где SOLID вредит тестам

Принципы созданы для кода, который живёт и меняется годами. **Тело
теста** — не тот случай: его читают чаще, чем меняют, и прямолинейность
там дороже абстракции.

```
код фреймворка   SOLID задаёт вопросы о change/dependency/contract
тело теста       читаемость важнее принципов
```

Тест из трёх строк с повтором понятнее теста из одной строки, за которой
стоит иерархия из трёх классов.

## Проверка себя

Возьми файл фреймворка и спроси: **какие изменения должны происходить вместе,
а какие независимы**. Несколько методов или операций не нарушают SRP, если они
поддерживают один cohesive contract. Разделение оправдано только когда уменьшает
coupling/change radius и не ухудшает локальное понимание.
