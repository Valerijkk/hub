# Шаги и читаемость отчёта

Reporting step не равен Page Object action и не равен scenario flow. Action
выполняет mechanics, flow связывает действия, step наблюдаемо подписывает
отрезок, test формулирует business oracle. Step не создаёт новый слой только
ради красивого отчёта.

Шаг превращает лог прогона в историю, которую можно прочитать, не открывая
код. Плохая разбивка делает обратное — прячет то, что искали.

## 1. Шаг описывает действие пользователя, не вызов функции

Плохо:

```python
with step("api.post"):
    ...
with step("json parse"):
    ...
```

Хорошо:

```python
with step("Создать заказ на 1500 рублей"):
    ...
with step("Оплатить заказ картой"):
    ...
```

**Что сломается:** отчёт повторяет код. Человек, разбирающий падение в CI,
получает те же строки, что и в трассировке, — только длиннее.

Шаг отвечает на вопрос **что делали**, а не **чем делали**.

## 2. Гранулярность: смысловые этапы

Плохо: шаг на каждую строку — отчёт длиннее теста.

Плохо: один шаг «Выполнить сценарий» — отчёт бесполезен.

Хорошо: шаг на смысловой этап. Диапазон три–семь часто удобен для scenario
test, но это review heuristic, не quota и не валидатор качества.

**Что сломается:** при слишком мелкой разбивке падение теряется среди
двадцати зелёных строк; при слишком крупной — непонятно, на чём именно
остановились.

## 3. Подготовка отделена от проверки

```python
with step("Подготовка: пользователь с premium-тарифом"):
    user = make_user(tier="premium")

with step("Действие: создать заказ на 1000"):
    order = create_order(api, user, amount=1000)

with step("Проверка: скидка 10 процентов"):
    assert order["discount"] == 100
```

**Что сломается:** без разделения падение в подготовке читается как
провал проверки. Диагноз неверный: сломалось создание пользователя, а
записано «скидка не сработала».

## 4. Вложенность не глубже двух уровней

Плохо: шаг в шаге в шаге в шаге.

Хорошо: верхний уровень — этапы сценария, второй — существенные действия
внутри этапа.

**Что сломается:** отчёт превращается в дерево, которое надо
разворачивать. Смысл шагов — увидеть картину сразу.

## 5. В шаг попадают данные, влияющие на результат

Плохо: `step("Создать заказ")`

Хорошо: `step(f"Создать заказ на {amount} {currency}")`

**Что сломается:** в параметризованном тесте все прогоны выглядят
одинаково, и по отчёту не отличить, какой упал.

Оговорка: секреты, токены и персональные данные в текст шага не
подставляются — отчёт хранится дольше прогона и читается шире.

## 6. Вложения прикрепляются к шагу, а не к тесту

Плохо: скриншот и ответ сервера в конце теста общей кучей.

Хорошо: ответ прикреплён к шагу запроса, скриншот — к шагу проверки
интерфейса.

**Что сломается:** десять вложений в конце теста не сопоставить с шагами.
Разбор превращается в угадывание, какое из них относится к падению.

## 7. Шаг не меняет поведение теста

Плохо: шаг с обработчиком, который глушит исключение, чтобы «отчёт был
красивее».

Хорошо: шаг только оборачивает и подписывает.

**Что сломается:** тест зелёный, отчёт красивый, дефект пропущен.
Оформление, влияющее на вердикт, — не оформление.

## Что даёт правильная разбивка

| Без шагов | С шагами |
|---|---|
| Трассировка на 40 строк | Видно, на каком этапе остановились |
| Непонятно, дошло ли до проверки | Видно, что подготовка прошла |
| Вложения кучей | Каждое у своего шага |
| Параметризованные прогоны неразличимы | Данные в заголовке шага |

## Проверка себя

Открой отчёт упавшего теста и попробуй понять, что произошло, **не
открывая код**. Не получилось — шаги не выполняют свою работу.
