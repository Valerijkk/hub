# DRY, KISS, YAGNI — и где они вредят тестам

Три принципа, которые в тестовом коде работают не так, как в
продуктовом. Здесь у них есть цена, и её надо знать.

## DRY: не повторяйся

### DAMP: смысл теста должен быть локально виден

В reusable mechanics действует DRY. В теле теста при конфликте побеждает DAMP
(`Descriptive And Meaningful Phrases`): небольшое повторение допустимо, если
setup, action и oracle видны без перехода в общий helper.

Плохо:

```python
def test_admin_cannot_delete_owner(api, users):
    actor, target = users("admin_owner")
    assert_denied(lambda: delete(api, actor, target))
```

Хорошо:

```python
def test_admin_cannot_delete_owner(api, user_factory):
    admin = user_factory(role="admin")
    owner = user_factory(role="owner")
    response = api.delete_user(actor=admin, target=owner)
    assert response.status_code == 403
```

Во втором варианте requirement и oracle понятны на месте. Повторяемые mechanics
`user_factory` и API client остаются DRY; бизнес-смысл не спрятан.

### Где применять

Плохо:

```python
def test_a(api):
    r = api.post("/login", json={"user": "u", "pass": "p"})
    token = r.json()["token"]
    api.headers["Authorization"] = f"Bearer {token}"
    ...

def test_b(api):
    r = api.post("/login", json={"user": "u", "pass": "p"})
    token = r.json()["token"]
    api.headers["Authorization"] = f"Bearer {token}"
    ...
```

Хорошо: фикстура `auth_token`.

**Что сломается:** сменился путь авторизации — правятся сорок тестов.
Механика, повторённая дословно, обязана жить в одном месте.

### Где вредит

Плохо: один параметризованный тест на все случаи ручки, а внутри тела
`if` по ожидаемому исходу — в одной ветке успех, в другой отказ.

Хорошо: два теста, у каждого своя параметризация внутри своего класса
случаев. Разбор с кодом — [`parametrization.md`](parametrization.md) §3.

**Что сломается:** ветвление в теле означает, что тест проверяет два
разных требования. При падении непонятно, какая ветка сработала, а
добавление третьего случая усложняет обе.

**Правило границы:** объединяется **механика**, не **смысл**. Два теста,
похожих кодом, но проверяющих разные требования, остаются двумя.

### «Правило трёх» — только эвристика

Количество повторений не доказывает общую абстракцию. Обобщать нужно тогда,
когда найдено одно знание и одна причина изменения, а не автоматически на
втором или третьем похожем фрагменте.

**Что сломается при раннем обобщении:** появляется хелпер с флагами,
обслуживающий разные concepts в одном теле. Читать его тяжелее, чем несколько
прямолинейных кусков, а следующий случай требует ещё одной ветки.

### Дубль, который решили оставить

Иногда дублирование осознанное: константа нужна в двух рантаймах, парсер
продублирован ради независимости слоёв, таблица статусов повторена в клиенте
и в фикстуре.

Это допустимо ровно при одном условии — **есть тест, который краснеет, когда
копии разошлись**:

```python
def test_status_table_parity():
    assert client.STATUSES == fixtures.STATUSES
```

**Что сломается без него:** копии расходятся молча. Правят одну, вторая
продолжает работать по-старому, и обнаруживается это не при правке, а
через месяц на непонятном падении в третьем месте.

Дубль без теста паритета — не «осознанное дублирование», а обычное
дублирование с объяснением. Разница между ними — наличие красного теста.

## KISS: проще — лучше

Плохо:

```python
def test_discount(api):
    for tier, expected in [("basic", 0), ("premium", 100)]:
        with subtests.test(tier=tier):
            user = make_user(tier=tier)
            order = api.create_order(user, amount=1000)
            assert order["discount"] == expected
```

Хорошо: та же таблица случаев, отданная параметризации раннера —
[`parametrization.md`](parametrization.md) §1.

**Что сломается:** цикл внутри теста скрывает, какая итерация упала, и
прогон останавливается на первой. Параметризация раннером даёт отдельный
результат на каждый случай и понятное имя в отчёте.

Общее правило: **если механизм раннера умеет это делать, не пиши свой**.

## KISS в утверждениях

Плохо:

```python
assert all(o["status"] in ALLOWED for o in orders if o["user_id"] == user.id)
```

Хорошо:

```python
own = [o for o in orders if o["user_id"] == user.id]
assert own, "у пользователя нет заказов — проверять нечего"
assert {o["status"] for o in own} == {"new"}
```

**Что сломается:** первый вариант зелёный при пустом списке — `all` по
пустому истинен. Проверка, которая проходит при отсутствии данных, ничего
не проверяет.

Плюс отчёт печатает `assert False`, и что именно не сошлось — неизвестно.

## YAGNI: не строй впрок

Плохо: интерфейс с одной реализацией, слой абстракции над библиотекой,
конфигурация под окружения, которых нет.

Хорошо: то, что нужно сегодня. Абстракция появляется, когда появляется
второй случай.

**Что сломается:** абстракция, спроектированная под один случай,
оказывается неудобной, когда появляется второй — её проектировали не по
фактам. Переделывать дороже, чем было бы написать сразу по двум.

## Сводка

| Принцип | В коде фреймворка | В теле теста |
|---------|-------------------|--------------|
| DRY | Применять к механике | Не склеивать разные требования |
| DAMP | Имена и contracts обязательны | При конфликте с DRY выбирать локальную ясность |
| KISS | Применять | Применять строже: читаемость важнее краткости |
| YAGNI | Применять | Применять |
| Абстракции | Когда доказано общее знание/change reason | Избегать без повторяемой механики |

## Проверка себя

Прочитай тест как человек, впервые открывший файл. **Сколько мест надо
открыть, чтобы понять, что он проверяет?** Больше двух — обобщение зашло
дальше, чем помогает.
