# Параметризация

Один тест с набором данных вместо пяти копий. Работает, пока случаи
отличаются **значением**, а не **смыслом**.

## 1. Вместо серии близнецов

Плохо:

```python
def test_login_empty_password(api): ...
def test_login_short_password(api): ...
def test_login_long_password(api): ...
def test_login_spaces_password(api): ...
```

Хорошо:

```python
@pytest.mark.parametrize("password,expected_code", [
    ("",           400),
    ("ab",         400),
    ("a" * 200,    400),
    ("   ",        400),
])
def test_login_rejects_invalid_password(api, password, expected_code):
    assert api.login("user", password).status_code == expected_code
```

**Что сломается:** четыре копии по двадцать строк правятся в четырёх
местах, и однажды правку внесут в три из четырёх.

## 2. Идентификатор случая обязателен

Плохо: в отчёте `test_login_rejects_invalid_password[password3]`.

Хорошо:

```python
@pytest.mark.parametrize("password,expected_code", [
    pytest.param("",        400, id="пусто"),
    pytest.param("ab",      400, id="короче минимума"),
    pytest.param("a" * 200, 400, id="длиннее максимума"),
    pytest.param("   ",     400, id="только пробелы"),
])
```

**Что сломается:** упал `password3` — надо открывать код и считать
позиции. С идентификатором отчёт сразу говорит, какой случай сломался.

## 3. Смысл не склеивается

Плохо:

```python
@pytest.mark.parametrize("case", [
    ("valid",   201, "new"),
    ("no_auth", 401, None),
    ("too_big", 413, None),
])
def test_order_creation(api, case): ...
```

**Что сломается:** три разных требования — успех, авторизация, лимит — в
одном теле. Внутри неизбежно появляется ветвление, и тест перестаёт
отвечать на вопрос «что именно сломано».

Хорошо: три теста, у каждого своя параметризация внутри своего класса
случаев.

**Критерий:** параметризуются случаи, у которых **одно ожидаемое
поведение** и разные входы. Разные ожидаемые поведения — разные тесты.

## 4. Данные отдельно от логики

Плохо: сорок строк параметров прямо над функцией.

Хорошо: набор вынесен в константу или файл данных рядом, тест остаётся
читаемым.

```python
INVALID_EMAILS = [
    pytest.param("нет-собаки",     id="без @"),
    pytest.param("@example.com",   id="без имени"),
    pytest.param("a@",             id="без домена"),
]

@pytest.mark.parametrize("email", INVALID_EMAILS)
def test_registration_rejects_invalid_email(api, email): ...
```

**Что сломается:** тело теста тонет в данных, и логика проверки не видна
с одного экрана.

## 5. Комбинации — осознанно, а не перемножением

Плохо: три параметра по пять значений — 125 прогонов, из которых
осмысленны десять.

Хорошо: попарное покрытие либо явный список интересных комбинаций.

**Что сломается:** прогон растёт в разы, а находит то же самое.
Медленный набор перестают гонять на каждый PR — и он перестаёт защищать.

## 6. Параметризация фикстуры, когда меняется окружение

```python
@pytest.fixture(params=["chromium", "firefox"])
def browser(request): ...
```

Уместно, когда **весь набор** должен пройти в каждом варианте.
Неуместно для данных одного теста — там параметризуется тест.

**Что сломается:** параметризованная фикстура умножает **все** тесты,
которые её просят, включая те, которым браузер безразличен.

## 7. Ожидание в параметрах, а не в теле

Плохо:

```python
@pytest.mark.parametrize("amount", [0, 1, 1000000, 1000001])
def test_amount(api, amount):
    code = 400 if amount in (0, 1000001) else 201
    assert api.create_order(amount).status_code == code
```

Хорошо: пара «вход → ожидание» в самих параметрах.

**Что сломается:** логика ожидания в теле дублирует правило, которое
проверяется. Ошиблись в условии — тест зелёный при неверном продукте.

## Проверка себя

Посмотри на набор параметров и ответь: **что общего у всех случаев**.
Не находится общего ожидаемого поведения — это не один тест, а несколько,
склеенных ради экономии строк.
