# ООП в автотестах

Классы в тестах нужны реже, чем кажется. Заводить их стоит там, где есть
**состояние** или **несколько реализаций одного контракта**. Во всех
прочих случаях функция читается лучше.

## 1. Композиция вместо наследования

Плохо:

```python
class BaseTest:
    def setup(self): ...
    def login(self): ...
    def create_order(self): ...
    def check_email(self): ...

class TestOrders(BaseTest): ...
class TestProfile(BaseTest): ...     # логин нужен, заказы нет
class TestCatalog(BaseTest): ...     # ничего из этого не нужно
```

Хорошо:

```python
def test_order_created(api, auth_token, order_factory):
    order = order_factory(amount=100)
    assert order["status"] == "new"
```

**Что сломается:** базовый класс растёт от каждой новой потребности и
через полгода тянет за собой почту, платежи и склад в тест каталога.
Изменение в нём задевает все тесты сразу, а понять, что именно
унаследовано, можно только чтением всей цепочки.

Правило: **наследование для «является», композиция для «использует»**.
Тест не «является» базовым тестом — он им пользуется.

## 2. Базовый класс без бизнес-логики

Плохо: `BasePage` умеет логиниться, знает про корзину и проверяет
уведомления.

Хорошо: `BasePage` умеет только то, что верно для **любой** страницы —
открыть, дождаться готовности, найти элемент, снять скриншот.

**Что сломается:** страница логина наследует знание о корзине, которого у
неё нет. Метод есть, вызывать нельзя, а компилятор об этом не скажет.

Признак нарушения: метод базового класса, который осмысленен не для всех
наследников.

## 3. Класс там, где есть состояние

Функция:

```python
def unique_email() -> str: ...
def wait_until(predicate, *, timeout): ...
```

Класс:

```python
class ApiClient:          # держит сессию, базовый адрес, заголовки
class OrderPage:          # держит ссылку на страницу браузера
class TestDataBuilder:    # накапливает состояние между вызовами
```

**Что сломается:** класс без состояния — это модуль функций с лишним
синтаксисом. Читатель ищет, что там хранится, и не находит.

## 4. Инкапсуляция: наружу выходит намерение, не механика

Плохо:

```python
page.driver.find_element("css", "[data-testid=total]").text
```

Хорошо:

```python
page.total
```

**Что сломается:** тест знает про механику поиска. Сменили библиотеку
драйвера — правятся все тесты, а не один класс страницы.

## 5. Полиморфизм там, где реализаций правда несколько

Уместно:

```python
class Notifier(Protocol):
    def sent_to(self, address: str) -> bool: ...

class EmailNotifier(Notifier): ...
class SmsNotifier(Notifier): ...
```

Неуместно: интерфейс с одной реализацией, заведённый «на будущее», —
разбор в [`dry-kiss.md`](dry-kiss.md) §YAGNI.

**Что сломается:** тест, которому нужен второй канал уведомлений, без
протокола лезет в конкретный класс и начинает знать про его устройство.
Признак, что полиморфизм здесь нужен: подмена реализации требуется в
самом тесте, а не «когда-нибудь».

## 6. Наследование тестовых классов — не для переиспользования данных

Плохо: `class TestPremiumOrders(TestOrders)` — чтобы прогнать те же
тесты с другим тарифом.

Хорошо: параметризация тарифом.

**Что сломается:** наследование запускает **все** родительские тесты
повторно, включая те, которым тариф безразличен. Прогон растёт вдвое,
а покрытие — нет.

## Проверка себя

Открой класс и ответь: **какое состояние он хранит и сколько у него
реализаций**. Ни того ни другого — это функции, а не класс.
