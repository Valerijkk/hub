# Фикстуры, фабрики, билдеры

Фикстура готовит состояние и убирает за собой. Всё остальное — не её
работа.

## 1. Фабрика с осмысленными значениями по умолчанию

Плохо:

```python
def make_user(name, email, phone, tier, is_active, created_at):
    ...
# в тесте
user = make_user("Иван", "i@e.com", "+700", "premium", True, datetime.now())
```

Хорошо:

```python
def make_user(**overrides):
    data = {
        "name": "Тестовый Пользователь",
        "email": unique_email(),
        "tier": "basic",
        "is_active": True,
    }
    return create(data | overrides)

# в тесте видно только то, что важно для проверки
user = make_user(tier="premium")
```

**Что сломается:** в плохом варианте читатель не понимает, что влияет на
результат. Добавили обязательное поле — правятся все вызовы. И `datetime.now()`
в аргументе делает тест зависимым от времени.

## 2. Фикстура возвращает объект, а не готовит глобальное состояние

Плохо:

```python
@pytest.fixture(autouse=True)
def setup_catalog(db):
    db.execute("INSERT INTO items ...")     # ничего не возвращает
```

Хорошо:

```python
@pytest.fixture
def catalog(api):
    items = [api.create_item(name=n) for n in ("Телефон", "Книга")]
    yield SimpleNamespace(phone=items[0], book=items[1])
    api.delete_items([i.id for i in items])
```

**Что сломается:** тест не знает идентификаторов созданного и ищет их
поиском по имени — хрупко и медленно. Плюс `autouse` навязывает
подготовку тестам, которым она не нужна.

## 3. Лесенка вместо одной большой фикстуры

Плохо: `prepared_environment`, создающая пользователя, оплату, заказ и
отгрузку.

Хорошо: `user` → `paid_order` → `shipped_order`, каждая достраивает
предыдущую.

**Что сломается:** тесту на оплату не нужна отгрузка, но он её ждёт.
Прогон медленнее, а падение отгрузки роняет тест про оплату — диагноз
неверный.

## 4. Очистка переживает падение

Плохо: удаление последней строкой тела теста.

Хорошо: удаление после `yield` в фикстуре либо в конструкции,
гарантирующей выполнение.

**Что сломается:** упало утверждение — очистка не выполнилась. Через сто
прогонов окружение забито, и причина неочевидна.

## 5. Уникальность там, где есть ограничение

Плохо: `email="test@example.com"` в фикстуре.

Хорошо: генератор уникальных значений на каждый вызов.

**Что сломается:** второй прогон падает на уникальности. На чистой базе
CI это не видно, и ломается при первом переиспользовании окружения.

## 6. Фикстура не зависит от чужой подготовки

Плохо: `api.get_user_by_email("test@example.com")` — рассчитывает найти.

Хорошо: создаёт то, что ей нужно.

**Что сломается:** на чистой базе всё падает, а причина не в коде.
Неявная зависимость от порядка либо от ручной подготовки стенда.

## 7. Синтетические данные, всегда

Реальные адреса, телефоны, документы, платёжные данные в фикстурах не
появляются — даже «тестовые» реальных людей.

**Что сломается:** тестовое окружение однажды отправит письмо или
списание на реальный контакт. Плюс персональные данные в репозитории —
проблема не техническая.

Реальное значение уже попало в фикстуру — это инцидент, и порядок
жёсткий: остановиться → сообщить путь и класс, не само значение →
ротация → очистка ([`../rules/50`](../rules/50-data-handling.md) §3.2).
Фикстура уезжает в историю, в логи CI и в чужие клоны тремя путями
сразу, поэтому убрать значение из текущей версии файла недостаточно.

## Проверка себя

Вопросы к самой фикстуре, а не к телу теста — оно проверяется в
[`../practices/test-data.md`](../practices/test-data.md).

- Что она **вернёт** тесту? Ничего — тест будет искать созданное поиском.
- Что произойдёт, если тест **упадёт** посередине? Очистка обязана
  выполниться и тогда.
- Что произойдёт на **втором прогоне** без чистой базы? Падение на
  уникальности — признак фиксированного значения там, где есть
  ограничение.
- Сколько лишнего она готовит для теста, которому нужна только её первая
  ступень?
