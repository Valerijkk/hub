# Клиенты внешних систем

Клиент — тонкая обёртка над транспортом. Он умеет обратиться и вернуть
ответ, а не решать, что с ответом делать.

## 1. Клиент возвращает ответ, а не бросает при отказе

Плохо:

```python
class ApiClient:
    def get(self, path, **kw):
        r = self.session.get(self.base + path, **kw)
        r.raise_for_status()          # 4xx и 5xx превращаются в исключение
        return r.json()
```

Хорошо:

```python
class ApiClient:
    def get(self, path, **kw) -> Response:
        return self.session.get(self.base + path, **kw)
```

**Что сломается:** негативный тест написать невозможно. Проверка «без
токена возвращается 401» падает с исключением вместо ответа, и приходится
оборачивать в try — а это скрывает разницу между «вернулся 401» и
«сеть недоступна».

Отказ — валидный ответ системы, а не авария клиента.

## 2. Диагностика в ошибке, а не в логе

Плохо:

```python
def post(self, path, **kw):
    r = self.session.post(self.base + path, **kw)
    if r.status_code >= 500:
        logger.error("server error")
        raise ApiError("request failed")
```

Хорошо:

```python
def post(self, path, **kw):
    r = self.session.post(self.base + path, **kw)
    if r.status_code >= 500:
        raise ApiError(
            f"POST {path} -> {r.status_code}\n"
            f"request-id: {r.headers.get('x-request-id', 'нет')}\n"
            f"тело: {r.text[:500]}"
        )
    return r
```

**Что сломается:** «request failed» в CI не даёт ничего. Идентификатор
запроса и тело ответа — то, с чем можно идти к разработчику; без них
разбор начинается с воспроизведения.

## 3. Таймаут задаётся, а не подразумевается

Плохо: `session.get(url)` без таймаута.

Хорошо: таймаут обязательный параметр транспорта, значение приходит из
конфигурации окружения.

**Что сломается:** зависший запрос вешает прогон до общего таймаута
раннера. В CI это выглядит как «упало через 40 минут без сообщения» —
самый дорогой вид падения.

## 4. Базовый адрес и заголовки — снаружи

Плохо:

```python
class ApiClient:
    BASE = "https://staging.example.com/api/v1"
```

Хорошо:

```python
class ApiClient:
    def __init__(self, base_url: str, default_headers: dict | None = None):
        ...
```

**Что сломается:** прогон против другого стенда требует правки кода.
Захардкоженный адрес неизбежно попадает в чужое окружение и бьёт по
чужим данным.

## 5. Один клиент — один протокол

Плохо: класс, который умеет и HTTP, и очередь, и базу, потому что «так
удобнее в тестах».

Хорошо: три клиента, каждый со своим транспортом; сценарий их
комбинирует.

**Что сломается:** падение в очереди диагностируется как «ошибка
ApiClient». Границы отказа размываются, а вместе с ними — триаж.

## 6. Ретраи только на идемпотентном и только явно

Плохо: клиент повторяет любой запрос трижды при 5xx.

Хорошо: повтор включается вызывающим и только для операций, которые
можно повторить безопасно.

**Что сломается:** молчаливый повтор POST создаёт два заказа. Тест на
идемпотентность при этом зелёный — он не знает, что клиент сходил дважды.

## Проверка себя

Напиши негативный тест: «без токена — 401». Если для этого приходится
ловить исключение или обходить клиент — клиент решает за тест, и это
надо чинить до того, как на нём вырастут сотни проверок.
