# Практики кода тестового фреймворка

Как писать **код фреймворка**: клиенты, фикстуры, хелперы, страницы,
утилиты. Это не про сами тесты — те в
[`../practices/`](../practices/README.md).

## Почему это отдельно

Код фреймворка живёт дольше тестов и ломает больше при ошибке. Плохой
тест портит один сценарий; плохой клиент API портит все тесты, которые
через него ходят, и падают они непонятно где.

```
тест        одна проверка, легко переписать
фреймворк   инфраструктура под сотнями тестов
```

Отсюда разная планка: в тесте допустима прямолинейность ради читаемости,
в коде фреймворка — нет.

## Три правила поверх всего

**Первое. Падение фреймворка обязано быть отличимо от падения теста.**
Тест упал — проблема в продукте или в проверке. Фреймворк упал —
проблема в инфраструктуре, и разбирать её надо иначе. Ошибка, не
говорящая, что именно сломалось, стоит часов.

**Второе. Хелпер не прячет проверку.** Функция, которая внутри себя
делает утверждение, лишает тест видимой проверки: читаешь тест — не
понимаешь, что он проверяет. Хелперы готовят и возвращают, утверждения
остаются в тесте.

**Третье. Фреймворк не знает про конкретные тесты.** Клиент, в котором
есть ветка «если это тест такой-то, вести себя иначе», перестаёт быть
инфраструктурой и становится частью одного теста — со всеми чужими
тестами в зависимостях.

## Как читать пары

У каждой практики блоки «плохо» и «хорошо». Плохой блок — не карикатура:
это код, который работает, проходит ревью и начинает мешать через
полгода, когда тестов становится много.

Под каждой парой стоит **что сломается** — конкретная ситуация, в которой
плохой вариант даёт неверный или непонятный результат.
