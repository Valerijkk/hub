# Переносимость: тест не должен зависеть от машины

Тест проходит у автора и падает в CI — либо наоборот. Разбирают такое
дольше всего: код верный, поведение верное, а причина в том, что машины
разные.

Шесть классов ниже дают почти все такие случаи.

## 1. Захардкоженный временный каталог

Плохо:

```python
def test_export_writes_file():
    api.export_report(path="/tmp/report.csv")
    assert os.path.exists("/tmp/report.csv")
```

Хорошо:

```python
def test_export_writes_file(tmp_path):
    target = tmp_path / "report.csv"
    api.export_report(path=str(target))
    assert target.exists()
```

**Что сломается:** на Windows `/tmp` не существует. Но хуже другое — два
теста, пишущие один и тот же путь, при параллельном прогоне затирают друг
друга, и падает то один, то другой без всякой системы.

Временный каталог даёт фикстура: он уникален на тест и убирается сам.

## 2. Литерал пути в утверждении

Плохо:

```python
assert result.path == "data/exports/report.csv"
```

Хорошо:

```python
assert result.path == os.path.join("data", "exports", "report.csv")
```

**Что сломается:** разделитель. На Windows тот же путь придёт как
`data\exports\report.csv`, и сравнение строк не сойдётся, хотя путь тот же.

Собирать ожидаемый путь тем же способом, каким его собирает код.

## 3. Разбиение по `\n`

Плохо:

```python
lines = output.split("\n")
assert lines[0] == "OK"
```

Хорошо:

```python
lines = output.splitlines()
assert lines[0] == "OK"
```

**Что сломается:** вывод с `\r\n` даёт `"OK\r"` в первом элементе. Тест
краснеет с разницей, невидимой в отчёте: обе строки печатаются как `OK`,
и человек смотрит на них, не понимая, чем они отличаются.

Это самый дорогой класс в разборе — именно из-за невидимости различия.

## 4. Утверждение на биты прав

Плохо:

```python
assert oct(os.stat(path).st_mode)[-3:] == "600"
```

**Что сломается:** на Windows модель прав другая, и значение не
воспроизводится. Тест либо всегда падает, либо его отключают целиком — и
вместе с ним теряется проверка, которая на Linux была осмысленной.

Правильно — пропустить явно, с причиной и указанием платформы:

```python
@pytest.mark.skipif(os.name == "nt", reason="права POSIX; на Windows модель другая")
```

Пропуск с причиной честнее удаления: он говорит, что проверка есть, но
не для этой платформы.

## 5. Запуск внешней программы без проверки

Плохо: тест вызывает `docker`, `psql`, `git` и падает с
«команда не найдена», если её нет.

Хорошо: проверить доступность и пропустить с причиной либо считать
отсутствие ошибкой окружения, а не теста.

**Что сломается:** падение выглядит как дефект продукта. Разбор начинается
с кода и только потом доходит до того, что на раннере нет нужного бинаря.

## 6. Зависимость от локали и часового пояса

Форматирование чисел и дат, сортировка строк, регистр — всё это меняется
вместе с локалью. Прогон на машине с другой локалью даёт другой результат
при том же коде.

Разобрано отдельно — [`determinism.md`](determinism.md) §6.

## Проверка себя

- Каждый временный файл создан фикстурой, а не по фиксированному пути?
- Пути в утверждениях собраны тем же способом, что и в коде?
- Разбиение вывода переживает `\r\n`?
- Платформенно-зависимое пропущено явно, а не удалено?
- Внешние программы проверяются на доступность?

Быстрая проверка на глаз: если в тесте есть строка с `/` внутри кавычек
или литерал `\n` в разборе вывода — стоит присмотреться.
