# Тестовые данные, фикстуры, фабрики

Данные — половина теста. Плохие данные делают зелёным тест, который
ничего не проверяет, и красным тест, с которым всё в порядке.

## 1. Данные, не относящиеся к проверке

Плохо:

```python
def test_discount_for_premium(api):
    user = api.create_user(
        name="Иван Петров",
        email="ivan@example.com",
        phone="+70000000000",
        address="Москва, ул. Ленина, 1",
        birthday="1990-01-01",
        tier="premium",
    )
    assert api.calc_discount(user, amount=1000) == 100
```

Хорошо:

```python
def test_discount_for_premium(api, user_factory):
    user = user_factory(tier="premium")
    assert api.calc_discount(user, amount=1000) == 100
```

**Что сломается:** ничего, но читатель теста не понимает, что важно.
Через полгода кто-то поменяет город и будет гадать, влияет ли это на
скидку. В тесте видно **только то, что относится к проверке**, остальное
даёт фабрика значениями по умолчанию.

## 2. Магические значения без смысла

Плохо:

```python
def test_bulk_limit(api):
    items = [{"id": i} for i in range(101)]
    assert api.bulk_create(items).status_code == 400
```

Хорошо:

```python
MAX_BULK_ITEMS = 100

def test_bulk_above_limit_rejected(api):
    items = [{"id": i} for i in range(MAX_BULK_ITEMS + 1)]
    assert api.bulk_create(items).status_code == 400
```

**Что сломается:** лимит поменяли на 200 — тест падает, и непонятно,
это баг или устаревшее ожидание. Число 101 не говорит, что оно означает
«на единицу больше предела».

### Константа теста берётся из требования, а не из продукта

Соблазн — импортировать предел оттуда же, откуда его берёт продукт:
тогда изменение лимита не потребует правки теста. Это ловушка.

```python
✗ from product.config import MAX_BULK_ITEMS   # тест следует за продуктом
✓ MAX_BULK_ITEMS = 100                        # значение из требования
```

**Что сломается:** предел поменяли по ошибке — с общим источником тест
меняется вместе с ним и остаётся зелёным. Дефект, ради которого тест и
писался, становится невидимым.

Падение теста при изменении лимита — не неудобство, а **сигнал**: кто-то
изменил поведение, описанное в требовании. Правка теста здесь обязана
быть осознанной и идти вместе с правкой требования.

То же правило в другой форме — [`assertions.md`](assertions.md) §4:
ожидаемое не вычисляется тем же способом, каким его получает продукт.

## Конструирование фикстур — не здесь

Как писать фабрику, лесенку фикстур, очистку и уникальность —
[`../code/fixtures.md`](../code/fixtures.md). Здесь только то, что видно
**в теле теста**: какие значения он подаёт и почему именно эти.

Граница: практика отвечает на «какие данные брать», код — на «как
устроен механизм, который их выдаёт».

## Проверка себя

Прочитай тест и назови, **какие данные влияют на результат**. Если в теле
есть значения, про которые нельзя сказать «вот это здесь потому-то» —
они лишние и мешают понимать проверку.
