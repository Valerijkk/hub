# Следы генерации: как отличить тест от текста, похожего на тест

Сгенерированный код проходит линтер и выглядит аккуратно. Отличают его
не стиль, а признаки — и они одни и те же независимо от языка.

## 1. Комментарий-пересказ

Плохо:

```python
# Создаём пользователя
user = api.create_user()

# Проверяем, что статус равен 200
assert response.status_code == 200
```

Хорошо:

```python
user = api.create_user()

# Статус проверяется отдельно от тела: ручка возвращает 200
# с пустым списком, если у пользователя нет заказов, — это
# валидный случай, а не ошибка
assert response.status_code == 200
```

**Признак:** комментарий повторяет следующую строку словами. Он ничего
не добавляет и устаревает при первой же правке кода — а его никто не
поправит, потому что он «и так очевидный».

Комментарий уместен, когда объясняет **почему**, а не **что**.

## 2. Комментарий-эхо в конце блока

Плохо:

```python
def test_order_created(api):
    ...
    assert order.status == "new"
    # конец теста
```

**Признак:** комментарий дублирует структуру, видимую по отступам:
«конец функции», «начало цикла», «блок проверок».

## 3. Заглушки, оставшиеся от генерации

| Признак | Пример |
|---|---|
| Шаблонные адреса | `test@test.com`, `user@example.com` в каждом тесте |
| Названия-заполнители | `test`, `foo`, `Пример`, `Название` |
| Метка нерешённого без ссылки | `TODO`, `FIXME` без номера задачи и даты |
| Повторяющееся число без смысла | `123`, `999` в разных несвязанных тестах |

Шаблонное значение само по себе не дефект. Дефект — когда оно **везде
одинаковое**: тесты перестают отличаться данными, и падение одного не
локализуется.

## 4. Расхождение имени и тела

Плохо:

```python
def test_user_cannot_delete_others_order(api, user, other_order):
    response = api.get(f"/orders/{other_order.id}", user=user)
    assert response.status_code == 403
```

**Признак:** имя обещает проверку удаления, тело проверяет чтение. Самый
частый след генерации по шаблону: имя взяли из списка требований, тело —
из соседнего теста.

Опасность в том, что при разборе покрытия имя читают, а тело нет. В
матрице стоит галочка напротив удаления, которого никто не проверял.

## 5. Серия близнецов вместо параметризации

Плохо: пять тестов, отличающихся одним значением, с одинаковым телом на
двадцать строк.

Хорошо: один параметризованный тест с пятью наборами.

**Признак:** соседние функции совпадают дословно, кроме одной константы.
Помимо объёма это ещё и риск: правку внесут в четыре из пяти.

Оговорка: если случаи отличаются **смыслом**, а не значением, разные
тесты правильнее — параметризация склеит несвязанное.

## 6. Проверка ради проверки

Плохо:

```python
assert result is not None
assert isinstance(result, dict)
assert len(result) > 0
```

**Признак:** утверждения, истинные почти при любом ответе. Добавлены,
чтобы в тесте что-то было. Разбор — в
[`assertions.md`](assertions.md).

## Как искать

Для конкретного репозитория составляется список команд поиска под его
язык и раннер. Категории universal, выражения — нет.

Ориентиры для поиска:

```
комментарий из одного слова с глаголом в первом лице множественного числа
метка нерешённого без цифр рядом
одинаковый адрес почты более чем в трёх тестах
две соседние функции с совпадением тела выше порога
имя теста содержит слово, которого нет в его теле
```

## Важно: находка — кандидат, а не приговор

Каждый признак ловит и правильные случаи. Шаблонный адрес уместен в
тесте на валидацию формата; повторяющийся комментарий — в учебном
примере; близнецы — когда случаи действительно разные по смыслу.

Поэтому находка означает **посмотреть**, а не «удалить». Автоматическое
удаление по признаку ломает рабочие тесты и приучает игнорировать
инструмент.

## Проверка себя

Прочитай свой тест как чужой и спроси: **что здесь узнает читатель,
чего не видно из кода?** Ничего — комментарии лишние. Имя не совпадает с
телом — имя врёт, и это дороже всего остального в этом файле.
