# Security-критичные тесты

Отдельный класс: эти тесты нельзя удалять, ослаблять или «временно
отключать». Их падение означает открытую дыру, а не неудобство прогона.

## Правило обращения

```
Обычный тест   мешает — разбираемся, можно и переписать
Security-тест  мешает — разбираемся, переписывать только с ревьюером
```

Ослабление проверки безопасности выглядит как обычный рефакторинг теста
и не отличается от него по диффу. Поэтому изменение помечается явно и
проходит отдельное ревью — не потому, что автору не доверяют, а потому
что цена ошибки несимметрична.

## Классы проверок, которые обязаны быть

| Класс | Что проверяется | Признак отсутствия |
|---|---|---|
| Отказ без учётных данных | Запрос без токена отклонён | Покрыт только путь с токеном |
| Отказ с чужими правами | Доступ к чужому ресурсу отклонён | Покрыт только владелец |
| Отказ с истёкшим доступом | Просроченный токен отклонён | Не проверяется вовсе |
| Отсутствие лишнего в ответе | Секреты и внутренние поля не отдаются | Проверяют только «нужное есть» |
| Проверка подписи | Событие с подделанной подписью отклонено | Подпись проверяется только в проде |
| Ограничение размера | Слишком большое тело отклонено | Ограничение есть в коде, теста нет |
| Изоляция данных | Пользователь видит только свои записи | Проверяется на одном пользователе |

Последняя строка — самая частая дыра. Тест с **одним** пользователем не
может обнаружить утечку между пользователями: чтобы её увидеть, нужен
второй.

## Опасные паттерны, которые ловятся тестом или ревью

Обобщённый каталог. Конкретные имена функций зависят от стека, суть —
нет.

| Паттерн | Риск | Чем закрывается |
|---|---|---|
| Запрос по URL, пришедшему от пользователя, без проверки адреса | Обращение во внутреннюю сеть | Валидация адреса до запроса, тест с внутренним адресом |
| Чтение тела запроса целиком без ограничения | Исчерпание памяти | Ограниченное чтение, тест с большим телом |
| Сравнение секретов обычным оператором | Утечка по времени ответа | Сравнение за постоянное время |
| Прямой доступ к слою хранения из обработчика | Обход проверок доступа | Тест, что обработчик не видит хранилище напрямую |
| Аварийное завершение в рабочем пути | Отказ обслуживания | Возврат ошибки, тест на некорректный вход |
| Пропуск проверки подписи события | Подделка события | Тест с подделанной подписью |
| Ошибка с деталями внутреннего устройства | Разведка для атаки | Тест, что в теле ошибки нет путей и версий |

## Как писать негативный security-тест

Плохо:

```python
def test_admin_endpoint(api, admin):
    assert api.get("/admin/users", user=admin).status_code == 200
```

Хорошо:

```python
def test_admin_endpoint_allows_admin(api, admin):
    assert api.get("/admin/users", user=admin).status_code == 200

def test_admin_endpoint_denies_regular_user(api, user):
    assert api.get("/admin/users", user=user).status_code == 403

def test_admin_endpoint_denies_anonymous(api):
    assert api.get("/admin/users", user=None).status_code == 401

def test_admin_endpoint_denies_expired_token(api, expired_admin_token):
    assert api.get("/admin/users", token=expired_admin_token).status_code == 401
```

**Что сломается:** права проверяются не в том месте, проверка снята при
рефакторинге, роль читается из недоверенного заголовка — все три случая
проходят первый тест и падают на остальных трёх.

## Проверка утверждения здесь обязательна

Security-тест, который не умеет краснеть, опаснее отсутствующего: он
создаёт документированную уверенность в защите, которой нет.

По [`rules/40`](../rules/40-verification-protocol.md): сломать управляемый
вход — подменить роль в стабе авторизации, вернуть чужой идентификатор,
подать просроченный токен — и убедиться, что тест краснеет.

Отдельная оговорка про стабы: тест на стабе доказывает, что проверка
читает то, что ей дают. Соответствие стаба реальной системе он не
доказывает — для security это ограничение записывается явно и
компенсируется проверкой против настоящего механизма хотя бы на одном
сценарии.

## Что не кладётся в тесты никогда

- реальные токены, ключи, пароли — даже просроченные;
- реальные персональные данные;
- работающие полезные нагрузки эксплойтов из внешних источников;
- обходные пути, которые тест «на всякий случай» оставляет включёнными.

Для проверки отказа достаточно синтетически некорректного значения. Тест
не обязан демонстрировать работающую атаку, чтобы доказать, что она
отклонена.

**Реальное значение уже в тесте — это инцидент, а не уборка.** Порядок
жёсткий: остановиться → сообщить путь и класс, никогда само значение →
ротация → и только потом очистка
([`rules/50`](../rules/50-data-handling.md) §3.2).

Ротация раньше очистки, потому что фикстура с настоящим токеном успевает
уехать тремя путями сразу: в историю репозитория, в логи прогона CI и в
чей-то локальный клон. Убрать значение из текущей версии файла — не
значит отменить, что оно там было.

Найти такое во всей истории, а не только в последней версии:

```
python scripts/scan_secrets.py --root <корень> --history
```

## Проверка себя

По каждой защищённой ручке ответь: **есть ли тест, который падает, если
снять проверку доступа?** Нет такого теста — защита не покрыта,
независимо от того, сколько тестов на неё написано.
