# API-тесты: специфика

Проверяется контракт, а не реализация. Контракт — это коды ответа, схемы,
права, побочные эффекты и то, чего быть не должно.

## 1. Контракт целиком, а не один код

Плохо: покрыт только успешный ответ.

Хорошо: покрыты **все коды ответа из контракта**, каждый отдельным тестом
с проверкой тела там, где тело документировано.

Матрица минимума на ручку:

```
200/201  успех, минимальный набор полей
200/201  успех, все необязательные поля
400      нет обязательного поля
400      неверный тип поля
401      без токена
403      чужой ресурс или недостаточно прав
404      несуществующий идентификатор
409      конфликт, если контракт его объявляет
413/422  превышение размера или семантическая ошибка
```

Кода нет в контракте — тест на него не пишется. Выдуманный 409 закрепляет
поведение, которого никто не обещал, и ломается при первом изменении.

## 2. Проверять и то, чего быть не должно

Плохо:

```python
def test_get_user(api, user):
    body = api.get(f"/users/{user.id}").json()
    assert body["id"] == user.id
    assert body["email"] == user.email
```

Хорошо:

```python
def test_get_user_does_not_expose_secrets(api, user):
    body = api.get(f"/users/{user.id}").json()

    assert body["id"] == user.id
    assert body["email"] == user.email
    assert "password_hash" not in body
    assert "internal_notes" not in body
```

**Что сломается:** ручка начала отдавать хеш пароля после рефакторинга
сериализатора. Все проверки «нужное есть» зелёные. Утечка ловится только
проверкой «лишнего нет».

## 3. Схема — не замена проверке содержимого

Схема проверяет **форму**: типы, обязательность, формат. Она не знает,
что у пользователя с тремя заказами вернулись именно его три.

Нужны обе проверки:

```python
def test_orders_match_schema(api, user):
    response = api.get("/orders", user=user)
    validate(response.json(), schema=ORDERS_SCHEMA)

def test_orders_contain_only_own(api, user, other_user):
    ids = {o["id"] for o in api.get("/orders", user=user).json()["items"]}
    assert ids == {o.id for o in user.orders}
    assert other_user.orders[0].id not in ids
```

## 4. Побочный эффект — часть контракта

Плохо:

```python
def test_order_cancelled(api, order):
    assert api.cancel(order).status_code == 200
```

Хорошо:

```python
def test_cancel_releases_stock_and_notifies(api, order, mail, warehouse):
    assert api.cancel(order).status_code == 200

    assert api.get(order.id).status == "cancelled"
    assert warehouse.reserved(order.item_id) == 0
    assert mail.sent_to(order.customer.email, template="order_cancelled")
```

**Что сломается:** отмена вернула 200, но резерв на складе не снят и
письмо не ушло. Клиент видит «отменено», товар недоступен другим,
уведомления нет. Код ответа об этом ничего не говорит.

Побочные эффекты, объявленные в контракте, проверяются наравне с ответом.

## 5. Заголовки и коды, влияющие на клиента

Часто пропускают, а клиент на них полагается:

| Что | Когда важно |
|---|---|
| `Location` при 201 | Клиент идёт по нему за созданным ресурсом |
| `ETag` и условные запросы | Кеширование и оптимистичные блокировки |
| Пагинация: курсор, общее число | Клиент не пройдёт дальше первой страницы |
| `Retry-After` при 429 | Клиент не узнает, когда повторять |
| `Content-Type` | Разбор ответа на стороне клиента |

## 6. Стабы: доказательство есть, соответствие — нет

Стаб делает тест быстрым и детерминированным. Но он же создаёт риск,
которого нет при работе с реальной системой: **стаб может врать**.

```
Тест зелёный + стаб соответствует реальности  → поведение проверено
Тест зелёный + стаб разошёлся с реальностью   → проверена фантазия
```

Проверка утверждения по
[`rules/40`](../rules/40-verification-protocol.md) доказывает, что тест
зависит от ответа стаба. Она **не доказывает**, что стаб отвечает как
настоящая система.

Расхождение ловится отдельно: контрактными тестами против схемы
поставщика, периодической сверкой записанных ответов с живым сервисом,
проверкой версии контракта. В отчёте это отмечается как риск, а не
закрывается прогоном.

## Проверка себя

Возьми контракт ручки и матрицу покрытия. Каждый код ответа из контракта
обязан встретиться в матрице — либо тестом, либо пометкой `N/A` с
причиной. Кода нет ни там, ни там — это дыра, а не решение.
