# UI и сквозные сценарии: специфика

Самые дорогие и самые хрупкие тесты. Каждый должен оправдывать своё
существование: то, что проверяется дешевле уровнем ниже, на UI не
проверяется.

## 1. Что вообще выносить на этот уровень

| Проверять на UI | Проверять ниже |
|---|---|
| Пользователь проходит сценарий целиком | Валидация каждого поля формы |
| Данные корректно отображаются | Бизнес-логика расчёта |
| Переходы между экранами работают | Все коды ответа ручки |
| Критичный путь до денег или регистрации | Граничные значения |

Правило: **на UI проверяется то, что ломается только на UI**. Валидация
двадцати полей через браузер — это двадцать минут прогона вместо двадцати
секунд на уровне API, и та же самая найденная ошибка.

## 2. Селекторы: тестовые атрибуты, а не вёрстка

Плохо:

```python
page.click("div.container > div:nth-child(3) > button.btn-primary")
```

Хорошо:

```python
page.click("[data-testid=submit-order]")
```

**Что сломается:** дизайнер поменял вложенность или класс кнопки — тест
падает, хотя функциональность цела. Такие падения приучают чинить тест
не разбираясь, и однажды так «починят» настоящий баг.

Тестовый атрибут — контракт между разработкой и автоматизацией. Он
меняется осознанно, вёрстка — когда угодно.

## 3. Ожидание состояния, а не времени

Плохо:

```python
page.click("[data-testid=submit-order]")
time.sleep(2)
assert page.text("[data-testid=order-status]") == "Оплачен"
```

Хорошо:

```python
page.click("[data-testid=submit-order]")
page.wait_for_text("[data-testid=order-status]", "Оплачен",
                   timeout=env.ui_timeout)
```

**Что сломается:** на медленной машине CI двух секунд не хватит, на
быстрой они потратятся впустую. UI особенно чувствителен: анимации,
догрузка данных, повторный рендер.

## 4. Подготовка через API, проверка через UI

Плохо: регистрация, вход, добавление товара, оформление — всё кликами,
чтобы проверить страницу оплаты.

Хорошо:

```python
def test_payment_page_shows_order_total(api, page, user):
    order = api.create_order(user, amount=1500)   # подготовка — API

    page.login_as(user)
    page.open(f"/orders/{order.id}/pay")          # проверка — UI

    assert page.text("[data-testid=total]") == "1 500"
```

**Что сломается:** сломается регистрация — упадёт тест про оплату, и
диагноз будет неверным. Плюс четыре лишние минуты на каждый прогон.

Подготовка состояния через API быстрее, стабильнее, и падение указывает
на настоящую причину.

## 5. Свидетельства при падении

UI-падение без визуального свидетельства разбирается вслепую: логи
показывают, что элемент не найден, но не показывают, что было на экране.

Обязательный минимум при падении:

```
скриншот
HTML страницы на момент падения
последний URL
логи консоли браузера
логи сетевых запросов, если доступны
```

Без этого воспроизведение занимает часы, а часть падений не
воспроизводится вовсе.

## 6. Один сценарий — один тест

Плохо: тест на пятьдесят шагов, проходящий регистрацию, покупку, возврат
и отзыв.

Хорошо: четыре теста, каждый со своей подготовкой через API.

**Что сломается:** длинный тест падает на шаге 37 — предыдущие 36 надо
проходить заново при каждой отладке. И падение одного шага скрывает
состояние остальных: неизвестно, работал бы возврат, если бы покупка
прошла.

Исключение — сценарий, где важна **непрерывность**: сохранение состояния
между шагами, накопительная логика, мастер с несколькими экранами. Тогда
это осознанно один тест, и причина записывается в его описании.

## Проверка себя

Два вопроса к каждому UI-тесту:

1. Можно ли это проверить уровнем ниже? Можно — переноси.
2. Что увидит человек, разбирающий падение через неделю? Не будет
   скриншота и HTML — он не разберёт.
