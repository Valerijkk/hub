# Часть A. Индустриальный baseline (готово из коробки)

## A1. Структура теста: AAA (Arrange–Act–Assert)

```
// Arrange — подготовка мира: данные, зависимости, состояние
дано: пользователь с ролью viewer, документ чужого workspace

// Act — ОДНО действие, которое тестируем
когда: viewer запрашивает PATCH /documents/{id}

// Assert — проверка наблюдаемого результата
тогда: 403, документ не изменён
```

Правила:
- Три блока визуально разделены (пустая строка или комментарии-маркеры, если так принято в проекте).
- Один Act на тест. Два действия = два теста (кроме связного flow на e2e).
- Assert проверяет **контракт**, не реализацию: статус/состояние/событие, а не «метод X вызвался 2 раза» (verify-вызовы — только когда взаимодействие И ЕСТЬ контракт, напр. отправка события).
- Cleanup — симметричен Arrange и гарантирован (defer/afterEach/t.Cleanup), даже при падении теста.

## A2. FIRST — критерии качества любого теста

| Принцип | Значит | Типовое нарушение |
|---------|--------|--------------------|
| **F**ast | Юнит — миллисекунды, сьют — минуты | Реальная БД в юните, sleep-ожидания |
| **I**solated | Не зависит от порядка и соседей | Общие мутируемые данные, глобальный стейт |
| **R**epeatable | Одинаков локально/CI/в 3 часа ночи | Зависимость от time.Now(), сети, локали |
| **S**elf-validating | PASS/FAIL без чтения логов человеком | «Тест», печатающий результат в stdout |
| **T**imely | Пишется с кодом, не «потом» | Тестовый долг, покрытие задним числом |

## A3. Пирамида и выбор уровня

```
Правило минимального уровня: проверяй на САМОМ НИЗКОМ уровне пирамиды,
где дефект обнаружим.
- Логика/ветвления/валидация  → unit
- Контракт слоёв, SQL, сериализация → integration
- Маршрут HTTP + auth + middleware  → API/contract
- Пользовательский флоу целиком     → e2e (мало и только критичные)
Ошибка «e2e-тест на валидацию поля» — дорогой, медленный, flaky дубль юнита.
```

## A4. Фикстуры и тестовые данные

```
Иерархия предпочтений (сверху — лучше):
1. Builder/Factory с дефолтами и override:  makeUser(withRole("admin"))
2. Функция-фикстура на файл/пакет:          newTestOrder(t)
3. Статичные фикстуры (json/yaml)            — только для контрактных снапшотов
4. Общие глобальные seed-данные              — ⛔ источник связности тестов
```

Правила:
- Каждый тест создаёт **свои** данные с уникальными ключами (uuid/префикс имени теста) — параллельный запуск не должен ронять соседей.
- Фикстура задаёт только релевантные поля; остальное — валидные дефолты. Тест, в Arrange которого 40 строк установки полей — сигнал делать builder.
- «Минимально валидный объект» — отдельная фабрика; невалидность для негативных кейсов делается явным override валидного, а не отдельной кривой фабрикой.
- Данные говорят о кейсе: `email = "blocked-user@test"` лучше `"a@b.c"`.

## A5. Хелперы

- Хелпер убирает шум, но не прячет суть: Arrange можно выносить, **Assert с логикой кейса — нельзя** (ассерты, скрытые в хелпере, делают тест нечитаемым и находки неотлаживаемыми).
- Хелпер, принимающий 5+ флагов поведения — это два хелпера.
- Хелперы падают через тестовый механизм (t.Helper()+t.Fatal / throw), не возвращают error в тест.
- Общие хелперы живут в одном известном месте (см. Часть B4), не копипастятся по файлам.

## A6. Табличные / параметризованные тесты

```
Использовать когда: одна логика × много входов (валидация, парсинг, маппинг).
НЕ использовать когда: кейсы различаются сценарием, а не данными —
таблица с if-ами внутри хуже трёх отдельных тестов.
Каждая строка таблицы: имя кейса (обязательное, говорящее), вход, ожидание.
Строки независимы: без накопления состояния между итерациями.
```

## A7. Моки, стабы, фейки

| Дублёр | Что делает | Когда |
|--------|-----------|-------|
| Stub | Возвращает заготовленный ответ | Управляем входными условиями |
| Fake | Рабочая упрощённая реализация (in-memory repo) | Много взаимодействий, нужна консистентность |
| Mock | Записывает вызовы + ассерты на них | Взаимодействие = контракт (события, нотификации) |
| Spy | Реальный объект + запись вызовов | Частичная проверка поверх реального |

Правила:
- Мокай **границы** (внешние API, часы, рандом, файловая система), не соседние классы своего модуля — иначе тест дублирует реализацию и ломается при каждом рефакторинге.
- Не мокай то, чем владеешь и что дёшево поднять (in-memory/локальная БД в integration).
- Мок внешнего API обязан уметь и ошибки: таймаут, 500, кривой JSON — негативные кейсы против живого мока-отличника не тестируют ничего.
- Verify-ассерты на количество/порядок вызовов — минимум: только контрактные.

## A8. Асинхронность, время, конкурентность

```
⛔ sleep(N) как синхронизация — базовая причина flaky.
✅ Ожидание с поллингом и таймаутом: eventually(assert, timeout, interval).
✅ Инъекция часов: Clock-интерфейс / fake timers — тест времени без времени.
✅ Синхронизация через события/каналы/promise, не через задержки.
✅ Конкурентные тесты гоняются с детектором гонок, если стек его имеет
   (см. PROJECT-CONTEXT §4 — обязательные флаги).
```

## A9. API-тесты (contract/integration)

Минимальный чек-набор на эндпоинт:

```
1. Happy path: валидный вход → ожидаемый статус + схема ответа (не только статус!).
2. Валидация: обязательные поля, типы, лимиты длины/значений → 4xx с внятной ошибкой.
3. Auth: без токена → 401; чужой ресурс/не та роль → 403 (или 404 по политике проекта).
4. Not found / конфликт: несуществующий ID → 404; дубль уникального → 409.
5. Идемпотентность (PUT/DELETE повторно) и пагинация (границы: пустая, последняя страница).
6. Контракт ошибки: формат тела ошибки единый по API.
```

- Ассерты на схему ответа (contract), а не полное сравнение JSON: снапшот всего тела ломается от каждого нового поля.
- Тестовые запросы строятся билдером/клиентом, не строковой конкатенацией URL.

## A10. UI-тесты (component + e2e)

```
Component (unit-уровень UI):
- Тестируй поведение через пользовательские действия (click/type/submit),
  а не внутренний стейт и методы компонента.
- Селекторы: role/label/text (accessible queries) > data-testid > ⛔ CSS-классы/XPath по вёрстке.
- Ассерты на видимый результат: текст, доступность, aria — не на props.

E2E:
- Page Object / screenplay: селекторы и действия страницы — в одном месте,
  спека читается как сценарий пользователя.
- Каждая спека самодостаточна: свой пользователь, свои данные, свой login
  (через API-шорткат, не через UI-форму — UI-login тестируется одной спекой).
- Ожидания встроенные (auto-wait фреймворка), ⛔ жёсткие sleep.
- Скриншоты/трейсы — только артефакты падения, не в репозиторий.
```

## A11. Негативные и security-кейсы (обязательный минимум фичи)

```
1. Невалидный вход каждого типа: пусто, null, мусор, превышение лимита, кривая кодировка.
2. Граничные значения: min-1, min, min+1, max-1, max, max+1.
3. Denial: чужой ресурс → 403/404, эскалация роли → 403.
4. Отказ зависимости: внешний API 500/timeout → graceful degradation, не 500-каскад.
5. Повтор/гонка: двойной сабмит, конкурентное изменение → конфликт, не порча данных.
6. Инъекции в строковые входы (если поле попадает в SQL/HTML/команды).
```

## A12. Ассерты

- Один концепт на тест: можно несколько assert-ов об **одном** результате, нельзя проверять три фичи подряд.
- Сообщение ассерта отвечает «что сломалось», если раннер не показывает diff сам.
- Сравнение структур — целиком с diff-ом (Equal(want, got)), не поле-за-полем в 15 строк.
- want/expected — слева/первым аргументом по конвенции раннера; перепутанные местами аргументы дают врущие сообщения об ошибке.
- ⛔ Ассерты в циклах без имени итерации — падение «expected true» без контекста.
