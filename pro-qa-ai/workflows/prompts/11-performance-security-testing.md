## Нагрузочное: планирование

1. Спроектируй нагрузочный сценарий для {{эндпоинт/флоу}}: реалистичный профиль (соотношение операций как в проде), целевые метрики (RPS, p50/p95/p99, error rate), критерии успеха/провала из SLO {{цели}}.
2. Определи для {{продукт}} виды нагрузочных тестов и что каждый отвечает: load (ожидаемая нагрузка), stress (точка деградации), spike (резкий всплеск), soak (утечки на длительном), breakpoint (предел) — какие релевантны и почему.
3. Составь модель нагрузки из реальных данных: распределение запросов по эндпоинтам {{источник аналитики}}, пиковые часы, размер данных, think-time пользователей — синтетика должна быть похожа на прод, иначе тест врёт.
4. Определи, что мерить помимо времени ответа: насыщение ресурсов (CPU/память/соединения/пул БД), очереди, GC-паузы, деградация зависимостей — метрики, объясняющие ПОЧЕМУ падает производительность.
5. Спроектируй окружение нагрузочного теста: близкое к проду (иначе цифры бессмысленны), изолированное, с мониторингом; отличия от прода — задокументируй как оговорки к результатам.

## Нагрузочное: исполнение и анализ

6. Напиши нагрузочный тест {{эндпоинт}} инструментом стека ({{инструмент}}): ramp-up, плато, ramp-down; корректная генерация данных (уникальные, не кэшируемые ложно), реалистичная auth.
7. Установи baseline производительности {{эндпоинт}}: зафиксируй текущие p50/p95/p99/RPS/error rate как эталон, добавь регрессионный тест-предохранитель (алерт при деградации > {{порог}}).
8. Проведи breakpoint-тест {{сценарий}}: постепенно повышай нагрузку до деградации, зафиксируй точку перегиба и первый узкий ресурс (что упирается первым — CPU? пул? БД?).
9. Проведи soak-тест {{сценарий}} на {{длительность}}: ищи утечки (рост памяти/соединений/файловых дескрипторов во времени), деградацию (растёт latency при стабильной нагрузке), накопление в очередях.
10. Разбери результаты нагрузочного {{отчёт}}: где узкое место (профиль, а не догадка), это код/конфиг/ресурс/зависимость, что даст наибольший выигрыш; отдели «медленно» от «не масштабируется».
11. Проведи spike-тест {{сценарий}}: резкий всплеск ×{{N}} → система выживает (rate limiting, очереди, graceful degradation) или падает; восстановление после спада нагрузки.
12. Тест деградации под нагрузкой: при перегрузе {{модуль}} отдаёт понятные ошибки (429/503) вместо зависания/таймаутов-каскадов, приоритетный трафик проходит, восстанавливается сам.

## Производительность на уровне кода

13. Напиши микробенчмарк {{функция}} инструментом стека: стабильные условия, прогрев, несколько итераций, зафиксируй baseline, регрессионный порог; бенчмарк на реалистичных, не тепличных данных.
14. Найди N+1 в {{модуль}} тестом: перехвати счётчик запросов к БД для операции на {{N}} элементах — должно быть O(1)/O(log n), не O(n); тест-предохранитель от регресса.
15. Тест аллокаций {{функция}} (если стек позволяет): число аллокаций/объём на операцию, регрессионный порог на горячем пути; отдели преждевременную оптимизацию от реальной проблемы профилем.
16. Напиши тест на алгоритмическую сложность {{функция}}: время/операции на входах ×1, ×10, ×100 — рост соответствует ожидаемой сложности, не хуже (защита от случайного O(n²)).

## Security: авторизация и доступ

17. Составь denial-сьют {{ресурс}} (авторизованное тестирование своего продукта): матрица роль × операция — каждая запрещённая комбинация отклоняется, включая обходные пути (прямой ID, API вместо UI, массовое присвоение полей owner/role).
18. Тесты IDOR {{эндпоинт}}: доступ к чужому объекту по угаданному/перебранному ID → отказ; последовательные ID не позволяют перечисление; ответ не раскрывает существование чужого ресурса.
19. Тесты privilege escalation {{модуль}}: пользователь пытается повысить права через тело запроса (role/is_admin), через смену owner, через прямой вызов админ-эндпоинта — все отклонены.
20. Тесты авторизации на КАЖДОМ слое {{флоу}}: проверка прав не только в UI/gateway, но и в сервисе/репозитории (defense in depth) — обход верхнего слоя не даёт доступа.
21. Тесты изоляции тенантов {{продукт}} (multi-tenant): чтение/запись/поиск/экспорт/агрегаты одного тенанта не видят данных другого; пользователь двух тенантов не смешивает контексты.

## Security: аутентификация и сессии

22. Тесты устойчивости аутентификации {{модуль}}: rate limiting на попытки входа, таймингобезопасное сравнение секретов (нет утечки по времени ответа), брутфорс-защита, блокировка после N попыток по спеке.
23. Тесты жизненного цикла токенов {{модуль}}: истечение соблюдается, отзыв (логаут/смена пароля) немедленен, refresh-ротация, невозможность повторного использования одноразовых токенов, подпись проверяется.
24. Тесты сессий {{модуль}}: фиксация сессии невозможна (новый ID после логина), одновременные сессии по политике, cookie-флаги (HttpOnly/Secure/SameSite), CSRF-защита на изменяющих операциях.
25. Тесты сброса пароля/magic-link {{флоу}}: ссылка одноразовая, истекает, не перечислима, не раскрывает существование аккаунта, старая инвалидируется при новой.

## Security: ввод и инъекции

26. Тесты инъекций {{эндпоинт}} (авторизованный аудит своего кода): SQL/NoSQL-метасимволы в каждом строковом поле, попадающем в запрос → экранированы/параметризованы, не выполняются; проверь и поля поиска/фильтров/сортировки.
27. Тесты XSS {{модуль}}: пользовательский контент с HTML/JS-payload → экранируется при выводе (не исполняется), проверь все точки отражения (имена, комментарии, сообщения об ошибках с эхом ввода).
28. Тесты path traversal / file inclusion {{эндпоинт}}: имена файлов с `../`, абсолютные пути, спецсимволы → нормализация/отказ, доступ только в разрешённой директории.
29. Тесты SSRF {{модуль}} (эндпоинты, делающие исходящие запросы по user-URL): внутренние адреса (169.254.x, localhost, метадата-эндпоинты облака), редиректы на внутреннее, нестандартные схемы → блокируются валидатором.
30. Тесты десериализации/парсинга {{модуль}}: billion laughs (XML), глубокая вложенность JSON, огромные числа, полиморфная десериализация недоверенного типа → ограничения соблюдены, не DoS/RCE.
31. Тесты лимитов на вход {{эндпоинт}}: размер тела, длина полей, число элементов, глубина вложенности — превышение отклоняется ДО обработки (защита от memory DoS через io.LimitReader-паттерн).

## Security: данные и раскрытие

32. Тесты утечки данных в ответах {{API}}: ответы не содержат лишних полей (пароли/хэши/токены/внутренние ID), сообщения об ошибках не раскрывают стек/пути/версии/SQL, разные ошибки для «нет юзера» и «неверный пароль» не различимы (user enumeration).
33. Тесты логирования {{модуль}}: секреты/PII/токены не попадают в логи (маскирование), при этом достаточно контекста для дебага; проверь и happy path, и ветки ошибок.
34. Тесты шифрования данных {{модуль}}: чувствительные поля зашифрованы в хранилище (не plaintext), в транзите TLS, ключи не в коде/конфигах-в-репо.
35. Тесты CSV/formula инъекций при экспорте {{фича}}: значения, начинающиеся с =/+/-/@ экранируются, чтобы не исполнились в Excel/Sheets получателя.

## Инструментальные

36. Настрой SAST/линтер безопасности для {{модуль}} в CI: правила под стек, gate на новые находки (не блокировать на историческом долге), исключения задокументированы.

38. Настрой сканирование секретов в diff/истории {{продукт}}: паттерны ключей/токенов/паролей, pre-commit + CI-gate, процесс ротации при утечке.
39. Составь security-чеклист тестов для новой фичи {{фича}}: authz на всех слоях, валидация всех входов, отсутствие injection-точек, минимизация данных в ответах/логах, лимиты — как PR-темплейт.

## Chaos и resilience

46. Спроектируй chaos-эксперимент для {{сервис}}: гипотеза устойчивости, инъекция отказа (задержка/ошибка/недоступность зависимости), метрики влияния, критерий «выдержал» — контролируемо, с планом отката.
47. Тесты устойчивости к отказу зависимости {{модуль}}: убей {{зависимость}} во время работы → graceful degradation/circuit breaker/очередь по спеке, восстановление без рестарта, ошибки не каскадят.
48. Тесты сетевых сбоев {{сервис}}: задержка, потеря пакетов, разрыв соединения, медленный DNS — таймауты срабатывают, ресурсы освобождаются, нет зависаний.
49. Тесты исчерпания ресурсов {{сервис}}: пул соединений/памяти/дескрипторов на пределе → понятный отказ (не краш), приоритетный трафик проходит, восстановление после спада.
50. Тесты восстановления после краша {{сервис}}: убей процесс посреди операции → рестарт без потери зафиксированных данных, дообработка in-flight (или чистый откат), нет полусозданных сущностей.

## Масштабируемость и конкурентность

51. Тесты горизонтального масштабирования {{модуль}}: N инстансов не дублируют работу (лидер-выборы/локи), консистентность общего состояния, линейный рост пропускной способности.
52. Тесты конкурентной корректности под нагрузкой {{модуль}}: параллельные операции над общими данными → нет потерянных обновлений/гонок (оптимистичный лок/транзакции), проверь на реальном параллелизме, не последовательно.
53. Тесты идемпотентности под нагрузкой {{операция}}: дубли запросов при ретраях клиента/сети → эффект применён ровно раз даже при высоком параллелизме.
54. Тесты справедливости/приоритизации под нагрузкой {{модуль}}: тяжёлый клиент не голодит остальных, quota соблюдается, служебный трафик приоритетен при перегрузке.

## Security углублённо (авторизованный аудит своего продукта)

55. Тесты broken access control по OWASP {{модуль}}: вертикальная (роль) и горизонтальная (владение) эскалация, forced browsing к скрытым URL, манипуляция параметрами — полная denial-матрица.
56. Тесты бизнес-логики на злоупотребление {{флоу}}: обход шагов, отрицательные количества/суммы, повтор одноразового, гонки на лимитах/балансе, манипуляция ценой/скидкой на клиенте.
57. Тесты защиты от автоматизации {{флоу}}: rate limiting, CAPTCHA-триггеры (где есть), детект перебора, блокировка после аномалий — без блокировки легитимных всплесков.
58. Тесты управления сессиями углублённо {{модуль}}: фиксация, таймаут неактивности, одновременные сессии, инвалидация при смене пароля/прав, безопасные cookie-флаги, CSRF на всех изменяющих.
59. Тесты криптографии {{модуль}}: секреты сравниваются таймингобезопасно, пароли хешируются сильным алгоритмом с солью, токены криптостойкие (не предсказуемые), TLS обязателен, ключи не в репо.
60. Тесты авторизации API-ключей/токенов {{модуль}}: скоупы соблюдаются (ключ read не пишет), отзыв немедленен, истечение, ротация без даунтайма, ключ в логах замаскирован.
61. Тесты защиты файловых операций {{модуль}}: path traversal, symlink-атаки, magic-bytes проверка типа (не расширение), лимит размера до чтения, изоляция директорий, антивирус-хук (если есть).
62. Тесты защиты от injection всех видов {{продукт}}: SQL/NoSQL/command/LDAP/template/header injection в каждой точке пользовательского ввода, попадающей в интерпретатор — параметризация/экранирование/валидация.
63. Тесты защиты данных {{продукт}}: PII шифруется в хранилище и маскируется в логах/ответах/ошибках, право на удаление (GDPR), минимизация данных в ответах, аудит доступа к чувствительному.
