## Измерение

1. Прогони покрытие {{модуль}} exact command из active profile `COMMANDS.md`/`CI-PIPELINE.md`, выведи процент по пакетам/файлам, отсортируй по возрастанию; артефакты профилирования удали после снятия метрик.
2. Сравни покрытие {{модуль}} с целевыми порогами {{пороги}}: таблица пакет | факт | цель | дельта | приоритет (критичность зоны × размер дельты).
3. Построй тренд покрытия {{модуль}} по git-истории за {{период}}: растёт ли покрытие вместе с кодом или отстаёт; точки резкого падения — с привязкой к коммитам.
4. Настрой измерение покрытия так, чтобы оно НЕ включало сгенерированный код, моки, тестовые файлы — иначе процент врёт вверх; проверь текущую конфигурацию на это.
5. Раздели покрытие {{модуль}} по типам тестов: что даёт юнит-слой, что интеграционный, что E2E — пересечение и уникальный вклад каждого уровня.

## Gap-анализ (важнее процента)

6. Проанализируй непокрытые строки {{отчёт}} по КАЧЕСТВУ, не количеству: раздели на (а) ветки с логикой и риском — нужны тесты, (б) тривиальные геттеры/делегаты — пропустить, (в) мёртвый код — удалить. Не гонись за процентом ради процента.
7. Найди непокрытые ветки обработки ошибок в {{модуль}}: catch/if err/recover без теста — самые опасные дыры (ошибки не тестируют → в проде ведут себя непредсказуемо). Список с приоритетом.
8. Найди в {{модуль}} функции с высокой цикломатической сложностью и низким покрытием — пересечение «сложное И непроверенное» = главные кандидаты на тесты, отсортируй по риску.
9. Проверь покрытие критичных зон {{модуль}} из active profile `PROJECT.md` Verified constraints: для них цель — покрытие ВЕТОК, не строк; непокрытая ветка в критичной зоне — блокер.
10. Найди «покрытые, но не проверенные» строки: код выполняется тестом, но его результат не ассертится (покрытие есть, проверки нет) — ложное чувство защиты; выяви по несоответствию покрытия и ассертов.
11. Составь матрицу требования × покрытие для {{модуль}}: каждое требование из спеки — есть ли тест, покрывающий его код? Требование без покрытия — дыра опаснее строки без покрытия.
12. Предложи тест-кейсы на непокрытые ветки {{функция}}: для каждой — какие вход/состояние приведут в неё, какой ожидаемый результат (из спеки, не из кода); ранжируй по риску.

## Пороги и гейты

13. Предложи реалистичные пороги покрытия для {{модуль}} по критичности: security/деньги/данные — высокий, UI-обвязка — умеренный, сгенерированное — исключить; обоснуй каждый, не «80% везде».
14. Настрой coverage-гейт в CI для {{модуль}}: падение при снижении относительно базовой линии (не абсолют — чтобы новый код не размывал), исключения задокументированы, гейт быстрый.
15. Настрой diff-coverage гейт: новый/изменённый код в PR должен иметь покрытие ≥{{порог}}, старый долг не блокирует — фокус на «не ухудшать».
16. Проверь, не гейтит ли текущий порог покрытия ФЕЙКОВО: тесты без ассертов дают покрытие. Выбери 10 покрытых функций критичной зоны и для каждой найди утверждение, зависящее от её поведения. Не нашёл — процент накручен.

## Сила утверждений

17. Разбери {{функция}}: перечисли 10 изменений её поведения (инверсия условия, off-by-one, удалённая ветка, другой оператор или константа) и для каждого назови тест, который обязан упасть. Изменение без падающего теста = дыра, несмотря на «покрытие».
18. Составь по {{модуль}} карту «поведение → тест, который его защищает». Поведение без защищающего теста приоритизируй по критичности зоны.
19. Разбери незащищённое поведение {{отчёт}}: каждый — либо недостающий ассерт (почини тест), либо изменение, не влияющее на результат (задокументируй исключение), либо мёртвый код (удали).
20. Сравни процент покрытия с долей покрытых строк, у которых есть зависящее от них утверждение. Большой разрыв — сигнал «тесты выполняют, но не проверяют»; список самых показательных файлов.

## Отчётность и приоритизация

21. Составь план закрытия покрытия {{модуль}} до {{цель}}: ранжируй дыры по (риск × частота изменений файла), оцени объём тестов на каждую, порядок «максимум защиты за минимум усилий».
22. Найди «горячие непокрытые» файлы: высокая частота изменений (git) + низкое покрытие за {{период}} — здесь баги наиболее вероятны и наиболее дороги; топ-список.
23. Оцени ROI дозакрытия покрытия {{модуль}} с {{X}}% до {{Y}}%: какие классы багов поймаем, сколько тестов, стоимость поддержки — стоит ли, или усилия эффективнее в другом модуле.
24. Составь coverage-дашборд {{продукт}}: по модулям процент + доля защищённого поведения + тренд + критичность — одной таблицей со светофорами для приоритизации.
25. Напиши сводку покрытия для стейкхолдеров: не голый процент, а «что защищено / где риски / план» — на языке рисков, не метрик.

## Специальные виды покрытия

26. Оцени покрытие сценариев (не кода) для {{фича}}: матрица TC × автоматизация — какие пользовательские сценарии из спеки не покрыты ни одним тестом любого уровня.
27. Оцени покрытие негативных путей {{модуль}}: доля тестов на ошибки/границы/denial от общего числа — перекос в happy path списком по файлам.
28. Оцени покрытие интеграционных точек {{модуль}}: каждая пара «модуль × внешняя система» — есть ли тест успеха/ошибки/таймаута/реконнекта; дыры таблицей.
29. Оцени покрытие конфигураций {{продукт}}: комбинации фича-флагов/окружений, реально встречающиеся в проде, — какие ни разу не тестируются.

## Диагностика метрики

30. Проверь честность метрики покрытия {{модуль}}: включены ли тестовые/сгенерированные файлы (завышают), считаются ли ветки или только строки (строки врут об if/else), исключён ли dead code.
31. Найди тесты, накручивающие покрытие без ценности: прогоняют код в try/catch без ассертов, «дымовые» тесты «просто вызвать функцию» — переоцени как реальную защиту или удали.
32. Сравни покрытие в CI и локально {{модуль}}: расхождение означает разные наборы прогоняемых тестов (флаги/теги/окружение) — выясни, какой набор канонический.

## Связки

33. Связка «поднять покрытие с умом»: #6 (качественный gap) → #9 (критичные ветки) → #12 (кейсы на дыры) → #21 (план по ROI) для {{модуль}}.
34. Связка «проверить честность»: #16 (фейк-гейт) → #17 (разбор утверждений) → #20 (разрыв метрик) → #31 (накрутки) для {{модуль}}.
35. Связка «гейт для новой работы»: #13 (пороги) → #15 (diff-coverage) → #14 (базовая линия) для {{модуль}}.
36. Связка «отчёт руководству»: #24 (дашборд) → #22 (горячие зоны) → #25 (сводка на языке рисков) для {{продукт}}.

## Виды покрытия углублённо

37. Измерь branch coverage {{модуль}} (не line): каждая ветвь if/switch/тернарник пройдена в обе стороны; line-покрытие врёт об if без else — покажи разрыв line% vs branch%.
38. Измерь condition/decision coverage {{функция}} для сложных булевых условий: каждое подусловие в составном (A && B || C) проверено независимо — MC/DC для критичных зон.
39. Измерь path coverage критичной {{функция}}: комбинации ветвей (не только каждая по отдельности) — реалистичные пути через несколько условий; полный path обычно невозможен, покрой рискованные.
40. Измерь покрытие циклов {{функция}}: ноль итераций, одна, несколько, максимум — типичные баги на границах цикла (пустая коллекция, единственный элемент).
41. Оцени покрытие обработки ошибок отдельной метрикой {{модуль}}: доля покрытых catch/error-путей — обычно самая низкая и самая опасная зона.

## Gap-анализ по риску (расширение)

42. Построй тепловую карту риска {{продукт}}: модуль × (покрытие ветвей × частота изменений × критичность) — визуальный приоритет, где тесты нужнее всего.
43. Найди «иллюзию покрытия» {{модуль}}: высокий line%, но ключевые бизнес-правила (из спеки) не проверены ни одним ассертом — покрытие кода ≠ покрытие требований.
44. Сопоставь покрытие с картой инцидентов {{период}}: зоны прошлых багов имеют адекватное покрытие сейчас? Повторный инцидент в непокрытой зоне — приоритет №1.
45. Найди недостижимый код через анализ покрытия {{модуль}}: строки, которые НЕ покрываются ни одним тестом и не могут быть достигнуты (мёртвые ветки) — кандидаты на удаление, а не на тесты.
46. Оцени покрытие конкурентных путей {{модуль}}: строки в критических секциях/горутинах — покрыты ли тестами под нагрузкой/параллелизмом (обычный прогон не заходит в гонки).

## Инструменты и настройка (расширение)

47. Настрой инкрементальное/дифференциальное покрытие в {{CI}}: покрытие только изменённых строк PR, комментарий с непокрытыми строками нового кода inline.
48. Настрой объединение покрытия из нескольких прогонов {{продукт}}: юниты + интеграция + E2E → суммарная картина (что покрыто только E2E — кандидат на понижение уровня).
49. Настрой исключения из покрытия осознанно {{модуль}}: сгенерированный код, тривиальные аксессоры, main/bootstrap — задокументируй каждое исключение, чтобы не пряталась реальная дыра.
50. Проверь корректность инструментации покрытия {{продукт}}: покрытие считается с учётом всех прогоняемых тестов (не только части), флаги сборки не отключают код, нет расхождения CI/локально.
51. Настрой визуализацию покрытия для ревью {{модуль}}: непокрытые строки видны в diff/IDE, ревьюер видит, что новый код не покрыт, до мержа.

## Сила утверждений (расширение)

52. Проведи полный разбор утверждений {{модуль}}: доля защищённого поведения по файлам и типам, незащищённое списком; приоритизируй критичные зоны — разбор трудоёмок, не на весь код сразу.
53. Категоризируй незащищённое поведение {{отчёт}}: (а) недостающий ассерт → усилить тест, (б) изменение, не влияющее на результат → задокументировать, (в) мёртвый код → удалить, (г) слабый тест → переписать.
54. Заведи гейт силы утверждений для критичных модулей {{список}}: минимальная доля защищённого поведения, гейт только на новом коде (исторический долг не блокирует), проверка инкрементальная.
55. Сравни ROI разбор силы утверждений vs coverage для {{модуль}}: assertion ловит слабые ассерты, но дорог; где применять постоянно, где разово, где не стоит.

## Специализированное покрытие

56. Оцени покрытие API-контракта {{API}}: каждый эндпоинт × статус-код (2xx/4xx/5xx) имеет тест — матрица, дыры в error-путях.
57. Оцени покрытие пользовательских сценариев {{продукт}}: критичные user journeys из аналитики — каждый покрыт E2E/интеграцией? Не код, а бизнес-путь.
58. Оцени покрытие конфигураций/флагов {{продукт}}: реально встречающиеся в проде комбинации флагов — какие ни разу не тестируются (untested prod config = мина).
59. Оцени покрытие миграций/версий данных {{продукт}}: миграции протестированы на реальных структурах данных, откаты, идемпотентность — обычно слепая зона.
60. Оцени покрытие интеграционных точек {{продукт}}: каждая внешняя зависимость × (успех/ошибка/таймаут/деградация) — матрица устойчивости.

## Отчётность и коммуникация (расширение)

61. Составь honest coverage report {{продукт}}: не только %, но и «что это % значит» — branch vs line, долю защищённого поведения, покрытие требований, известные дыры; % без контекста вводит в заблуждение.
62. Объясни стейкхолдеру, почему «80% покрытия» — не гарантия качества: покажи пример высокого покрытия со слабыми ассертами (assertion), свяжи с реальными escaped-багами.
63. Составь план повышения качества (не процента) {{модуль}}: усиление ассертов слабых тестов (assertion), покрытие error-путей и требований — а не гонка line%.
64. Настрой coverage-бюджет по модулям {{продукт}}: разные цели по критичности, тренд «не ухудшать», исключения задокументированы — вместо единого нереалистичного порога.

## Шаблоны и обслуживание

69. Сгенерируй скрипт снятия покрытия {{модуль}} по канону стека с записью профиля вне репо и очисткой артефактов после — не коммить дампы.
70. Сгенерируй coverage-дашборд-шаблон {{продукт}}: модуль | branch% | assertion | тренд | критичность | дыры — со светофорами.
71. Сгенерируй PR-комментарий-шаблон с diff-coverage: непокрытые строки нового кода, дельта к базовой линии, ссылка на полный отчёт.
72. Сгенерируй чек-лист «честного покрытия» для ревью: branch не line, ассерты не только выполнение, требования покрыты, error-пути покрыты — для аудита.
73. Настрой регулярный отчёт деградации покрытия {{продукт}}: файлы, где покрытие упало за {{период}}, с привязкой к коммитам — раннее предупреждение.

## Продвинутый анализ

74. Проведи анализ «тесты без покрытия»: тесты, которые прогоняются, но не увеличивают покрытие (дублируют другие полностью) — кандидаты на удаление после проверки.
75. Проведи анализ «код без тестов, но в проде критичный»: пересечение низкого покрытия и высокой нагрузки/критичности (из метрик прода) — приоритет.
76. Оцени эффективность каждого уровня пирамиды по покрытию {{продукт}}: сколько уникального покрытия даёт каждый уровень, что дублируется — оптимизация состава.
77. Найди «over-tested» зоны {{продукт}}: код с избыточным покрытием (много тестов на тривиальное) при дырах в сложном рядом — перебалансируй усилия.
78. Проведи корреляционный анализ покрытие↔дефекты {{период}}: подтверди/опровергни, что низкопокрытые зоны дают больше багов — если нет, покрытие меряет не то.

## Процесс

79. Внедри coverage-review в процесс {{команда}}: не гнаться за %, а обсуждать на ревью «что важное не покрыто» — качество через дискуссию, не через гейт-число.
80. Составь политику покрытия команды {{продукт}}: цели по критичности, что меряем (branch+assertion для критичного), «не ухудшать», как обосновывать исключения — документ в context/.
