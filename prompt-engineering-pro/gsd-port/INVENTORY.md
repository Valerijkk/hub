# Инвентаризация GSD → Touchstone Pro

Полный разбор 79 скилов `~/.claude/skills/gsd-*` с решением по каждому.
Прочитан frontmatter и тело каждого `SKILL.md`; назначение взято из файла,
не из названия.

Pro — издание для разработки продукта, поэтому фильтр один: помогает ли
паттерн команде довести фичу от «что делаем» до «доказано, что работает».
Всё, что обслуживает саму установку GSD, отсекается.

## Сводка

| Решение | Скилов | Что значит |
|---------|--------|------------|
| ПОРТИРОВАН | 7 | Паттерн уже лежит в Pro — playbook, skill или extract |
| АДАПТИРОВАТЬ | 47 | Контракт ценный, но переписывается под Pro без `.planning/` и `gsd-sdk` |
| НЕ ТАЩИМ | 25 | Инфраструктура GSD, дубль, автономный режим или служебное |

Принцип из README Pro сохранён: берём контракты и гейты, тела скилов
целиком не копируем.

## Жизненный цикл фазы

Ядро GSD и ядро Pro. Четыре шага уже перенесены, остальные девять — дельта.

| `gsd-extract_learnings` | Вытаскивает решения, уроки, паттерны и сюрпризы из артефактов закрытой фазы в LEARNINGS.md | АДАПТИРОВАТЬ | Берём четыре рубрики (решение / урок / паттерн / сюрприз). В Pro — шаблон ретро фазы рядом с `playbooks/handoff-state.md`: без него знание остаётся в чате |

| `gsd-ui-phase` | Создаёт дизайн-контракт UI-SPEC.md для фронтовой фазы через пару агентов researcher → checker с вердиктами BLOCK/FLAG/PASS | АДАПТИРОВАТЬ | Берём саму идею дизайн-контракта до кода и трёхзначный вердикт проверяющего. | `gsd-ai-integration-phase` | Дизайн-контракт AI-SPEC.md для фаз с AI: выбор фреймворка, гайд из официальных доков, стратегия оценки, guardrails, продовый мониторинг | АДАПТИРОВАТЬ | Берём структуру контракта: критические режимы отказа → измеримые рубрики → эталонный датасет. В Pro — `extracts/ai-spec.md`; для команды, которая сама строит AI-фичи, это единственный способ не сдать «оно вроде отвечает» |

## Аудит и качество

Самый недоукомплектованный кластер в Pro: ревью-роли описаны, но
процедур с классификацией находок и вердиктами нет.

| Скил | Что делает | Решение | Обоснование |
|------|------------|---------|-------------|
| `gsd-code-review` | Ревью изменённых за фазу файлов на баги, безопасность и качество; три глубины quick / standard / deep, приоритет источников файлов `--files` > SUMMARY > git diff | АДАПТИРОВАТЬ | Берём три глубины и явный порядок определения scope. В Pro — процедура в `agents/code-reviewer.md`: сейчас роль есть, а как ограничить scope и на какую глубину идти — не сказано |
| `gsd-code-review-fix` | Чинит находки ревью отдельным агентом-фиксером, коммитит каждую атомарно, по флагу `--auto` крутит цикл fix → re-review, потолок 3 итерации | АДАПТИРОВАТЬ | Берём разделение ревьюера и фиксера (в Pro уже `readonly: true` у ревьюера) и жёсткий потолок итераций. В Pro — `playbooks/review-fix-loop.md`: без потолка агент чинит бесконечно |
| `gsd-audit-uat` | Сканирует все фазы на pending / skipped / blocked / human_needed UAT, сверяет с кодом на протухшую документацию, выдаёт приоритизированный план ручных проверок | АДАПТИРОВАТЬ | Берём четыре статуса непройденной приёмки и детект протухшего статуса. В Pro — обязанность `agents/qa-manual.md`: «отложено» перестаёт быть невидимым |
| `gsd-audit-fix` | Гоняет аудит, классифицирует находки на авто-чинимые и только-ручные, чинит с проверкой тестами и атомарными коммитами; `--max N`, `--severity`, `--dry-run` | АДАПТИРОВАТЬ | Берём классификацию auto-fixable vs manual-only и режим `--dry-run` как обязательный первый проход. Автономную часть — нет: правка идёт через гейт человека, как в остальном Pro |
| `gsd-audit-milestone` | Проверяет, достигнут ли DoD вехи: покрытие требований, межфазная интеграция, сквозные сценарии; агрегирует существующие VERIFICATION.md | АДАПТИРОВАТЬ | Берём три оси проверки вехи и принцип «агрегируем уже собранные доказательства, а не перепроверяем». В Pro — `playbooks/milestone-audit.md`, верхний ярус goal-backward над фазовым |
| `gsd-plan-milestone-gaps` | Читает отчёт аудита вехи, группирует разрывы в фазы и заводит их в roadmap одной командой | АДАПТИРОВАТЬ | Берём замыкание петли: аудит без автоматического заведения работы — просто список претензий. В Pro — финальный шаг того же playbook, выход — задачи по `extracts/backlog-task.md` |
| `gsd-validate-phase` | Аудит покрытия валидации по Найквисту для закрытой фазы; три состояния — есть VALIDATION.md, есть только SUMMARY, фаза не исполнялась | АДАПТИРОВАТЬ | Берём машину трёх состояний ретроспективного аудита (аудит / реконструкция по артефактам / выход с подсказкой) — она универсальна для всех «ретро»-проверок Pro. ## Что это меняет в Pro

Инвентаризация вскрыла семь пробелов. Все — в зоне «разработка продукта»,
то есть ровно то, ради чего существует Pro.

1. **Нет гейта до discuss.** `spec-phase` показывает, что «что делаем»
   фиксируется отдельным шагом с числовым порогом неоднозначности. У Pro
   цикл начинается сразу с discuss, и невнятная постановка проезжает
   дальше по конвейеру. Нужен `extracts/spec-gate.md` и шаг 0 в
   `playbooks/gsd-lifecycle.md`.
2. **Нет петли planner ↔ checker.** В GSD план проверяется отдельным
   агентом goal-backward до исполнения и переписывается до pass. В Pro
   goal-backward стоит только на приёмке — то есть плохой план ловится
   после написания кода. Самая дорогая из найденных дыр.
3. **Аудит описан ролями, но не процедурами.** `code-review` с тремя
   глубинами, `code-review-fix` с потолком в 3 итерации, `audit-uat` с
   четырьмя статусами, `audit-milestone` с тремя осями — у Pro есть
   `agents/code-reviewer.md` и `agents/security-reviewer.md`, но нет ни
   классификации находок, ни правил определения scope, ни потолка
   итераций починки.
4. **Правило «волна без пересечения файлов» нечем исполнить.**
   `analyze-dependencies` даёт три конкретных критерия зависимости —
   пересечение файлов, семантика, поток данных. Без них нарезка на волны
   держится на интуиции оркестратора.
5. **Нет дизайн-контрактов до кода.** `ui-phase` и `ai-integration-phase`
   выдают UI-SPEC и AI-SPEC с вердиктами BLOCK/FLAG/PASS до реализации, а
   `ui-review` и `eval-review` проверяют результат по шкале. У Pro есть
   `frontend-dev`, но фронт и AI-фичи начинаются без контракта.
6. **Знание фазы никуда не оседает.** `extract_learnings`,
   `milestone-summary`, `spike-wrap-up` и `sketch-wrap-up` устроены
   одинаково: работа не закрыта, пока результат не превращён в
   переиспользуемый артефакт. В Pro этого шага нет вообще — уроки
   остаются в чате.
7. **Между STATE и фазой ничего нет.** `thread` держит межсессионную
   работу, не принадлежащую фазе, а `plant-seed` — идею с условием
   всплытия. В Pro всё непристроенное валится в STATE и там теряется.

Восьмое, не пробел, а подтверждение: ретро-аудиты GSD (`validate-phase`,
`secure-phase`, `eval-review`) устроены по одной машине трёх состояний —
артефакт есть, артефакта нет но есть следы работы, работы не было. Эту
машину стоит вынести в Pro один раз как общий скелет любой
ретроспективной проверки, а не переписывать в каждой процедуре.
