# Ролевая модель GSD — разбор и переносимые паттерны

> Разбор 31 агента `~/.claude/agents/gsd-*.md` против 12 ролей Touchstone Pro.
> Цель — не скопировать ростер, а вытащить механики, которые в Pro
> сейчас держатся на дисциплине, а не на контракте.

Тела агентов GSD сюда не переносятся: они весят 5–47 KB и завязаны на
`.planning/`, `gsd-sdk query` и шаблоны GSD. Переносится структура ответственности.

## 2. Паттерны, которые стоит перенести

### 2.1 Разрез по фазе цикла, а не по предметной области

GSD режет ответственность по вопросу «какой артефакт на входе и какой на выходе»:

```
researcher → planner → checker → executor → verifier
   факты      план     вердикт    код       вердикт
```

Каждая передача — новый агент с новым контекстом. Смысл не в специализации,
а в том, что **автор не принимает свою работу**. В Pro эта граница есть только
для `code-reviewer` (не автор diff). Для плана и для приёмки фазы автором и
приёмщиком остаётся `orchestrator`.

Формулировка из `gsd-plan-checker`, которую стоит взять дословно как принцип:

> `gsd-verifier` проверяет, что код **достиг** цели. `gsd-plan-checker` проверяет,
> что план **достигнет** цели. Одна методология, разное время, разный объект.

### 2.2 Набор инструментов как структурная гарантия

Read-only у GSD — не просьба в теле промпта, а отсутствие Write/Edit во frontmatter.

| Агент | Что не может | Зачем |
|-------|--------------|-------|
| plan-checker | Писать вообще ничего | Не может «дописать в план недостающее» и объявить PASS |
| ui-checker | Менять UI-SPEC.md | Явно: «report findings, let the researcher fix» |
| integration-checker | Менять код | Проверяет связи, не чинит их |
| assumptions-analyzer | Писать | Возвращает допущения в оркестратор, не фиксирует их сам |
| user-profiler | Bash, Grep, Glob | Только Read: агент, читающий чужие сообщения, не должен уметь ходить в систему |
| research-synthesizer | Grep, Glob | Синтезатор не добывает новые факты, только сводит выданные |

Отдельный приём — **граница по объекту там, где запись нужна**.
`gsd-nyquist-auditor` имеет Write и Edit, но контракт сужает объект:

> Файлы реализации — read-only. Создавать и менять можно только тесты, фикстуры
> и VALIDATION.md. Баг в реализации → ESCALATE, не чинить.

Правило для Pro: набор инструментов и список разрешённых к записи путей —
часть контракта роли, а не деталь раннера. `code-reviewer` и `security-reviewer`
уже помечены `readonly`, но `{{allow_fix}}=false` живёт в теле, а не в границе.

### 2.3 Парность: кто проверяет за кем

| Продюсер | Чекер | Объект проверки | Словарь вердикта |
|----------|-------|-----------------|------------------|
| planner | plan-checker | PLAN.md | VERIFICATION PASSED / ISSUES FOUND |
| executor | verifier | код против цели фазы | PASS / gaps |
| verifier (по фазам) | integration-checker | стыки фаз и E2E | по связям, не по существованию |
| code-reviewer | code-fixer | REVIEW.md → фиксы | FIXED / SKIPPED + причина |
| ui-researcher | ui-checker | UI-SPEC.md | BLOCK / FLAG / PASS |
| исполнитель UI | ui-auditor | реализованный UI | скор 1–4 по 6 столпам |
| doc-writer | doc-verifier | утверждения в доках | PASS / FAIL / SKIP по каждому claim |
| planner (threat model) | security-auditor | митигации в коде | SECURED / OPEN_THREATS / ESCALATE |
| eval-planner | eval-auditor | покрытие eval | COVERED / PARTIAL / MISSING |

Механика пары: чекер читает **ровно тот артефакт**, который написал продюсер,
и возвращает список issue с `severity` и `fix_hint`. Он не переписывает и не
«поправил по мелочи». Возврат идёт продюсеру, а не следующему по цепочке.

### 2.4 Revision Gate: ограничитель цикла и детекция застоя

Из `get-shit-done/references/gates.md` (не агент — общий справочник GSD) — четыре типа ворот, к одному из которых обязан
сводиться любой чекпоинт:

| Ворота | Когда | Поведение при провале |
|--------|-------|------------------------|
| Pre-flight | На входе, до работы | Блок входа, частичной работы не создано |
| Revision | После продюсера | Возврат продюсеру с конкретной обратной связью, cap на итерации |
| Escalation | Цикл ревизии исчерпан | Пауза, варианты человеку, ожидание решения |
| Abort | Продолжение вредно | Стоп, состояние сохранено, причина в отчёте |

Ключевая деталь Revision Gate, которой в Pro нет:

> Цикл эскалирует досрочно, если число issue **не уменьшилось** между двумя
> подряд итерациями. После max-итераций эскалирует безусловно.

Это ловит косметические правки без прогресса. Cap калибруется по стоимости
итерации: дорогая операция — меньше попыток. У Pro есть «re-review после фикса»
без cap и без стоп-условия — цикл потенциально бесконечный.

Эвристика выбора: начинай с Pre-flight; если проверка после произведённой
работы — это Revision; если цикл не сходится — Escalation; если продолжать
опасно — Abort.

### 2.5 Агент-синтезатор параллельных выходов

`gsd-research-synthesizer` — отдельный вызов после четырёх параллельных ресёрчеров:

1. Ресёрчеры **пишут файлы, но не коммитят**. Коммитит синтезатор — одним
   коммитом на весь набор. В git нет полусостояния «два из четырёх».
2. Инструменты синтезатора урезаны до `R W B`: он не может пойти догуглить.
   Синтез отделён от добычи.
3. Контракт требует мнения: «Be opinionated. Потребителю нужны рекомендации,
   а не обтекаемые сводки». Критерий качества — «synthesized, not concatenated».
4. Обязательные разделы: **Confidence Assessment** по каждой области-источнику
   и **Gaps to Address** — синтезатор обязан признать, чего не знает.

В Pro синтез сейчас делает сам `orchestrator` (п.7 «Сбор outputs»). Он же
нарезал волну и уже прочитал часть выходов по ходу — это не независимый свод.
Переносить стоит правило, а не роль: при ≥3 параллельных исполнителях свод
делается отдельным вызовом с урезанными инструментами, и точка коммита — одна.

### 2.6 Контракт «upstream → downstream» в теле роли

Почти каждый агент GSD несёт два блока-таблицы:

- `<upstream_input>` — какие секции входного артефакта роль читает и как их трактует
  (например: `## Decisions` — LOCKED, реализовать точно; `## Deferred Ideas` —
  вне скоупа, флагать при появлении; `## Claude's Discretion` — свобода, не флагать);
- `<downstream_consumer>` — какая секция выхода кем и зачем будет прочитана.

Эффект: роль знает, какие поля обязаны быть заполнены, потому что знает
конкретного потребителя. В Pro есть блок `Handoff` («кому / что»), но без
разбивки по секциям артефакта. Дешёвое усиление: добавить в каждую роль Pro
таблицу «секция выхода → потребитель → зачем».

### 2.7 Именованные измерения вместо чек-листа прозой

`gsd-plan-checker` держит 12+ пронумерованных измерений. Каждое — по шаблону:
**Question** → **Process** (шаги) → **Red flags** → **пример issue в YAML**.
Плюс два правила:

- пропуск измерения обязан быть объявлен: `Dimension 12: SKIPPED (no PATTERNS.md found)`;
- у каждого измерения свой класс severity, а не общий «на усмотрение».

Issue — машиночитаемый объект, а не абзац:

```yaml
issue:
  dimension: scope_reduction
  severity: blocker
  description: "План сводит D-26 с «расчёт стоимости» к «статичным подписям»"
  plan: "03"
  task: 1
  fix_hint: "Либо реализовать D-26 полностью, либо вернуть PHASE SPLIT RECOMMENDED"
```

Оркестратор роутит по полям, не парся прозу. В Pro формат находки
(`[SEVERITY] path:line — проблема → фикс`) уже строгий, но не структурированный
по измерению и без `fix_hint` как обязательного поля.

### 2.8 Отдельные механики, готовые к переносу

| Механика | Источник | Суть |
|----------|----------|------|
| **Scope Reduction Detection** | plan-checker, D-7b | Лексические маркеры тихого урезания: `v1`, `simplified`, `static for now`, `hardcoded`, `placeholder`, `will be wired later`, `stub`, `too complex`, оценки времени как оправдание. Совпадение → сверить с исходным решением → всегда **blocker**, никогда warning |
| **Key links, не артефакты** | plan-checker D-4, integration-checker | Проверять проводку `component → API → DB`, а не наличие файлов. «Existence ≠ Integration» |
| **User-observable truths** | plan-checker D-6 | Критерий приёмки — «пароли защищены», а не «bcrypt установлен». Реализационная формулировка truth = дефект плана |
| **Числовые пороги скоупа** | plan-checker D-5 | 2–3 задачи на план норма, 4 warning, 5+ blocker; 5–8 файлов норма, 15+ blocker. Число вместо «не делай большие планы» |
| **Deviation rules 1–4** | executor | Авто-фикс багов / авто-добавление критичного (валидация, authz, обработка ошибок) / авто-фикс блокеров / **СТОП и спросить** на архитектурном изменении. Плюс fix attempt limit и явный приоритет правил |
| **Analysis paralysis guard** | executor | 5+ подряд Read/Grep/Glob без единого Edit/Write/Bash → прекратить разведку, действовать |
| **Per-finding rollback** | code-fixer | Перед фиксом записать список файлов к правке. Откат = `git checkout -- {file}`, не перезапись через Write (частичная запись при сбое портит файл). Откат находки N не трогает коммиты 1..N−1 |
| **3-tier verification** | code-fixer | Tier 1 (минимум, всегда) → Tier 2 (если доступен линтер/типы) → Tier 3 (fallback). Полный прогон тестов между фиксами **запрещён** — он на этапе verifier |
| **Re-verification mode** | verifier, шаг 0 | При повторном заходе: полная трёхуровневая проверка только упавших пунктов, для прошедших — быстрый регрессионный чек существования. Экономит контекст на итерациях |
| **Calibration tiers** | advisor-researcher, assumptions-analyzer | Один агент, три глубины вывода: `full_maturity` / `standard` / `minimal_decisive`. Глубина задаётся вызовом, а не тремя ролями |
| **Схема допущения** | assumptions-analyzer | `Assumption` → `Why this way` (обязательно путь к файлу) → `If wrong` (конкретное последствие, не «могут быть проблемы») → `Confidence: Confident\|Likely\|Unclear`. Плюс отдельный раздел `Needs External Research` |
| **Фокус-области одной роли** | codebase-mapper | Четыре параллельных запуска одного агента с фокусом `tech` / `arch` / `quality` / `concerns` вместо четырёх ролей. Каждый пишет свои документы сам, оркестратор получает только подтверждение |
| **Skip rules верификатора** | doc-verifier | Явный список того, что **не** проверять: примеры после «e.g.», placeholder-пути (`your-`, `<name>`, `example`), цитаты вендора, блоки с тегом `diff`/`example`/`template`. Без этого верификатор тонет в ложных срабатываниях |
| **Context budget** | mapper, checker, auditor | «Грузить индекс скилов (лёгкий), файлы реализации — инкрементально, под конкретную проверку. Не грузить полные AGENTS.md (100 KB+)» |
| **Побочный артефакт не грязнит репо** | ui-auditor | Перед первым скриншотом — гарантировать `.gitignore` в каталоге вывода. Класс правила: роль, порождающая бинарники или дампы, обязана закрыть их от git до первой записи |
| **Training data = гипотеза** | project-researcher | Знание модели о версиях и API — гипотеза, подлежащая проверке в источнике. Плюс запрет негативных утверждений без доказательства («библиотека X это не умеет» требует ссылки) |

## 3. Дыры в ростере Pro

Для каждой дыры вопрос один: **какой процесс останется без владельца, если её не завести**.

### 3.1 Заводить ролями (3)

| Роль | Процесс без владельца | Обоснование |
|------|------------------------|-------------|
| **verifier** | Приёмка плана до исполнения и приёмка результата после | Сейчас `orchestrator` режет планы (п.4.2) и сам же принимает по `verify-goal` (п.4.8). Автор — приёмщик. Ни один сторонний агент не читает план до того, как на нём сожгут контекст. Отдельная роль делает независимой приёмку и позволяет дать ей readonly-границу, которую `orchestrator` иметь не может |
| **researcher** | Доказательный внешний ресёрч с уровнями доверия | Никто в Pro не владеет вопросом «этот факт про библиотеку ещё актуален». `architect` выбирает фреймворк, но по памяти — ровно тот анти-паттерн, который `orchestrator` сам запрещает для выбора моделей («Выбор по памяти, маркетинговому имени или неподтверждённому benchmark»). Layer 05 задаёт пирамиду evidence для кода, но не для внешних фактов |
| **ui-reviewer** | Независимая оценка визуального качества | `frontend-dev` пишет UI и сам решает, что он хорош; `qa-manual` проверяет сценарии, а не типографику, цвет и состояния пустоты/ошибки. Автор не видит собственных дефолтов. Роль readonly, вход — реализованный UI и (если есть) дизайн-контракт, выход — скор по столпам и три приоритетных фикса |

Три роли берут Pro с 12 до 15. Больше добавлять не нужно: остальное покрывается
режимами.

**Про verifier — почему одна роль, а не две.** GSD держит `plan-checker` и
`verifier` раздельно, и объяснение честное: разное время, разный объект. Но
методология у них одна (goal-backward), и разделение продиктовано конвейером
команд GSD, а не природой работы. Для Pro корректнее одна роль с режимами:
`plan` (проверка плана, readonly, без Write), `goal` (проверка результата фазы),
`integration` (стыки на уровне майлстоуна), `claims` (сверка утверждений в
доках с кодом). Роль — это контракт ответственности, а не набор инструментов.

### 3.2 Закрывать режимами и шагами, без новых ролей (8)

| Процесс без владельца | Кому отдать | Почему не роль |
|-----------------------|-------------|----------------|
| Кросс-фазная интеграция и E2E-стыковка | `verifier`, режим `integration` | Та же goal-backward логика, поднятая с фазы на майлстоун. `qa-manual` смотрит продукт глазами пользователя, а не граф экспорт/импорт — но разводить два верификатора на одну методологию избыточно |
| Сверка фактов в доках с кодом | `verifier`, режим `claims` | Сейчас `docs-writer` заявлен как «сверка с фактами», то есть проверяет сам себя. Отдельная роль ради проверки одного типа артефакта не окупается — окупается разрыв «автор ≠ проверяющий» |
| Карта аналогов «новый файл → на что похож» | Шаг в `skills/phase-plan` | Разовая аналитическая процедура перед фазой, а не устойчивая зона ответственности. У Pro уже есть `PATTERN-INDEX.md` и approved cards — не хватает шага, который сопоставляет **конкретные новые файлы** с конкретными аналогами и цитирует строки |
| Явные допущения до планирования | Шаг в `skills/phase-plan` | Схема из §2.8 (`Assumption / Why / If wrong / Confidence`) — это формат вывода, а не роль. Владелец — тот, кто планирует |
| Свод параллельных выходов | Правило в `extracts/wave-protocol.md` | Владелец процесса есть — `orchestrator`. Не хватает правила: при ≥3 параллельных выходах свод делается отдельным вызовом, точка коммита одна, синтезатор не добывает новых фактов |
| Постфактумный аудит покрытия требований тестами | `qa-auto`, режим аудита | Тот же объект (автотесты) и та же экспертиза. Что добавить из GSD: жёсткая граница «файлы реализации read-only, баг в реализации → эскалация, не фикс» и лимит на итерации отладки теста |
| Трассируемость угроза → митигация → код | `security-reviewer`, режим `threat register` | Роль есть, не хватает механики: реестр угроз фиксируется на этапе плана, аудит сверяет наличие каждой митигации в коде и выдаёт SECURED / OPEN_THREATS / ESCALATE вместо свободного списка находок |
| Ведение изолированной сессии отладки | `orchestrator` + `playbooks/handoff-state.md` | Ценна идея, а не агент: длинный цикл отладки живёт в отдельном контексте и отдаёт наверх компактный итог, а не всю переписку с гипотезами |

### 3.3 Не заводить сейчас (сознательный отказ)

| Дыра | Решение |
|------|---------|
| AI-контур: framework-selector, ai-researcher, domain-researcher, eval-planner, eval-auditor | Пока Pro не ведёт AI-фичи, процесс без владельца не образуется. Если начнёт — одна роль `ai-evaluator`, а не пять |
| Карта репо и intel-файлы (codebase-mapper, intel-updater) | Уже покрыто: profile `PROJECT.md` + `SOURCE-MAP.md` + скилы `bootstrap-test-context` / `refresh-test-context`. Заводить роль — дублировать существующий контур |
| Профиль разработчика (user-profiler) | Не относится к доставке продукта; плюс агент читает историю сессий пользователя — приватность против нулевой пользы для Pro |

## 4. Чего не тащим

| Что | Почему |
|-----|--------|
| Тела агентов целиком | 5–47 KB на агента (planner 46 KB, debugger 47 KB, plan-checker 35 KB) против 4–10 KB в Pro. Формат Pro — контракт роли, а не runbook; слияние форматов уничтожает читаемость обоих |
| Привязка к `.planning/` и `gsd-sdk query` | Pro обезличен и живёт в чужих репозиториях. Конкретная схема каталогов и собственный CLI ломают переносимость. Идея STATE и артефактов уже взята в layer 06 без команд |
| Хуки во frontmatter (`PostToolUse`, `npx eslint --fix $FILE`) | Конфигурация раннера, не контракт роли. Привязаны к node/eslint; в самих файлах GSD закомментированы |
| Цвета и иконки агентов | Косметика конкретного раннера |
| Числовые пороги как догма | 5+ задач = blocker, spacing кратен 4, не более 4 размеров шрифта — калиброваны под типовой проект GSD. Переносить как слоты (`{{max_tasks}}`, `{{style_guide}}`), не как константы |
| 6 столпов UI целиком с их порогами | Рамку (столпы, скор 1–4, три приоритетных фикса) — берём. Конкретные значения спейсинга и палитры — нет: в обезличенном издании они приходят из `{{style_guide}}` проекта |
| Терминология «Nyquist» | Внутренний жаргон GSD, вне GSD не читается. Смысл (какие требования не имеют ни одного автоматического доказательства) переносим под своим именем |
| Дублирование ролей под каждый артефакт | GSD имеет 31 агента при 3 базовых механиках (goal-backward, revision gate, парность). Pro копирует механики, а не гранулярность: три новые роли с режимами вместо восьми одноразовых |
| Интерактивные опросники (`AskUserQuestion` в framework-selector, eval-planner) | Механизм конкретного раннера. В Pro эквивалент — нормализация запроса оркестратором и вопрос только при материальной неоднозначности |
