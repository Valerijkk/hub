# Верификация цели (`verify-goal`)

Оценивать **достижение исхода**, а не закрытие чекбоксов задач. У каждого success
criterion должен быть прикреплённый evidence нужного уровня либо явный NOT_RUN.

## Цель ≠ сумма закрытых задач

Закрытая задача отвечает на вопрос «работа сделана?». Достигнутая цель отвечает на
вопрос «исход наступил?». Второй не выводится из первого.

Задача «создать обработчик» закрывается в момент, когда файл существует и собирается.
Цель «чужой ресурс недоступен» не достигнута, пока нет проверки владельца и теста,
который её ловит. В трекере обе записи зелёные; цель — нет.

Пять способов, которыми «все задачи закрыты» расходится с «цель достигнута»:

| Расхождение | Что видно в трекере | Что на самом деле |
|-------------|---------------------|-------------------|
| **Заглушка** | задача закрыта | артефакт существует, поведения в нём нет |
| **Сирота** | задача закрыта | артефакт существует, но с прод-пути не вызывается |
| **Пустой поток** | задача закрыта | вызывается, но данные не доходят: константа, пустой ответ, захардкоженный вход |
| **Дыра в покрытии** | все задачи закрыты | у критерия изначально не было ни одной задачи |
| **Дрейф документации** | задача закрыта | док обещает поведение, которого в коде нет |

Отсюда рабочее правило: `verify-goal` читает **критерии**, а не список задач.
Перечень выполненных задач в отчёт приёмки не входит и вердикт не обосновывает.
Формулировка «все задачи волны закрыты» не является evidence ни для одного критерия.

## Когда использовать

- Волна/фаза заявлена complete — до handoff или merge-ready
- После цикла исправлений после FAIL
- Перед выставлением `verified: true` в отчётах или skills

## Когда остановиться

- Нет PLAN или success criteria → остановиться; запросить PLAN у `phase-plan`
- Для критерия не определён тип evidence → FAIL по этому критерию; не выводить PASS по догадке
- Verifier — единственный автор всех артефактов без независимой проверки → отметить в отчёте;
  при high-impact вердикт **BLOCKED** и эскалация по
  [rules/40](../../../prompt-engineering/rules/40-verification-protocol.md)

## Принцип

```
Goal (from PLAN)
  → Truths (наблюдаемые факты)
    → Artifacts (A1 exists → A2 substantive → A3 wired → A4 data flows)
      → Key links (проводка)
        → Evidence уровня L0–L4 по классу риска
          → Verdict PASS | FAIL | BLOCKED
```

Закрытые задачи без evidence по критерию = **FAIL**.

## Процедура goal-backward

**Ш0. Режим.** Есть предыдущий отчёт с незакрытыми gaps → режим повторной верификации
(§ «Повторная верификация»). Иначе — начальный.

**Ш1. Goal дословно.** Прочитать goal из PLAN как есть. Не пересказывать списком задач
и не переформулировать под то, что получилось.

**Ш2. Собрать полный набор критериев.** Критерии берутся из всех источников (goal фазы,
исходная задача/spec, PLAN). **PLAN не может сузить набор**: он вправе добавить
критерии, но не заменить собой исходные. Если PLAN перечисляет меньше — верифицируется
объединение, а расхождение фиксируется в отчёте.

**Ш3. Восстановить цепочку.** Критерий → факты → артефакты → связи. Если PLAN содержит
секцию goal-backward — взять оттуда. Если нет — вывести здесь и **записать до сбора
evidence**; иначе цепочка неизбежно подгонится под то, что удалось найти.

**Ш4. Артефакты по уровням A1–A4.** Каждый артефакт цепочки проходит четыре уровня.

**Ш5. Ключевые звенья.** Проверить проводку отдельно от артефактов: большинство заглушек
живёт именно здесь — куски существуют, но не соединены.

**Ш6. Evidence по классу риска.** Определить требуемый уровень L0–L4 и собрать его:
открыть файлы, прогнать команды из profile или пометить `NOT_RUN` с причиной.
Не заявлять о прогонах без вывода.

**Ш7. Регрессия.** Применить scope регрессии из PLAN; integration gate волны, если задан.
Работа только с docs → `N/A` с обоснованием. «Изменение маленькое» обоснованием не является.

**Ш8. Скан изменённых файлов на признаки незавершённости:** маркеры TODO/FIXME,
формулировки «позже»/«скоро», пустые возвраты и пустые обработчики, захардкоженные
значения там, где ожидались динамические. Найденное классифицируется: блокер (мешает
цели) / предупреждение / информация. Значение по умолчанию, которое дальше
перезаписывается реальным источником, заглушкой не является — проверить, кто пишет
в переменную, прежде чем помечать.

**Ш9. Что не проверяется программно.** Внешний вид, сквозной пользовательский сценарий,
реальное время, интеграция с внешним сервисом, читаемость сообщений об ошибке — в список
проверок человеком с формулировкой «что сделать / что ожидается / почему не автоматизируется».

**Ш10. Отфильтровать deferred** (см. ниже) и определить вердикт.

## Уровни артефакта A1–A4

| Уровень | Вопрос | Провал |
|---------|--------|--------|
| **A1 существует** | путь есть, экспорт/объявление на месте | `MISSING` |
| **A2 содержателен** | реализация, а не заглушка, TODO или пустой возврат | `STUB` |
| **A3 подключён** | импортируется **и** вызывается с продакшн-пути | `ORPHANED` |
| **A4 данные текут** | на вход приходят реальные данные, не константа, не пустой литерал, не значение, захардкоженное в точке вызова | `HOLLOW` |

A4 проверяется для всего, что отдаёт наружу динамические данные; для утилит и конфигов — `N/A`.

**A1–A4 — про артефакт. L0–L4 — про доказательство.** Их нельзя смешивать: артефакт может
формально пройти A1–A4 при доказательстве уровня L0 («агент сказал, что подключено») —
это ноль. Уровень артефакта отвечает на «что построено», уровень evidence — на «чем
это подтверждено».

## Доказательства: пирамида L0–L4

Уровни определены в [layers/05](../../layers/05-verification-mutation.md).
Минимальная планка по классу критерия:

| Класс критерия | Минимум | Что именно прикладывается |
|----------------|---------|---------------------------|
| Docs-only / контекст | L2 | пути + проверенные ссылки + чек-лист приёмки |
| Behavior | L1 + L2 | тест существует + лог команды PASS + путь к коду |
| API contract | L1 + L2 | выравнивание doc/route; обработчик зарегистрирован |
| UI | L2 | путь к компоненту/тесту + наблюдаемая проверка |
| Infra | L2 | diff конфига + sync deploy-дока |
| Фикс с тестом / регрессионный guard | L3 | мутация: RED → restore → GREEN |
| Security, доступ, деньги, разрушающие операции | L3 + L4 | denial-тест + ссылка на constraint + независимый verifier |

Правила:

- **L0 не evidence ни при каких условиях.** Текст агента без команды не засчитывается.
- Evidence ниже требуемой планки — не PASS (см. BLOCKED).
- При расхождении приоритет у project profile над этой таблицей.

### Мутационный контракт

Для критериев уровня L3 проверяется спецификация из трёх полей — *что ломать · какой
тест · слой* — и результат прогона
([extracts/mutation-evidence](../../extracts/mutation-evidence.md)):

| Вердикт мутации | Как влияет на критерий |
|-----------------|------------------------|
| `PROVEN` | RED на мутации + GREEN после restore, слой совпал → критерий может быть PASS |
| `mutation_failed_to_build` | сборка сломалась → guard не доказан → критерий **BLOCKED**, переформулировать мутацию |
| `layer_mismatch` | тест бьёт в копию/мок, не в прод-guard → критерий **BLOCKED**, чинить тест/слой |
| `NOT_PROVEN` | нет RED или нет спецификации → критерий **FAIL** |

Спецификация мутации, написанная после закрытия задачи, подгоняется под существующий
тест и доказательством не считается.

## Вердикт: PASS | FAIL | BLOCKED

| Вердикт | Значение | Следующий шаг |
|---------|----------|---------------|
| **PASS** | все критерии PASS или задокументированный N/A; в списке проверок человеком нет невыполненных строк | handoff / merge-ready |
| **FAIL** | доказано, что цель не достигнута | fix по таблице gaps, повторная приёмка |
| **BLOCKED** | не доказано ни достижение, ни провал | не fix, а доступ / данные / независимый verifier |

**BLOCKED — не мягкий PASS.** Handoff и `verified: true` запрещены при нём ровно так же,
как при FAIL.

Когда BLOCKED вместо PASS:

| Условие | Почему не PASS и не FAIL |
|---------|--------------------------|
| Нет PLAN или success criteria | нечего проверять |
| Критерий требует прогона, команда/окружение недоступны | `NOT_RUN` ≠ пройдено |
| Класс риска требует L3–L4, собран L1–L2 | доказательство ниже планки, а не отсутствие результата |
| `mutation_failed_to_build` или `layer_mismatch` | мутация guard не подтвердила и не опровергла |
| Критерий проверяем только человеком, проверка не выполнена | зелёная автоматика этого критерия не закрывает |
| Verifier = автор всей работы, класс high-impact | self-check не является независимым доказательством ([rules/40](../../../prompt-engineering/rules/40-verification-protocol.md)) |
| Открытый CRITICAL/HIGH из review без mitigation | приёмка блокируется по severity ([rules/30](../../../prompt-engineering/rules/30-severity-policy.md)) |
| PLAN сузил набор критериев относительно источника | верифицируется неполный контракт |

**Соответствие словарю rules/40.** Общий вердикт этого скила — `PASS | FAIL | BLOCKED`.
Поле `Verdict` внутри evidence-блока rules/40 остаётся из своего словаря
(`PASS | FAIL | PARTIAL | NOT_RUN`); BLOCKED отображается туда как `PARTIAL`, если часть
критериев доказана, и как `NOT_RUN`, если прогон не состоялся вовсе.

## Отложенное (deferred) ≠ провал

Незакрытый пункт, который **явно** закрывается более поздней запланированной фазой или
задачей, помечается `deferred`, а не gap: он не влияет на вердикт и не требует плана закрытия.

Матчить консервативно: совпадение по формулировке цели/критерия более поздней фазы, а не
«похоже по смыслу». Сомневаешься — это gap. Каждый deferred в отчёте указывает, где именно
он закрывается.

## Повторная верификация

После цикла исправлений — **полный проход по критериям**, не частичный:

- ранее красные критерии — полная процедура (A1–A4 + evidence нужного уровня);
- ранее зелёные — регрессионная проверка (A1–A3 + команда);
- фиксируются три числа: закрытые gaps, оставшиеся gaps, **регрессии** (было PASS, стало FAIL).

Любая регрессия — блокер вне зависимости от того, сколько gaps закрыто.

## Принятые отклонения (override)

Осознанно принятое отклонение фиксируется явно: критерий · причина · кто принял · когда.
Такой критерий идёт в отчёт как `PASS (override)`, а их количество — отдельным числом.
Override без человека-владельца невалиден; verifier не выписывает override сам себе.

## Шаблон отчёта

```markdown
## Goal verification — {{phase / wave}} — {{date}}

Verifier: {{role}} | Profile: {{profile}} | Mode: initial | re-verify

### Goal
<from PLAN, дословно>

### Criteria
| ID | Criterion | Evidence | Level | Status |
|----|-----------|----------|-------|--------|
| C1 | … | `path:line` / `cmd` → exit 0 / log excerpt | L1/L2/L3/L4 | PASS/FAIL/BLOCKED/N/A |

### Artifacts (A1–A4)
| Artifact | A1 exists | A2 substantive | A3 wired | A4 data | Status |
|----------|-----------|----------------|----------|---------|--------|

### Key links
| From | To | Via | Status | Detail |
|------|----|-----|--------|--------|

### Mutation (L3, если применимо)
| Критерий | Что ломали | Тест | Слой | Вердикт |
|----------|------------|------|------|---------|

### Regression
- Scope: {{from PLAN/profile}}
- Status: PASS | FAIL | N/A — evidence: …

### Docs / context sync
- Status: PASS | FAIL | N/A — paths: …

### Review / security
- CRITICAL open: 0 | list
- HIGH open: 0 | list + mitigation?

### Требует проверки человеком
| # | Что сделать | Что ожидается | Почему не автоматизируется | Кто и когда | Результат |
|---|-------------|---------------|----------------------------|-------------|-----------|

Две последние колонки заполняются после выполнения. Без них список
невозможно закрыть: проверку выполнили, а записать некуда — и PASS
недостижим для любой фазы с UI или сквозным сценарием.

### Deferred
| Пункт | Где закрывается | Основание |
|-------|-----------------|-----------|

### Verdict
PASS | FAIL | BLOCKED — overrides applied: {{N}}

### Gaps (if FAIL / BLOCKED)
| Gap | Тип (stub/orphan/hollow/coverage/drift) | Severity | Owner | Next |
|-----|------------------------------------------|----------|-------|------|

### Re-verify (если повторный проход)
- Закрыто: … | Осталось: … | Регрессии: …

Verification:
- Claims checked: each criterion evidence inspected at required level
- Evidence: commands run / files read (list)
- Not run / N/A: …
- Risks / assumptions: …
- Mode: self-check | independent(author:X, verifier:Y)
- Verdict: PASS | FAIL | PARTIAL | NOT_RUN
```

`verified: true` только когда общий вердикт PASS, в списке проверок человеком нет невыполненных строк и блок
evidence заполнен.

## Handoff

- **PASS** → merge-ready / handoff по `playbooks/handoff-state.md`
- **FAIL** → владельцы gaps; `wave-orchestrate` или inline fix; повторить verify-goal
- **BLOCKED** → снять причину блокировки (доступ, данные, независимый verifier, переформулированная
  мутация), затем полный повторный проход. Замена BLOCKED на PARTIAL «чтобы не держать релиз» —
  дефект процесса
- Не делать handoff с PARTIAL. Владелец не «принимает PARTIAL» — он может
  оформить `PASS (override)` по §Override, с записью, что именно принято
  недоказанным и почему. Разница не в словах: override оставляет след,
  «принятый PARTIAL» растворяется в переписке

## Анти-паттерны

- Вердикт на основании списка закрытых задач вместо критериев
- PASS по одному зелёному локальному прогону без маппинга на критерии
- PASS при том, что документация обещает поведение, которого нет в коде (drift)
- Смешение уровня артефакта (A) и уровня доказательства (L): «файл на месте» как evidence
- Засчитывание `mutation_failed_to_build` как доказанного guard
- Пропуск регрессии из-за «маленького изменения»
- Частичный повторный проход только по бывшим красным критериям
- Пометка gap как deferred по смысловому сходству, без явной более поздней фазы

## Куда записывается отчёт

Отчёт приёмки сохраняется файлом рядом с планом фазы — по умолчанию
`{{phase_dir}}/VERIFICATION.md`, либо в принятое в репозитории место.

Без этого шага режим повторной приёмки недостижим: он требует предыдущий
отчёт, а взять его неоткуда. Отчёт, оставшийся только в переписке, для
следующего прогона не существует.

`{{phase_dir}}` — каталог артефактов фазы. Если в репозитории такого нет,
годится любое стабильное место рядом с планом; требование одно — путь
воспроизводим и не зависит от сессии.
