# Планирование фазы (`phase-plan`)

Превратить verified goal в исполнимый PLAN: закрытые серые зоны, задачи, выведенные
**от критерия приёмки**, атомарные единицы работы, параллельные волны без пересечения
файлов, evidence-контракт на каждую задачу и явный handoff к execution.

План — это промпт для исполнителя, а не документ о намерениях. Всё, чего в нём нет,
исполнитель додумает удобным для себя способом.

## Когда использовать

- Новая фича/фаза до первого `wave-orchestrate`
- После discuss/spec, когда scope зафиксирован
- Replan после `verify-goal` FAIL/BLOCKED или пересекающейся file map в волне

## Когда не использовать

- Микро-фикс одного файла (один артефакт, один слой) — execute inline
- Goal всё ещё неоднозначен — сначала уточнить spec

## Когда остановиться

- Goal нельзя выразить одним фальсифицируемым исходом → остановиться; запросить spec
- Success criteria не могут назвать тип evidence (command, path, metric) → остановиться; уточнить criteria
- Серая зона попадает в класс, где решение принимает владелец (см. §1) → остановиться; эскалировать
- Нет profile/context для commands или layout → отметить в PLAN как `UNKNOWN`; не изобретать paths
- Объём фазы не помещается в бюджет исполнителей → **не урезать scope молча**; вернуть предложение разбить фазу

## Контекст (загрузить сначала)

| Нужно | Primary | Legacy fallback |
|------|---------|-----------------|
| Ограничения проекта | `context/projects/<profile>/PROJECT.md` | `context/PROJECT-CONTEXT.md` |
| Commands для criteria | `context/projects/<profile>/COMMANDS.md` | PROJECT-CONTEXT §4 |
| Scope тестов/регрессии | `context/projects/<profile>/CI-PIPELINE.md`, `TEST-ARCHITECTURE.md` | TESTFRAMEWORK-MAP |
| Паттерны-аналоги | `PATTERN-INDEX.md` + `patterns/approved/` | PATTERNS-LIBRARY |
| Шаблон делегирования | `agents/templates/phase-kickoff.md`, `wave-delegate.md` | — |
| Lifecycle | `playbooks/gsd-lifecycle.md` | — |

От пользователя: `{{goal}}`, constraints, список Won't, опциональные ссылки STATE/roadmap.

## Порядок работы

```
серые зоны → goal-backward цепочка → атомарные задачи → граф зависимостей
  → волны → evidence-контракт задач → PLAN → self-check → handoff
```

## 1. Серые зоны — закрыть до плана, не в коде

**Серая зона** — решение, которое меняет исход и не зафиксировано ни в goal, ни в
constraints, ни в profile. Оставленная открытой, она будет закрыта исполнителем
молча и в свою пользу.

Искать по поверхности, к которой относится фаза:

| Поверхность | Типовые серые зоны |
|-------------|--------------------|
| Кто-то **видит** | состояния (пусто / загрузка / ошибка), плотность, порядок, что показывать при отказе |
| Система **вызывает** | форма ответа, коды и тело ошибки, авторизация, версионирование, идемпотентность |
| Оператор **запускает** | формат вывода, флаги, режимы, поведение при частичном отказе |
| Кто-то **читает** | структура, глубина, адресат, что считать источником правды |
| Что-то **организуется** | критерий группировки, именование, исключения из правила |

Серая зона — это конкретная развилка («поведение при пустом списке»), а не категория («UX»).

Каждая найденная зона получает ровно один исход:

| Исход | Что записать в PLAN |
|-------|---------------------|
| **Locked** | решение владельца дословно + ID; задачи ссылаются на этот ID |
| **Discretion** | явно отдано исполнителю; выбор фиксируется в отчёте задачи |
| **Deferred** | вне scope; попадает в Won't, а не в задачи |
| **UNKNOWN** | ответа нет и владельца рядом нет; слот в PLAN + задача-решение до зависимых задач |

**Решает владелец, не планировщик:** доступ и security, деньги/тарификация, публичные
контракты, миграции и удаление данных, внешние обязательства. Такие зоны помечаются
approval boundary и не превращаются в Discretion.

**Запрещено:** переносить открытую серую зону в execute; заменять решение владельца
«разумным дефолтом»; изобретать paths и команды вместо `UNKNOWN`.

## 2. Goal-backward: задачи выводятся от критерия приёмки

Прямое планирование отвечает на «что построим» и даёт список активностей.
Goal-backward отвечает на «что обязано стать ИСТИНОЙ, чтобы цель считалась
достигнутой» и даёт условия, которым активности обязаны удовлетворить.
Задачи появляются **последними**.

```
Goal (исход)
  → Факты (что обязано быть истинным, 3–7)
    → Артефакты (что обязано существовать)
      → Связи (что обязано быть соединено)
        → Ключевые звенья (где вероятнее всего порвётся)
          → Задачи
```

**Ш0. Goal как исход.** Формулировка описывает состояние мира, а не работу.
«Собрать компоненты» ❌ → «чужой ресурс недоступен, регрессия зелёная» ✅.

**Ш1. Факты (3–7).** Каждый — с позиции потребителя (человек, вызывающая система,
оператор) и проверяем снаружи. «Библиотека подключена» — не факт, это деталь реализации.
Слишком общий факт («всё работает») дробится на проверяемые.

**Ш2. Артефакты.** Для каждого факта: что обязано **существовать**. Артефакт — конкретный
путь или объект хранилища, не «модуль аутентификации». Для каждого фиксируется, что
именно он обеспечивает.

**Ш3. Связи.** Для каждого артефакта: что обязано быть **соединено**, чтобы он работал.
Здесь прячется большинство заглушек: артефакты созданы, проводка — нет.

**Ш4. Ключевые звенья.** Где разрыв даёт каскадный отказ и при этом внешне незаметен.
Каждое звено записывается как `откуда → куда → чем` плюс признак, по которому его
можно найти в коде. Это вход для `verify-goal`.

**Ш5. Достижимость.** Для каждого артефакта проверить, что существует реальный путь,
которым он возникает и вызывается: сущность создаётся, поток запускается действием или
вызовом, флаг имеет значение по умолчанию и потребителя, экран доступен из навигации.
Нет пути → UNREACHABLE → переделать план, а не «подключим позже».

**Ш6. Задачи.** Только теперь. Каждая задача обязана называть критерий/факт, который
она двигает.

**Ш7. Двусторонняя трассировка** — обязательная проверка перед записью PLAN:

| Направление | Проверка | Нарушение |
|-------------|----------|-----------|
| критерий → задачи | у каждого критерия ≥ 1 задача | непокрытый критерий = блокер плана |
| задача → критерий | у каждой задачи ≥ 1 критерий | задача без критерия = scope creep: убрать или добавить критерий |

Ни один критерий не «покрывается» одной размытой задачей на три критерия сразу.

## 3. Атомарность единицы работы

**Атомарная задача** — минимальный объём работы, который одновременно:

1. даёт **самостоятельный вердикт** — её можно принять или отклонить, не открывая другие задачи;
2. живёт в **одном слое** (или на одном контракте), а не сшивает два;
3. занимает **непересекающийся** набор файлов;
4. укладывается в **один осмысленный коммит**;
5. помещается в **бюджет контекста одного исполнителя с запасом**.

Почему именно эти пять — что ломается без каждого:

| Свойство | Что ломается без него |
|----------|-----------------------|
| Самостоятельный вердикт | FAIL нельзя локализовать: откатывать приходится всю фазу |
| Один слой | ревью и мутационная проверка бьют мимо слоя, где живёт guard |
| Непересекающиеся файлы | волна не параллелится, сборка даёт конфликты |
| Один коммит | нет точечного отката, история нечитаема |
| Бюджет контекста | к концу задачи исполнитель «экономит» и режет качество молча |

### Сигналы размера

| Сигнал | Действие |
|--------|----------|
| Формулировка соединяет слои через «и» (схема **и** обработчик, сервер **и** интерфейс) | разрезать по слоям |
| Затрагивает > 3–5 файлов или > 2 модулей | разрезать |
| Описание действия не помещается в абзац | разрезать |
| Внутри и решение («выбрать подход»), и реализация | решение — в серые зоны (§1), реализация — задача |
| Есть только вместе со следующей, отдельного acceptance нет | склеить со следующей |
| Правит конфиг/проводку в одном файле | склеить с потребителем |

Оценка — в доле бюджета контекста исполнителя, не в часах и днях. Человеческие единицы
времени в задачах агентов бессмысленны и регулярно используются как аргумент за
скрытое урезание scope.

**Сложность не является основанием сократить задачу.** Легитимных причин разрезать
или эскалировать ровно три: не помещается в бюджет контекста; отсутствуют входные
данные; блокирующая зависимость от другой фазы. Всё остальное планируется как есть.

## 4. Зависимости и волны

Думать графом, а не последовательностью. Для каждой задачи зафиксировать:

- `needs` — что обязано существовать до старта
- `creates` — что она производит для других
- требуется ли решение человека (checkpoint / approval boundary)

Правила сборки волн:

1. Нет зависимостей → волна 1.
2. `wave = max(wave(зависимостей)) + 1`.
3. **Неявная зависимость по файлам:** если две задачи трогают один путь, более поздняя
   уходит в следующую волну. Пересчитать после каждого сдвига.
4. Внутри волны пересечение `files only` = **0**. Это условие проверяется, а не декларируется.
5. **Вертикальные срезы вместо горизонтальных слоёв.** «Функция целиком» параллелится;
   «все схемы → все обработчики → весь интерфейс» сериализуется. Горизонталь — только
   когда общий фундамент действительно обязателен.
6. **Interface-first:** контракты (типы, схемы, сигнатуры) создаются первой задачей,
   реализации пишутся против них, проводка — последней. Иначе исполнители уходят
   исследовать репозиторий, чтобы восстановить контракт.
7. Цикл в графе — блокер. Разрезается выделением общего контракта в отдельную задачу волны 1.
8. Рефлекторное `depends: всё предыдущее` — дефект: раздувает контекст и убивает параллель.

## 5. Evidence-контракт задачи

Задача без контракта приёмки не исполняема. Обязательные слоты (пустой = `N/A: причина`):

| Слот | Требование |
|------|------------|
| Done | измеримое состояние завершения, не «готово» |
| Evidence | тип доказательства: команда + ожидаемый код возврата, path, секция дока, метрика |
| Автопроверка | конкретная быстрая команда; нет теста → задача волны 0, создающая его, и ссылка на неё |
| Regression scope | из profile (`COMMANDS.md` / `CI-PIPELINE.md`), не изобретённый |
| Mutation | для фикса/закрытия задачи с тестом: что ломать · какой тест · слой ([extracts/mutation-evidence](../../extracts/mutation-evidence.md)) |
| Stop when | условие остановки и эскалации |

Правила:

- **Плотность автопроверок.** В любом окне из трёх подряд идущих реализующих задач
  волны минимум две несут автоматизируемую проверку. Три подряд без неё — план не готов.
- **Мутация специфицируется в плане, а не после закрытия.** Постфактум спецификация
  подгоняется под уже написанный тест и ничего не доказывает.
- Долгие сквозные прогоны в качестве единственной проверки задачи — сигнал заменить
  на быструю целевую; watch-режимы недопустимы.
- Уровень доказательства по классу риска — [layers/05](../../layers/05-verification-mutation.md).
  Security / доступ / деньги / разрушающие операции планируются сразу с L3–L4.

## 6. Шаблон PLAN (выход)

```markdown
# PLAN: {{phase_name}}

## Goal
<one verifiable outcome sentence>

## Won't (out of scope)
- …

## Decisions / gray zones
| ID | Зона | Исход | Формулировка |
|----|------|-------|--------------|
| D-01 | … | locked / discretion / deferred / UNKNOWN | … |

## Depends on
- [ ] {{artifact / ADR / prior wave}}

## Success criteria
- [ ] C1 — evidence: `{{command}}` or `{{path}}`
- [ ] C2 — …
- [ ] Docs/context sync if behavior or commands changed

## Goal-backward
- Truths: T1 … T5 (наблюдаемые, с позиции потребителя)
- Artifacts: `{{path}}` — что обеспечивает
- Key links: `{{from}}` → `{{to}}` via `{{механизм}}` — признак: `{{pattern}}`
- Reachability: путь возникновения/вызова для каждого артефакта

## Tasks
| # | Task | Crit | Owner | Files only | Do not touch | Depends | Est (ctx) | Verifier |
|---|------|------|-------|------------|--------------|---------|-----------|----------|
| 1 | … | C1 | … | … | … | — | S | … |

## Task acceptance
- #1 — Done: … | Evidence: … | Auto: `{{cmd}}` | Regression: … | Mutation: что ломать / тест / слой | Stop when: …

## Waves
- Wave 1 (parallel): #1, #2 — file map: no overlap
- Sync: merge artifacts, conflict check
- Wave 2: #3 (depends Wave 1)

## Quality gates
- New behavior: implement → test → fix loop until green
- Regression scope: {{from COMMANDS.md / CI-PIPELINE.md}}
- Integration gate: {{project gate command or N/A with reason}}

## Risks
| Risk | Impact | Mitigation |
|------|--------|------------|

## Handoff
- Execute: `wave-orchestrate`
- Accept: `verify-goal` against criteria above
```

Записать PLAN в согласованное место (напр. `.planning/phases/<id>/PLAN.md` или эквивалент проекта).

## 7. Self-check: признаки плохого плана

Полнота плана ≠ достижимость цели. План, где все поля заполнены, всё ещё промахивается
мимо цели, если критерий не покрыт, проводка не запланирована или scope тихо урезан.
Пройти перед handoff; блокер означает «переделать», а не «отметить риск».

| Измерение | Признак | Severity |
|-----------|---------|----------|
| Покрытие критериев | критерий без задачи; одна размытая задача на три критерия | блокер |
| Полнота задачи | нет files / action / автопроверки / done | блокер |
| Границы файлов | задача без `files only`; пересечение внутри волны | блокер |
| Зависимости | цикл, ссылка на несуществующую задачу, волна не согласована с `depends` | блокер |
| Проводка | артефакты создаются, но ни одна задача их не соединяет | блокер |
| Достижимость | артефакт без пути возникновения/вызова | блокер |
| Скрытое урезание scope | «пока статикой», «заглушка», «подключим позже», «упрощённая версия», «в будущей фазе», «слишком сложно» | блокер, всегда |
| Решения владельца | задача противоречит locked-решению или реализует deferred | блокер |
| Плотность автопроверок | три подряд реализующих задачи волны без автопроверки | блокер |
| Мутация | фикс с тестом без спецификации мутации | блокер |
| Атомарность | смешаны слои; > 3–5 файлов; действие на несколько абзацев | блокер, если ломает вердикт задачи; иначе предупреждение |
| Формулировка критериев | критерий зеркалит название задачи и не называет тип evidence | блокер |
| Факты | сформулированы как детали реализации («библиотека подключена») вместо наблюдаемого поведения | предупреждение |
| Контекст задачи | рефлекторные ссылки на все предыдущие артефакты | предупреждение |
| Won't / Depends | секции пропущены | предупреждение |

**Скрытое урезание scope — отдельно.** Это самый незаметный отказ: план ссылается на
решение владельца и при этом доставляет его долю. Признак — versioning-язык («v1»,
«базовая версия»), которого нет в исходном решении. Правильная реакция — доставить
полностью либо вернуть предложение разбить фазу; никогда — сократить молча.

## Evidence до handoff

Добавить блок [rules/40](../../../prompt-engineering/rules/40-verification-protocol.md) —
фокус на полноте плана, не на выполнении кода:

```markdown
Verification:
- Claims checked: goal falsifiable; criteria have evidence types; two-way traceability; waves file-disjoint; reachability ok
- Evidence: PLAN path; profile commands cited where used
- Not run / N/A: code tests (pre-execution)
- Risks / assumptions: UNKNOWN slots, approval boundaries
- Mode: self-check
- Verdict: PASS | FAIL | BLOCKED
```

## Handoff

- Execute: `wave-orchestrate` → per-task execution
- Accept: `verify-goal` по success criteria и goal-backward цепочке из этого PLAN
- Replan: возврат сюда при FAIL/BLOCKED приёмки или конфликте файлов в волне
