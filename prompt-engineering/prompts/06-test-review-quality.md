## Ревью diff-а с тестами

1. Проведи ревью тестов в {{diff}} по полному чек-листу test-code-reviewer (2.1–2.4): паттерны, нейминг, ценность, гигиена — вердикт с severity и готовыми исправлениями.
2. Быстрый префильтр {{diff}} перед смысловым ревью: .only/.skip без тикета, закомментированные тесты, sleep, пустые тела, всегда-истинные ассерты, артефакты прогона — только машинно-находимое.
3. Проверь каждый тест {{diff}} вопросом «что упадёт, если сломать код?»: мысленная инверсия проверяемого условия — тесты, которые не упадут, пометь CRITICAL с объяснением, почему они фейковые.
4. Сверь {{diff}} с заявленными TC/требованиями {{список}}: каждый TC реализован? каждый тест трассируется к TC? лишние тесты без TC — вопрос (недокументированное поведение?).
5. Проверь {{diff}} на уровень пирамиды: каждый новый тест — на минимально возможном уровне (A3)? E2E/интеграционные, дублирующие юниты — с предложением переноса.
6. Ревью негативного покрытия {{diff}}: новая функциональность имеет невалидный вход + denial + отказ зависимости (A11)? Отсутствие класса — HIGH с перечислением недостающего.
7. Проверь изоляцию новых тестов {{diff}}: уникальные данные, отсутствие общего мутируемого стейта, порядконезависимость — по коду, не по «вроде ок».
8. Ревью ассертов {{diff}}: конкретные значения vs «не пусто/нет ошибки», схема vs полный снапшот, контракт vs реализация — каждой слабости конкретное усиление.
9. Проверь cleanup в {{diff}}: каждый созданный ресурс освобождается механизмом раннера и при падении; глобальные патчи/env восстанавливаются.
10. Ревью читаемости {{diff}}: тест читается сверху вниз? Arrange не 40 строк? хелперы не прячут ассерты? магические значения именованы?

## Нейминг

11. Прогони naming-аудит {{diff}} по канону (context/NAMING-CONVENTIONS или rules/10): файлы (шаблон, директория, соответствие коду) + функции (структура что/условие/ожидание, запрещённые имена) — каждому ERROR готовое имя.
12. Проверь «имя не врёт» для тестов {{файл}}: открой тело каждого — сценарий и ожидание из имени реально ассертятся? Имена-вруны — CRITICAL списком.
13. Переименуй тесты {{файл}} по канону: таблица старое → новое → обоснование; сценарии в именах сохрани, стиль выровняй.
14. Найди в {{сьют}} информационно-пустые имена (Test1, works, should work, happyPath) и предложи говорящие по содержимому тестов.
15. Проверь консистентность нейминга между файлами {{модуль}}: одинаковые сценарии называются одинаково? want/got vs expected/actual не смешаны? язык имён един?

## Anti-AI и говнокод

16. Прогони /anti-ai-check по {{scope}}: нарраторы, мета-комментарии («fixed the...», «as requested»), плейсхолдеры, фейковые тесты, мёртвый код — отчёт с severity по формату скила.
17. Найди в {{diff}} комментарии-нарраторы (пересказ кода) и мета-комментарии (обращение к ревьюеру) — все на удаление; полезные «почему»-комментарии сохрани и отметь как эталон.
18. Проверь {{diff}} на признаки бездумной генерации: дублирование существующих хелперов вместо переиспользования, стиль чужого фреймворка, импорты не из канона проекта, изобретение своих фабрик при живых проектных.
19. Найди в тестах {{модуль}} копипаст-блоки (3+ повторения одинакового сетапа/ассертов) — вынеси в фабрики/хелперы по канону, покажи дифф до/после для одного случая.
20. Проверь комментарии {{файл}} на актуальность: комментарии, противоречащие коду рядом (врущие) — исправить или удалить; TODO без тикета/владельца — оформить или удалить.
21. Найди в {{scope}} отключённые тесты: .skip/.only/Skip/xit/@Disabled — таблицей: тест | причина указана? | тикет? | сколько живёт (git blame) | вердикт (включить/удалить/оформить карантин).

## Ценность и мутационная проверка

22. Мутационный смоук {{модуль}}: топ-10 минимальных мутаций логики (инверсии условий, off-by-one, удаление веток, замена операторов) — какие тесты ловят каждую? Непойманные мутации — недостающими кейсами.
23. Найди в {{сьют}} «казино-тесты»: ожидание скопировано с фактического вывода кода без сверки со спекой (симптомы: странные точные значения без источника, снапшоты «как есть»). Каждому — сверка с документацией.
24. Оцени {{сьют}} на overspecification: тесты, ломающиеся от любого рефакторинга без смены контракта — счётчик изменений тестов при последних {{N}} рефакторингах, самые хрупкие — на переписывание.
25. Найди дубли в {{сьют}}: пары тестов с одинаковой сигнатурой вход+состояние+ожидание — какие удалить/объединить без потери покрытия классов.
26. Ранжируй тесты {{сьют}} по ценности: (вероятность поймать реальный баг × критичность зоны) / стоимость поддержки — кандидаты на удаление снизу списка с обоснованием.

## Аудиты сьюта целиком

27. Полный health-аудит {{сьют}}: размер, скорость, изоляция (случайный порядок), доля негативных, флаки-частота, дубли, мёртвые тесты, нейминг-долг — сводная таблица со светофорами и топ-5 действий.
28. Аудит соответствия канону {{сьют}} против context/PATTERNS-LIBRARY: процент тестов на канонических фабриках/хелперах, отступления по файлам, план миграции по одному паттерну за волну.
29. Аудит пирамиды {{продукт}}: фактическое распределение тестов по уровням против целевого, стоимость прогона каждого уровня, тесты не на своём уровне — план перебалансировки.
30. Аудит регрессионной защиты {{модуль}}: последние {{N}} багов прода — какой тест должен был поймать каждый? почему не поймал (нет теста/тест слабый/тест skip)? Дыры — регрессионными кейсами на класс.
31. Аудит тестов после большого рефакторинга {{рефакторинг}}: тесты, потерявшие смысл (тестируют удалённое через шимы), тесты, случайно ослабленные (ассерты закомментированы «временно»), дыры на новых путях.

## Процесс ревью

32. Составь PR-чеклист тестов для шаблона репозитория: 10 пунктов из rules/20 DoD, проверяемых автором до запроса ревью.
33. Напиши ревью-комментарий по находке {{находка}}: проблема → почему это важно (какой баг пропустит/что сломает) → конкретный фикс → ссылка на канон. Тон — про код, не про автора.
34. Разбери спор по находке {{находка}}: аргументы обеих сторон, что говорит канон (context/ → rules/), чего в каноне не хватает; проект решения владельцу + формулировка нового правила, чтобы спор не повторился.
35. Сформулируй итог ревью {{diff}} для автора: вердикт, находки по severity со ссылками, что именно нужно для следующей итерации, что было сделано хорошо (закрепление паттернов).
36. Проанализируй историю ревью {{период}}: топ повторяющихся классов находок → какие превратить в автофильтры (линтер/греп в CI), какие — в обучение, какие — в правило канона.

## Ревью по типам тестов

43. Ревью юнит-тестов в {{diff}}: изоляция от границ (моки только на границах), скорость, детерминизм, контракт vs реализация, полнота ветвей — по чек-листу 02.
44. Ревью интеграционных тестов в {{diff}}: реальные зависимости на границах (не всё замокано — псевдоинтеграция), изоляция данных, ассерты всех затронутых хранилищ, cleanup — по чек-листу 03.

47. Ревью тестов производительности в {{diff}}: реалистичные данные/нагрузка, зафиксирован baseline, регрессионный порог, метрики ресурсов помимо времени — по чек-листу 11.
48. Ревью security-тестов в {{diff}}: denial-полнота, все точки инъекций, проверка авторизации на всех слоях, отсутствие раскрытия данных — по чек-листу 11.

50. Найди в {{diff}} тесты, ассерты которых закомментированы/ослаблены «временно» — временное без тикета не проходит; каждый случай на восстановление или обоснование.

## Кросс-командные и системные

54. Оцени зрелость тестовой культуры команды по {{сьют}} и истории ревью: где команда сильна, где системные слепые зоны (негативы? изоляция? нейминг?), план развития.
55. Составь калибровочный набор для ревьюеров команды: 5 diff-ов с эталонными вердиктами — чтобы разные ревьюеры оценивали одинаково; расхождения калибруй.
56. Проверь консистентность вердиктов ревью {{период}}: одинаковые находки получают одинаковую severity у разных ревьюеров? Расхождения → уточнение severity-политики (rules/30).

## Анти-AI углублённо

57. Проверь {{diff}} на «AI-правдоподобный, но бессмысленный» тест: синтаксически корректный, покрытие даёт, но ассертит тривиальное/не связанное с риском — реальная ценность или накрутка?
58. Найди в {{diff}} тесты, сгенерированные по шаблону чужого фреймворка (не канон проекта): импорты, структура, фабрики не из наших — переписать под канон.
59. Проверь {{diff}} на галлюцинированные API: тест вызывает несуществующие методы/поля/хелперы (компилируется по случайности или мокнуто так, что не ловит) — сверь с реальным кодом.
60. Найди в {{scope}} AI-комментарии, объясняющие очевидное или обращающиеся к пользователю («Now we test...», «This ensures...») — на удаление; оставь только «почему»-комментарии.

## Самопроверка перед сдачей ревью

71. Перепроверь свой вердикт по {{diff}}: каждая находка имеет severity по rules/30, точное место, нарушенный канон (ссылка), готовое исправление? Находки без «как исправить» — доработай.
72. Проверь свой вердикт на ложные срабатывания: каждая находка — реально дефект или стилевое предпочтение/легаси-зона (context §5)? Убери субъективное, оставь обоснованное каноном.
73. Проверь полноту своего ревью {{diff}}: прошёл все секции чек-листа (паттерны/нейминг/ценность/гигиена/anti-AI)? Пропущенная секция — слепая зона; добери.
74. Проверь свой вердикт на пропущенные CRITICAL: перечитай {{diff}} специально на фейковые тесты и имена-вруны — самый дорогой пропуск ревьюера; докажи, что каждый новый тест может упасть.
75. Сформулируй уверенность по каждой находке {{diff}}: CONFIRMED (доказуемо) vs PLAUSIBLE (подозрение) — не выдавай догадку за факт, PLAUSIBLE помечай явно.
