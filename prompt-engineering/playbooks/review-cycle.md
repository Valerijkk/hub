# Playbook: ревью-цикл тестового кода

> Порядок: сначала дешёвые автоматические фильтры, потом дорогое смысловое ревью. Ревьюер не тратит внимание на то, что ловит греп.

## Конвейер

```
diff с тестами готов
│
1. АВТОФИЛЬТРЫ (параллельно, машинные)
│    a. skills/anti-ai-check/SKILL.md по diff — фейковые тесты, плейсхолдеры, мета-комментарии
│    b. skills/naming-check/SKILL.md по diff — файлы + функции
│    c. линтеры/форматтеры проекта (active profile `COMMANDS.md`)
│    CRITICAL/ERROR любого фильтра → возврат автору ДО ревью
│
2. ПРОГОН
│    затронутые сьюты под флагами канона; лог — в PR
│    красный → автор чинит (при необходимости через debugging-плейбук) до ревью
│
3. test-code-reviewer (templates/review-request.md)
│    смысловое ревью: паттерны, ценность тестов, «имя не врёт», уровень пирамиды
│    request changes → автор фиксит → ПОВТОР с шага 1 (фильтры снова: фикс мог
│    внести новые находки) — цикл до approve
│
4. approve → мерж по процессу проекта
│
└─ 5. post-merge (опционально, batch): test-documenter обновляет карту сьютов/
      coverage-док, если diff менял структуру
```

## Правила цикла

1. Итерация ревью — полный круг (фильтры → прогон → ревьюер), не только «посмотреть исправленное»: точечные фиксы ломают соседей чаще, чем кажется.
2. Ревьюер получает diff с уже зелёными фильтрами и прогоном — иначе возвращает не глядя (экономия смыслового ревью — принцип конвейера).
3. Три возврата подряд по одному классу находок → системная проблема: пауза, разбор канона с автором (обучение), не четвёртая итерация молча.
4. Спор автора с находкой решает канон (`context/projects/<profile>/` → approved cards → `rules/`); канон молчит → решение владельца + отдельная curation, не автоматическое новое правило.

## SLA-ориентиры (настраиваются проектом)

| Этап | Ориентир |
|------|----------|
| Автофильтры | минуты, автоматически |
| Прогон сьютов | из active profile `COMMANDS.md` / `CI-PIPELINE.md` |
| Смысловое ревью | ≤ 1 рабочего дня |
| Полный цикл PR с тестами | ≤ 2–3 итераций при рабочем каноне |
