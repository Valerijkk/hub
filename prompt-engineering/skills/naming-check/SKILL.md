# /naming-check — аудит нейминга тестов

> Канон — `context/NAMING-CONVENTIONS.md` (заполнен context-intake). Если он в статусе template — стоп, сначала `/context-intake`. Скил не выбирает конвенции — только сверяет с каноном.

## Step 1. Собрать объекты проверки

```
Вход: {{scope}} — diff | директория | весь testframework.
1. Список тестовых файлов в scope (масс-паттерны из TESTFRAMEWORK-MAP §2).
2. Для каждого файла — список тестовых функций/кейсов
   (rg "func Test|it\(|test\(|def test_" по scope).
```

## Step 2. Проверка имён файлов

Для каждого файла сверь с таблицей NAMING-CONVENTIONS §1:

| Проверка | Вердикт при нарушении |
|----------|----------------------|
| Суффикс/префикс соответствует уровню (unit/integration/e2e) | ERROR |
| Регистр и разделители соответствуют канону | ERROR |
| Файл теста соответствует файлу кода по правилу «тест ↔ код» | WARN (если правило best-effort) / ERROR (если строгое) |
| Файл лежит в правильной директории уровня/домена | ERROR |
| Файл в зоне легаси-отступлений (§5 канона) | WARN, не ERROR |

## Step 3. Проверка имён функций/кейсов

Для каждой функции сверь с NAMING-CONVENTIONS §2:

```
1. Структура имени: {{Unit_Scenario_Expected / should.../ given-when-then}} —
   все три компонента различимы?
2. Язык имени соответствует канону?
3. Имя не из запрещённого списка (Test1, TestFix, it('works')...)?
4. Имя читается в CI-отчёте без открытия файла?
5. Если канон требует привязку к TC/REQ-ID (§3) — она есть?
```

Нарушение структуры/запрещённое имя — **ERROR**; стилистика («можно яснее») — **WARN**.

## Step 4. Проверка соответствия «имя ↔ содержимое»

Выборочно (для diff — все, для аудита — 10 случайных на домен):

```
1. Открой тело теста. Имя обещает сценарий X и ожидание Y —
   тест реально делает X и ассертит Y?
2. Имя говорит «ReturnsError», а тест ассертит только отсутствие паники — ERROR
   (имя врёт — хуже плохого имени).
3. Тест проверяет больше, чем в имени (скрытые ассерты на смежное) — WARN.
```

## Step 5. Хелперы и переменные (для diff-режима)

По NAMING-CONVENTIONS §4: фикстуры, sut, want/got, табличные поля. Нарушения — WARN (не блокируют, но идут в отчёт для консистентности).

## Формат отчёта

```
## Naming Check — {{scope}} — {{date}}

Файлы: N проверено
  ❌ ERROR: file — <правило> → <как переименовать>
  ⚠️ WARN:  file — <причина>
Функции: M проверено
  ❌ ERROR: file:line TestName — <нарушение> → <предложенное имя>
  ⚠️ WARN:  ...
Имя ↔ содержимое: K проверено, расхождений: X

Вердикт: PASS (0 ERROR) | FAIL (N ERROR)
```

## Верификация перед сдачей (rules/40)

Прогони 10-этапный протокол по отчёту. Акценты скила:

- **Этап 1 (контекст):** `context/NAMING-CONVENTIONS.md` в статусе `filled` — иначе стоп, сверять не с чем.
- **Этап 5 (точность):** легаси-зоны (§5 канона) репортятся как WARN, не ERROR; ERROR — только реальное нарушение действующего канона.
- **Этап 6 (критич.класс):** проверка «имя не врёт» (Step 4) выполнена — имя-врун опаснее плохого имени.
- **Этап 8 (формат):** каждый ERROR сопровождён готовым правильным именем.

Приложи компактный блок верификации к отчёту.

## Политика

- ERROR блокирует мерж diff-а; WARN — нет, но копится в отчёте аудита.
- Каждый ERROR сопровождается **готовым правильным именем** — находка без предложения не принимается.
- Массовые переименования легаси — отдельной задачей, не в feature-diff.
