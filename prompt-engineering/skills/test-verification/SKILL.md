# /test-verification — верификация тест-кейсов

> Прогоняется после `test-case-generator` (или для ручных TC) и ДО автоматизации. Принцип: кейс, не выводимый из документации — не «креативность», а фантазия; кейс, дублирующий другой — шум; требование без кейса — дыра.

## Вход

- Набор TC (выход test-case-generator или ручной).
- Документация-источник: {{spec / requirements / API-док}} — та же, по которой генерировали.
- `context/TESTFRAMEWORK-MAP.md`, `context/NAMING-CONVENTIONS.md`.

## Step 1. Трассируемость (каждый кейс ← требование)

```
Для каждого TC:
1. Указан источник (раздел/пункт документации)? Нет → FINDING: untraceable.
2. Открой источник. Кейс РЕАЛЬНО следует из текста? Проверь цитатой.
3. Кейс проверяет то, что заявлено в его названии/цели?
4. Ожидаемый результат в TC дословно выводится из документации,
   а не «додуман»? Додумка → FINDING: invented-expectation
   (даже если додумка разумна — её место в вопросах к аналитику).
```

## Step 2. Покрытие (каждое требование → кейсы)

```
1. Составь список атомарных требований из документации
   (каждое «должен/обязан/если...то» — отдельная строка).
2. Матрица: требование × TC. Требование без единого TC → FINDING: gap.
3. Для каждого требования с TC проверь наличие минимум:
   - позитивный сценарий
   - негативный сценарий (невалидный вход / отказ зависимости)
   - граничные значения (если требование содержит числа/лимиты/длины)
   - авторизационный кейс (если ресурс имеет владельца/роли)
   Отсутствие класса → FINDING: incomplete-coverage (с указанием класса).
```

## Step 3. Качество отдельного кейса

```
Каждый TC проверь по чек-листу:
1. Шаги воспроизводимы без автора (конкретные данные, не «введите валидное значение»).
2. Ожидаемый результат наблюдаем и проверяем (assert-able): статус-код,
   состояние UI, запись в БД — не «работает корректно».
3. Предусловия полны: окружение, данные, состояние системы.
4. Кейс атомарен: одна проверка = один кейс (кроме связного flow).
5. Кейс не дублирует другой TC (та же комбинация вход/состояние/ожидание).
6. Приоритет проставлен и обоснован (severity риска, не «всё High»).
7. Имя/ID соответствует NAMING-CONVENTIONS §3.
```

## Step 4. Пригодность к автоматизации

```
Для TC, помеченных к автоматизации:
1. Уровень выбран верно? (правило: минимально возможный уровень пирамиды —
   логика юнитом, контракт интеграционным, флоу e2e; TESTFRAMEWORK-MAP §1).
2. Есть инфраструктура? (нужный тип фикстур/моков существует в фреймворке —
   TESTFRAMEWORK-MAP §3; нет → отметить «требует инфраструктуры: что именно»).
3. Кейс детерминирован? (нет зависимости от времени суток, внешних сервисов,
   порядка запуска — иначе пометка flaky-risk с причиной).
```

## Step 5. Вопросы к документации

Всё, что при верификации оказалось неоднозначным в самой документации (противоречия, недосказанности, «а что если») — отдельным списком вопросов. Это выход не хуже findings: дыры в доке — источник будущих багов.

## Формат отчёта

```
## TC Verification — {{feature}} — {{date}}

Кейсов проверено: N | Требований в матрице: M

❌ REJECT (кейс исключить/переписать):
  - TC-xxx — untraceable | invented-expectation | duplicate of TC-yyy
⚠️ FIX (кейс доработать):
  - TC-xxx — <нарушенный пункт Step 3/4> → <что исправить>
🕳 GAP (требование без покрытия):
  - <требование, цитата> → предложить TC-класс
❓ Вопросы к документации:
  - <раздел> — <вопрос>

Матрица: M требований, покрыто K (K/M%), gaps: G
Вердикт: APPROVED (0 REJECT, 0 GAP) | NEEDS WORK
```

## Мета-верификация отчёта (rules/40)

Этот скил САМ является independent-режимом rules/40 для TC-набора (Steps 1–5 = этапы 2/4/8 протокола применительно к кейсам). Дополнительно перед сдачей своего отчёта прогони по нему:

- **Этап 1 (контекст):** документация-источник — та же, по которой генерировали (иначе сверка бессмысленна); ты ≠ автор набора (независимость).
- **Этап 3 (факты):** каждый REJECT/GAP подтверждён цитатой источника, не «мне кажется».
- **Этап 9 (воспроизводимость):** матрица покрытия полна и перепроверяема; вердикт APPROVED/NEEDS WORK доказан findings.

Приложи компактный блок верификации к отчёту.

## Политика

- APPROVED — единственный пропуск в автоматизацию.
- Верификатор не переписывает кейсы сам — возвращает генератору (независимость проверки).
- Повторная верификация после доработки — полная, не только исправленных.
