# /context-intake — бутстрап контекста проекта

> Единственный скил, который превращает обезличенный тулкит в рабочий инструмент конкретного проекта. Принцип: **факты из кода, не из головы**. Каждая строка в context-доках должна иметь источник.

## Режимы

- **full** (по умолчанию) — полный скан, заполнение всех четырёх context-доков с нуля.
- **--refresh** — перечитать источники, обновить изменившиеся секции, не трогая вручную дополненные (помеченные `<!-- manual -->`).

## Step 0. Инвентаризация источников

```
1. Прочитай верхний уровень репозитория (ls корня, 2 уровня вглубь).
2. Найди манифесты стека: go.mod, package.json, pyproject.toml, pom.xml,
   Cargo.toml, Gemfile, composer.json — всё что есть.
3. Найди документацию: README*, docs/, CONTRIBUTING*, AGENTS.md, CLAUDE.md,
   style guide, test plan, ADR-папки.
4. Найди CI: .github/workflows/, .gitlab-ci.yml, Jenkinsfile, azure-pipelines.
5. Найди конфиги тест-раннеров: vitest/jest/playwright/cypress config,
   pytest.ini, phpunit.xml, Makefile-цели с test.
```

Зафиксируй список найденного — он пойдёт в колонки «Источник факта».

## Step 1. PROJECT-CONTEXT.md

```
1. Название/тип/описание — из README и манифестов.
2. Стек с версиями — ТОЛЬКО из манифестов (не из README, он врёт чаще).
3. Дерево репо — реальный вывод ls/tree, отфильтрованный от мусора
   (node_modules, dist, build, .git).
4. Команды — приоритет источников: CI-конфиг > Makefile/package.json scripts >
   docs. Команда из CI = канон, она гарантированно рабочая.
5. Каждую команду ПРОВЕРЬ запуском (или пометь «не проверена: причина»).
6. Гейты качества — из CI: обязательные джобы, coverage-пороги, блокирующие шаги.
```

## Step 2. TESTFRAMEWORK-MAP.md

```
1. Найди ВСЕ тестовые файлы по масс-паттернам: *_test.go, *.test.*, *.spec.*,
   test_*.py, *Test.java и т.д. Посчитай по директориям.
2. Классифицируй уровни: unit/integration/e2e — по раннерам, build-тегам,
   путям, конфигам. Не по названиям папок «на глаз»: проверь, что реально
   импортируется/поднимается в 2–3 файлах каждого уровня.
3. Найди инфраструктуру: фикстуры, фабрики, моки, page objects, тестовую БД
   (грепни по testcontainers, compose, sqlite::memory:, msw, httptest).
4. Зафиксируй канонический способ запуска каждого уровня + обязательные флаги
   (ищи в CI: -race, -count=1, --runInBand, workers=1 — их наличие в CI
   означает «обязательно», даже если локально работает без них).
5. Болевые точки: грепни skip/quarantine/flaky/retry в тестах и CI,
   посмотри последние 20 коммитов с fix.*test в message.
```

## Step 3. NAMING-CONVENTIONS.md

```
1. Возьми выборку: 30–50 тестовых файлов из разных директорий.
2. Выведи ФАКТИЧЕСКИЕ паттерны имён файлов (частотный анализ:
   какой суффикс/префикс доминирует, какие исключения).
3. Выведи фактические паттерны имён функций/кейсов: структура
   (Unit_Scenario_Expected? should...? given/when/then?), язык, регистр.
4. Сверь со style guide проекта, если он есть. Расхождение факт ↔ гайд —
   зафиксируй в §5 «Известные отступления», канон НЕ выбирай сам —
   пометь TODO(owner): выбрать канон.
5. Найди формат TC-ID и привязку тестов к требованиям (грепни TC-, REQ-,
   ссылки на тикеты в тестах).
```

## Step 4. PATTERNS-LIBRARY.md

```
1. Выбери по одному ЛУЧШЕМУ файлу-эталону на уровень (unit/integration/e2e/
   негативный). Критерии: свежий, полный (setup/act/assert/cleanup),
   использует инфраструктуру фреймворка, читается без контекста.
2. Скопируй в док РЕАЛЬНЫЕ фрагменты кода эталонов (не переписывай своими
   словами — паттерн должен компилироваться в голове читателя).
3. Антипаттерны — из реальных находок: грепни sleep( в тестах, закомментированные
   тесты, .only(, пустые catch, assert без сообщений. Каждому — замену.
4. Негативные/security-кейсы: найди существующие denial-тесты
   (403/401/forbidden в тестах) — они каноны для новых.
```

## Step 5. Финализация

```
1. Проставь в каждом доке frontmatter: status: filled, filled_at: <дата>.
2. Прогрепай все четыре дока на незаполненные {{...}} — каждый оставшийся
   должен быть либо внутри примера-иллюстрации, либо заменён на
   TODO(intake): <что не нашли и где искали>.
3. Выведи отчёт.
```

## Формат отчёта

```
## Context Intake Report — {{project}} — {{date}}

| Док | Статус | Заполнено секций | TODO(intake) |
|-----|--------|------------------|--------------|
| PROJECT-CONTEXT.md | filled | 7/7 | 0 |
| TESTFRAMEWORK-MAP.md | filled | 6/7 | 1 (perf-тесты не найдены) |
| NAMING-CONVENTIONS.md | filled | 5/5 | 0 |
| PATTERNS-LIBRARY.md | filled | 8/8 | 0 |

Проверенные команды: N из M (список непроверенных с причиной)
Расхождения факт ↔ style guide: <список или «нет»>
Следующий шаг: smoke-тест агентов (INSTALL.md Шаг 4)
```

## Верификация перед сдачей (rules/40)

Прогони 10-этапный протокол по заполненным context-докам. Акценты скила:

- **Этап 3 (факты):** каждый заполненный факт имеет источник; команды §4 прогнаны или помечены; дерево репо — реальный вывод, не память.
- **Этап 4 (негатив/границы):** проверены не только «есть» уровни/паттерны, но и явно зафиксировано отсутствующее (`TODO(intake)`), а не пропущено молча.
- **Этап 6 (критич.класс):** ни одного выдуманного пути/команды/числа; расхождения факт↔style guide зафиксированы, канон не выбран самовольно.
- **Этап 9 (воспроизводимость):** другой исполнитель по тем же источникам заполнит доки так же.

Приложи компактный блок верификации к Intake Report.

## Запреты

- ⛔ Выдумывать команды, пути, версии. Нет источника → `TODO(intake)`.
- ⛔ Выбирать канон нейминга при расхождении факта и гайда — это решение владельца.
- ⛔ Переписывать код эталонов «красивее» — только реальные фрагменты.
- ⛔ Затирать секции с пометкой `<!-- manual -->` в режиме --refresh.
