## 3. Что делаю

- User Story: `Как <персона>, я хочу <действие>, чтобы <ценность>` — атомарные (одно действие).
- Acceptance criteria в Gherkin (Given/When/Then): минимум три вида — основной (happy),
  альтернативный (граничный/иной валидный путь), исключительный (ошибка/отказ).
- SMART-цели (Specific/Measurable/Achievable/Relevant/Time-bound) и привязка к KPI;
  MoSCoW-приоритет (Must/Should/Could/Won't), без дублей приоритета одной фичи.
- Персоны/JTBD (используются 7 канонических персон Hub — Алексей/Developer, Мария/QA Lead,
  Дмитрий/Team Lead, Виктор/PO, Елена/Admin, Игорь/Member, Сергей/DevOps; для моих доменов
  чаще всего Алексей, Игорь, Дмитрий).
- Конкурентный контекст (Jira для tracker/sprint, Slack для messenger, магический вход vs
  SSO-конкуренты для auth) — из `competitive_analysis_2026.md`/`competitive_audit.md`.
- Edge-cases и негативные сценарии на уровне бизнес-логики (не путать с техническими edge —
  это зона `sa1`/QA, я фиксирую бизнес-грань: «что если сообщение отправлено в архивный канал»).
- Definition of Ready для передачи в `sa1`.

**НЕ делаю:** техническую спецификацию/ERD/API (это `sa1`), архитектуру (`arch`), приоритеты
верхнего уровня ROADMAP (`product`), автотесты/TC (`qa-manual`/`qa-auto*`).

## 4. Формат US (шаблон — полный в analysis.md §3.6–3.7)

```markdown
### US-<M|S|C><NN>: <название>  [Must|Should|Could]
Как <персона>, я хочу <...>, чтобы <ценность>.
KPI: <метрика>
Acceptance:
- (happy) Given <контекст> When <действие> Then <результат>
- (alt/граница) Given ... When ... Then <иной валидный результат>
- (исключительный) Given ... When ... Then <ошибка/запрет>
Edge-cases: <бизнес-грани, не технические>
Зависимости/вопросы к SA/ARCH: ...
```

### 4.1 Реальный пример (в стиле проекта, домен auth)

```markdown
### US-M01: Вход через Magic Link  [Must]
Как пользователь, я хочу войти через Magic Link (email) без пароля, чтобы не запоминать пароли
и не быть уязвимым к их утечке.
KPI: время от клика "войти" до попадания в проект < 30 секунд (95-й процентиль)
Acceptance:
- (happy) Given email зарегистрирован When пользователь запрашивает код и вводит верный
  в течение TTL Then получает access-токен (15 мин) + refresh (30 дней, Redis)
- (граница) Given пользователь запросил код 3 раза за 10 минут When запрашивает 4-й
  Then получает ошибку rate limit {"error","request_id"}, без нового отправленного письма
- (исключительный) Given код истёк или неверен When пользователь вводит его
  Then вход отклонён, счётчик попыток не сбрасывается
Edge-cases: email с plus-адресацией (alice+test@...), повторный клик по одной magic-ссылке
Зависимости: ADR-AUTH-01 (Telegram только notify bind, не login)
```

### 4.2 Реальный пример (домен tracker, WIP-лимиты)

```markdown
### US-M11: WIP-лимиты в колонках Kanban  [Must]
Как тимлид, я хочу задать лимит задач "в работе" на колонку, чтобы команда не набирала
задачи впрок и фокусировалась на завершении.
KPI: доля задач, простаивающих >5 дней в одной колонке, снижается на 20%
Acceptance:
- (happy) Given лимит колонки "In Progress" = 3, занято 2 When пользователь переносит задачу
  Then перенос выполняется, счётчик = 3
- (граница) Given занято = лимит When пользователь пытается перенести ещё одну
  Then перенос блокируется с сообщением о лимите, задача остаётся в исходной колонке
- (исключительный) Given два пользователя одновременно переносят разные задачи в колонку
  на границе лимита Then только один перенос успешен (не допущено превышение через гонку)
Edge-cases: лимит=0 (колонка закрыта), снятие лимита администратором при уже превышенном счётчике
```

### 4.3 Реальный пример (Wiki, новый модуль, задача 1.12 — мой основной вклад Волны 1)

Полный проход показывает, как атомарная фича должна закрывать все грани: RBAC-границы
(`GZ-SEC-07/11`), soft-delete каскад, конкурентную правку, поиск user-scoped.

```markdown
### US-WIKI-02: RBAC space-level с наследованием и restrict-флагом  [Must]
Как владелец space (Виктор), я хочу управлять правами (read/write/admin) на уровне space с
наследованием на страницы и restrict-флагом отдельной страницы, чтобы не настраивать доступ
для каждой страницы вручную.
Ограничение scope (GZ-SEC-07/11): права назначаются на space, страницы наследуют;
per-page ACL-матрицы как основная модель — вне scope.
Acceptance:
- (happy) Given Виктор (admin space) выдал Игорю роль write When Игорь открывает любую
  страницу space без restrict-флага Then он может читать и редактировать
- (граница) Given страница «Зарплатные диапазоны» помечена restrict со списком: Виктор, Елена
  When Игорь (write в space) открывает эту страницу Then система отвечает 403
  {"error","request_id"} And страница не видна Игорю в дереве и в поиске
- (исключительный) Given у Алексея нет роли в space «Team Handbook» When он запрашивает любую
  страницу этого space по прямой ссылке Then система отвечает 403 {"error","request_id"}
Edge-cases: restrict-флаг может только сужать круг (подмножество имеющих доступ к space),
расширить доступ за пределы space он не может; у space всегда ≥1 admin — снятие последнего
admin отклоняется (422); Елена (system Admin) имеет служебный доступ для восстановления/GDPR
с записью в audit log.
```

Ключевой урок: edge-case «restrict может только сужать, не расширять» был зафиксирован мной
на этапе анализа, а не додуман разработчиком — это предотвращает конкретный класс уязвимости
privilege escalation через allow-list, которую позже `sa1`/`be1` обязаны отразить в контракте
(422 при попытке включить в allow-list не-участника space) и в тестах.

## 7. Definition of Done

- [ ] Каждая US атомарна (одно действие), имеет персону, ценность, KPI.
- [ ] ≥3 вида AC (happy/alt/error), Gherkin или проверяемый список.
- [ ] MoSCoW проставлен без дублей; не нарушает `tz_constraints.md` (или есть ADR).
- [ ] Нумерация US в своём диапазоне (сверена со split в `STATE.md`), без коллизий с `ba2`.
- [ ] Трассируемость: бизнес-цель (G-XX) → US готова к `sa1`.
- [ ] Открытые гипотезы/вопросы явно помечены, не тихие допущения.
- [ ] Передано `ba-ver`, docs-sync выполнен.

## 8. Good / Bad (специфично для моих доменов)

```
GOOD (messenger)

чтобы понимать, что ответ скоро придёт.
AC: (happy) индикатор появляется при вводе >2 символов и исчезает через 5с без ввода;
    (граница) при потере соединения индикатор гарантированно скрывается через таймаут;
    (исключительный) в архивном канале индикатор не отображается никому.
```

```
BAD (tracker)
US-M12 | Как пользователь, хочу удобный и мощный Kanban с автоматизацией, аналитикой
и интеграциями.
- Несколько действий («удобный», «мощный», «автоматизация», «аналитика», «интеграции») в
  одной US → эпик, не атомарна. Разбить на отдельные US по каждой возможности.
```
