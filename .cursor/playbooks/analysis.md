## 1. Назначение и принципы playbook аналитики

### 1.1 Зачем этот документ

Аналитическое крыло Hub производит не код, а **контракты**: описания того, что должно быть
построено, зачем, для кого и с какими ограничениями. Ошибка аналитика дешевле ошибки
разработчика ровно до момента, пока она не попала в код: расплывчатая User Story рождает
неверную реализацию, нетестируемое NFR рождает «зелёные» тесты без смысла, пропущенная связь
в ERD рождает миграцию с потерей данных. Поэтому цена точности здесь максимальна.

Playbook описывает **единый способ работы** для пяти аналитических агентов и трёх
верификаторов. Он не заменяет skill-файлы (`BA_skill.md`, `SA_skill.md`, `ARCH_skill.md`),
а разворачивает их в детальные процедуры, шаблоны и примеры «хорошо/плохо». Skill-файл
отвечает на вопрос «что я делаю и куда пишу лог»; playbook отвечает на вопрос «как именно
и по какому стандарту».

### 1.2 Базовые принципы

| Принцип | Что означает на практике |
|---------|--------------------------|
| Единая база знаний | Перед задачей загружаются все файлы `docs/`. Дублировать их содержимое в артефактах запрещено — только ссылки. |
| Один артефакт — один владелец | `vision_and_scope.md` — BA, `system_specification.md` — SA, `architecture.md` — ARCH. Чужой файл правит только владелец. |
| Всё измеримо и проверяемо | Цель без метрики, US без acceptance criteria, NFR без числового порога — брак. |
| Трассируемость сквозная | Каждый нижний артефакт ссылается на верхний: US → G-XX, FR → US, API → FR, TC → AC. |
| Не ломать TZ | `docs/tz_constraints.md` — закон. Mandatory нельзя убирать, forbidden нельзя вводить без ADR. |
| Атомарность | Одна итерация — один связный кусок (эпик/модуль/фича), ≤200–300 строк изменений в docs. |
| Docs sync немедленный | Изменил артефакт → в той же сессии обновил `.planning/STATE.md` и связанные docs (правило `.cursor/rules/55-docs-sync.mdc`). |
| Верификация обязательна | Артефакт получает `verified: true` только после независимой проверки соответствующим `*-ver`. |
| Понятное описание | К каждому артефакту — 2–5 предложений простым языком для верификатора и разработчика. |

### 1.3 Как аналитик передаёт работу дальше

Поток создания ценности в Hub линеен и цикличен одновременно:

```
Идея / запрос PO
   → BA:  бизнес-цель (SMART) + персона + JTBD + User Story + AC + MoSCoW  → vision_and_scope.md
   → SA:  FR/NFR + ERD + API-контракт + DFD + матрица трассируемости       → system_specification.md, wiki/API.md
   → ARCH: C4 + выбор библиотек + ADR + deployment + атрибуты качества      → architecture.md, stack_and_tools.md
   → BE/FE: реализация + тесты
   → QA:  тест-кейсы + регрессия
   → *-ver: верификация каждого шага
```

Каждая стрелка — это **handoff** с описанием на простом языке и обязательной верификацией.
Аналитик не начинает следующий слой, пока предыдущий не получил `verified: true` или пока
явно не согласована параллельная работа с фиксацией допущений (см. раздел 7).

### 1.4 Что playbook НЕ разрешает

- Аналитик не пишет production-код (это BE/FE) и не редактирует чужой доменный doc.
- Аналитик не ставит сам себе `verified: true` — это делает верификатор.
- BA не принимает технических решений (стек, схема БД) — это SA/ARCH.
- SA не меняет бизнес-приоритеты (MoSCoW) — это BA.
- ARCH не переопределяет бизнес-цели — только реализует их технически.
- Никто из аналитиков не удаляет mandatory-ограничения из TZ без ADR и согласования.

## 2. Кто и когда: распределение ролей ba1/ba2/sa1/sa2/arch

### 2.1 Обзор ролей

| Агент | Роль | Основной артефакт | Маршрутизация | Режим |
|-------|------|-------------------|---------------|-------|
| `ba1` | Business Analyst (поток A) | `docs/vision_and_scope.md` (разделы A) | `inherit` | readonly-анализ |
| `ba2` | Business Analyst (поток B) | `docs/vision_and_scope.md` (разделы B) | `inherit` | readonly-анализ |
| `sa1` | System Analyst (модули A) | `docs/system_specification.md` (модули A) | `inherit` | readonly-анализ |
| `sa2` | System Analyst (модули B) | `docs/system_specification.md` (модули B) | `inherit` | readonly-анализ |
| `arch` | Architect | `docs/architecture.md`, `docs/stack_and_tools.md` | `inherit` | readonly-анализ |
| `ba-ver` | Верификатор BA | проверка vision_and_scope | `inherit` | readonly |
| `sa-ver` | Верификатор SA | проверка system_specification | `inherit` | readonly |
| `arch-ver` | Верификатор ARCH | проверка architecture | `inherit` | readonly |

`ba1`/`ba2` и `sa1`/`sa2` — это **две параллельные инстанции одной роли**, работающие над
разными доменами/эпиками одновременно, чтобы ускорить анализ крупного milestone. `arch`
существует в единственном числе, потому что архитектурная целостность требует единого
взгляда; вместо распараллеливания `arch` работает последовательными атомарными итерациями
по контейнерам/компонентам.

### 2.2 Когда подключается каждая роль

| Триггер | Кто первый | Далее |
|---------|-----------|-------|
| Новая фича / эпик от PO | `ba1` или `ba2` (по домену) | `sa` → `arch` (если меняется структура) |
| Новая сущность / изменение схемы БД | `sa` (модуль) | `arch` (если влияет на модульность) |
| Новый API endpoint / контракт | `sa` | `arch` (если новая интеграция) |
| Смена стека / библиотеки | `arch` | `sa` (обновить NFR) |
| Новое ADR-решение | `arch` | все аналитики читают |
| Уточнение бизнес-приоритета | `ba` | `sa` пересматривает scope |
| Новый milestone | `ba1`+`ba2` параллельно | `sa1`+`sa2` параллельно → `arch` |

Для мелкого фикса без изменения поведения аналитики не нужны — идёт прямой путь `be`/`fe` →
`be-ver`/`fe-ver` → `/qa-gate` (см. REGULATION §5, hotfix path).

### 2.3 Как ba1 и ba2 делят работу без конфликтов

Оба BA пишут в **один файл** `docs/vision_and_scope.md`. Чтобы избежать конфликтов при
параллельной работе, действует протокол разделения:

1. **Разделение по разделам/доменам.** Перед стартом milestone оркестратор (или один из BA)
   фиксирует карту разделения в `.planning/STATE.md`:

```
## Analysis split — milestone v5 (2026-07-02)
ba1: домены Tracker, TMS, Calls        → US-M/US-S для этих модулей, персоны Алексей/Мария/Сергей
ba2: домены Messenger, Intranet, CRM   → US-M/US-S для этих модулей, персоны Игорь/Виктор/Елена
Общие разделы (глоссарий, KPI, MoSCoW-сводка): владелец ba1, ba2 предлагает через комментарий-заметку
```

2. **Договорённость о нумерации.** Идентификаторы US не должны пересекаться. Принята схема:

| Поток | Диапазон US | Диапазон целей | Диапазон персон |
|-------|-------------|----------------|-----------------|
| `ba1` | US-M01…M20, US-S01…S15 | G-01…G-06 (общие, редактирует только по согласованию) | P-01…P-04 |
| `ba2` | US-M21…M40, US-S16…S30 | предлагает G-07+ | P-05…P-08 |

   Если поток исчерпал диапазон — расширяет его вверх, не залезая в чужой. Конфликт номеров —
   это дефект процесса, а не «поправим потом».

3. **Единый глоссарий.** Термины (например, «эпик», «инцидент», «канал», «прогон») ведутся
   в одном месте — в приложении к `vision_and_scope.md` или в `docs/README.md`. Перед вводом
   нового термина BA проверяет, нет ли синонима. `ba2` не вводит «беседа», если `ba1` уже
   ввёл «канал».

4. **Непересекающиеся секции файла.** Физически BA правят разные заголовки markdown. Если оба
   должны тронуть общий раздел (например, таблицу KPI), это делает владелец раздела, второй
   передаёт правку текстом в handoff-заметке. Так исключается редактирование одних и тех же
   строк.

5. **Синхронизация в конце.** После завершения обоих потоков один из BA (владелец общих
   разделов) сводит MoSCoW-приоритизацию целиком, проверяя отсутствие дублей (например,
   Web Push не должен быть одновременно Should и Could — реальный дефект из лога `ba-ver`).

#### Good / Bad: разделение работы BA

```
GOOD (ba1)
- Взял домены Tracker/TMS согласно split в STATE.md
- US-M03 (задачи), US-M05 (тест-кейсы), US-M11 (Kanban) — все в диапазоне M01–M20
- Новый термин «swimlane» сверил с глоссарием — отсутствовал, добавил с определением
- Таблицу KPI не трогал (владелец ba1 по split — сам, но изменение согласовал заметкой)
```

```
BAD (ba2)
- Начал писать US про Kanban с ID US-M11 (уже занят ba1) → конфликт номеров
- Ввёл термин «дорожка» вместо «swimlane» → синоним, расхождение глоссария
- Отредактировал таблицу KPI одновременно с ba1 → merge-конфликт строк
- Поставил US-M11 приоритет Could, хотя ba1 держит Must → противоречие MoSCoW
```

### 2.4 Как sa1 и sa2 делят работу без конфликтов

`sa1`/`sa2` пишут в `docs/system_specification.md` и `docs/wiki/API.md`. Разделение —
**по модулям backend** (`backend/internal/<module>`), что естественно, поскольку FR/API
группируются по модулям.

1. **Разделение по модулям.** Пример карты:

```
## SA split — milestone v5 (2026-07-02)
sa1: tracker, sprint, tms, calls        → FR-TASK*, FR-SCRM*, FR-TMS*, FR-CALL*, API этих модулей
sa2: messenger, notification, search    → FR-MSG*, FR-NOTF*, FR-SRCH*, API этих модулей
arch: cross-cutting NFR + module boundaries (после sa1/sa2)
```

2. **Нумерация FR/NFR.** FR нумеруются с префиксом модуля: `TASK-01`, `MSG-04` — конфликтов
   между потоками нет по построению. NFR — сквозная общая нумерация `NFR-01…NFR-NN`; новые NFR
   резервируются диапазонами:

| Поток | FR-префиксы | Диапазон новых NFR |
|-------|-------------|--------------------|
| `sa1` | TASK, SCRM, TMS, CALL | NFR-31…NFR-40 |
| `sa2` | MSG, NOTF, SRCH | NFR-41…NFR-50 |
| `arch` | cross-cutting | NFR-51+ |

3. **ERD-целостность.** Сущности разных модулей связаны (например, `Issue` ↔ `TestCase` ↔
   `Message`). Общая ER-диаграмма — единая; каждый SA правит свои сущности, а **связи между
   доменами** согласуются: если `sa1` добавляет FK `TestCase.issue_id`, он фиксирует это в
   handoff для `sa2`, владеющего смежным доменом, и для `arch`.

4. **API-контракты.** Каждый SA описывает эндпоинты своих модулей в `wiki/API.md` в своей
   секции. Общие соглашения (формат ошибки `{"error","request_id"}`, пагинация, коды ответов)
   — единый раздел, владелец `sa1`, изменяется по согласованию.

5. **Синхронизация счётчиков.** Итоговый inventory эндпоинтов (например, «Total REST 286»)
   сводит один SA, суммируя per-module counts обоих потоков. Реальный дефект из лога `sa-ver`:
   SA заявил 293, независимый пересчёт дал 285 — расхождение из-за несведённых per-module
   счётчиков. Правило: числа в сводке = сумма проверяемых слагаемых, а не «на глаз».

#### Good / Bad: разделение работы SA

```
GOOD (sa1)
- FR-TASK-14 (WIP-лимиты) — префикс модуля, конфликтов нет
- Добавил FK TestCase.issue_id, зафиксировал в handoff для sa2 и arch
- Новый NFR-31 (лимит вложенности тредов) — в своём диапазоне 31–40
- Пересчитал tracker routes через RegisterRoutes: 48, записал в inventory
```

```
BAD (sa2)
- Ввёл FR-01 без префикса модуля → неясно, чей и коллизия с чужим FR-01
- Изменил формат ошибки в общем разделе без согласования с владельцем sa1
- Заявил «messenger 44 routes» без пересчёта по коду → drift с реальностью
- Взял NFR-33 (чужой диапазон) → пересечение с sa1
```

### 2.5 Роль arch относительно параллельных SA

`arch` включается **после** того, как `sa1`/`sa2` описали FR/API своих модулей, и решает
cross-cutting задачи: границы модулей, зависимости, общие паттерны, deployment, атрибуты
качества. `arch` — арбитр при спорах о том, куда положить общую сущность или как разрешить
циклическую зависимость между доменами двух SA. Если `sa1` и `sa2` расходятся в том, чей
модуль владеет сущностью `Notification`, решение принимает `arch` и фиксирует ADR.

| Изменение | ba1/ba2 | sa1/sa2 | arch | Верификаторы |
|-----------|---------|---------|------|--------------|
| Новая бизнес-цель | ✅ (владелец домена) | пересмотр scope | — | ba-ver |
| Новая User Story | ✅ | FR-декомпозиция | — | ba-ver → sa-ver |
| Новое FR | consult | ✅ | — | sa-ver |
| Новое NFR | — | ✅ | атрибут качества | sa-ver → arch-ver |
| Новая сущность/поле | — | ✅ (ERD) | границы модуля | sa-ver → arch-ver |
| Новый endpoint | — | ✅ (контракт) | — | sa-ver |
| Смена/выбор библиотеки | — | обновить NFR | ✅ (ADR) | arch-ver |
| Новая интеграция (внешняя) | US-контекст | API-контракт | C4 + ADR + security | все три |
| Deployment-изменение | — | — | ✅ | arch-ver + devops |

## 3. Бизнес-анализ (BA)

Владелец раздела: `ba1`, `ba2`. Основной артефакт: `docs/vision_and_scope.md`.
Верификатор: `ba-ver`. Вспомогательные источники: `docs/user_needs_analysis_2026.md`
(персоны, JTBD, MoSCoW), `docs/competitive_analysis_2026.md`, `docs/competitive_audit.md`
(конкуренты, backlog best practices), `.planning/PROJECT.md`, `.planning/ROADMAP.md`.

### 3.1 Что делает BA и чего не делает

**Делаю:** выявление и формализация требований, User Story, acceptance criteria, SMART-цели,
KPI, персоны и JTBD, MoSCoW-приоритизация, конкурентный анализ, gap-анализ, ведение backlog,
success criteria фазы.

**НЕ делаю:** технические решения (схема БД, стек, эндпоинты), код, прямое редактирование
ROADMAP (передаю SA/ARCH и оркестратору), выбор библиотек, архитектуру.

### 3.2 Выявление требований (elicitation)

Требования не «придумываются», а **выявляются** из источников и проверяются вопросами.
Источники в Hub:

| Источник | Что извлекаем |
|----------|---------------|
| Запрос PO / пользователя | Явная потребность, боль, ожидаемый результат |
| `docs/user_needs_analysis_2026.md` | Персоны, JTBD, приоритеты MoSCoW |
| `docs/competitive_analysis_2026.md` | Что делают Jira/Slack/TestRail/Lark/Bitrix, gaps |
| `docs/competitive_audit.md` | Best practices, feature backlog |
| Существующий `vision_and_scope.md` | Текущие цели/US — для gap-анализа |
| `.planning/PROJECT.md`, `ROADMAP.md` | Границы milestone, фазы |
| Аудиты (`.planning/AUDIT-*.md`) | Нереализованные обещания, drift |

Техника выявления: для каждой потребности задать пять вопросов —
**Кто** (персона), **Что** (действие), **Зачем** (ценность), **Когда/при каких условиях**
(контекст), **Как поймём, что готово** (критерии). Ответы на эти вопросы и есть заготовка
User Story + acceptance criteria.

### 3.3 SMART-цели

Бизнес-цель Hub оформляется в таблицу целей `vision_and_scope.md` и обязана быть SMART:
Specific, Measurable, Achievable, Relevant, Time-bound.

Шаблон строки цели:

```
| ID   | Цель                              | Измеримость                         | Срок    |
|------|-----------------------------------|-------------------------------------|---------|
| G-NN | <конкретный измеримый результат>  | <метрика с числом/фактом проверки>  | <фаза>  |
```

Реальные примеры из проекта (образец стиля):

```
| G-04 | Production-ready безопасность и стабильность | 0 CRITICAL findings, unit ≥ 80% security-critical, e2e критические пути | v2.5 |
| G-06 | Снизить стоимость владения TMS vs Allure TestOps | Собственный Allure-парсер + TMS без лицензии TestOps | v1.0 ✓ |
```

#### Good / Bad: SMART-цель

```
GOOD
G-07 | Ускорить онбординг нового участника | Время от инвайта до первого действия в проекте < 10 минут, замер на 20 инвайтах | v5
- Specific: онбординг участника
- Measurable: < 10 минут, выборка 20
- Achievable: есть онбординг-флоу (US-M08)
- Relevant: снижает отток, связано с G-01
- Time-bound: v5
```

```
BAD
G-07 | Улучшить онбординг | Пользователям будет удобнее | скоро
- Не Specific: «улучшить» — как?
- Не Measurable: «удобнее» без метрики
- Не Time-bound: «скоро» — не срок
- Нельзя проверить → верификатор вернёт FAIL
```

### 3.4 KPI

KPI — измеримые индикаторы достижения целей, ведутся отдельной таблицей. KPI отражают **факт**,
а не желаемое: если Lighthouse ещё не gated, KPI пишет реальный статус («CI artifact,
non-blocking»), а не «≥90 ✅». Реальный дефект из лога `ba-ver`: KPI заявлял «API ~230», SA
насчитал 285 — KPI должен совпадать с проверяемым источником.

Шаблон:

```
| Метрика | Целевое значение | Текущий статус |
|---------|------------------|----------------|
| <что меряем> | <порог/цель> | <факт со ссылкой на источник> |
```

Правила KPI:
- Каждый KPI ссылается на верифицируемый источник (файл, отчёт, команда).
- Статус «✅» ставится только при подтверждённом факте.
- KPI не противоречит `system_specification.md` (например, число REST endpoints едино).

### 3.5 Персоны и JTBD

Персона — обобщённый пользователь с ролью, потребностями и сценариями. В Hub 7 канонических
персон (Алексей/Developer, Мария/QA Lead, Дмитрий/Team Lead, Виктор/Project Owner,
Елена/Admin, Игорь/Member, Сергей/DevOps). Новые персоны вводятся только при реальной новой
роли, с непересекающимся ID.

Шаблон персоны:

```
| Персона | Роль | Потребности | Ключевые сценарии |
|---------|------|-------------|-------------------|
| <Имя, Роль> | <должность> | <список болей/потребностей> | <2–4 сценария> |
```

JTBD (Jobs To Be Done) формулирует работу, которую персона «нанимает» продукт выполнить:

```
Когда <ситуация>, я хочу <мотивация/действие>, чтобы <ожидаемый результат>.
```

#### Good / Bad: JTBD

```
GOOD
Когда мой автотест упал в CI, я хочу за один клик завести баг со ссылкой на прогон и кейс,
чтобы не терять контекст и не копировать логи вручную.
(персона: Мария, QA Lead; связано с US-M05, G-02)
```

```
BAD
Пользователь хочет, чтобы всё работало быстро и удобно.
- Нет ситуации, нет персоны, нет измеримого результата → не JTBD, а лозунг
```

### 3.6 User Story

User Story — атомарное требование в формате роли-действия-ценности. Формат Hub:

```
Как <персона/роль>, хочу <действие>, чтобы <ценность>.
```

Каждая US имеет:
- **ID** (`US-M<NN>` Must, `US-S<NN>` Should, `US-C<NN>` Could, `US-F<NN>`/`US-V<NN>` для
  будущих milestone) — не пересекается между `ba1`/`ba2`;
- **Acceptance Criteria** — проверяемые условия готовности (см. 3.7);
- **привязку к цели** (`G-NN`) и **приоритет** MoSCoW;
- по возможности — ссылку на персону и JTBD.

Шаблон строки US в таблице:

```
| ID | История | Acceptance Criteria |
|----|---------|---------------------|
| US-M<NN> | Как <роль>, хочу <действие>, чтобы <ценность> | <краткие AC или ссылка на Gherkin-сценарии ниже> |
```

Реальные образцы стиля из проекта:

```
| US-M01 | Как пользователь, хочу войти через Magic Link (email) без пароля | JWT 15 мин + refresh 30 дней; rate limit 3/10 мин; TG только notify bind (ADR-AUTH-01) |
| US-M07 | Как пользователь, хочу глобальный поиск (Ctrl+K) по всем сущностям | User-scope фильтрация; задачи, кейсы, пользователи, проекты, каналы, файлы; JQL для задач |
```

#### Good / Bad: User Story

```
GOOD
US-S16 | Как QA-инженер, хочу помечать тест-кейс как flaky и видеть историю нестабильности,
        чтобы приоритизировать стабилизацию.
AC:
  - в карточке кейса есть флаг flaky и счётчик нестабильных прогонов за 30 дней
  - фильтр «только flaky» в списке кейсов
  - при 3+ разных исходах на одной ревизии кейс автоматически подсвечивается
Привязка: G-02 (traceability/качество), персона Мария, приоритет Should
```

Почему хорошо: одна роль, одно действие, ясная ценность, проверяемые AC, привязка к цели и
персоне, приоритет задан, тестируемо.

```
BAD
US-S16 | Как пользователь, хочу удобную и современную систему тестирования с аналитикой,
        интеграциями и уведомлениями.
- Несколько действий в одной US (система + аналитика + интеграции + уведомления) → не атомарна
- «Удобную и современную» — не проверяемо
- Нет AC, нет привязки к цели, нет приоритета
- Роль «пользователь» слишком общая (какая персона?)
```

Правило дробления: если в US больше одного «и» в действии — это эпик, его надо разбить на
несколько US.

### 3.7 Acceptance Criteria (Gherkin)

Acceptance criteria описывают **проверяемые условия готовности**. Предпочтительная форма —
Gherkin (Given/When/Then), особенно для сценарных требований; для простых — маркированный
список проверяемых утверждений.

Шаблон Gherkin:

```gherkin
Scenario: <краткое имя сценария>
  Given <предусловие/состояние системы>
  And <дополнительное предусловие>
  When <действие пользователя/системы>
  Then <ожидаемый наблюдаемый результат>
  And <дополнительная проверка>
```

Пример (US-M01, Magic Link):

```gherkin
Scenario: Успешный вход по Magic Link
  Given пользователь с email alice@example.com существует и активен
  When он запрашивает Magic Link и вводит корректный код в течение TTL
  Then он получает access-токен со сроком 15 минут
  And refresh-токен со сроком 30 дней сохраняется хэшем в Redis

Scenario: Превышение лимита попыток входа
  Given пользователь сделал 3 запроса Magic Link за 10 минут
  When он запрашивает четвёртый в том же окне
  Then система отвечает ошибкой rate limit в формате {"error","request_id"}
  And новый код не отправляется
```

#### Good / Bad: Acceptance Criteria

```
GOOD (проверяемо, покрывает happy path + границу + ошибку)
Given задача в статусе "In Progress"
When пользователь переносит её в колонку, где достигнут WIP-лимит
Then перенос блокируется и показывается сообщение о лимите
And задача остаётся в исходной колонке
```

```
BAD (непроверяемо, только happy path)
- Kanban должен работать корректно
- WIP-лимиты должны учитываться
(нет конкретного наблюдаемого результата, нет граничного и ошибочного случая)
```

Каждая нетривиальная US должна иметь минимум три вида AC: **основной** (happy path),
**альтернативный** (граничный/иной валидный путь), **исключительный** (ошибка/отказ). Это
зеркалит требование REGULATION к сценариям (основной/альтернативный/исключительный) и
напрямую питает тест-дизайн QA (см. `verification.md`, чек-лист qa-manual-ver).

### 3.8 MoSCoW-приоритизация

MoSCoW делит требования на Must / Should / Could / Won't. Правила:

- Каждая US имеет ровно один приоритет. Дублирование приоритета для одной фичи в разных
  категориях — дефект (реальный кейс: Web Push числился и Should, и Could).
- Won't фиксирует явно исключённое из текущих milestone с причиной/ссылкой на будущую фазу.
- Must — то, без чего milestone не имеет смысла; Should — важное, но откладываемое; Could —
  желательное; Won't — вне scope сейчас.
- Приоритет согласуется с ROADMAP: Must не может быть в фазе, которая позже Should.

Шаблон Won't (образец стиля из проекта):

```
### Won't Have (v1–v2) — updated v2.5 PO lock
- ~~Видеозвонки с вебкамерами~~ → Phase 16 (ADR-TZ-REWRITE)
- Нативные мобильные приложения (PWA достаточно)
- SSO/LDAP/OAuth, SaaS billing (later), ~~Gantt~~ → Phase 16, multi-org (v5)
```

Зачёркивание (`~~...~~`) с указанием фазы — принятый способ показать, что ранее исключённое
переехало в scope конкретной фазы.

### 3.10 Backlog

## 4. Системный анализ (SA)

Владелец раздела: `sa1`, `sa2`. Основной артефакт: `docs/system_specification.md` +
`docs/wiki/API.md`. Верификатор: `sa-ver`. Вспомогательно: `docs/architecture.md`
(согласование контрактов), `docs/test_plan.md` (матрица покрытия), `.planning/COVERAGE.md`.

### 4.1 Что делает SA и чего не делает

**Делаю:** декомпозиция User Story в FR/NFR, проектирование ERD, API-контрактов, DFD,
матрицы трассируемости требование→API→код→тест, ведение `COVERAGE.md`, gap-анализ.

**НЕ делаю:** код, архитектурные решения о модульности/стеке (→ ARCH), бизнес-приоритеты
(→ BA).

### 4.2 Функциональные требования (FR)

FR — что система должна делать, на уровне поведения, а не реализации. В Hub FR группируются
по модулям с префиксом модуля (`AUTH`, `TASK`, `MSG`, `TMS`, …). Нумерация: `<PREFIX>-<NN>`.

Формат FR (из SA_skill):

```
REQ-ID: <MODULE>-<NN>
Source: US-M<NN>            # какая User Story порождает
Technical: endpoint / schema / constraint
NFR link: NFR-<NN>          # связанные нефункциональные требования
```

Требования тестируемости FR:
- Один FR — одно проверяемое поведение (атомарность).
- FR ссылается на порождающую US (`Source`) — иначе он «висит» и попадёт под вопрос sa-ver.
- FR формулируется в терминах наблюдаемого результата, а не внутренней реализации.

#### Good / Bad: FR

```
GOOD
REQ-ID: TMS-14
Source: US-S16
Technical: PATCH /api/tms/cases/:id { "flaky": true } — помечает кейс flaky;
           GET /api/tms/cases?flaky=true — фильтр; счётчик нестабильных прогонов за 30 дней
           хранится в TestCase.flaky_count (пересчёт при submit результата)
NFR link: NFR-14 (pagination offset/limit), NFR-24 (optimistic lock version)
Acceptance: соответствует AC US-S16 (флаг, фильтр, автоподсветка при 3+ исходах)
```

```
BAD
REQ-ID: TMS-14
Требование: сделать flaky-кейсы
- Нет Source (какая US?)
- Нет контракта (endpoint/schema)
- Нет связи с NFR
- «Сделать» — не проверяемое поведение
```

### 4.3 Нефункциональные требования (NFR)

NFR — ограничения качества: производительность, безопасность, надёжность, совместимость.
В Hub NFR имеют сквозную нумерацию `NFR-01…NFR-NN` и обязаны быть **числовыми/проверяемыми**.

Образцы стиля из проекта (реальные NFR):

```
| NFR-01 | Response time API (p95) | < 500ms для CRUD |
| NFR-05 | Auth rate limit | 3 попытки / 10 мин |
| NFR-13 | Error format | {"error": "...", "request_id": "uuid"} |
| NFR-24 | Optimistic locking | version int на каждой изменяемой Ent |
| NFR-25 | Primary keys | UUID v4 only — string IDs запрещены |
```

Требования тестируемости NFR:
- Числовой порог или однозначный факт (не «быстро», а «p95 < 500ms»).
- Указан способ проверки (нагрузочный тест, статический анализ, наличие поля в схеме).
- NFR не противоречит `tz_constraints.md` (mandatory-ограничения — источник многих NFR).

#### Good / Bad: NFR

```
GOOD
NFR-31 | Глубина вложенности тредов мессенджера | ≤ 1 уровень (тред от корневого сообщения);
         проверка: попытка ответить в ответ возвращает 422 {"error","request_id"}
```

```
BAD
NFR-31 | Мессенджер должен быть производительным и удобным
- Не измеримо, не проверяемо, нет порога, нет способа проверки → sa-ver вернёт FAIL
```

### 4.4 ERD (модель данных)

SA проектирует сущности, атрибуты, связи, ключи. Hub использует Ent + PostgreSQL для
реляционных данных, MongoDB для сообщений/отчётов, Redis для сессий/лимитов.

Обязательные инварианты изменяемой Ent-сущности (из TZ и NFR):

| Инвариант | Требование |
|-----------|-----------|
| Primary key | `id` UUID v4, `field.UUID("id", uuid.UUID{}).Default(uuid.New).Immutable()` — строки запрещены (NFR-25) |
| Оптимистичная блокировка | `version` int на каждой изменяемой схеме (NFR-24) |
| Время | `created_at`, `updated_at` в UTC; TZ конвертирует фронт (NFR-12) |
| Soft delete | `deleted_at` или запись в `TrashItem`, retention 30 дней (NFR-11) |

Шаблон описания сущности:

```
### Сущность: TestCase
Поля:
  - id: UUID v4, PK, immutable
  - project_id: UUID, FK → Project (cascade on project delete → soft)
  - title: string, not null
  - kind: enum {classic, bdd}
  - flaky: bool, default false
  - flaky_count: int, default 0            # NFR: пересчёт при submit результата
  - version: int                            # optimistic lock (NFR-24)
  - created_at, updated_at: UTC timestamp
  - deleted_at: UTC timestamp, nullable     # soft delete (NFR-11)
Связи:
  - TestCase 1—N TestRun
  - TestCase N—1 Issue (nullable, issue_id) # traceability тест→баг
Индексы:
  - (project_id, deleted_at) для листинга активных кейсов
  - (project_id, flaky) для фильтра flaky
```

Текстовая ER-диаграмма (образец стиля проекта — псевдографика допустима):

```
Project ──┬── Issue ──┬── Comment
          │           └── IssueLink
          ├── TestCase ── TestRun ── TestResult
          └── Channel
TestCase N──1 Issue   (issue_id, traceability)
```

#### Good / Bad: ERD

```
GOOD
- Issue.id UUID v4, version int, deleted_at nullable — все инварианты соблюдены
- Связь TestCase→Issue объявлена явно с nullable FK и described cascade
- Индекс под фильтр flaky задан
```

```
BAD
- TestCase.id как string "TC-42" → нарушает NFR-25 (UUID only)
- Нет version → нарушает NFR-24 (optimistic lock), гонки при конкурентной правке
- Hard delete без TrashItem → нарушает NFR-11 (soft delete 30 дней)
- Связь TestCase↔Issue «подразумевается», но не описана → sa-ver вернёт FAIL
```

### 4.5 API-контракты

SA описывает REST-контракты в `system_specification.md` (сводно) и `docs/wiki/API.md`
(детально). Обязательные соглашения Hub:

| Аспект | Правило |
|--------|---------|
| Base URL | `/api` |
| Auth | `Authorization: Bearer <jwt>` или `X-API-Key: <key>` |
| Content-Type | `application/json` |
| Формат ошибки | `{"error": "message", "request_id": "uuid"}` (NFR-13) |
| Пагинация задач | offset/limit: `?offset=0&limit=50` (NFR-14) |
| Пагинация чата | cursor (infinite scroll): `?cursor=...` (NFR-15) |
| Rate limits | API 100/сек (NFR-06), сообщения 60/мин (NFR-07), файлы 10/мин (NFR-08) |
| Коды ответов | 200/201 успех, 400 валидация, 401 auth, 403 RBAC, 404 not found, 409 конфликт версии, 422 бизнес-правило, 429 rate limit |

Шаблон контракта эндпоинта:

```
### POST /api/projects/:id/issues
Назначение: создать задачу в проекте
Auth: Bearer JWT; RBAC: право issue.create в проекте
Request body:
  {
    "title": "string, required, 1..255",
    "type": "enum: task|bug|story|... (9 типов)",
    "assignee_id": "uuid, optional"
  }
Responses:
  201 { "id": "uuid", "key": "HUB-123", "version": 1, ... }
  400 { "error": "title is required", "request_id": "uuid" }
  403 { "error": "forbidden", "request_id": "uuid" }
  409 { "error": "version conflict", "request_id": "uuid" }   # optimistic lock
Пагинация: N/A (create)
Идемпотентность: нет
Source FR: TASK-01 (Source US-M03)
```

Шаблон контракта листинга с пагинацией:

```
### GET /api/projects/:id/issues?offset=0&limit=50&status=open
Auth: Bearer JWT; RBAC: issue.read
Query: offset (int, ≥0), limit (int, 1..100, default 50), фильтры status/assignee/type
Response 200:
  {
    "items": [ { "id": "uuid", "key": "HUB-123", ... } ],
    "total": 1234,
    "offset": 0,
    "limit": 50
  }
Ошибки: 400 при limit>100 {"error","request_id"}
```

#### Good / Bad: API-контракт

```
GOOD
- Формат ошибки строго {"error","request_id"} на всех кодах
- Пагинация offset/limit для задач, cursor для сообщений — по NFR
- 409 при конфликте version (optimistic lock) описан явно
- Source FR указан → трассируемость
```

```
BAD
- Ошибка возвращается как {"message":"..."} → нарушает NFR-13
- Листинг задач без пагинации отдаёт весь список → нарушает NFR-14, DoS-риск
- Нет 409/422 → неясно поведение при конфликте версии/бизнес-правиле
- Нет Source FR → эндпоинт не привязан к требованию
```

### 4.6 DFD (Data Flow Diagram)

DFD показывает поток данных через слои. Образец стиля проекта (создание задачи):

```
[User] → POST /issues → [Auth Middleware] → [RBAC Check]
    → [IssueService.Create] → [IssueRepository] → [PostgreSQL]
    → [Outbox.Publish] → [NATS: hub.issues.created]
    → [WS Hub] → подписчики room project:<id>
    → [Notification] → in-app / Telegram / Web Push
```

DFD обязателен для сценариев с несколькими слоями/интеграциями (WS, NATS, внешние webhooks),
потому что именно там прячутся security-инварианты (RBAC-проверка до сервиса, подпись
webhook, user-scope фильтр). SA фиксирует, где проходят эти проверки.

## 5. Архитектура (ARCH)

Владелец раздела: `arch`. Основные артефакты: `docs/architecture.md`, `docs/stack_and_tools.md`,
`docs/code_style_guide.md` (при изменении стандартов), ADR в `.planning/decisions/`.
Верификатор: `arch-ver`. Закон границ: `docs/tz_constraints.md` (mandatory/forbidden).

### 5.1 Что делает ARCH и чего не делает

**Делаю:** C4-модель (context/container/component), выбор библиотек с обоснованием, ADR,
deployment-топология, границы модулей, атрибуты качества (безопасность, производительность,
масштабируемость, надёжность), соответствие TZ, паттерны (Clean Architecture, Repository,
Event-Driven/Outbox).

**НЕ делаю:** реализация кода (→ BE/FE), бизнес-приоритеты (→ BA), детальные API-контракты
(→ SA; ARCH только согласует их непротиворечивость).

### 5.2 C4-модель

Hub документирует три уровня C4. Уровень 1 (Context) — Hub и внешние акторы/системы; уровень 2
(Container) — процессы и хранилища; уровень 3 (Component) — модули backend/frontend.

Образец стиля (Container, из architecture.md) — псевдографика:

```
Browser (React SPA) ⇄ Caddy :80/443 ⇄ ┌ Go Backend (Fiber v3) :3000
                                        ├ WS Handler (Fiber) :3000
                                        └ static (Vite build)
Backend ⇄ PostgreSQL 17 (Ent) · MongoDB 8 (messages) · Redis 7 (sessions/limits)
        · NATS JetStream (pub/sub) · SeaweedFS (S3) · LiveKit (WebRTC)
```

Шаблон C4 Context:

```
Акторы:
  - <Персона/роль> → взаимодействует с Hub через <канал>
Внешние системы:
  - GitHub/GitLab (webhooks, PR/MR)
  - Telegram (notify bind)
  - LiveKit (WebRTC media)
  - SMTP/Resend/hub-mail (email)
Hub System:
  - принимает <входы>, отдаёт <выходы>, хранит <данные>
```

Шаблон C4 Component (модуль):

```
Модуль: tms
Слои: handler (handler_cases.go, handler_runs.go)
      → service (service.go)
      → repository (repository.go interface, ent_repository.go)
      → Ent (PostgreSQL) + Mongo (allure_reports)
Зависимости: tracker (issue link), notification (bug alert), storage (attachments)
События: publishes hub.tms.run.finished (NATS/outbox)
```

При изменении C4 ARCH держит диаграммы **синхронными с кодом**: реальный дефект из лога
`arch-ver` — docs заявляли «18 модулей», код содержал 21; «Go 1.24» при фактической 1.25.
Правило: каждое число/факт в architecture.md сверяется с кодом (grep, go.mod, routeTree).

### 5.3 Выбор библиотек с обоснованием

Любой выбор/замена библиотеки — решение с обоснованием и записью в `stack_and_tools.md` +
ADR. Критерии выбора:

| Критерий | Вопрос |
|----------|--------|
| Соответствие TZ | Не нарушает ли mandatory/forbidden? (Fiber, NATS, SeaweedFS, TanStack Router — фиксированы) |
| Зрелость/поддержка | Активно ли развивается, есть ли релизы, лицензия совместима? |
| Безопасность | Нет ли известных CVE, безопасны ли дефолты (таймауты, лимиты)? |
| Совместимость | Работает ли с Go 1.25 / React 19 / текущим стеком? |
| Стоимость владения | Размер зависимостей, влияние на CI-время (бюджет ~3000 мин/мес) |
| Альтернативы | Рассмотрены ≥2 варианта, зафиксирован проигравший и почему |

Шаблон записи выбора:

```
Библиотека: <name@version>
Задача: <что решает>
Альтернативы: <A vs B vs C>
Выбор: <name>, потому что <обоснование по критериям>
Риски: <что может пойти не так>, митигация: <как>
TZ: не нарушает (или ADR-XXX если нужно исключение)
```

Запрещённые паттерны (из `code_style_guide.md`, TZ) — ARCH следит, чтобы выбор их не вводил:
`http.DefaultClient` для user-URL (SSRF), `io.ReadAll` без `LimitReader`, `!=` для секретов,
`*ent.Client` в Service/Handler, `panic()` в проде, `seaweedfs:latest` без pin.

### 5.4 ADR (Architecture Decision Record)

ADR фиксирует значимое архитектурное решение: контекст, варианты, решение, последствия. ADR
неизменяем после принятия (новое решение = новый ADR, старый помечается Superseded).

Полный шаблон ADR:

```markdown
# ADR-<NNN>: <краткое название решения>

- Статус: Proposed | Accepted | Superseded by ADR-XXX | Deprecated
- Дата: YYYY-MM-DD
- Автор: arch
- Связанные: US-XX, FR-XX, NFR-XX, TZ-раздел

## Контекст
<Какая проблема/сила требует решения. Ограничения TZ, NFR, текущее состояние кода.>

## Рассмотренные варианты
1. <Вариант A> — плюсы / минусы
2. <Вариант B> — плюсы / минусы
3. <Вариант C> — плюсы / минусы

## Решение
<Что выбрано и почему. Явная привязка к критериям 5.3 и к TZ.>

## Последствия
- Положительные: <...>
- Отрицательные / долг: <...> (регистрируется как TD-XX при необходимости)
- Влияние на NFR: <...>
- Влияние на deployment: <...>

## Проверка соответствия
<Как arch-ver убедится, что решение реализовано: файл:строка, команда, тест.>
```

Пример (в стиле проекта — ADR-AUTH-01 упоминается в TZ):

```markdown
# ADR-AUTH-01: Telegram — только notify bind, не login

- Статус: Accepted
- Дата: 2026-06-21
- Связанные: US-M01, NFR-05, TZ Authentication (mandatory)

## Контекст
Требуется единый метод входа. TZ: Magic Link (email) — единственный метод; SSO/OAuth forbidden.
Telegram обсуждался как второй способ входа.

## Рассмотренные варианты
1. Telegram login — противоречит TZ (единственный метод — Magic Link), forbidden.
2. Telegram только для notify bind/delivery — соответствует TZ.

## Решение
Telegram используется исключительно для привязки уведомлений, не для аутентификации.

## Последствия
- Положительные: соответствие TZ, меньше поверхность атаки на auth.
- Отрицательные: пользователи не могут войти через TG (осознанно).

## Проверка соответствия
Нет endpoint auth через TG; `backend/internal/auth/` не содержит TG-login; notify bind в notification.
```

### 5.6 Ограничения TZ (mandatory / forbidden)

`docs/tz_constraints.md` (зеркало `.cursor/rules/60-tz-constraints.mdc`) — закон. ARCH — его
хранитель. Ключевые mandatory и forbidden, которые ARCH проверяет в каждом решении:

| Категория | MANDATORY | FORBIDDEN |
|-----------|-----------|-----------|
| Auth | Magic Link only; JWT 15 мин; refresh 30 дней Redis; rate 3/10 мин | SSO/LDAP/OAuth; Telegram login |
| Data | UTC в БД; version optimistic lock; UUID v4 PK; soft delete 30д | string PK; hard delete без запроса Admin/GDPR |
| API | ошибки `{"error","request_id"}`; пагинация offset/cursor; rate limits | — |
| Real-time | WebSocket через Fiber; NATS JetStream only | net/http/gorilla для WS; Redis pub/sub |
| Storage | SeaweedFS через aws-sdk-go-v2; presigned URLs; max 25MB | minio-go; seaweedfs:latest |
| Frontend | TanStack Router; Tailwind 4 + Shadcn/ui | замена роутера/UI-фреймворка; `!important`; index как key |
| Infra | Docker Compose (dev), K3s (prod); Caddy; GitHub Actions | nginx; DEV_MODE=true в prod CI |
| Security | webhook signature check; WS RBAC; search user-scope; ValidateOutboundURL | skip подписи; WS без membership; search без scope |

Любое отклонение от mandatory или ввод forbidden — только через ADR с явным согласованием.
Без ADR `arch-ver` ставит FAIL.

## 6. Сквозная трассируемость: business goal → US → FR → API → код → TC → autotest

### 6.1 Зачем нужна цепочка

Трассируемость — это гарантия, что каждая строка кода имеет причину, а каждая цель имеет
доказательство реализации. В Hub цепочка сквозная и двунаправленная:

```
Business Goal (G-XX, vision_and_scope)
   → User Story (US-XX, vision_and_scope)
      → Acceptance Criteria (Gherkin, vision_and_scope)
         → Functional Requirement (FR <PREFIX>-XX, system_specification)
            → NFR link (NFR-XX)
            → API-контракт (wiki/API.md)
               → Код (backend/internal/<module>, frontend/src/...)
                  → Test Case (docs/test_plan.md / TMS)
                     → Autotest (testframework/**, Vitest, Playwright)
                        → Coverage (COVERAGE.md, %)
```

Двунаправленность означает: сверху вниз («что реализует эту цель?») и снизу вверх («зачем
этот код существует?»). Разрыв в любом звене — это либо мёртвый код (нет вышестоящего
требования), либо невыполненное обещание (есть требование, нет реализации/теста).

### 6.2 Кто за какое звено отвечает

| Звено | Владелец | Артефакт |
|-------|----------|----------|
| Goal, US, AC | BA (`ba1`/`ba2`) | `vision_and_scope.md` |
| FR, NFR, API, ERD | SA (`sa1`/`sa2`) | `system_specification.md`, `wiki/API.md` |
| Границы/паттерны/ADR | ARCH | `architecture.md` |
| Код | BE/FE | `backend/`, `frontend/` |
| TC | QA | `test_plan.md` / TMS |
| Autotest, Coverage | QA/BE/FE | `testframework/**`, `COVERAGE.md` |
| Матрица целиком | SA (ведёт), все дополняют | `.planning/COVERAGE.md` |

### 6.3 Матрица трассируемости (полный шаблон)

Единая таблица `COVERAGE.md`, связывающая все звенья:

```
| Goal | US    | AC | FR      | NFR    | API                         | Code                              | TC        | Autotest                          | Cov   | Gap |
|------|-------|----|---------|--------|-----------------------------|-----------------------------------|-----------|-----------------------------------|-------|-----|
| G-02 | US-S16| 3  | TMS-14  | NFR-24 | PATCH /tms/cases/:id        | tms/handler_cases.go, service.go  | TC-TMS-14 | testframework/tms/flaky_test.go   | 82.0% (2026-06-22) | —   |
| G-01 | US-M03| 5  | TASK-01 | NFR-14 | POST /projects/:id/issues   | tracker/handler_issues.go         | TC-TASK-01| testframework/tracker/*_test.go   | 82.4% (2026-06-22) | —   |
```

Статусы (методология COVERAGE.md): Code = ✅ Implemented / ⚠️ Partial / ❌ Missing /
🔧 Fixed post-audit; Tests = ✅ Covered / ⚠️ Partial / ❌ Missing; Gap = открытый finding.

### 6.4 Как аналитики поддерживают COVERAGE-матрицу

- **BA** при добавлении US добавляет строку с Goal+US+AC, остальные колонки — TBD.
- **SA** заполняет FR/NFR/API/ERD-звенья, сверяя счётчики эндпоинтов с кодом (реальный
  дефект: заявлено 293, проверено 285 — сводить нужно по факту).
- **ARCH** не ведёт строки, но проверяет, что связи между модулями в матрице не нарушают
  границы (например, FR модуля A не тянет напрямую Ent модуля B).
- После реализации **BE/FE/QA** заполняют Code/TC/Autotest/Cov.
- **SA** периодически запускает gap-анализ: строки с ❌/⚠️ = backlog для BA/QA.

### 6.5 Gap-анализ по матрице

Gap-анализ — сравнение «обещано» (Goal/US/FR) и «сделано» (Code/Tests). Виды gap:

| Тип gap | Симптом в матрице | Действие |
|---------|-------------------|----------|
| Нереализованное требование | US/FR есть, Code = ❌ | backlog BE/FE |
| Непокрытое тестами | Code = ✅, Tests = ❌ | backlog QA (`gsd-add-tests`) |
| Мёртвый код | Code есть, нет US/FR | вопрос BA: нужна US или удалить |
| Drift чисел | KPI≠spec≠код | пересчёт по коду, синхронизация |
| Недостижимая цель | Goal без US | BA добавляет US или корректирует цель |

Связь с `verification.md`: gap-анализ — вход для `sa-ver` (покрытие требований) и `qa-ver`
(матрица покрытия актуальна). Связь с `test_plan.md`: каждая AC должна иметь TC.

### 6.6 Пример полной цепочки (сквозной проход)

```
G-02  Сквозная traceability задача→тест→баг
  └ US-M05  Как QA, хочу результаты из CI (Allure) и создание бага из failed
      └ AC (Gherkin): Given failed результат ... When «Создать баг» ... Then Issue type=Bug со связью
          └ FR TMS-05  парсер Allure JSON, матчинг по ID/annotation, создание Issue из failed
              └ NFR-13 (ошибки), NFR-24 (version у Issue)
                  └ API: POST /tms/runs/:id/results ; POST /tms/cases/:id/create-bug
                      └ Code: tms/allure_parser.go, tms/handler_runs.go, tracker/service.go
                          └ TC-TMS-05 (happy/alt/error)
                              └ Autotest: testframework/tms/allure_test.go
                                  └ Cov: 82.0% (2026-06-22)
```

Разрыв на любом уровне ловится верификатором соответствующего слоя.

## 7. Работа с неопределённостью

### 7.1 Принцип

Аналитик не выдумывает недостающее и не «замолкает» при неясности — он **явно фиксирует
неопределённость** и разрешает её одним из способов: вопрос к продукту, гипотеза с проверкой,
spike, или GSD-процедура уточнения. Молчаливое допущение — источник самых дорогих ошибок.

### 7.2 Вопросы к продукту (PO)

Когда требование неоднозначно, аналитик формулирует **конкретный закрытый вопрос** с
вариантами, а не «что делать?». Хороший вопрос экономит раунд уточнений.

Шаблон вопроса:

```
Вопрос [US-S16, flaky-подсветка]
Контекст: неясен порог автоподсветки flaky.
Варианты:
  A) 3+ разных исхода на одной ревизии за любое окно
  B) 3+ разных исхода за 30 дней (rolling)
  C) настраиваемый порог на уровне проекта
Рекомендация BA: B (баланс простоты и полезности), по умолчанию 3/30д.
Влияние: A проще в реализации; C дороже (настройка + UI).
```

#### Good / Bad: вопрос к продукту

```
GOOD
"Порог flaky: 3 исхода за 30 дней (rolling) или настраиваемый на проект? Рекомендую rolling 3/30д."
- Закрытый, с вариантами, с рекомендацией и влиянием
```

```
BAD
"Как должны работать flaky-тесты?"
- Открытый, перекладывает весь анализ на PO, не двигает работу
```

### 7.3 Гипотезы

Если ответ PO недоступен, а работу нужно продолжать, аналитик формулирует **гипотезу-допущение**
и помечает артефакт как «на допущении». Гипотеза обязана быть проверяемой и записанной.

Шаблон:

```
ГИПОТЕЗА H-01 [US-S16]
Допущение: порог flaky = 3 исхода за 30 дней (rolling).
Основание: аналог в Allure TestOps; user_needs_analysis JTBD Марии.
Проверка: подтвердить у PO до реализации FR; если опровергнута — изменить TMS-14.
Риск при ошибке: переделка фильтра и счётчика (низкий, изолировано в tms).
Статус: OPEN
```

Гипотезы собираются в раздел «Открытые вопросы/допущения» артефакта и в `STATE.md`.
`ba-ver`/`sa-ver` проверяют, что ни одна OPEN-гипотеза не «протекла» в `verified: true` без
пометки риска.

### 7.4 Spike

Spike — короткое исследование для снятия технической/продуктовой неопределённости, результат
которого выбрасывается (код-эксперимент) или превращается в знание. Инициирует обычно SA/ARCH.

Когда spike:
- неясна реализуемость (например, производительность Meilisearch на 1M записей);
- неясен выбор между библиотеками до ADR;
- неясна форма API внешней интеграции.

GSD-инструменты: `gsd-spike` (техническая проверка), `gsd-sketch` (UI-эксперимент),
`gsd-spike-wrap-up` / `gsd-sketch-wrap-up` (упаковка находок в знание).

Шаблон результата spike:

```
SPIKE S-01: производительность фильтра flaky на 100k кейсов
Вопрос: укладывается ли GET /tms/cases?flaky в NFR-01 (p95<500ms)?
Метод: индекс (project_id, flaky), замер на сид-данных 100k.
Результат: p95 ~120ms с индексом; без индекса ~1.4s.
Вывод: индекс обязателен → зафиксировать в ERD (SA) и в FR TMS-14.
Артефакт выброшен: да (эксперимент). Знание перенесено в system_specification.
```

### 7.5 GSD-процедуры уточнения

| Ситуация | GSD Skill | Кто |
|----------|-----------|-----|
| Нужно прояснить WHAT фазы, falsifiable-требования | `gsd-spec-phase` | BA |
| Собрать контекст фазы адаптивными вопросами | `gsd-discuss-phase` | BA |
| Исследовать реализацию перед планированием | `gsd-research-phase` | ARCH/SA |
| Проверить реализуемость экспериментом | `gsd-spike` / `gsd-sketch` | ARCH/FE |
| Аудит покрытия требований | Hub `/coverage-audit` | SA |
| Не знаю, какая команда | `gsd-do` | любой |

`gsd-spec-phase` даёт SPEC.md с falsifiable-требованиями до обсуждения реализации;
`gsd-discuss-phase` — контекст через вопросы (режимы `--all`, `--auto`, `--chain`, `--power`).
Аналитик выбирает spec-phase, когда неясно ЧТО, и discuss-phase, когда ЧТО ясно, но много
серых зон в КАК.

### 7.6 Правило «не оставлять тихих допущений»

Каждое допущение → одна из четырёх судеб: (1) подтверждено PO → становится требованием;
(2) опровергнуто → требование меняется; (3) осталось OPEN → артефакт помечен «на допущении»
с риском, `verified` не выставляется как окончательный; (4) снято spike → знание в docs.
Тихое допущение (никак не помеченное) — антипаттерн, ловится верификатором.

## 8. Definition of Ready и Definition of Done

### 8.1 Definition of Ready (требование готово к разработке)

Требование (US + AC + FR + контракт) считается **Ready**, когда BE/FE может взять его в работу
без дополнительных вопросов. Чек-лист DoR:

```
[ ] US в формате «Как <роль>, хочу <действие>, чтобы <ценность>», атомарна (одно действие)
[ ] Привязка к бизнес-цели (G-XX) и приоритет MoSCoW заданы
[ ] Есть AC: основной + альтернативный + исключительный (Gherkin или проверяемый список)
[ ] Персона/JTBD определены
[ ] FR декомпозирован (Source = US), тестируемое поведение
[ ] Связанные NFR указаны (rate limit, пагинация, ошибки, version, UUID)
[ ] API-контракт описан: метод, путь, body, ответы (вкл. 4xx/409/422), формат ошибки
[ ] ERD-изменения описаны с инвариантами (UUID v4, version, UTC, soft delete)
[ ] Нет нарушений TZ (mandatory соблюдены, forbidden отсутствуют; иначе есть ADR)
[ ] Все OPEN-гипотезы либо закрыты, либо явно помечены с оценкой риска
[ ] Зависимости от других US/FR перечислены
[ ] Описание простым языком (2–5 предложений) приложено
```

Если хоть один пункт не выполнен — требование **не Ready**, разработку начинать нельзя.

### 8.2 Definition of Done для аналитических артефактов

Аналитический артефакт (обновление vision/spec/architecture) считается **Done**, когда:

```
[ ] Артефакт обновлён по шаблону раздела (BA §3 / SA §4 / ARCH §5)
[ ] Трассировка вверх и вниз проставлена (US→G, FR→US, API→FR)
[ ] Нет противоречий с другими docs/ (числа, приоритеты, контракты сведены)
[ ] Соответствие TZ проверено
[ ] Docs sync выполнен: .planning/STATE.md + связанные docs (правило 55-docs-sync)
[ ] COVERAGE.md обновлена (для SA — обязательно; для BA — новые строки US)
[ ] Лог изменений в соответствующем skill-файле дополнен
[ ] Описание простым языком приложено
[ ] Артефакт передан верификатору, получен verified: true с датой/временем
```

Различие: DoR — про **входное** требование для разработки; DoD — про **выходной** артефакт
аналитика. Оба обязательны; verified: true ставит только верификатор (см. `verification.md`).

### 8.3 Матрица DoR/DoD по ролям

| Артефакт | Владелец | DoR-чек кто применяет | DoD-верификатор |
|----------|----------|----------------------|-----------------|
| US + AC | BA | SA (перед декомпозицией) | ba-ver |
| FR + API + ERD | SA | BE/FE (перед кодом) | sa-ver |
| ADR + C4 | ARCH | BE/FE + SA | arch-ver |

## 9. Антипаттерны аналитики

Таблица типичных дефектов аналитических артефактов, как их распознать и чем заменить.

| Антипаттерн | Симптом | Почему плохо | Замена |
|-------------|---------|--------------|--------|
| Расплывчатая US | «хочу удобную систему» | нельзя реализовать/проверить | конкретное действие + ценность + AC |
| US-эпик под видом US | несколько «и» в действии | не атомарна, не оценима | разбить на атомарные US |
| Отсутствие AC | US без критериев готовности | «готово» субъективно | ≥3 AC (happy/alt/error), Gether |
| Нетестируемое NFR | «быстро», «надёжно» | нельзя измерить | числовой порог + способ проверки |
| Цель без метрики | «улучшить онбординг» | не SMART | измеримость + срок |
| KPI-желаемое вместо факта | «Lighthouse ≥90 ✅» при отсутствии gate | вводит в заблуждение | статус = реальный факт + источник |
| Drift чисел | KPI≠spec≠код (293 vs 285) | недоверие к docs | сводить по проверяемому источнику |
| Дубль MoSCoW | фича и Should, и Could | противоречие приоритета | один приоритет на фичу |
| FR без Source | требование «висит» | мёртвый код/непонятна цель | привязка Source = US |
| ERD без инвариантов | нет version/UUID/soft delete | гонки, нарушение TZ | добавить обязательные поля |
| API без формата ошибки | `{"message":...}` | нарушает NFR-13 | `{"error","request_id"}` |
| Листинг без пагинации | отдаёт весь список | DoS, нарушает NFR-14/15 | offset/limit или cursor |
| Тихое допущение | нигде не помечено | скрытый риск | гипотеза H-XX с проверкой |
| Открытый вопрос вместо закрытого | «как сделать?» | не двигает работу | варианты + рекомендация |
| Нарушение TZ без ADR | ввёл forbidden/убрал mandatory | ломает контракт проекта | ADR + согласование |
| Stale C4/числа | docs говорят 18 модулей, код 21 | недоверие к архитектуре | сверять с кодом (grep/go.mod) |
| Правка чужого артефакта | SA меняет MoSCoW | нарушение владения | через владельца/handoff |
| Конфликт номеров | ba1 и ba2 оба US-M11 | коллизия, merge-конфликт | диапазоны нумерации по split |
| Синонимы в глоссарии | «канал» vs «беседа» | путаница терминов | единый глоссарий, сверка |
| verified сам себе | аналитик ставит verified: true | нет независимой проверки | только *-ver ставит verified |

#### Слой 3 — ARCH (`architecture.md`, ADR)

Вопрос границ: пересчёт flaky_count при submit — inline в TMSService или через event?
ARCH решает ADR:

```markdown
# ADR-042: Пересчёт flaky_count синхронно в транзакции submit

- Статус: Accepted
- Дата: 2026-07-02
- Связанные: US-S16, FR TMS-14, NFR-31, NFR-01

## Контекст
flaky_count нужно обновлять при каждом submit результата. Варианты: (1) синхронно в той же
транзакции; (2) асинхронно через NATS-consumer.

## Рассмотренные варианты
1. Синхронно в Tx — простота, консистентность; минимум задержки при малом числе результатов.
2. Асинхронно через event — развязка, но eventual consistency и сложнее отладка.

## Решение
Синхронный пересчёт в транзакции submit (вариант 1). Дашборд-агрегат (TMS-15) — асинхронно
через outbox-event hub.tms.case.flaky_changed, т.к. это read-model.

## Последствия
- Плюс: карточка кейса всегда консистентна; фильтр flaky точен сразу.
- Минус: submit чуть тяжелее (один UPDATE + пересчёт), в рамках NFR-01.
- Границы: tms владеет flaky_count; dashboard только читает через event (не тянет Ent tms).

## Проверка соответствия
tms/service.go SubmitResult в одной Tx обновляет TestResult и TestCase.flaky_count;
dashboard подписан на hub.tms.case.flaky_changed, не импортирует tms/ent.
```

C4 Component дополнение:

```
Модуль: tms (дополнение)
  service.SubmitResult → repository.Tx(TestResult+TestCase.flaky_count)
  publishes hub.tms.case.flaky_changed (outbox)
Модуль: dashboard
  subscribes hub.tms.case.flaky_changed → обновляет read-model flaky-rate (граница соблюдена)
```

### 10.7 Расширенный каталог good/bad

#### FR vs NFR (частая путаница)

```
GOOD FR (поведение): "TMS-14: пометка кейса flaky и фильтр flaky"
GOOD NFR (качество): "NFR-31: пересчёт flaky_count идемпотентен, в транзакции"
BAD: "NFR: сделать flaky-кейсы" — это FR, не NFR (поведение, не качество)
BAD: "FR: система должна быть быстрой" — это NFR, не FR (качество, не поведение)
```

#### US vs эпик

```
GOOD US: "Как QA, хочу помечать кейс flaky, чтобы фильтровать нестабильные"
BAD (эпик): "Как QA, хочу полноценную систему управления качеством тестов с аналитикой,
             дашбордами, автоподсветкой, экспортом и интеграцией с CI"
Разбить эпик на: пометка flaky (US-S16) + дашборд-метрика (US-S17) + экспорт (US-C) + CI (US-S)
```

#### AC: полнота видов

```
GOOD (три вида):
  happy:  When помечаю кейс flaky Then флаг сохранён, version инкрементирован
  alt:    When фильтрую по flaky Then вижу только flaky-кейсы с пагинацией
  error:  When шлю PATCH с устаревшим version Then 409 {"error","request_id"}
BAD (только happy): "флаг flaky работает" — нет границы и ошибки
```

#### ERD: инварианты

```
GOOD: TestCase{ id UUID, version int, deleted_at nullable, created_at/updated_at UTC }
BAD:  TestCase{ id "TC-42" string, нет version, hard delete } — три нарушения TZ сразу
```

#### API: коды ответов

```
GOOD: перечислены 200/201, 400, 401, 403, 404, 409 (version), 422 (бизнес), 429 (rate)
BAD:  только 200 и 500 — не описано поведение при конфликте/валидации/лимите
```

### 10.12 Связь аналитики с тестированием и верификацией

Аналитические артефакты — прямой вход для QA и верификаторов:

- Каждая AC (§3.7) должна породить как минимум один тест-кейс (`test_plan.md` / TMS) и, при
  автоматизации, один autotest (`testframework/**`). Это проверяет `qa-ver` (см.
  `verification.md`, чек-лист qa-manual-ver и qa-auto-ver).
- Три вида AC (happy/alt/error) напрямую соответствуют техникам тест-дизайна: классы
  эквивалентности, граничные значения, негативные сценарии.
- FR/NFR — критерий приёмки для `be-ver`/`fe-ver`: реализация сверяется с контрактом, а не
  «работает ли вообще».
- Матрица COVERAGE — общий язык SA и QA: строки без Tests = задача QA; строки без Code =
  задача BE/FE.
- ADR и TZ — критерий для `arch-ver` и `code-reviewer`: любое нарушение mandatory/forbidden
  без ADR блокирует.

Полное описание процесса проверки — в парном документе `.cursor/playbooks/verification.md`.

### 10.13b Фреймворки приоритизации backlog (справочник BA)

MoSCoW — основной механизм, но для сортировки внутри Should/Could полезны вспомогательные
метрики. Они не заменяют MoSCoW, а уточняют порядок.

| Фреймворк | Формула/суть | Когда |
|-----------|--------------|-------|
| Value vs Effort | быстрые победы = высокая ценность + низкие усилия | сортировка внутри приоритета |
| RICE | (Reach × Impact × Confidence) / Effort | сравнение конкурирующих US |
| Kano | must-be / performance / delighter | классификация ожиданий |
| Cost of Delay | ценность × срочность | что делать раньше при равном приоритете |

Шаблон оценки кандидата backlog:

```
US-кандидат: <ID>
MoSCoW: Should
Reach: <сколько персон/сценариев затрагивает>
Impact: <вклад в цель G-XX, шкала 0.25..3>
Confidence: <уверенность оценки, %>
Effort: <оценка SA/ARCH, story points>
Вывод: RICE=<число> → позиция в backlog
```

Правило: приоритизация — предложение BA; фиксация в ROADMAP — оркестратор/SA. BA не правит
ROADMAP напрямую (зона ответственности).

НИКОГДА: расплывчатые US · нетестируемые NFR · тихие допущения · нарушение TZ без ADR ·
