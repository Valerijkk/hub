## 1. Назначение и принципы playbook аналитики

### 1.1 Зачем этот документ

Аналитическое крыло Hub производит не код, а **контракты**: описания того, что должно быть
построено, зачем, для кого и с какими ограничениями. Ошибка аналитика дешевле ошибки
разработчика ровно до момента, пока она не попала в код: расплывчатая User Story рождает
неверную реализацию, нетестируемое NFR рождает «зелёные» тесты без смысла, пропущенная связь
в ERD рождает миграцию с потерей данных. Поэтому цена точности здесь максимальна.

Playbook описывает **единый способ работы** для пяти аналитических агентов и трёх
верификаторов. Он не заменяет skill-файлы (`BA_skill.md`, `SA_skill.md`, `ARCH_skill.md`),
а разворачивает их в детальные процедуры, шаблоны и примеры «хорошо/плохо». Skill-файл
отвечает на вопрос «что я делаю и куда пишу лог»; playbook отвечает на вопрос «как именно
и по какому стандарту».

### 1.2 Базовые принципы

| Принцип | Что означает на практике |
|---------|--------------------------|
| Единая база знаний | Перед задачей загружаются все файлы `docs/`. Дублировать их содержимое в артефактах запрещено — только ссылки. |
| Один артефакт — один владелец | `vision_and_scope.md` — BA, `system_specification.md` — SA, `architecture.md` — ARCH. Чужой файл правит только владелец. |
| Всё измеримо и проверяемо | Цель без метрики, US без acceptance criteria, NFR без числового порога — брак. |
| Трассируемость сквозная | Каждый нижний артефакт ссылается на верхний: US → G-XX, FR → US, API → FR, TC → AC. |
| Не ломать TZ | `docs/tz_constraints.md` — закон. Mandatory нельзя убирать, forbidden нельзя вводить без ADR. |
| Атомарность | Одна итерация — один связный кусок (эпик/модуль/фича), ≤200–300 строк изменений в docs. |
| Docs sync немедленный | Изменил артефакт → в той же сессии обновил `.planning/STATE.md` и связанные docs (правило `.cursor/rules/55-docs-sync.mdc`). |
| Верификация обязательна | Артефакт получает `verified: true` только после независимой проверки соответствующим `*-ver`. |
| Понятное описание | К каждому артефакту — 2–5 предложений простым языком для верификатора и разработчика. |

### 1.3 Как аналитик передаёт работу дальше

Поток создания ценности в Hub линеен и цикличен одновременно:

```
Идея / запрос PO
   → BA:  бизнес-цель (SMART) + персона + JTBD + User Story + AC + MoSCoW  → vision_and_scope.md
   → SA:  FR/NFR + ERD + API-контракт + DFD + матрица трассируемости       → system_specification.md, wiki/API.md
   → ARCH: C4 + выбор библиотек + ADR + deployment + атрибуты качества      → architecture.md, stack_and_tools.md
   → BE/FE: реализация + тесты
   → QA:  тест-кейсы + регрессия
   → *-ver: верификация каждого шага
```

Каждая стрелка — это **handoff** с описанием на простом языке и обязательной верификацией.
Аналитик не начинает следующий слой, пока предыдущий не получил `verified: true` или пока
явно не согласована параллельная работа с фиксацией допущений (см. раздел 7).

### 1.4 Что playbook НЕ разрешает

- Аналитик не пишет production-код (это BE/FE) и не редактирует чужой доменный doc.
- Аналитик не ставит сам себе `verified: true` — это делает верификатор.
- BA не принимает технических решений (стек, схема БД) — это SA/ARCH.
- SA не меняет бизнес-приоритеты (MoSCoW) — это BA.
- ARCH не переопределяет бизнес-цели — только реализует их технически.
- Никто из аналитиков не удаляет mandatory-ограничения из TZ без ADR и согласования.

## 2. Кто и когда: распределение ролей ba1/ba2/sa1/sa2/arch

### 2.1 Обзор ролей

| Агент | Роль | Основной артефакт | Маршрутизация | Режим |
|-------|------|-------------------|---------------|-------|
| `ba1` | Business Analyst (поток A) | `docs/vision_and_scope.md` (разделы A) | Выбирает оркестратор | readonly-анализ |
| `ba2` | Business Analyst (поток B) | `docs/vision_and_scope.md` (разделы B) | Выбирает оркестратор | readonly-анализ |
| `sa1` | System Analyst (модули A) | `docs/system_specification.md` (модули A) | Выбирает оркестратор | readonly-анализ |
| `sa2` | System Analyst (модули B) | `docs/system_specification.md` (модули B) | Выбирает оркестратор | readonly-анализ |
| `arch` | Architect | `docs/architecture.md`, `docs/stack_and_tools.md` | Выбирает оркестратор | readonly-анализ |
| `ba-ver` | Верификатор BA | проверка vision_and_scope | Выбирает оркестратор | readonly |
| `sa-ver` | Верификатор SA | проверка system_specification | Выбирает оркестратор | readonly |
| `arch-ver` | Верификатор ARCH | проверка architecture | Выбирает оркестратор | readonly |

В каждом dispatch явно передавай model и effort по [`model-routing.md`](model-routing.md).

`ba1`/`ba2` и `sa1`/`sa2` — это **две параллельные инстанции одной роли**, работающие над
разными доменами/эпиками одновременно, чтобы ускорить анализ крупного milestone. `arch`
существует в единственном числе, потому что архитектурная целостность требует единого
взгляда; вместо распараллеливания `arch` работает последовательными атомарными итерациями
по контейнерам/компонентам.

### 2.2 Когда подключается каждая роль

| Триггер | Кто первый | Далее |
|---------|-----------|-------|
| Новая фича / эпик от PO | `ba1` или `ba2` (по домену) | `sa` → `arch` (если меняется структура) |
| Новая сущность / изменение схемы БД | `sa` (модуль) | `arch` (если влияет на модульность) |
| Новый API endpoint / контракт | `sa` | `arch` (если новая интеграция) |
| Смена стека / библиотеки | `arch` | `sa` (обновить NFR) |
| Новое ADR-решение | `arch` | все аналитики читают |
| Уточнение бизнес-приоритета | `ba` | `sa` пересматривает scope |
| Новый milestone | `ba1`+`ba2` параллельно | `sa1`+`sa2` параллельно → `arch` |

Для мелкого фикса без изменения поведения аналитики не нужны — идёт прямой путь `be`/`fe` →
`be-ver`/`fe-ver` → применимый fixed root Compose service (см. REGULATION §5,
hotfix path).

### 2.3 Как ba1 и ba2 делят работу без конфликтов

Оба BA пишут в **один файл** `docs/vision_and_scope.md`. Чтобы избежать конфликтов при
параллельной работе, действует протокол разделения:

1. **Разделение по разделам/доменам.** Перед стартом milestone оркестратор (или один из BA)
   фиксирует карту разделения в `.planning/STATE.md`:

```
## Analysis split — milestone v5 (2026-07-02)
ba1: домены Tracker, TMS, Calls        → US-M/US-S для этих модулей, персоны Алексей/Мария/Сергей
ba2: домены Messenger, Intranet, CRM   → US-M/US-S для этих модулей, персоны Игорь/Виктор/Елена
Общие разделы (глоссарий, KPI, MoSCoW-сводка): владелец ba1, ba2 предлагает через комментарий-заметку
```

2. **Договорённость о нумерации.** Идентификаторы US не должны пересекаться. Принята схема:

| Поток | Диапазон US | Диапазон целей | Диапазон персон |
|-------|-------------|----------------|-----------------|
| `ba1` | US-M01…M20, US-S01…S15 | G-01…G-06 (общие, редактирует только по согласованию) | P-01…P-04 |
| `ba2` | US-M21…M40, US-S16…S30 | предлагает G-07+ | P-05…P-08 |

   Если поток исчерпал диапазон — расширяет его вверх, не залезая в чужой. Конфликт номеров —
   это дефект процесса, а не «поправим потом».

3. **Единый глоссарий.** Термины (например, «эпик», «инцидент», «канал», «прогон») ведутся
   в одном месте — в приложении к `vision_and_scope.md` или в `docs/README.md`. Перед вводом
   нового термина BA проверяет, нет ли синонима. `ba2` не вводит «беседа», если `ba1` уже
   ввёл «канал».

4. **Непересекающиеся секции файла.** Физически BA правят разные заголовки markdown. Если оба
   должны тронуть общий раздел (например, таблицу KPI), это делает владелец раздела, второй
   передаёт правку текстом в handoff-заметке. Так исключается редактирование одних и тех же
   строк.

5. **Синхронизация в конце.** После завершения обоих потоков один из BA (владелец общих
   разделов) сводит MoSCoW-приоритизацию целиком, проверяя отсутствие дублей (например,
   Web Push не должен быть одновременно Should и Could — реальный дефект из лога `ba-ver`).

#### Good / Bad: разделение работы BA

```
GOOD (ba1)
- Взял домены Tracker/TMS согласно split в STATE.md
- US-M03 (задачи), US-M05 (тест-кейсы), US-M11 (Kanban) — все в диапазоне M01–M20
- Новый термин «swimlane» сверил с глоссарием — отсутствовал, добавил с определением
- Таблицу KPI не трогал (владелец ba1 по split — сам, но изменение согласовал заметкой)
```

```
BAD (ba2)
- Начал писать US про Kanban с ID US-M11 (уже занят ba1) → конфликт номеров
- Ввёл термин «дорожка» вместо «swimlane» → синоним, расхождение глоссария
- Отредактировал таблицу KPI одновременно с ba1 → merge-конфликт строк
- Поставил US-M11 приоритет Could, хотя ba1 держит Must → противоречие MoSCoW
```

### 2.4 Как sa1 и sa2 делят работу без конфликтов

`sa1`/`sa2` пишут в `docs/system_specification.md` и `docs/wiki/API.md`. Разделение —
**по модулям backend** (`backend/internal/<module>`), что естественно, поскольку FR/API
группируются по модулям.

1. **Разделение по модулям.** Пример карты:

```
## SA split — milestone v5 (2026-07-02)
sa1: tracker, sprint, tms, calls        → FR-TASK*, FR-SCRM*, FR-TMS*, FR-CALL*, API этих модулей
sa2: messenger, notification, search    → FR-MSG*, FR-NOTF*, FR-SRCH*, API этих модулей
arch: cross-cutting NFR + module boundaries (после sa1/sa2)
```

2. **Нумерация FR/NFR.** FR нумеруются с префиксом модуля: `TASK-01`, `MSG-04` — конфликтов
   между потоками нет по построению. NFR — сквозная общая нумерация `NFR-01…NFR-NN`; новые NFR
   резервируются диапазонами:

| Поток | FR-префиксы | Диапазон новых NFR |
|-------|-------------|--------------------|
| `sa1` | TASK, SCRM, TMS, CALL | NFR-31…NFR-40 |
| `sa2` | MSG, NOTF, SRCH | NFR-41…NFR-50 |
| `arch` | cross-cutting | NFR-51+ |

3. **ERD-целостность.** Сущности разных модулей связаны (например, `Issue` ↔ `TestCase` ↔
   `Message`). Общая ER-диаграмма — единая; каждый SA правит свои сущности, а **связи между
   доменами** согласуются: если `sa1` добавляет FK `TestCase.issue_id`, он фиксирует это в
   handoff для `sa2`, владеющего смежным доменом, и для `arch`.

4. **API-контракты.** Каждый SA описывает эндпоинты своих модулей в `wiki/API.md` в своей
   секции. Общие соглашения (формат ошибки `{"error","request_id"}`, пагинация, коды ответов)
   — единый раздел, владелец `sa1`, изменяется по согласованию.

5. **Синхронизация счётчиков.** Итоговый inventory эндпоинтов (например, «Total REST 286»)
   сводит один SA, суммируя per-module counts обоих потоков. Реальный дефект из лога `sa-ver`:
   SA заявил 293, независимый пересчёт дал 285 — расхождение из-за несведённых per-module
   счётчиков. Правило: числа в сводке = сумма проверяемых слагаемых, а не «на глаз».

#### Good / Bad: разделение работы SA

```
GOOD (sa1)
- FR-TASK-14 (WIP-лимиты) — префикс модуля, конфликтов нет
- Добавил FK TestCase.issue_id, зафиксировал в handoff для sa2 и arch
- Новый NFR-31 (лимит вложенности тредов) — в своём диапазоне 31–40
- Пересчитал tracker routes через RegisterRoutes: 48, записал в inventory
```

```
BAD (sa2)
- Ввёл FR-01 без префикса модуля → неясно, чей и коллизия с чужим FR-01
- Изменил формат ошибки в общем разделе без согласования с владельцем sa1
- Заявил «messenger 44 routes» без пересчёта по коду → drift с реальностью
- Взял NFR-33 (чужой диапазон) → пересечение с sa1
```

### 2.5 Роль arch относительно параллельных SA

`arch` включается **после** того, как `sa1`/`sa2` описали FR/API своих модулей, и решает
cross-cutting задачи: границы модулей, зависимости, общие паттерны, deployment, атрибуты
качества. `arch` — арбитр при спорах о том, куда положить общую сущность или как разрешить
циклическую зависимость между доменами двух SA. Если `sa1` и `sa2` расходятся в том, чей
модуль владеет сущностью `Notification`, решение принимает `arch` и фиксирует ADR.

## 6. Сквозная трассируемость: business goal → US → FR → API → код → TC → autotest

### 6.1 Зачем нужна цепочка

Трассируемость — это гарантия, что каждая строка кода имеет причину, а каждая цель имеет
доказательство реализации. В Hub цепочка сквозная и двунаправленная:

```
Business Goal (G-XX, vision_and_scope)
   → User Story (US-XX, vision_and_scope)
      → Acceptance Criteria (Gherkin, vision_and_scope)
         → Functional Requirement (FR <PREFIX>-XX, system_specification)
            → NFR link (NFR-XX)
            → API-контракт (wiki/API.md)
               → Код (backend/internal/<module>, frontend/src/...)
                  → Test Case (docs/test_plan.md / TMS)
                     → Autotest (testframework/**, Vitest, Playwright)
                        → Coverage (COVERAGE.md, %)
```

Двунаправленность означает: сверху вниз («что реализует эту цель?») и снизу вверх («зачем
этот код существует?»). Разрыв в любом звене — это либо мёртвый код (нет вышестоящего
требования), либо невыполненное обещание (есть требование, нет реализации/теста).

### 6.2 Кто за какое звено отвечает

| Звено | Владелец | Артефакт |
|-------|----------|----------|
| Goal, US, AC | BA (`ba1`/`ba2`) | `vision_and_scope.md` |
| FR, NFR, API, ERD | SA (`sa1`/`sa2`) | `system_specification.md`, `wiki/API.md` |
| Границы/паттерны/ADR | ARCH | `architecture.md` |
| Код | BE/FE | `backend/`, `frontend/` |
| TC | QA | `test_plan.md` / TMS |
| Autotest, Coverage | QA/BE/FE | `testframework/**`, `COVERAGE.md` |
| Матрица целиком | SA (ведёт), все дополняют | `.planning/COVERAGE.md` |

### 6.3 Матрица трассируемости (полный шаблон)

Единая таблица `COVERAGE.md`, связывающая все звенья:

```
| Goal | US    | AC | FR      | NFR    | API                         | Code                              | TC        | Autotest                          | Cov   | Gap |
|------|-------|----|---------|--------|-----------------------------|-----------------------------------|-----------|-----------------------------------|-------|-----|
| G-02 | US-S16| 3  | TMS-14  | NFR-24 | PATCH /tms/cases/:id        | tms/handler_cases.go, service.go  | TC-TMS-14 | testframework/tms/flaky_test.go   | 82.0% (2026-06-22) | —   |
| G-01 | US-M03| 5  | TASK-01 | NFR-14 | POST /projects/:id/issues   | tracker/handler_issues.go         | TC-TASK-01| testframework/tracker/*_test.go   | 82.4% (2026-06-22) | —   |
```

Статусы (методология COVERAGE.md): Code = ✅ Implemented / ⚠️ Partial / ❌ Missing /
🔧 Fixed post-audit; Tests = ✅ Covered / ⚠️ Partial / ❌ Missing; Gap = открытый finding.

### 6.4 Как аналитики поддерживают COVERAGE-матрицу

- **BA** при добавлении US добавляет строку с Goal+US+AC, остальные колонки — TBD.
- **SA** заполняет FR/NFR/API/ERD-звенья, сверяя счётчики эндпоинтов с кодом (реальный
  дефект: заявлено 293, проверено 285 — сводить нужно по факту).
- **ARCH** не ведёт строки, но проверяет, что связи между модулями в матрице не нарушают
  границы (например, FR модуля A не тянет напрямую Ent модуля B).
- После реализации **BE/FE/QA** заполняют Code/TC/Autotest/Cov.
- **SA** периодически запускает gap-анализ: строки с ❌/⚠️ = backlog для BA/QA.

### 6.5 Gap-анализ по матрице

Gap-анализ — сравнение «обещано» (Goal/US/FR) и «сделано» (Code/Tests). Виды gap:

| Тип gap | Симптом в матрице | Действие |
|---------|-------------------|----------|
| Нереализованное требование | US/FR есть, Code = ❌ | backlog BE/FE |
| Непокрытое тестами | Code = ✅, Tests = ❌ | backlog QA (`gsd-add-tests`) |
| Мёртвый код | Code есть, нет US/FR | вопрос BA: нужна US или удалить |
| Drift чисел | KPI≠spec≠код | пересчёт по коду, синхронизация |
| Недостижимая цель | Goal без US | BA добавляет US или корректирует цель |

Связь с `verification.md`: gap-анализ — вход для `sa-ver` (покрытие требований) и `qa-ver`
(матрица покрытия актуальна). Связь с `test_plan.md`: каждая AC должна иметь TC.

### 6.6 Пример полной цепочки (сквозной проход)

```
G-02  Сквозная traceability задача→тест→баг
  └ US-M05  Как QA, хочу результаты из CI (Allure) и создание бага из failed
      └ AC (Gherkin): Given failed результат ... When «Создать баг» ... Then Issue type=Bug со связью
          └ FR TMS-05  парсер Allure JSON, матчинг по ID/annotation, создание Issue из failed
              └ NFR-13 (ошибки), NFR-24 (version у Issue)
                  └ API: POST /tms/runs/:id/results ; POST /tms/cases/:id/create-bug
                      └ Code: tms/allure_parser.go, tms/handler_runs.go, tracker/service.go
                          └ TC-TMS-05 (happy/alt/error)
                              └ Autotest: testframework/tms/allure_test.go
                                  └ Cov: 82.0% (2026-06-22)
```

Разрыв на любом уровне ловится верификатором соответствующего слоя.

## 7. Работа с неопределённостью

### 7.1 Принцип

Аналитик не выдумывает недостающее и не «замолкает» при неясности — он **явно фиксирует
неопределённость** и разрешает её одним из способов: вопрос к продукту, гипотеза с проверкой,
spike, или GSD-процедура уточнения. Молчаливое допущение — источник самых дорогих ошибок.

### 7.2 Вопросы к продукту (PO)

Когда требование неоднозначно, аналитик формулирует **конкретный закрытый вопрос** с
вариантами, а не «что делать?». Хороший вопрос экономит раунд уточнений.

Шаблон вопроса:

```
Вопрос [US-S16, flaky-подсветка]
Контекст: неясен порог автоподсветки flaky.
Варианты:
  A) 3+ разных исхода на одной ревизии за любое окно
  B) 3+ разных исхода за 30 дней (rolling)
  C) настраиваемый порог на уровне проекта
Рекомендация BA: B (баланс простоты и полезности), по умолчанию 3/30д.
Влияние: A проще в реализации; C дороже (настройка + UI).
```

#### Good / Bad: вопрос к продукту

```
GOOD
"Порог flaky: 3 исхода за 30 дней (rolling) или настраиваемый на проект? Рекомендую rolling 3/30д."
- Закрытый, с вариантами, с рекомендацией и влиянием
```

```
BAD
"Как должны работать flaky-тесты?"
- Открытый, перекладывает весь анализ на PO, не двигает работу
```

### 7.3 Гипотезы

Если ответ PO недоступен, а работу нужно продолжать, аналитик формулирует **гипотезу-допущение**
и помечает артефакт как «на допущении». Гипотеза обязана быть проверяемой и записанной.

Шаблон:

```
ГИПОТЕЗА H-01 [US-S16]
Допущение: порог flaky = 3 исхода за 30 дней (rolling).
Основание: аналог в Allure TestOps; user_needs_analysis JTBD Марии.
Проверка: подтвердить у PO до реализации FR; если опровергнута — изменить TMS-14.
Риск при ошибке: переделка фильтра и счётчика (низкий, изолировано в tms).
Статус: OPEN
```

Гипотезы собираются в раздел «Открытые вопросы/допущения» артефакта и в `STATE.md`.
`ba-ver`/`sa-ver` проверяют, что ни одна OPEN-гипотеза не «протекла» в `verified: true` без
пометки риска.

### 7.4 Spike

Spike — короткое исследование для снятия технической/продуктовой неопределённости, результат
которого выбрасывается (код-эксперимент) или превращается в знание. Инициирует обычно SA/ARCH.

Когда spike:
- неясна реализуемость (например, производительность Meilisearch на 1M записей);
- неясен выбор между библиотеками до ADR;
- неясна форма API внешней интеграции.

GSD-инструменты: `gsd-spike` (техническая проверка), `gsd-sketch` (UI-эксперимент),
`gsd-spike` / `gsd-sketch`, затем `gsd-capture` (упаковка выбранных находок в persistent artifact).

Шаблон результата spike:

```
SPIKE S-01: производительность фильтра flaky на 100k кейсов
Вопрос: укладывается ли GET /tms/cases?flaky в NFR-01 (p95<500ms)?
Метод: индекс (project_id, flaky), замер на сид-данных 100k.
Результат: p95 ~120ms с индексом; без индекса ~1.4s.
Вывод: индекс обязателен → зафиксировать в ERD (SA) и в FR TMS-14.
Артефакт выброшен: да (эксперимент). Знание перенесено в system_specification.
```

### 7.5 GSD-процедуры уточнения

| Ситуация | GSD Skill | Кто |
|----------|-----------|-----|
| Нужно прояснить WHAT фазы, falsifiable-требования | `gsd-spec-phase` | BA |
| Собрать контекст фазы адаптивными вопросами | `gsd-discuss-phase` | BA |
| Исследовать реализацию перед планированием | `gsd-plan-phase` (research stage) или `gsd-map-codebase` | ARCH/SA |
| Проверить реализуемость экспериментом | `gsd-spike` / `gsd-sketch` | ARCH/FE |
| Аудит покрытия требований | Hub `/coverage-audit` | SA |
| Не знаю, какая команда | `gsd-progress` | любой |

`gsd-spec-phase` даёт SPEC.md с falsifiable-требованиями до обсуждения реализации;
`gsd-discuss-phase` — контекст через вопросы (режимы `--all`, `--auto`, `--chain`, `--power`).
Аналитик выбирает spec-phase, когда неясно ЧТО, и discuss-phase, когда ЧТО ясно, но много
серых зон в КАК.

### 7.6 Правило «не оставлять тихих допущений»

Каждое допущение → одна из четырёх судеб: (1) подтверждено PO → становится требованием;
(2) опровергнуто → требование меняется; (3) осталось OPEN → артефакт помечен «на допущении»
с риском, `verified` не выставляется как окончательный; (4) снято spike → знание в docs.
Тихое допущение (никак не помеченное) — антипаттерн, ловится верификатором.

## 8. Definition of Ready и Definition of Done

### 8.1 Definition of Ready (требование готово к разработке)

Требование (US + AC + FR + контракт) считается **Ready**, когда BE/FE может взять его в работу
без дополнительных вопросов. Чек-лист DoR:

```
[ ] US в формате «Как <роль>, хочу <действие>, чтобы <ценность>», атомарна (одно действие)
[ ] Привязка к бизнес-цели (G-XX) и приоритет MoSCoW заданы
[ ] Есть AC: основной + альтернативный + исключительный (Gherkin или проверяемый список)
[ ] Персона/JTBD определены
[ ] FR декомпозирован (Source = US), тестируемое поведение
[ ] Связанные NFR указаны (rate limit, пагинация, ошибки, version, UUID)
[ ] API-контракт описан: метод, путь, body, ответы (вкл. 4xx/409/422), формат ошибки
[ ] ERD-изменения описаны с инвариантами (UUID v4, version, UTC, soft delete)
[ ] Нет нарушений TZ (mandatory соблюдены, forbidden отсутствуют; иначе есть ADR)
[ ] Все OPEN-гипотезы либо закрыты, либо явно помечены с оценкой риска
[ ] Зависимости от других US/FR перечислены
[ ] Описание простым языком (2–5 предложений) приложено
```

Если хоть один пункт не выполнен — требование **не Ready**, разработку начинать нельзя.

### 8.2 Definition of Done для аналитических артефактов

Аналитический артефакт (обновление vision/spec/architecture) считается **Done**, когда:

```
[ ] Артефакт обновлён по шаблону раздела (BA §3 / SA §4 / ARCH §5)
[ ] Трассировка вверх и вниз проставлена (US→G, FR→US, API→FR)
[ ] Нет противоречий с другими docs/ (числа, приоритеты, контракты сведены)
[ ] Соответствие TZ проверено
[ ] Docs sync выполнен: .planning/STATE.md + связанные docs (правило 55-docs-sync)
[ ] COVERAGE.md обновлена (для SA — обязательно; для BA — новые строки US)
[ ] Лог изменений в соответствующем skill-файле дополнен
[ ] Описание простым языком приложено
[ ] Артефакт передан верификатору, получен verified: true с датой/временем
```

Различие: DoR — про **входное** требование для разработки; DoD — про **выходной** артефакт
аналитика. Оба обязательны; verified: true ставит только верификатор (см. `verification.md`).

### 8.3 Матрица DoR/DoD по ролям

| Артефакт | Владелец | DoR-чек кто применяет | DoD-верификатор |
|----------|----------|----------------------|-----------------|
| US + AC | BA | SA (перед декомпозицией) | ba-ver |
| FR + API + ERD | SA | BE/FE (перед кодом) | sa-ver |
| ADR + C4 | ARCH | BE/FE + SA | arch-ver |

## 9. Антипаттерны аналитики

Таблица типичных дефектов аналитических артефактов, как их распознать и чем заменить.

| Антипаттерн | Симптом | Почему плохо | Замена |
|-------------|---------|--------------|--------|
| Расплывчатая US | «хочу удобную систему» | нельзя реализовать/проверить | конкретное действие + ценность + AC |
| US-эпик под видом US | несколько «и» в действии | не атомарна, не оценима | разбить на атомарные US |
| Отсутствие AC | US без критериев готовности | «готово» субъективно | ≥3 AC (happy/alt/error), Gether |
| Нетестируемое NFR | «быстро», «надёжно» | нельзя измерить | числовой порог + способ проверки |
| Цель без метрики | «улучшить онбординг» | не SMART | измеримость + срок |
| KPI-желаемое вместо факта | «Lighthouse ≥90 ✅» при отсутствии gate | вводит в заблуждение | статус = реальный факт + источник |
| Drift чисел | KPI≠spec≠код (293 vs 285) | недоверие к docs | сводить по проверяемому источнику |
| Дубль MoSCoW | фича и Should, и Could | противоречие приоритета | один приоритет на фичу |
| FR без Source | требование «висит» | мёртвый код/непонятна цель | привязка Source = US |
| ERD без инвариантов | нет version/UUID/soft delete | гонки, нарушение TZ | добавить обязательные поля |
| API без формата ошибки | `{"message":...}` | нарушает NFR-13 | `{"error","request_id"}` |
| Листинг без пагинации | отдаёт весь список | DoS, нарушает NFR-14/15 | offset/limit или cursor |
| Тихое допущение | нигде не помечено | скрытый риск | гипотеза H-XX с проверкой |
| Открытый вопрос вместо закрытого | «как сделать?» | не двигает работу | варианты + рекомендация |
| Нарушение TZ без ADR | ввёл forbidden/убрал mandatory | ломает контракт проекта | ADR + согласование |
| Stale C4/числа | docs говорят 18 модулей, код 21 | недоверие к архитектуре | сверять с кодом (grep/go.mod) |
| Правка чужого артефакта | SA меняет MoSCoW | нарушение владения | через владельца/handoff |
| Конфликт номеров | ba1 и ba2 оба US-M11 | коллизия, merge-конфликт | диапазоны нумерации по split |
| Синонимы в глоссарии | «канал» vs «беседа» | путаница терминов | единый глоссарий, сверка |
| verified сам себе | аналитик ставит verified: true | нет независимой проверки | только *-ver ставит verified |
