## 1. Философия верификации

### 1.1 Одна нейросеть проверяет другую

Ключевой принцип Hub (REGULATION §4.2): **верификатор независим от исполнителя**. Верификатор —
это отдельный агент, который не получает готовые ответы от того, кого проверяет, и не доверяет
описанию «на слово». Он проводит **собственную инспекцию**: воспроизводит сценарий из
требований, самостоятельно запускает тесты, независимо пересчитывает числа, ищет нарушения.

Причина такого устройства: исполнитель (BA/SA/ARCH/BE/FE/QA) находится внутри своего решения и
системно слеп к собственным допущениям. Независимый агент с чистым контекстом ловит то, что
исполнитель считает «очевидно верным». Это не бюрократия, а контроль качества методом
пересечения двух независимых взглядов.

### 1.2 Воспроизведение, а не доверие

Верификатор **воспроизводит** заявленный результат из первоисточника:

- `ba-ver` не верит «US полны» — сам проходит vision_and_scope и считает US, проверяет AC.
- `sa-ver` не верит «285 endpoints» — сам парсит `RegisterRoutes` и пересчитывает (реальный
  кейс: заявлено 293, независимый пересчёт дал 285).
- `be-ver` не верит «тесты проходят» — сам запускает `go test -race` и читает вывод.
- `fe-ver` не верит «a11y ок» — сам гоняет axe/Lighthouse или проверяет aria в коде.
- `qa-auto-ver` не верит «тест стабилен» — сам запускает несколько раз, ищет flaky.

Правило: **утверждение без воспроизведения не принимается**. Если верификатор не смог
воспроизвести — это FAIL или запрос на доказательство, но не «поверю».

### 1.3 Верификатор фиксирует, но не переписывает

Верификатор **не чинит** артефакт и **не пишет код за исполнителя**. Он:

1. Находит проблему.
2. Классифицирует её по severity (CRITICAL/HIGH/MEDIUM/LOW).
3. Формулирует замечание с доказательством (file:line, команда, ожидаемое vs фактическое).
4. Возвращает исполнителю с чётким списком.

Почему так: если верификатор сам исправит, теряется независимость (он становится соавтором и
перестаёт быть проверяющим), и исполнитель не учится. Исключение — тривиальная опечатка в
собственном отчёте верификатора. Массовые фиксы выполняет исполнитель или специализированный
агент (`gsd-code-review-fix`, `refactor-specialist`), но повторную верификацию проводит
верификатор.

### 1.4 Вердикт — датированный и обоснованный

Итог верификации — вердикт `verified: true|false` с датой и временем (`YYYY-MM-DD HH:MM`) и
списком замечаний с severity. `verified: true` — это утверждение о том, что артефакт
воспроизведён, сверен с docs/TZ, регрессия зелёная и лог приложен. Без любого из этих условий
ставится `verified: false`.

### 1.5 Что верификатор НЕ делает

- Не ставит `verified: true` без green-регрессии и приложенного лога (REGULATION §7).
- Не доверяет описанию исполнителя без воспроизведения.
- Не переписывает артефакт/код (только фиксирует замечания).
- Не смягчает severity, чтобы «пропустить» (CRITICAL/HIGH блокируют — см. раздел 4).
- Не проверяет «на глаз» то, что можно измерить (числа, покрытие, коды ответов).

### 1.6 Мышление верификатора: презумпция дефекта

Верификатор работает не из презумпции «скорее всего всё хорошо», а из презумпции «где-то есть
дефект, моя задача — найти его или доказать, что его нет». Это не пессимизм, а рабочая
установка: тот, кто ищет проблему, находит её; тот, кто ищет подтверждение — подтверждает.

Практические следствия:

- Верификатор начинает с самых опасных мест (security-инварианты, границы данных, TZ), а не с
  косметики.
- Верификатор проверяет **негативные** пути (что при ошибке, при конфликте, при превышении
  лимита), потому что там прячутся дефекты, которые исполнитель не тестировал.
- Верификатор задаёт вопрос «как это может сломаться?» к каждому пункту чек-листа.

### 1.7 Ложноположительные и ложноотрицательные вердикты

| Тип ошибки верификатора | Что произошло | Последствие | Как избегать |
|-------------------------|---------------|-------------|--------------|
| Ложноотрицательный (пропуск) | verified: true при наличии CRITICAL/HIGH | дефект в baseline/prod | воспроизведение + пофактовый чек-лист + регрессия |
| Ложноположительный (перебор) | FAIL по несуществующей проблеме | лишняя работа исполнителя, трение | доказательство обязательно (file:line, «ожидалось/фактически») |

Ложноотрицательный опаснее: он попадает в продукт. Поэтому при сомнении между PASS и FAIL
верификатор выбирает FAIL и требует доказательства обратного. Но FAIL без доказательства —
тоже дефект (ложноположительный), поэтому каждое замечание сопровождается фактом.

### 1.8 Конфликт интересов и его отсутствие

Верификатор не заинтересован в том, чтобы артефакт «прошёл». Его метрика успеха — не число
PASS, а отсутствие пропущенных дефектов. Если бы верификатор стремился к PASS, он бы смягчал
severity и верил на слово — ровно то, что запрещено. Правильная мотивация: «лучше я найду
проблему сейчас, чем её найдёт продакшн».

### 1.9 Разница верификации docs и кода

| Аспект | Docs-артефакт (ba/sa/arch) | Код-артефакт (be/fe/qa) |
|--------|---------------------------|-------------------------|
| Воспроизведение | пересчёт, сверка связей, прохождение сценария мысленно | запуск тестов/приложения |
| Регрессия | непротиворечивость docs + COVERAGE актуальна | green прогон + лог обязателен |
| Главный риск | drift чисел, нетестируемость, нарушение TZ | security-инварианты, layering, flaky |
| Доказательство | сравнение с кодом/другими docs | лог прогона, grep, file:line |

Общий каркас (раздел 2) одинаков; отличается способ воспроизведения и форма доказательства.

## 2. Общий протокол верификации

Единая последовательность для всех ролей. Специфика роли — в чек-листах раздела 3, но каркас
одинаков.

### 2.1 Шаги протокола

```
1. ЗАГРУЗИТЬ КОНТЕКСТ
   - все docs/ + tz_constraints
   - требование/артефакт под проверкой + описание исполнителя простым языком
   - связанные STATE.md, COVERAGE.md, ROADMAP.md
   - для кода: сам diff/файлы, а не только описание

2. ВОСПРОИЗВЕСТИ
   - пройти сценарий из требований самостоятельно
   - для кода — запустить, для docs — пересчитать/проверить связи
   - зафиксировать фактический результат

3. СВЕРИТЬ
   - с docs/ (соответствие спецификации/архитектуре/vision)
   - с tz_constraints (mandatory соблюдены, forbidden отсутствуют)
   - с code_style_guide / security_guidelines (для кода)
   - ожидаемое vs фактическое по каждому пункту чек-листа роли

4. ПРОВЕРИТЬ РЕГРЕССИЮ
   - green /qa-gate или профильный прогон слоя (см. раздел 6)
   - ЛОГ ПРОГОНА ОБЯЗАТЕЛЕН (без лога verified:true запрещён)

5. ВЫНЕСТИ ВЕРДИКТ
   - verified: true|false + YYYY-MM-DD HH:MM
   - замечания списком с severity (CRITICAL/HIGH/MEDIUM/LOW)
   - запись в skill-лог верификатора + отчёт (раздел 5)

6. ВЕРНУТЬ или ПРОПУСТИТЬ
   - FAIL (есть CRITICAL/HIGH) → возврат исполнителю со списком
   - PASS → артефакт в baseline проекта
```

### 2.2 Инвариант протокола

Протокол нельзя сокращать. Частые сокращения-нарушения:

- пропуск шага 2 (воспроизведение) → «поверил на слово» — антипаттерн;
- пропуск шага 4 (регрессия/лог) → `verified: true` без доказательства — запрещён;
- пропуск шага 3 (сверка с TZ) → пропуск нарушения mandatory/forbidden.

### 2.3 Вход и выход верификатора

| Что | Вход (получает) | Выход (производит) |
|-----|------------------|--------------------|
| Артефакт | docs/код под проверкой + описание | вердикт + замечания |
| Контекст | все docs/, TZ, STATE, COVERAGE | — |
| Доказательства | возможность запустить/пересчитать | лог прогона, пересчёты |
| Решение | severity-классификация | verified: true/false + дата |

### 2.4 Независимость на практике

- Верификатор читает **первоисточник** (код, docs), а не только summary исполнителя.
- Верификатор запускает команды **сам**, а не копирует чужой вывод.
- Верификатор пересчитывает числа **сам** (endpoints, coverage, US count).
- Если верификатор и исполнитель — одна модель, независимость обеспечивается чистым контекстом
  и запретом на доступ к внутренним рассуждениям исполнителя (только артефакт + описание).

### 2.5 Границы объёма верификации

Верификация атомарна, как и исполнение. Верификатор проверяет **конкретный артефакт/итерацию**,
а не «весь проект каждый раз». Но при этом обязан проверить, что изменение не ломает соседей —
для этого и нужна регрессия (раздел 6): она ловит регресс за пределами непосредственного diff.

```
Зона глубокой проверки: сам артефакт/diff/US, чек-лист роли пофактово.
Зона регрессионной проверки: затронутый модуль/слой (green прогон).
Зона сверки: docs + TZ + трассировка вверх.
Вне зоны: не связанные модули (их проверяют свои верификаторы в своих итерациях).
```

### 2.6 Что делать при недостатке контекста

Если верификатор не может воспроизвести (нет доступа к окружению, неясно требование,
отсутствует описание исполнителя), он **не ставит verified: true наугад**. Варианты:

```
- Требование неясно → замечание аналитику (артефакт не Ready) + verified: false.
- Нет описания исполнителя (2–5 предложений) → вернуть на доработку, это часть DoD.
- Не удаётся запустить регрессию → verified: false (без лога true запрещён), запросить окружение.
- Не хватает первоисточника → запросить, но не «поверить на слово» вместо него.
```

Отсутствие возможности проверить — это FAIL или блокирующий запрос, но никогда не «пропущу».

### 2.7 Порядок проверки внутри артефакта

Внутри одного артефакта верификатор идёт от наиболее опасного к наименее (§1.6):

```
1. Security-инварианты и TZ mandatory/forbidden (CRITICAL-зона)
2. Целостность данных (UUID/version/soft delete), контракты (ошибки/пагинация/коды)
3. Корректность логики и покрытие негативных/граничных путей
4. Соответствие паттернам/стилю (layering, Rules of Hooks, error wrapping)
5. Косметика (naming, комментарии, опечатки)
```

Так самые дорогие дефекты находятся первыми, и при обнаружении CRITICAL верификатор уже знает
исход (FAIL), но продолжает, чтобы вернуть исполнителю полный список, а не по одному.

## 4. Severity и что блокирует baseline

### 4.1 Уровни severity

| Severity | Определение | Примеры | Блокирует? |
|----------|-------------|---------|------------|
| CRITICAL | Ломает безопасность, целостность данных, TZ mandatory, или делает фичу неработоспособной | пропуск webhook signature (SEC-02); отсутствие version → гонки; string PK; secret в репо; WS без RBAC; search без scope | ДА — baseline запрещён |
| HIGH | Существенное нарушение контракта/качества, серьёзный дефект, но не немедленная катастрофа | формат ошибки не {"error","request_id"}; листинг без пагинации; io.ReadAll без limit; Rules of Hooks нарушены; drift чисел | ДА — baseline запрещён |
| MEDIUM | Дефект качества/сопровождаемости, обходимый | time.Sleep в тесте; stale C4-число; отсутствие негативного TC; неоптимальный индекс | НЕТ — но фиксируется, план исправления |
| LOW | Косметика, стиль, мелкие улучшения | опечатка в docs; уточнение глоссария; naming | НЕТ — рекомендация |

### 4.2 Правило блокировки

- **CRITICAL или HIGH ⇒ verified: false.** Артефакт возвращается исполнителю. В baseline не
  попадает до устранения.
- **Только MEDIUM/LOW ⇒ verified: true возможен**, но замечания фиксируются, и MEDIUM
  желательно закрыть в ближайшей итерации (заносится в backlog/TD).
- Верификатор **не смягчает** severity ради прохождения. Классификация — по факту воздействия,
  а не по удобству.

### 4.3 Эскалация и связь с аудитом

Severity верификации согласована с аудит-циклом (`.cursor/rules/56-regression-verify.mdc`):
до статуса «production-ready» число CRITICAL должно быть 0, product score ≥ 75. CRITICAL из
верификации попадают в remediation backlog (`.planning/AUDIT-*.md`) и закрываются в первую
очередь. Security-CRITICAL дополнительно проходят `security-auditor` / `gsd-secure-phase`.

### 4.4 Матрица «нарушение → severity» (частые случаи)

| Нарушение | Severity |
|-----------|----------|
| Пропуск подписи webhook / skip при отсутствии claim | CRITICAL |
| WS room без membership/RBAC | CRITICAL |
| Search без user-scope | CRITICAL |
| Отсутствие version (optimistic lock) | CRITICAL |
| String PK вместо UUID v4 | CRITICAL |
| Hardcoded secret / DEV_MODE=true в prod | CRITICAL |
| panic() в production-пути | CRITICAL/HIGH |
| Формат ошибки не {"error","request_id"} | HIGH |
| Листинг без пагинации | HIGH |
| io.ReadAll без LimitReader | HIGH |
| *ent.Client в Service/Handler | HIGH |
| Rules of Hooks нарушены | HIGH |
| key={index} в списках | HIGH/MEDIUM |
| verified без green regression + лог | HIGH (процессный) |
| Drift чисел (KPI≠spec≠код) | HIGH/MEDIUM |
| time.Sleep вместо poll в тесте | MEDIUM |
| Stale C4/число модулей | MEDIUM |
| Отсутствие негативного/граничного TC | MEDIUM |
| Narrating-комментарий, опечатка | LOW |

## 5. Формат отчёта верификации и запись в skill-лог

### 5.1 Шаблон отчёта (REVIEW.md / VERIFICATION.md)

Единый формат для всех верификаторов и code-reviewer:

```markdown
# Verification Report — <роль верификатора>

- Артефакт: <файл/модуль/PR>
- Исполнитель: <ba1|sa2|be|fe|qa|...>
- Верификатор: <ba-ver|sa-ver|...>
- Дата/время: YYYY-MM-DD HH:MM
- Вердикт: verified: true | false

## Контекст и воспроизведение
<Что проверялось, какой сценарий воспроизведён, какие команды запущены.>

## Регрессия
- Команда: <go test -race / npx vitest / /qa-gate>
- Результат: PASS | FAIL
- Лог:
```
<вставленный вывод прогона или ссылка на файл лога>
```

## Сверка с docs/TZ
<Соответствие system_specification/architecture/vision + tz_constraints.>

## Замечания
| # | Severity | Файл:строка / раздел | Ожидалось | Фактически | Действие |
|---|----------|----------------------|-----------|------------|----------|
| 1 | CRITICAL | tms/webhook.go:44 | signature проверяется | skip при отсутствии claim | исправить, вернуть |
| 2 | HIGH | wiki/API.md GET /tms/cases | пагинация limit≤100 | без ограничения | добавить |
| 3 | MEDIUM | flaky_test.go:20 | poll по условию | time.Sleep(2s) | заменить |

## Итог
<PASS: артефакт в baseline; или FAIL: возврат исполнителю со списком выше.>
```

### 5.2 Запись в skill-лог верификатора

Помимо отчёта, верификатор дополняет таблицу лога в своём `*_VER_skill.md` (как в реальных
файлах проекта):

```markdown
## Лог проверок
| Дата | Артефакт/PR | Результат | Замечания |
|------|-------------|-----------|-----------|
| 2026-07-02 | vision US-S16..S17 | FAIL | Web Push Should/Could дубль; KPI без источника |
| 2026-07-02 | tms flaky (code) | PASS | -race OK; лог приложен; MEDIUM sleep→poll закрыт |
```

И проставляет статус в таблице верификации артефакта (у исполнителя и у себя):

```markdown
| Статус | Дата | Верификатор |
|--------|------|-------------|
| verified: true | 2026-07-02 14:30 | be-ver |
```

### 5.3 Требования к отчёту

- Каждое замечание — с **доказательством** (file:line / раздел / команда), «ожидалось vs
  фактически», и **действием**.
- Регрессионный лог — **обязательная** секция; без него verified: true запрещён (раздел 6).
- Дата/время в вердикте — обязательны.
- Замечания отсортированы по severity (CRITICAL первыми).
- Отчёт самодостаточен: исполнитель может исправить всё по списку без доп. вопросов.

## 6. Регрессия как обязательное условие verified: true

### 6.1 Правило

REGULATION §7: **без green-регрессии и приложенного лога `verified: true` запрещён.** Это
неотменяемое условие для верификаторов кода (be-ver/fe-ver/qa-*) и code-reviewer. Для
docs-верификаторов (ba-ver/sa-ver/arch-ver) «регрессия» = отсутствие противоречий с другими
docs + (для sa-ver) актуальность COVERAGE, но при изменении, влияющем на код/поведение,
требуется и код-регрессия.

### 6.2 Профильные прогоны по слою

| Слой | Команда регрессии |
|------|-------------------|
| Backend (local) | `cd backend && go build -tags release ./... && go vet ./... && go test -race -count=1 -timeout=600s ./...` |
| Backend (Docker, канонично) | `go test -tags hubtest -race -count=1 -timeout=600s ./testframework/...` в `deployments/docker-compose.test.yml` |
| Frontend | `cd frontend && npx tsc --noEmit && npm run lint && npx vitest run` (+ `npx playwright test` для E2E) |
| Полный gate | `/qa-gate` — build + test + lint + security scan, останавливается на первой FAIL |
| Матрица | `/coverage-audit` — требования × код × тесты |

### 6.3 Что значит «green + лог»

- **Green** — прогон завершился без FAIL; для backend — включая `-race`.
- **Лог** — фактический вывод прогона (или ссылка на файл), вставленный в отчёт. Не «тесты
  прошли», а конкретный `ok ./internal/tms 12.4s` / `Test Files 37 passed (37)`.
- Лог должен соответствовать проверяемому изменению (тот же модуль/дата).

### 6.4 Test triage при FAIL (REGULATION §9)

Если регрессия падает, верификатор требует от исполнителя (или проводит сам) triage до любого
«озеленения»:

```
1. Воспроизвести ФУНКЦИОНАЛ по docs/ (не только assert)
2. Определить: код неверен ИЛИ тест устарел
3. Чинить минимальный слой
4. Записать triage: ROOT=code|test, файл, обоснование
```

Skill: `.cursor/skills/test-triage/SKILL.md`. **Запрещено** делать тесты зелёными без проверки
спецификации. Верификатор, принявший «озеленённый» без triage тест, сам нарушает протокол.

### 6.5 Артефакты-мусор после прогона

После регрессии верификатор убеждается, что не осталось coverage-дампов в репо
(`.cursor/rules/45-artifacts-cleanup.mdc`): `*.out`, `cover*`, `cov_*`, `tmp_*` — не должны
попасть в git status. Профили пишутся во временную папку вне репо.

## 7. GSD-инструменты верификации: когда что применять

| Инструмент | Назначение | Кто/когда |
|------------|-----------|-----------|
| `gsd-verify-work` | Валидация фичи через диалоговый UAT против требований | все верификаторы — базовый |
| `gsd-code-review` | Ревью изменённых файлов на баги/security/качество | be-ver, code-reviewer |
| `gsd-code-review-fix` | Авто-фикс findings из REVIEW.md (атомарные коммиты) | после code-review (исполнитель) |
| `gsd-validate-phase` | Заполнить Nyquist-пробелы валидации фазы (тесты/покрытие) | qa-ver / qa-auto-ver |
| `gsd-secure-phase` | Проверить митигации угроз из threat model в коде | arch-ver, security-auditor |
| `gsd-audit-uat` | Кросс-фазовый аудит невыполненных UAT/verification | sa-ver, qa |
| `gsd-ui-review` | Ретроспективный 6-pillar визуальный аудит фронта | fe-ver, designer-ver |
| `/qa-gate` | Полный quality gate (build/test/lint/security) | все, перед PASS |
| `/coverage-audit` | Матрица требований × код × тесты | sa-ver, qa-ver |
| `/test-triage` | Протокол: функционал → код vs тест | все при FAIL |

Правило выбора:

```
Проверяю фичу целиком против требований      → gsd-verify-work
Проверяю diff/файлы на дефекты               → gsd-code-review (+ /qa-gate)
Проверяю полноту тестов/покрытия фазы        → gsd-validate-phase + /coverage-audit
Проверяю security-митигации                  → gsd-secure-phase
Проверяю UI/дизайн                            → gsd-ui-review
Упал тест                                     → /test-triage перед любым фиксом
```

## 8. Антипаттерны верификации

| Антипаттерн | Симптом | Почему плохо | Замена |
|-------------|---------|--------------|--------|
| Проверка «на глаз» | «выглядит корректно/адаптивно/быстро» | не измеримо, пропускает дефекты | воспроизвести и измерить |
| Доверие без воспроизведения | «исполнитель написал, что работает» | нарушение независимости (§1.2) | сам запустить/пересчитать |
| verified без регрессии | true без green + лога | обещание без доказательства | приложить лог прогона (§6) |
| «Озеленение» без triage | тест сделан зелёным без проверки функционала | скрывает реальный баг (§10) | test-triage: ROOT=code\|test |
| Смягчение severity | CRITICAL записан как MEDIUM ради PASS | пропуск блокера в baseline | severity по факту воздействия |
| Верификатор переписывает | сам чинит артефакт/код | теряет независимость, исполнитель не учится | фиксировать замечание, вернуть |
| Замечание без доказательства | «тут что-то не так» | нельзя исправить, спор «на глаз» | file:line + ожидалось/фактически |
| Проверка только happy path | принят TC/код без границ/ошибок | дефекты в edge-case не пойманы | требовать 3 вида сценариев |
| Пропуск сверки с TZ | не проверил mandatory/forbidden | нарушение контракта проекта | шаг 3 протокола обязателен |
| Принятие чужого лога | вставил вывод исполнителя как свой | не воспроизведено независимо | запустить самому |
| Один прогон вместо -count | «стабильно» после 1 запуска | flaky не выявлен | -count=3 / repeat-each |
| Пропуск docs sync | код принят без обновления docs | drift, нарушение §11 | проверить STATE + domain docs |
| Апрув «LGTM» | ревью без чтения по существу | пропуск багов/секретов | пройти чек-лист роли |
| Числа на слово | принял endpoint count/coverage без пересчёта | drift чисел | независимый пересчёт |
| Нет даты/времени в вердикте | verified: true без метки | неотслеживаемо | YYYY-MM-DD HH:MM обязательно |
| Оставленный мусор | cover*/*.out в git status | грязный репо | cleanup (rule 45) |
