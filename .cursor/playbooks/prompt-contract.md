# Prompt Contract — контракт промпта для всех агентов Hub

> **Для кого:** все 30 агентов. **Тема:** как агент принимает задачу, каким форматом отвечает, какие техники применяет, с какой температурой работает, как верифицирует себя перед сдачей и кому передаёт.
>
> Канон шаблона делегирования: [`.cursor/agents/team-lead.md`](../agents/team-lead.md) §5.2 = [`team-workflow.md`](team-workflow.md) §5.3.1. Переносимый (обезличенный) аналог: [`prompt-engineering/agents/templates/_MASTER-PROMPT-TEMPLATE.md`](../../prompt-engineering/agents/templates/_MASTER-PROMPT-TEMPLATE.md). 10-этапная верификация: [`prompt-engineering/rules/40-verification-protocol.md`](../../prompt-engineering/rules/40-verification-protocol.md).

*Создано: 2026-07-19 — единый контракт качества промпта для всей команды.*

---

## 1. Зачем этот playbook

Качество ответа агента определяется не только его экспертизой, но и **структурой промпта на входе** и **дисциплиной проверки на выходе**. Раньше это было прописано только у `team-lead` (как делегировать). Здесь — симметричная часть: как **принимающий** агент обязан работать с задачей, чтобы результат был воспроизводимым и проверяемым.

Три источника брака, которые закрывает контракт:

| Брак | Причина | Что закрывает |
|------|---------|----------------|
| Агент домыслил scope | Задача пришла свободным текстом («сделай X») | §2 приём задачи |
| Ответ не парсится следующим звеном | Нет фиксированного формата | §3 формат ответа |
| «Вроде зелёное» → handoff | Нет обязательной самопроверки | §6 верификация |

## 2. Приём задачи (обязательно для каждого агента)

Жду промпт по шаблону §5.2 с блоками: `[РОЛЬ И ЗАДАЧА]`, `[КОНТЕКСТ]` (факты + границы файлов + кто использует результат), `[ФОРМАТ ОТВЕТА]`, `[ДОПОЛНИТЕЛЬНЫЕ УСЛОВИЯ]`.

**Задача пришла не по шаблону** (свободный текст, нет границ, нет контекста) — **не додумываю**. Возвращаю с явным перечнем недостающего:

```
Не хватает для старта (шаблон §5.2):
- [КОНТЕКСТ] границы файлов/модулей: что можно трогать, что нет
- [КОНТЕКСТ] кто использует результат (следующий агент / baseline)
- [ФОРМАТ ОТВЕТА] нужен код+тесты или анализ?
Готов стартовать по получении.
```

Обоснование: субагент не видит контекст чата отправителя (§5.1). Домысливание = drift scope = переделка. Один уточняющий возврат дешевле одной неверной волны.

**Исключение:** тривиальная однозначная правка (уровень `codex-micro` / `gsd-fast`) — можно без полного шаблона, но границы всё равно обязательны.

## 3. Формат ответа (универсальный каркас)

Если в задаче не задан свой формат — отвечаю так:

1. **Краткое резюме / вердикт** — первым, читатель занят.
2. **Подробное решение** по пунктам.
3. **Артефакт** (код / таблица / TC / схема / чек-лист), если применимо.
4. **Риски и mitigation.**
5. **Следующий шаг / handoff** — кому и что.
6. **Блок верификации** (§6) — обязателен.

Если у роли есть собственный формат вердикта в её agent-файле (например `be-ver` §10, `debugger` §7, `code-reviewer` §5) — **приоритет у него**, этот каркас применяется только к недостающим частям.

## 4. Техники по типу задачи

| Техника | Когда применять | Кому особенно |
|---------|-----------------|----------------|
| **Chain-of-Thought** — показать рассуждения до вывода | Анализ, дебаг, тест-дизайн, ревью | `debugger`, `code-reviewer`, `*-ver`, `qa-manual`, `sa*`, `ba*` |
| **Few-shot** — эталон формата/стиля из репо | Новый формат артефакта, стиль кода/тестов | `be*`, `fe*`, `qa-auto*`, `designer` |
| **Step-Back** — сначала принцип, затем решение | Стратегия, архитектура, приоритизация | `arch`, `tech-lead`, `product`, `team-lead`, `devops-engineer` |
| **ReAct** — план → команда → интерпретация → шаг | Расследование, работа с окружением | `debugger`, `devops-engineer`, `security-auditor`, `*-ver` |
| **Self-consistency** — два независимых прохода, сверка | Дорогая ошибка (security, прод, деньги) | `security-auditor`, `be-ver`, `arch-ver` |

Правило: техника обслуживает задачу, а не наоборот. CoT на механической правке — шум.

## 5. Температура (если инструмент даёт доступ)

| Диапазон | Тип работы | Роли |
|----------|-----------|------|
| **0.0–0.2** | Код, тесты, ассерты, верификация, факты, дебаг | `be*`, `fe*`, `qa-auto*`, все `*-ver`, `debugger`, `code-reviewer`, `security-auditor`, `codex-micro` |
| **0.2–0.4** | Спецификации, архитектура, планы, конфиги, документация | `sa*`, `arch`, `tech-lead`, `team-lead`, `devops-engineer`, `docs-writer` |
| **0.4–0.6** | Тест-дизайн, US/AC, продуктовые решения, UX | `ba*`, `qa-manual`, `product`, `designer` |
| **0.7+** | Только brainstorm вариантов, не финальный артефакт | любой на этапе идей |

Жёсткое правило: **всё, что попадёт в репозиторий как код или факт, генерится на низкой температуре.**

## 6. Верификация перед сдачей (10 этапов)

Полный протокол: [`prompt-engineering/rules/40-verification-protocol.md`](../../prompt-engineering/rules/40-verification-protocol.md). Согласован с REGULATION §3/§7 и [`verification.md`](verification.md) — не заменяет их, а даёт единый чек-лист самопроверки перед handoff.

| # | Этап | Вопрос к себе |
|---|------|----------------|
| 1 | Контекст | Загрузил нужные docs/playbooks? Вход полон? |
| 2 | Требование | Каждый пункт задачи закрыт? Ничего лишнего сверх scope? |
| 3 | Факты | Команды **прогнаны** (лог), пути проверены, числа посчитаны? |
| 4 | Негатив/границы | Проверил не только happy path? |
| 5 | Точность | Отсеял стилевое/ложное? Severity по канону? |
| 6 | Критический класс | Целевой проход на самое дорогое для моей роли (см. матрицу §8) |
| 7 | Регрессия | Затронутое + смежное зелёное, логи приложены? |
| 8 | Формат | Строго по формату, находки с готовым исправлением? |
| 9 | Воспроизводимость | Другой агент повторит? CONFIRMED vs PLAUSIBLE помечено? |
| 10 | Врата | 1–9 зелёные, открытые вопросы перечислены, handoff указан? |

**Компактный блок в ответ (обязателен):**

```
Verification (prompt-contract §6):
1✓ 2✓ 3✓(лог) 4✓ 5✓ 6✓ 7✓(регрессия) 8✓ 9✓ 10✓
Уверенность: CONFIRMED | PLAUSIBLE (по спорным пунктам)
```

`verified: true` без пройденных 1–9 и приложенных доказательств — запрещён (REGULATION §7).

## 7. Хендофф

Передача следующему звену — **сама по шаблону §5.2**: принимающий агент тоже не видит твой контекст. Минимум в хендоффе: что сделано, где артефакт, что проверено (лог), что осталось открытым, что именно требуется от принимающего.

## 9. Good / Bad

**Bad (приём):** пришло «поправь тесты в bases» → агент сам решает, какие файлы трогать, чинит три сьюта, ломает контракт с `qa-auto2`, отдаёт без лога прогона.

**Good (приём):** тот же вход → агент возвращает: «не хватает границ файлов и критерия готовности; какие TC покрываем?» → получает уточнение → работает строго в границах → отдаёт с логом и блоком верификации.

**Bad (выход):** «Готово, всё работает, тесты зелёные.» — нет формата, нет лога, нет верификации, следующему звену нечего парсить.

**Good (выход):** резюме → изменения по пунктам → лог прогона → риски → handoff `be-ver` с указанием что проверить → блок `Verification §6`.
