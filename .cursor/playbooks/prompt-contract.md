# Prompt Contract — контракт промпта для всех агентов Hub

> **Для кого:** все 30 агентов. **Тема:** как агент принимает задачу, каким форматом отвечает, какие техники применяет, с какой температурой работает, как верифицирует себя перед сдачей и кому передаёт.
>
> Канон шаблона делегирования: [`.cursor/agents/team-lead.md`](../agents/team-lead.md) §5.2 = [`team-workflow.md`](team-workflow.md) §5.3.1. Переносимый (обезличенный) аналог: [`prompt-engineering/agents/templates/_MASTER-PROMPT-TEMPLATE.md`](../../prompt-engineering/agents/templates/_MASTER-PROMPT-TEMPLATE.md). 10-этапная верификация: [`prompt-engineering/rules/40-verification-protocol.md`](../../prompt-engineering/rules/40-verification-protocol.md).

*Создано: 2026-07-19 — единый контракт качества промпта для всей команды.*

---

## 1. Зачем этот playbook

Качество ответа агента определяется не только его экспертизой, но и **структурой промпта на входе** и **дисциплиной проверки на выходе**. Раньше это было прописано только у `team-lead` (как делегировать). Здесь — симметричная часть: как **принимающий** агент обязан работать с задачей, чтобы результат был воспроизводимым и проверяемым.

Три источника брака, которые закрывает контракт:

| Брак | Причина | Что закрывает |
|------|---------|----------------|
| Агент домыслил scope | Задача пришла свободным текстом («сделай X») | §2 приём задачи |
| Ответ не парсится следующим звеном | Нет фиксированного формата | §3 формат ответа |
| «Вроде зелёное» → handoff | Нет обязательной самопроверки | §6 верификация |

## 2. Приём задачи (обязательно для каждого агента)

Жду промпт по шаблону §5.2 с блоками: `[РОЛЬ И ЗАДАЧА]`, `[КОНТЕКСТ]` (факты + границы файлов + кто использует результат), `[ФОРМАТ ОТВЕТА]`, `[ДОПОЛНИТЕЛЬНЫЕ УСЛОВИЯ]`.

**Задача пришла не по шаблону** (свободный текст, нет границ, нет контекста) — **не додумываю**. Возвращаю с явным перечнем недостающего:

```
Не хватает для старта (шаблон §5.2):
- [КОНТЕКСТ] границы файлов/модулей: что можно трогать, что нет
- [КОНТЕКСТ] кто использует результат (следующий агент / baseline)
- [ФОРМАТ ОТВЕТА] нужен код+тесты или анализ?
Готов стартовать по получении.
```

Обоснование: субагент не видит контекст чата отправителя (§5.1). Домысливание = drift scope = переделка. Один уточняющий возврат дешевле одной неверной волны.

**Исключение:** тривиальная однозначная правка (уровень `codex-micro` / `gsd-fast`) — можно без полного шаблона, но границы всё равно обязательны.

## 3. Формат ответа (универсальный каркас)

Если в задаче не задан свой формат — отвечаю так:

1. **Краткое резюме / вердикт** — первым, читатель занят.
2. **Подробное решение** по пунктам.
3. **Артефакт** (код / таблица / TC / схема / чек-лист), если применимо.
4. **Риски и mitigation.**
5. **Следующий шаг / handoff** — кому и что.
6. **Блок верификации** (§6) — обязателен.

Если у роли есть собственный формат вердикта в её agent-файле (например `be-ver` §10, `debugger` §7, `code-reviewer` §5) — **приоритет у него**, этот каркас применяется только к недостающим частям.

## 4. Техники по типу задачи

| Техника | Когда применять | Кому особенно |
|---------|-----------------|----------------|
| **Chain-of-Thought** — показать рассуждения до вывода | Анализ, дебаг, тест-дизайн, ревью | `debugger`, `code-reviewer`, `*-ver`, `qa-manual`, `sa*`, `ba*` |
| **Few-shot** — эталон формата/стиля из репо | Новый формат артефакта, стиль кода/тестов | `be*`, `fe*`, `qa-auto*`, `designer` |
| **Step-Back** — сначала принцип, затем решение | Стратегия, архитектура, приоритизация | `arch`, `tech-lead`, `product`, `team-lead`, `devops-engineer` |
| **ReAct** — план → команда → интерпретация → шаг | Расследование, работа с окружением | `debugger`, `devops-engineer`, `security-auditor`, `*-ver` |
| **Self-consistency** — два независимых прохода, сверка | Дорогая ошибка (security, прод, деньги) | `security-auditor`, `be-ver`, `arch-ver` |

Правило: техника обслуживает задачу, а не наоборот. CoT на механической правке — шум.

## 5. Температура (если инструмент даёт доступ)

| Диапазон | Тип работы | Роли |
|----------|-----------|------|
| **0.0–0.2** | Код, тесты, ассерты, верификация, факты, дебаг | `be*`, `fe*`, `qa-auto*`, все `*-ver`, `debugger`, `code-reviewer`, `security-auditor`, `codex-micro` |
| **0.2–0.4** | Спецификации, архитектура, планы, конфиги, документация | `sa*`, `arch`, `tech-lead`, `team-lead`, `devops-engineer`, `docs-writer` |
| **0.4–0.6** | Тест-дизайн, US/AC, продуктовые решения, UX | `ba*`, `qa-manual`, `product`, `designer` |
| **0.7+** | Только brainstorm вариантов, не финальный артефакт | любой на этапе идей |

Жёсткое правило: **всё, что попадёт в репозиторий как код или факт, генерится на низкой температуре.**

## 6. Верификация перед сдачей (10 этапов)

Полный протокол: [`prompt-engineering/rules/40-verification-protocol.md`](../../prompt-engineering/rules/40-verification-protocol.md). Согласован с REGULATION §3/§7 и [`verification.md`](verification.md) — не заменяет их, а даёт единый чек-лист самопроверки перед handoff.

| # | Этап | Вопрос к себе |
|---|------|----------------|
| 1 | Контекст | Загрузил нужные docs/playbooks? Вход полон? |
| 2 | Требование | Каждый пункт задачи закрыт? Ничего лишнего сверх scope? |
| 3 | Факты | Команды **прогнаны** (лог), пути проверены, числа посчитаны? |
| 4 | Негатив/границы | Проверил не только happy path? |
| 5 | Точность | Отсеял стилевое/ложное? Severity по канону? |
| 6 | Критический класс | Целевой проход на самое дорогое для моей роли (см. матрицу §8) |
| 7 | Регрессия | Затронутое + смежное зелёное, логи приложены? |
| 8 | Формат | Строго по формату, находки с готовым исправлением? |
| 9 | Воспроизводимость | Другой агент повторит? CONFIRMED vs PLAUSIBLE помечено? |
| 10 | Врата | 1–9 зелёные, открытые вопросы перечислены, handoff указан? |

**Компактный блок в ответ (обязателен):**

```
Verification (prompt-contract §6):
1✓ 2✓ 3✓(лог) 4✓ 5✓ 6✓ 7✓(регрессия) 8✓ 9✓ 10✓
Уверенность: CONFIRMED | PLAUSIBLE (по спорным пунктам)
```

`verified: true` без пройденных 1–9 и приложенных доказательств — запрещён (REGULATION §7).

## 9. Good / Bad

**Bad (приём):** пришло «поправь тесты в bases» → агент сам решает, какие файлы трогать, чинит три сьюта, ломает контракт с `qa-auto2`, отдаёт без лога прогона.

**Good (приём):** тот же вход → агент возвращает: «не хватает границ файлов и критерия готовности; какие TC покрываем?» → получает уточнение → работает строго в границах → отдаёт с логом и блоком верификации.

**Bad (выход):** «Готово, всё работает, тесты зелёные.» — нет формата, нет лога, нет верификации, следующему звену нечего парсить.

**Good (выход):** резюме → изменения по пунктам → лог прогона → риски → handoff `be-ver` с указанием что проверить → блок `Verification §6`.

## 11. Заполненные примеры по архетипам ролей

> Шаблон §5.2 в теории понятен, на практике агенты «недозаполняют» `[КОНТЕКСТ]`. Ниже — эталонные заполнения на реальных модулях Hub. Копировать структуру, менять содержание.
>
> Ещё два примера: `team-lead.md` §5.3 (bases security fix, полный) и `team-workflow.md` Приложение I (BacklogService.Reorder, краткий).

### 11.1 Архетип «исполнитель кода» (`be1`/`be2`/`fe1`/`fe2`)

```markdown
[РОЛЬ И ЗАДАЧА]
Ты — be1, backend Go/Fiber/Ent эксперт (Hub).
Мне нужно реализовать WIP-лимиты Kanban-колонок в модуле tracker: при перемещении
задачи в колонку с достигнутым лимитом — отказ, задача остаётся в исходной колонке.

[КОНТЕКСТ]
- Требование: docs/system_specification.md §FR-TRACKER (WIP-лимиты), AC из US-TRCK-18.
- Инвариант TZ: docs/tz_constraints.md — optimistic locking через `version` в изменяемых
  Ent-схемах; задачи — offset/limit пагинация (не cursor).
- Границы: трогать только backend/internal/tracker/{repo_boards.go, service_boards.go,
  handler_boards.go} + backend/testframework/tracker/. НЕ трогать automation_engine.go
  (в этой волне у be2), НЕ трогать ent/schema (контракт зафиксирован sa1 в первом коммите).
- Контракт: тип `BoardColumnWipLimit` уже в types (коммит 3a1f2c от sa1).
- Кто использует результат: кросс-ревью be2 → be-ver → code-reviewer → baseline волны.
- Уровень детализации: production-код + unit-тесты, без рефакторинга соседних модулей.
- Playbooks: backend.md (layering, error wrapping), testing.md (каркас теста),
  observability.md (slog на границе), code-comments.md.

[ФОРМАТ ОТВЕТА]
1. Резюме: что реализовано, какие файлы затронуты.
2. Код по слоям (repo → service → handler), диффом.
3. Unit-тесты + лог прогона.
4. Риски (что может сломаться в смежных модулях).
5. Handoff be2 на кросс-ревью: что смотреть в первую очередь.

[ЦЕПОЧКА РАССУЖДЕНИЙ]
Покажи, на каком слое ставишь guard и почему именно там (не в handler — обходится
через другие вызовы service).

[ПАРАМЕТРЫ ГЕНЕРАЦИИ]
Temperature 0.1 (production-код).

[ДОПОЛНИТЕЛЬНЫЕ УСЛОВИЯ]
- Цикл качества нового: реализовать → go test -tags hubtest -race ./testframework/tracker/...
  -run TestBoards_WipLimit → FAIL? → triage → fix → повтор до green.
- Регрессия старого: весь домен tracker + смежный dashboard (читает board stats).
- Docs-sync (rule 55): system_specification §FR-TRACKER, COVERAGE.md, STATE.md.
- Верификация prompt-contract §6, критический класс: security-инварианты + тест реально падает.
- Не хватает данных — уточни, не расширяй scope молча.
```

### 11.2 Архетип «верификатор» (`be-ver`/`fe-ver`/`sa-ver`/`qa-*-ver`/`arch-ver`)

```markdown
[РОЛЬ И ЗАДАЧА]
```

## 12. Контекст-бюджет принимающего агента

> Приложение I `team-workflow.md` описывает бюджет со стороны **отправителя** (что вкладывать). Здесь — со стороны **получателя** (что и в каком порядке грузить, чтобы не утонуть).

### 12.1 Порядок загрузки (сверху вниз, не выборочно)

1. `.planning/STATE.md` — что происходит сейчас (30 секунд).
2. Свой agent-файл — обязанности, формат вердикта, DoD.
3. Строка матрицы §8 этого playbook — контекст/формат/техники/температура/критический класс.
4. Playbooks своей роли (`playbooks/README.md` §2.1) — **только профильные**.
5. Разделы `docs/`, указанные в `[КОНТЕКСТ]` задачи — **по разделам, не файлы целиком**.
6. Код/дифф в границах задачи.

### 12.2 Что НЕ грузить

| Не грузить | Почему | Что вместо |
|------------|--------|------------|
| Весь `docs/` целиком | Съедает контекст, нужный для работы | Разделы из `[КОНТЕКСТ]` задачи |
| Playbooks чужих ролей | Не относится к задаче | Свои по §2.1 обратной карты |
| Историю всех волн `.planning/` | Устарело и объёмно | `STATE.md` + конкретный артефакт по `.planning/README.md` |
| Код вне границ задачи | Провоцирует drift scope | Только файлы из `[КОНТЕКСТ] Границы` |
| Все 1000 промптов `prompt-engineering/prompts/` | Это справочник, не контекст | Нужную категорию точечно |

### 12.3 Сигнал переполнения

Контекста не хватает на работу (много прочитано, мало сделано) — **не продолжать «на памяти»**. Действие: сообщить оркестратору, что задача требует дробления, с предложением разбиения. Молчаливая работа на переполненном контексте даёт галлюцинации путей и «починил по памяти» — худший класс брака (ловится этапом 3 верификации, но дорого).

## 14. Антипаттерны промптинга (реальные)

| # | Антипаттерн | Чем оборачивается | Как правильно |
|---|-------------|-------------------|----------------|
| 1 | «Сделай X» без границ файлов | Два агента правят один файл, конфликт мержа, потерянная работа | `[КОНТЕКСТ] Границы: трогай только A, НЕ трогай B (у be2)` |

| 4 | Нет «кто использует результат» | Агент не понимает нужную глубину, делает или мало, или лишнее | `Кто использует: be-ver → code-reviewer → baseline` |
| 5 | Условия качества опущены | Handoff без регрессии, «вроде зелёное» | Цикл нового + регрессия старого в `[УСЛОВИЯ]` явно |

| 8 | «Заодно поправь X» внутри задачи | Расширение scope, неатомарный PR, сложная регрессия | Отдельная задача; в текущей — эскалация оркестратору |

| 10 | Пересказ артефакта вместо ссылки | Расхождение пересказа и файла, работа по устаревшему | Ссылка на путь + якорь секции |

## 15. Калибровка: как проверить, что агент следует контракту

> Контракт без проверки исполнения — декларация. Ниже — как оркестратор и сам агент убеждаются, что контракт работает.

### 15.1 Самоаудит агента (после задачи)

- [ ] Я запросил недостающее или додумал молча?
- [ ] Я загрузил ровно свой контекст (§12) или читал лишнее «на всякий случай»?
- [ ] Мой ответ по формату роли или свободным потоком?
- [ ] Блок `Verification` содержит **доказательства** (логи, команды) или галочки без опоры?
- [ ] Хендофф даёт принимающему всё нужное, или он придёт с уточнениями?

### 15.2 Проверка оркестратором (выборочно, на волне)

| Признак нарушения контракта | Что означает | Действие |
|------------------------------|--------------|----------|
| Ответ без блока `Verification` | Самопроверка не проводилась | Вернуть без чтения содержания |
| «Тесты зелёные» без лога | Этап 3 провален (факты не проверены) | Вернуть с требованием лога |
| Правки вне заявленных границ | Drift scope | Откатить лишнее, разобрать причину |
| Верификатор прислал патч вместо вердикта | Роль спутана | Напомнить readonly-границу |
| Принимающий агент пришёл с уточнениями | Хендофф был неполон | Доработать хендофф отправителя, не принимающего |

### 15.3 Метрика здоровья контракта (на ретро волны)

Считать по волне: доля задач, ушедших с полным §5.2; доля ответов с блоком `Verification`; число возвратов «не хватает контекста»; число drift-scope инцидентов. Рост возвратов — не проблема агентов, а сигнал, что оркестратор недозаполняет шаблон.
