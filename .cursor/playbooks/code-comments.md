# Hub — Playbook: комментарии в коде

> Для всех, кто пишет код и тесты: be1/be2, fe1/fe2, qa-auto1/qa-auto2, а также ревьюеров (be-ver/fe-ver/code-reviewer).
> Первоисточники: `.cursor/rules/10-style.mdc`, `docs/code_style_guide.md`. При конфликте правила `.cursor/rules/*` и ТЗ важнее этого playbook.

*Обновлено: 2026-07-02.*

---

## 1. Главный принцип: код говорит ЧТО, комментарий — ПОЧЕМУ

Код уже описывает **что** он делает. Комментарий нужен там, где из кода **не видно намерения, компромисса или ограничения**. Если комментарий пересказывает строку кода — он вреден: устаревает, шумит, создаёт ложное доверие.

| Категория | Нужен комментарий? |
|-----------|--------------------|
| Что делает очевидная строка | ❌ Нет |
| Почему выбран именно такой (неочевидный) подход | ✅ Да |
| Обход бага внешней системы | ✅ Да (со ссылкой) |
| Инвариант, который легко нарушить при правке | ✅ Да |
| Ссылка на требование/ADR/SEC-ID/тикет | ✅ Да |
| Предупреждение о грани/подводном камне | ✅ Да |

**Правило одной проверки:** прежде чем написать комментарий, спроси — «это видно из кода?». Если да — не пиши. Если объясняешь *почему*, *почему не иначе*, *при каком условии сломается* — пиши.

## 2. Запрещённые комментарии (анти-паттерны)

### 2.1. Пересказ кода (narration)

```go
// ❌ Плохо: пересказывает очевидное
i++ // увеличиваем счётчик
user := repo.Get(ctx, id) // получаем пользователя
return nil // возвращаем nil
```

```go
// ✅ Хорошо: без комментария там, где код самодостаточен
i++
user := repo.Get(ctx, id)
return nil
```

Типичные «мусорные» комментарии, которые в Hub **запрещены** (см. rule 10):
`// increment counter`, `// import module`, `// define function`, `// handle error`, `// return result`, `// loop over items`.

### 2.2. Закомментированный код

```typescript
// ❌ Плохо: мёртвый код в комментарии
// const oldClient = new ApiClient(BASE_URL)
// oldClient.setTimeout(5000)
const client = createApiClient()
```

Мёртвый код удаляем — история есть в git. Закомментированные блоки запрещены (кроме временного отладочного, который **нельзя** коммитить).

### 2.3. Дублирование сигнатуры

```go
// ❌ Плохо: комментарий повторяет сигнатуру
// CreateIssue creates an issue with the given title and returns it.
func (s *Service) CreateIssue(ctx context.Context, title string) (*Issue, error)
```

Если godoc не добавляет смысла сверх имени — либо перепиши его так, чтобы он объяснял контракт/ограничения, либо убери шум. Хороший godoc объясняет **гарантии, ошибки, побочные эффекты**, а не повторяет имя.

### 2.4. TODO без контекста

```go
// ❌ Плохо
// TODO: fix this later

// ✅ Хорошо: тикет + суть + условие
// TODO(HUB-482): убрать после миграции refresh-токенов на SHA-256 (см. ADR-AUTH-02).
```

TODO без тикета/владельца/условия — запрещён: он вечен и бесполезен.

### 2.5. Устаревшие и «врущие» комментарии

Комментарий, противоречащий коду, хуже отсутствия комментария. При изменении кода **обнови или удали** прилегающий комментарий в том же коммите.

## 3. Хорошие комментарии (что писать)

### 3.1. Неочевидное решение и компромисс

```go
// Сериализуем создание первого пользователя мьютексом: параллельные регистрации
// могли назначить роль founder дважды (SEC-06). Одиночная блокировка дешевле,
// чем распределённый advisory-lock, т.к. путь исполняется один раз на инстанс.
firstUserMu.Lock()
defer firstUserMu.Unlock()
```

### 3.2. Обход бага внешней системы (со ссылкой)

```typescript
// LiveKit egress иногда присылает participant_left до participant_joined при reconnect;
// поэтому не декрементируем счётчик ниже нуля. См. livekit/livekit#4821.
count = Math.max(0, count - 1)
```

### 3.3. Инвариант, который легко нарушить

```go
// ВАЖНО: закрываем только done. Продюсеры обязаны проверять <-done перед send,
// иначе паника "send on closed channel" (SEC-05). НЕ закрывать канал сообщений здесь.
close(h.done)
```

### 3.4. Ссылка на требование/безопасность

```go
// Сравнение секретов постоянным временем — защита от timing-атаки (NF-12, security_guidelines.md).
if subtle.ConstantTimeCompare(got, want) != 1 {
    return apperrors.Unauthorized("invalid code")
}
```

### 3.5. Предупреждение о грани

```typescript
// staleTime=0: список непрочитанных должен быть максимально свежим,
// т.к. бейдж влияет на поведение пользователя. Осознанно жертвуем кэшем.
useQuery({ queryKey: ['unread'], queryFn: getUnread, staleTime: 0 })
```

### 3.6. «Почему НЕ сделано иначе»

```go
// Не используем ent hook для этого: hook не видит контекст запроса (request_id),
// а нам нужен корреляционный лог. Публикуем событие явно в сервисе.
```

## 4. Go: документирующие комментарии

### 4.1. Package doc

Каждый нетривиальный пакет — с package doc. В Hub допустима русская проза (термины/идентификаторы английские), как в тестах репозитория:

```go
// Package tracker содержит доменную логику трекера задач: создание задач всех
// типов, оптимистичную блокировку через version, workflow-переходы, связи и метки.
// Слой сервиса зависит только от интерфейса Repository; *ent.Client живёт в ent_repository.go.
package tracker
```

### 4.2. Godoc экспортируемых сущностей

Godoc начинается с имени сущности и объясняет **контракт**: что гарантирует, какие ошибки, побочные эффекты.

```go
// CreateIssue создаёт задачу в проекте и присваивает issue_key вида <KEY>-<N>.
// Возвращает apperrors.NotFound, если проект не найден, и apperrors.Conflict
// при нарушении оптимистичной блокировки. Публикует событие hub.issues.created.
func (s *Service) CreateIssue(ctx context.Context, projectID uuid.UUID, in CreateIssueInput) (*ent.Issue, error)
```

```go
// ❌ Плохо: godoc-«эхо» имени, без контракта
// CreateIssue creates an issue.
func (s *Service) CreateIssue(...)
```

### 4.3. Deprecated

```go
// Deprecated: используйте CreateIssueV2 — этот метод не поддерживает custom fields.
// Будет удалён после HUB-500.
func (s *Service) CreateIssue(...)
```

### 4.4. Комментарий к сложному алгоритму

Разбивай алгоритм на смысловые шаги с *почему*, а не *что*:

```go
// JQL транслируем в предикаты Ent в два прохода: сначала строим AST (валидация
// синтаксиса и полей — ошибки понятны пользователю), затем маппим в predicate.
// Одним проходом нельзя: часть полей — computed и требует join, известный только после разбора.
```

### 4.5. Example-функции

Для публичного API полезны `ExampleXxx` — они и документация, и тест.

## 5. TypeScript/React

### 5.1. TSDoc там, где добавляет смысл

```typescript
/**
 * Одновременный refresh access-токена: если запрос уже идёт, ждём его,
 * а не шлём второй (иначе гонка отзовёт свежий refresh). Single-flight.
 */
async function refreshOnce(): Promise<string> { /* ... */ }
```

### 5.2. Обоснование `any` / отключения линтера

`any` без причины запрещён. Если неизбежен — комментарий с причиной:

```typescript
// any: тип приходит из стороннего editor SDK без типов; сузим после апгрейда до v3.
const doc = editor.getDocument() as any // eslint-disable-line -- см. HUB-321
```

### 5.3. Неочевидные a11y/CSS-решения

```tsx
// role="status" + aria-live: скринридер должен озвучить появление тоста,
// но не перехватывать фокус. Поэтому не button и не alertdialog.
<div role="status" aria-live="polite">{message}</div>
```

### 5.4. Комментарии к хукам с тонкой зависимостью

```typescript
// Намеренно пустой deps: подписка на WS создаётся один раз на маунт.
// queryClient стабилен (из провайдера). Добавление deps пересоздаст сокет.
useEffect(() => subscribe(queryClient), []) // eslint-disable-line react-hooks/exhaustive-deps -- см. комментарий
```

## 6. Комментарии в тестах

Тест — тоже документация. В Hub принято:

### 6.1. Package doc теста + описание сценария

```go
// Package tracker_test проверяет TrackerService: типы задач, optimistic locking,
// workflow-переходы, курсорную пагинацию. Мокаем Repository; БД не поднимаем.
package tracker_test
```

### 6.2. Привязка к тест-кейсу и требованию

Каждый значимый тест ссылается на TC-ID из `docs/TESTING.md` и/или требование — это часть трассируемости требование→TC→автотест:

```go
// TC-TRCK-04: конфликт версий. Требование: FR-TRCK-12 (optimistic locking).
// Проверяем, что update со старой version возвращает Conflict, а не молча перезаписывает.
func TestUpdateIssueOptimisticLocking(t *testing.T) { /* ... */ }
```

```typescript
// TC-AUTH-12: logout отзывает refresh. См. docs/TESTING.md.
test('logout revokes refresh token', async ({ page }) => { /* ... */ })
```

### 6.3. Объяснять «почему важно», а не «что делает assert»

```go
// ❌ Плохо
assert.Equal(t, 2, issue.Version) // version равен 2

// ✅ Хорошо: почему это важно
// После успешного update version обязан инкрементироваться — иначе следующий
// клиент со старой версией перезапишет данные (нарушение optimistic locking).
assert.Equal(t, 2, issue.Version)
```

## 7. Что в коде, что во внешней документации

| В коде (комментарий) | Во внешних docs |
|----------------------|-----------------|
| Локальный *почему*, инвариант, обход бага | Архитектура, C4, потоки |
| Контракт функции (godoc/TSDoc) | API-спека (`system_specification.md`, `wiki/API.md`) |
| Привязка теста к TC | Таблица TC↔автотест (`docs/TESTING.md`) |
| Ссылка на ADR/SEC-ID | Сам ADR (`.planning/decisions/`) |

Не дублируй в коде то, что живёт в docs — ставь ссылку (ID/файл), а не копию.

## 8. Язык и стиль

- Проза комментариев — **русский** допустим (как в репо); идентификаторы, типы, ключевые слова — английские.
- **Без эмодзи** в коде и комментариях (rule 10).
- Тон нейтральный, по делу; без шуток, которые устареют.
- Консистентность в пределах модуля: не смешивай стили без нужды.
- Комментарий располагается **над** кодом, к которому относится; инлайн — только для короткого пояснения к строке.

## 9. Антипаттерны (сводка)

| Нельзя | Почему | Как правильно |
|--------|--------|---------------|
| `// increment counter` | Пересказ кода, шум | Удалить |
| Закомментированный код | Мёртвый груз, путает | Удалить (есть git) |
| `// TODO: fix later` | Вечный, бесполезный | `TODO(HUB-XXX): суть + условие` |
| godoc = имя функции | Не добавляет смысла | Описать контракт/ошибки |
| Комментарий врёт коду | Хуже отсутствия | Обновить/удалить в том же коммите |
| `any` без причины | Теряется типобезопасность | Убрать или `// причина` |
| Assert-«эхо» в тесте | Не объясняет ценность | Объяснить инвариант/риск |
| Эмодзи в коде | Запрещено rule 10 | Убрать |

## 10. Чек-лист перед передачей ревью

- [ ] Нет комментариев-пересказов и закомментированного кода.
- [ ] Экспортируемые сущности Go имеют godoc с контрактом (ошибки/эффекты).
- [ ] Все `any`/`eslint-disable` снабжены причиной.
- [ ] Неочевидные решения/инварианты/обходы багов прокомментированы с ссылкой (ADR/SEC/issue).
- [ ] Значимые тесты ссылаются на TC-ID/требование.
- [ ] TODO содержат тикет и условие.
- [ ] Прилегающие комментарии обновлены под изменённый код.
- [ ] Нет эмодзи; язык и стиль консистентны.
