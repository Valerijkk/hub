## 1. Главный принцип: код говорит ЧТО, комментарий — ПОЧЕМУ

Код уже описывает **что** он делает. Комментарий нужен там, где из кода **не видно намерения, компромисса или ограничения**. Если комментарий пересказывает строку кода — он вреден: устаревает, шумит, создаёт ложное доверие.

| Категория | Нужен комментарий? |
|-----------|--------------------|
| Что делает очевидная строка | ❌ Нет |
| Почему выбран именно такой (неочевидный) подход | ✅ Да |
| Обход бага внешней системы | ✅ Да (со ссылкой) |
| Инвариант, который легко нарушить при правке | ✅ Да |
| Ссылка на требование/ADR/SEC-ID/тикет | ✅ Да |
| Предупреждение о грани/подводном камне | ✅ Да |
| Нестандартный порядок middleware/шагов | ✅ Да |

**Правило одной проверки:** прежде чем написать комментарий, спроси — «это видно из кода?». Если да — не пиши. Если объясняешь *почему*, *почему не иначе*, *при каком условии сломается* — пиши.

## 2. Запрещённые комментарии (анти-паттерны)

### 2.1. Пересказ кода (narration)

```go
// ❌ Плохо: пересказывает очевидное
i++ // увеличиваем счётчик
user := repo.Get(ctx, id) // получаем пользователя
return nil // возвращаем nil
```

```go
// ✅ Хорошо: без комментария там, где код самодостаточен
i++
user := repo.Get(ctx, id)
return nil
```

Типичные «мусорные» комментарии, которые в Hub **запрещены** (см. rule 10):
`// increment counter`, `// import module`, `// define function`, `// handle error`, `// return result`, `// loop over items`.

### 2.2. Закомментированный код

```typescript
// ❌ Плохо: мёртвый код в комментарии
// const oldClient = new ApiClient(BASE_URL)
// oldClient.setTimeout(5000)
const client = createApiClient()
```

Мёртвый код удаляем — история есть в git. Закомментированные блоки запрещены (кроме временного отладочного, который **нельзя** коммитить).

### 2.3. Дублирование сигнатуры

```go
// ❌ Плохо: комментарий повторяет сигнатуру
// CreateIssue creates an issue with the given title and returns it.
func (s *Service) CreateIssue(ctx context.Context, title string) (*Issue, error)
```

Если godoc не добавляет смысла сверх имени — либо перепиши его так, чтобы он объяснял контракт/ограничения, либо убери шум. Хороший godoc объясняет **гарантии, ошибки, побочные эффекты**, а не повторяет имя (реальный контрпример — §4.2).

### 2.4. TODO без контекста

```go
// ❌ Плохо
// TODO: fix this later

// ✅ Хорошо: тикет + суть + условие
// TODO(HUB-482): убрать после миграции refresh-токенов на SHA-256 (см. ADR-AUTH-02).
```

TODO без тикета/владельца/условия — запрещён: он вечен и бесполезен. **Факт из аудита Hub:** grep по `backend/internal` и `frontend/src` не находит ни одного голого `TODO` без контекста — это подтверждённая практика, а не теория; при код-ревью `code-reviewer` грепает именно это.

### 2.5. Устаревшие и «врущие» комментарии

Комментарий, противоречащий коду, хуже отсутствия комментария. При изменении кода **обнови или удали** прилегающий комментарий в том же коммите.

### 2.6. Комментарий вместо теста/валидации

```go
// ❌ Плохо: комментарий вместо реальной проверки
// предполагаем, что projectID валиден
issue, _ := s.repo.Create(ctx, projectID, title)
```

Если инвариант важен — проверяй его кодом (`if projectID == uuid.Nil { return ErrInvalidInput }`), а не декларируй комментарием. Комментарий описывает *почему* существующая проверка сделана именно так, а не заменяет проверку.

## 3. Хорошие комментарии (что писать)

### 3.1. Неочевидное решение и компромисс

```go
// Сериализуем создание первого пользователя мьютексом: параллельные регистрации
// могли назначить роль founder дважды (SEC-06). Одиночная блокировка дешевле,
// чем распределённый advisory-lock, т.к. путь исполняется один раз на инстанс.
firstUserMu.Lock()
defer firstUserMu.Unlock()
```

Реальный расширенный вариант того же инварианта — уже на уровне БД, `backend/internal/auth/repository.go`:

```go
// firstUserAdvisoryKey — pg_advisory_xact_lock для атомарной первой регистрации (SEC-06).
```
и
```go
// защита от гонки двух одновременных «первых пользователей» (SEC-06).
```

Обратите внимание: два независимых комментария (in-memory мьютекс в сервисе + advisory lock в репозитории) ссылаются на **один и тот же** SEC-ID — так читатель быстро понимает, что это защита в глубину одного и того же инварианта на двух уровнях.

### 3.2. Обход бага внешней системы (со ссылкой)

```typescript
// LiveKit egress иногда присылает participant_left до participant_joined при reconnect;
// поэтому не декрементируем счётчик ниже нуля. См. livekit/livekit#4821.
count = Math.max(0, count - 1)
```

### 3.3. Инвариант, который легко нарушить

```go
// ВАЖНО: закрываем только done. Продюсеры обязаны проверять <-done перед send,
// иначе паника "send on closed channel" (SEC-05). НЕ закрывать канал сообщений здесь.
close(h.done)
```

Реальный аналог из `backend/internal/ws/handler.go` (написан ПОСЛЕ того, как в проде была паника — комментарий описывает, почему именно так, а не «как удобнее»):

```go
// SEC-05: канал client.send больше НЕ закрывается со стороны Hub — сигналом
// завершения служит исключительно client.done. Это устраняет панику
// "send on closed channel" в параллельных producer'ах (Bridge/handler).
func writePump(conn *websocket.Conn, client *Client) {
```

и в другом месте того же файла:

```go
case TypePing:
    pong := ServerMessage{Type: TypePong}
    data, _ := json.Marshal(pong)
    // SEC-05: client.send никогда не закрывается, но проверяем done,
    // чтобы не писать в send после Unregister.
    select {
    case <-client.done:
    case client.send <- data:
    default:
    }
```

Это учебный пример: один SEC-ID процитирован в трёх местах одного файла — на объявлении функции, на закрытии канала и на попытке записи. Так инвариант виден в каждой точке, где его легко нарушить при будущей правке.

### 3.4. Ссылка на требование/безопасность

```go
// Сравнение секретов постоянным временем — защита от timing-атаки (NF-12, security_guidelines.md).
if subtle.ConstantTimeCompare(got, want) != 1 {
    return apperrors.Unauthorized("invalid code")
}
```

Реальный код из `backend/internal/auth/magiclink.go` — тот же паттерн с собственным SEC-ID:

```go
// SEC-07: constant-time compare — защита от timing side-channel при подборе кода.
if subtle.ConstantTimeCompare([]byte(stored), []byte(code)) != 1 {
    s.recordFailure(ctx, failsKey)
    return ErrMagicLinkInvalid
}
```

Аналогичные примеры из других модулей — единая конвенция «SEC-ID + короткое объяснение угрозы» повторяется по всей кодовой базе:

```go
// backend/internal/notification/push.go
// SEC-H3: defense-in-depth — endpoint валидируется ещё раз перед отправкой,

// backend/internal/gitlab/service.go
// SEC-04: отклоняем file://, userinfo и прочие не-http(s) URL до сохранения

// backend/internal/storage/filename.go
// sanitizeFilename убирает path-компоненты и небезопасные символы (NF-09).

// backend/internal/ai/content_policy.go
// CheckContentPolicy сканирует messages на injection/abuse (SEC-R8).
```

### 3.5. Предупреждение о грани

```typescript
// staleTime=0: список непрочитанных должен быть максимально свежим,
// т.к. бейдж влияет на поведение пользователя. Осознанно жертвуем кэшем.
useQuery({ queryKey: ['unread'], queryFn: getUnread, staleTime: 0 })
```

### 3.6. «Почему НЕ сделано иначе»

```go
// Не используем ent hook для этого: hook не видит контекст запроса (request_id),
// а нам нужен корреляционный лог. Публикуем событие явно в сервисе.
```

### 3.7. Нестандартный порядок вызовов (реальный пример из `tracker/handler.go`)

Иногда самое ценное — предупредить о неочевидном порядке аргументов API фреймворка, который легко перепутать при копипасте:

```go
// RegisterRoutes регистрирует все маршруты трекера под /api/projects/:projectId.
// authMw — middleware аутентификации, rbacSvc используется для проверки прав доступа.
//
// ВАЖНО (Fiber v3): Post(path, handler, ...middleware) — variadic middleware выполняются
// ПЕРЕД handler. RBAC передаётся после handler: route.Post(path, h.Handler, rbac.RequirePermission(...)).
// См. tms/handler.go и .planning/audits/2026-06/FA-RBAC-FIBER3-AUDIT.md (FA-02-02).
func (h *Handler) RegisterRoutes(api fiber.Router, authMw fiber.Handler, rbacSvc *rbac.RBACService) {
```

Это образцовый комментарий: объясняет неинтуитивную деталь конкретной версии фреймворка (Fiber v3 middleware после handler — большинство фреймворков делает наоборот), даёт правильный шаблон вызова и ссылается на аудит, который нашёл баг из-за этой путаницы (FA-02-02). Без этого комментария следующий разработчик почти гарантированно расположит RBAC-проверку неправильно.

### 3.8. Комментарий, объясняющий архитектурный слой сразу над структурой

```go
// backend/internal/tracker/handler.go
// Handler предоставляет HTTP-обработчики для модуля трекера задач.
type Handler struct {
    service    *TrackerService
    automation *AutomationService
}
```

Короткий godoc над структурой — не пересказ полей (поля самодостаточны по именам), а фиксация роли типа в слоистой архитектуре (`handler*.go` — HTTP-слой, см. `backend.md` §2).

## 4. Go: документирующие комментарии (godoc)

### 4.1. Package doc

Каждый нетривиальный пакет — с package doc. В Hub допустима русская проза (термины/идентификаторы английские), как в реальных пакетах репозитория:

```go
// Package tracker реализует трекер задач: CRUD, Kanban-доски, workflow, комментарии, учёт времени.
package tracker
```

```go
// Package auth реализует аутентификацию через Magic Link и Telegram, управление JWT-сессиями и профилями пользователей.
package auth
```

```go
// Package ws содержит WebSocket hub, клиентские подключения и broadcast-логику реального времени.
package ws
```

Другие реальные package doc из репозитория — обратите внимание, что каждый описывает **зону ответственности**, а не пересказывает импорты:

```go
// Package rbac реализует ролевое управление доступом: системные и кастомные роли, права, кеширование.
// Package storage реализует файловое хранилище через S3-совместимый бэкенд (SeaweedFS).
// Package search реализует глобальный полнотекстовый поиск по PostgreSQL (tsvector) и MongoDB ($text).
// Package backup реализует резервное копирование и восстановление данных (PostgreSQL + MongoDB + SeaweedFS).
// Package observability предоставляет обёртки для измерения времени операций.
```

### 4.2. Godoc экспортируемых сущностей

Godoc начинается с имени сущности и объясняет **контракт**: что гарантирует, какие ошибки, побочные эффекты.

```go
// CreateIssue создаёт задачу в проекте и присваивает issue_key вида <KEY>-<N>.
// Возвращает apperrors.NotFound, если проект не найден, и apperrors.Conflict
// при нарушении оптимистичной блокировки. Публикует событие hub.issues.created.
func (s *Service) CreateIssue(ctx context.Context, projectID uuid.UUID, in CreateIssueInput) (*ent.Issue, error)
```

Реальные примеры годного контрактного godoc из репозитория (обратите внимание — каждый объясняет формат/эффект, не повторяет имя):

```go
// FindIssueByKey возвращает задачу по её ключу (например "HUB-1") с eager loading связей.
// GetIssue возвращает задачу по ключу (например "HUB-1").
// FindTestCaseByKey возвращает тест-кейс по ключу (например "HUB-TC-42").
```

Все три однострочных godoc-а объединяет общий приём: сразу дают **пример формата** (`"HUB-1"`, `"HUB-TC-42"`) — это не очевидно из подписи функции (`string`), но критично для читателя, который не угадает формат ключа без примера.

```go
// ❌ Плохо: godoc-«эхо» имени, без контракта
// CreateIssue creates an issue.
func (s *Service) CreateIssue(...)
```

### 4.3. Deprecated

```go
// Deprecated: используйте CreateIssueV2 — этот метод не поддерживает custom fields.
// Будет удалён после HUB-500.
func (s *Service) CreateIssue(...)
```

### 4.4. Комментарий к сложному алгоритму

Разбивай алгоритм на смысловые шаги с *почему*, а не *что*:

```go
// JQL транслируем в предикаты Ent в два прохода: сначала строим AST (валидация
// синтаксиса и полей — ошибки понятны пользователю), затем маппим в predicate.
// Одним проходом нельзя: часть полей — computed и требует join, известный только после разбора.
```

Реальный алгоритмический комментарий из `backend/internal/tms/allure_matcher.go`, объясняющий стратегию сопоставления автотестов с тест-кейсами (несколько уровней fallback):

```go
// caseKeyInNameRegex ищет ключ тест-кейса вида PROJ-TC-123 в имени автотеста.
// Алгоритм: паттерн UpperCase-TC-Number с границами слов.
```
и в другом месте того же файла:
```go
// Стратегия 2.7: case_key в имени теста — ищем паттерн PROJ-TC-123
```
где нумерация («Стратегия 2.7») отсылает к общему списку стратегий сопоставления, описанному выше в файле — паттерн полезен, когда алгоритм состоит из упорядоченного набора fallback-эвристик.

### 4.5. Комментарий на служебном билд-теге (тест-хелперы, исключение из общей политики)

```go
//go:build hubtest

// Package auth — test export hooks for backend/testframework/auth/ (not compiled in release builds).
package auth
```

Это осознанное исключение: файл собирается только под тег `hubtest` (тестовая сборка, не release), комментарий на английском допустим как техническая пометка «это не прод-код» (аналогично `// biome-ignore`, см. §8). Не путать с package doc обычных production-пакетов — там русская проза обязательна.

### 4.6. Example-функции

Для публичного API полезны `ExampleXxx` — они и документация, и тест.

## 5. Swagger-аннотации (handler-слой)

Swagger-комментарии — единственное системное исключение из правила «код говорит что, комментарий почему»: они описывают контракт API для внешних потребителей (frontend, интеграции), а не внутреннее намерение кода. Обязательны на каждом exported HTTP-хендлере.

Реальный пример из `backend/internal/tracker/handler_links.go`:

```go
// CreateIssueLink — Создать связь между задачами
// @Summary Создать связь между задачами
// @Description Создаёт связь (блокирует, связана с, дублирует) между двумя задачами.
// @Tags Трекер
// @Accept json
// @Produce json
// @Param projectId path string true "ID проекта"
// @Param issueKey path string true "Ключ задачи"
// @Success 201 {object} IssueLinkResponse
// @Failure 400 {object} fiber.Error "Некорректный запрос"
// @Failure 403 {object} fiber.Error "Нет доступа"
// @Security BearerAuth
// @Router /api/projects/{projectId}/issues/{issueKey}/links [post]
func (h *Handler) CreateIssueLink(c fiber.Ctx) error {
```

### 5.1. Правила Swagger в Hub

- `@Summary`/`@Description`/`@Tags` — на русском (соответствует RU-COMMENTS, §8); поля протокола (`@Param`, `@Success`, `@Router`, имена типов) — по спецификации swaggo, менять нельзя.
- `@Router` путь должен **точно** совпадать с реальным маршрутом в `RegisterRoutes` — рассинхрон находит `docs-writer` при sync (`.cursor/rules/55-docs-sync.mdc`) и `sa-ver` при верификации API-контрактов.
- Каждый `@Failure` — реально возвращаемый код ошибки, а не «на всякий случай» весь список HTTP-кодов.
- Первая строка (`// CreateIssueLink — Создать связь между задачами`) дублирует `@Summary` намеренно — это одновременно валидный godoc (§4.2) и первая строка Swagger-блока; дублирование здесь не мусор, а конвенция инструмента.

## 6. TypeScript/React (TSDoc)

### 6.1. TSDoc там, где добавляет смысл

```typescript
/**
 * Одновременный refresh access-токена: если запрос уже идёт, ждём его,
 * а не шлём второй (иначе гонка отзовёт свежий refresh). Single-flight.
 */
async function refreshOnce(): Promise<string> { /* ... */ }
```

Реальный образцовый пример из `frontend/src/stores/auth-store.ts` — TSDoc на уровне интерфейса объясняет побочный эффект персиста, которого не видно из типа:

```typescript
/**
 * Состояние стора аутентификации.
 * Персистится в sessionStorage под ключом "hub-auth".
 * Сессия завершается при закрытии вкладки/браузера.
 */
interface AuthState {
	/** JWT access-токен для авторизации API-запросов. */
	accessToken: string | null;
	/** Refresh-токен для обновления access-токена. */
	refreshToken: string | null;
	...
}
```

Обратите внимание: комментарии на полях (`/** JWT access-токен... */`) не пересказывают тип (`string | null` виден и так) — они объясняют **роль** поля в домене (какой именно токен, для чего используется). Это разница между хорошим и «мусорным» инлайн-комментарием на поле.

Там же — образцовый комментарий-объяснение архитектурного решения перед сложным механизмом (multi-tab sync через `BroadcastChannel`):

```typescript
/**
 * Multi-tab синхронизация login/logout через BroadcastChannel (FE-H2).
 *
 * Когда пользователь делает login/logout в одной вкладке, событие
 * транслируется в другие вкладки того же origin. Это позволяет:
 *  - очистить TanStack Query cache при logout (см. useAuthSync в _authenticated.tsx)
 *  - переключить вкладку на страницу логина / главную при login
 *
 * Реализовано через BroadcastChannel API (есть в Chromium/Firefox/Safari 15.4+).
 * Если API недоступен — sync молча отключается (single-tab fallback).
 */
const AUTH_CHANNEL_NAME = "hub-auth";
```

Это образец «почему так, а не иначе» на уровне модуля: объясняет мотивацию (зачем sync), альтернативу с graceful degradation (fallback без API) и даёт ссылку на потребителя механизма (`useAuthSync`), не пересказывая сам код ниже.

### 6.3. Короткий TSDoc над каждым полем/методом хука (реальный пример из `gif-picker.tsx`)

Компонент `GifPicker` (`frontend/src/components/messenger/gif-picker.tsx`) — хороший образец плотной, но не шумной документации: каждая константа и метод хука снабжён однострочным TSDoc, объясняющим роль, а не тип:

```typescript
/** Объект GIF из ответа Giphy API. */
interface GiphyGif {
	/** Фиксированная ширина для превью в сетке. */
	...
	/** Оригинальный GIF для отправки. */
	...
	/** Маленькое неподвижное превью для lazy-загрузки. */
	...
}

/** Ключ Giphy API из переменных окружения. */
const GIPHY_API_KEY = ...
/** Базовый URL Giphy API. */
const GIPHY_BASE_URL = ...
/** Количество GIF на один запрос. */
const GIPHY_LIMIT = ...
/** Задержка дебаунса поиска (мс). */
const SEARCH_DEBOUNCE_MS = ...

/** Загрузить trending GIFs. */
async function fetchTrending() { ... }
/** Поиск GIF по запросу. */
async function searchGifs(query: string) { ... }
/** Отменить текущий запрос при размонтировании. */
useEffect(() => { ... }, []);
```

Это пограничный, но допустимый стиль: каждый комментарий добавляет контекст использования («для чего эта константа», «когда вызывается этот метод»), а не повторяет имя переменной. Если бы комментарий был `/** GIPHY_LIMIT — лимит */`, это стало бы пересказом (запрещено, §2.1) — здесь же «Количество GIF на один запрос» объясняет семантику числа в контексте API.

`any` без причины запрещён. Если неизбежен — комментарий с причиной:

```typescript
// any: тип приходит из стороннего editor SDK без типов; сузим после апгрейда до v3.

```

### 6.5. `biome-ignore` — реальный формат Hub (единственное системное исключение из русскоязычной политики)

Hub использует Biome (не ESLint) для линтинга фронтенда. Комментарий подавления линта пишется по формату Biome и **допустим на английском** — это зафиксированное исключение RU-COMMENTS (см. §8), т.к. текст после `biome-ignore` — часть синтаксиса инструмента, а не свободная проза:

```typescript
// biome-ignore lint/style/noNonNullAssertion: getMonthGridDays always returns >=35 days
const day = days[i]!;

// biome-ignore lint/style/noNonNullAssertion: PRIORITY_CONFIG.medium is always defined
const priorityCfg = (PRIORITY_CONFIG[tc.priority] ?? PRIORITY_CONFIG.medium)!;
```

Обратите внимание на паттерн: причина всегда объясняет **почему non-null безопасен** (инвариант данных: массив длины ≥35, дефолтный конфиг всегда определён), а не просто «нужно для типов». Это делает возможным будущий ревью: если инвариант перестанет быть верным, комментарий явно укажет, что проверить.

`useExhaustiveDependencies` — тот же принцип, но обычно комбинируется с русским комментарием-объяснением ПЕРЕД `biome-ignore` (сам биом-комментарий на английском, а объяснение решения — на русском, это две разные вещи):

```typescript
// Сброс пагинации при смене категории корзины — `activeTab`
// намеренный триггер effect, а не значение из тела effect.
// biome-ignore lint/correctness/useExhaustiveDependencies: effect intentionally re-runs only on activeTab change to reset pagination.
useEffect(() => {
	setPage(1);
}, [activeTab]);
```

```typescript
/** Авто-скролл при новых сообщениях. */
// biome-ignore lint/correctness/useExhaustiveDependencies: messages.length is the intentional re-run trigger; the scrollHeight read is imperative.
useEffect(() => {
	scrollRef.current?.scrollTo({ top: scrollRef.current.scrollHeight });
}, [messages.length]);
```

**Правило:** русский TSDoc/обычный комментарий над эффектом — обязателен и объясняет намерение (§8); строка `biome-ignore ...: <reason>` — техническая, на английском, по формату инструмента, и не заменяет объяснение выше.

### 6.6. Неочевидные a11y-решения

```tsx
// role="status" + aria-live: скринридер должен озвучить появление тоста,
// но не перехватывать фокус. Поэтому не button и не alertdialog.
<div role="status" aria-live="polite">{message}</div>
```

Реальные примеры `role="status"` для индикаторов загрузки встречаются по всему фронтенду Hub (`query-state-view.tsx`, `command-palette.tsx`, `org-directory.tsx`, модули `crm`/`hr`/`calendar`) — конвенция сама по себе не всегда требует отдельного комментария (она стандартна и повторяема), но **первое** появление паттерна в модуле или нестандартная комбинация (как в примере выше — почему не `alertdialog`) — комментировать нужно.

## 7. Комментарии в тестах

Тест — тоже документация. В Hub принято:

### 7.1. Package doc теста + описание сценария

```go
// Package tracker_test проверяет TrackerService: типы задач, optimistic locking,
// workflow-переходы, курсорную пагинацию. Мокаем Repository; БД не поднимаем.
package tracker_test
```

### 7.2. Привязка к тест-кейсу и требованию

Каждый значимый тест ссылается на TC-ID из `docs/TESTING.md` и/или требование — это часть трассируемости требование→TC→автотест:

```go
// TC-TRCK-04: конфликт версий. Требование: FR-TRCK-12 (optimistic locking).
// Проверяем, что update со старой version возвращает Conflict, а не молча перезаписывает.
func TestUpdateIssueOptimisticLocking(t *testing.T) { /* ... */ }
```

```typescript
// TC-AUTH-12: logout отзывает refresh. См. docs/TESTING.md.
test('logout revokes refresh token', async ({ page }) => { /* ... */ })
```

Реальный пример из истории коммитов Hub, привязывающий и тест, и коммит к TC-ID одновременно:
```
test(auth): cover magic-link brute-force lockout (TC-AUTH-10)
```
Ссылка на TC-ID в сообщении коммита не заменяет комментарий внутри теста — это два независимых уровня трассируемости (git история + код), оба нужны.

### 7.3. Объяснять «почему важно», а не «что делает assert»

```go
// ❌ Плохо
assert.Equal(t, 2, issue.Version) // version равен 2

// ✅ Хорошо: почему это важно
// После успешного update version обязан инкрементироваться — иначе следующий
// клиент со старой версией перезапишет данные (нарушение optimistic locking).
assert.Equal(t, 2, issue.Version)
```

### 7.4. Тестовые хелперы, экспортируемые только под build-тегом

Как показано в §4.5, файлы вида `export_hooks.go` открывают внутренние методы для `testframework/` через тонкие обёртки:

```go
//go:build hubtest

// Package notification — тестовые export-хуки для backend/testframework/ (не компилируются в release-сборках).
package notification

func ExportHandleLogin(t *TelegramBotAuth, ctx context.Context, msg *telego.Message) {
	t.handleLogin(ctx, msg)
}
```

Комментарий у самой функции-обёртки обычно не нужен (она самодостаточна по имени `ExportXxx` + однострочное тело) — но package doc обязателен и объясняет, что файл существует только для тестовой видимости приватных методов, а не является частью публичного API модуля.

## 8. Политика языка комментариев (RU-COMMENTS)

Hub прошёл целевую волну русификации комментариев и docs-прозы (`.planning/archive/tasks/TASKS-RU-COMMENTS-DOCS.md`, верифицировано в `.planning/audits/2026-06/RU-V-REPORT.md`). Итоговое правило:

**Проза комментариев — русский. Идентификаторы, типы, ключевые слова кода — английские** (не переводим `func`, `interface`, названия переменных/типов).

### 8.1. Зафиксированные исключения (единственные допустимые случаи английской прозы в комментариях)

| Исключение | Пример | Почему |
|---|---|---|
| `@swagger`/swaggo служебные теги | `@Param`, `@Router`, `@Success` | Синтаксис инструмента, не проза |
| URL | `см. livekit/livekit#4821` | Ссылки не переводятся |
| Имена полей API/JSON-ключи | `entity_id`, `issue_key` | Контракт данных |
| `@example` JSON-блоки | тело примера запроса/ответа | Данные, не проза |
| `// biome-ignore ...: reason` | см. §6.5 | Синтаксис линтера Biome |
| Generated files | код, сгенерированный `ent generate`, `swag init` | Не редактируется вручную |
| Заголовки разделов с именем продукта | `// Hub API`, названия брендов | Собственные имена не переводятся |
| Build-tag-guarded тест-хелперы (`export_hooks.go`) | см. §4.5, §7.4 | Технический маркер «не прод-код», не смысловая проза |

Всё остальное — обязательно на русском: godoc, TSDoc, инлайн-объяснения, package doc, комментарии в тестах, PR-описания (описания коммитов допустимо оставлять по конвенции Conventional Commits на английском для типа/scope — это формат git-workflow, см. `git-workflow.md` §3, но тело коммита с объяснением *почему* в Hub принято писать по-русски там, где это не мешает читаемости истории).

### 8.2. Практический пример перехода (было → стало)

```go
// ❌ Было (до волны русификации)
// CreateIssue creates a new issue and assigns it a project-scoped issue key.

// ✅ Стало
// CreateIssue создаёт задачу в проекте и присваивает issue_key вида <KEY>-<N>.
```

### 8.3. Как проверить соответствие перед PR

```bash
# Быстрый скан на остаточную английскую прозу в комментариях (эвристика, не 100% точность)
rg -n "^\s*//\s*[A-Z][a-zA-Z]+\s+[a-z]+\s+[a-z]+" backend/internal/<module> --glob '!*_test.go'
```
Ложные срабатывания (Swagger/URL/build-tag файлы) — отфильтровать вручную по таблице §8.1.

## 9. Запрет emoji и визуального шума

- **Без эмодзи** в коде и комментариях (rule 10) — ни в проде, ни в тестах, ни в TODO.
- Исключение — этот и другие playbook/rule-документы, где ✅/❌ используются как разметка примеров «хорошо/плохо» (не код, а документация о коде).
- Тон нейтральный, по делу; без шуток, которые устареют.
- Консистентность в пределах модуля: не смешивай стили без нужды (например, не чередуй `//` и `/* */` в одном файле без причины).
- Комментарий располагается **над** кодом, к которому относится; инлайн — только для короткого пояснения к строке (как большинство SEC-ID примеров в §3.4).

## 10. Что в коде, что во внешней документации

| В коде (комментарий) | Во внешних docs |
|----------------------|-----------------|
| Локальный *почему*, инвариант, обход бага | Архитектура, C4, потоки |
| Контракт функции (godoc/TSDoc) | API-спека (`system_specification.md`, `wiki/API.md`) |
| Swagger-аннотация конкретного эндпоинта | Сводная таблица всех эндпоинтов в `wiki/API.md` |
| Привязка теста к TC | Таблица TC↔автотест (`docs/TESTING.md`) |
| Ссылка на ADR/SEC-ID | Сам ADR (`.planning/decisions/`) |

Не дублируй в коде то, что живёт в docs — ставь ссылку (ID/файл), а не копию. Пример правильной ссылки без дублирования содержания:

```go
// Сравнение секретов постоянным временем — защита от timing-атаки (NF-12, security_guidelines.md).
```
Комментарий не пересказывает содержимое `security_guidelines.md`, а даёт координаты, где искать полное объяснение угрозы NF-12.

## 11. Разбор реального файла: хорошо и плохо рядом

Возьмём `backend/internal/tracker/handler.go` как эталон того, какие комментарии нужны handler-слою, а какие были бы избыточны, если бы их добавили.

<good-example>

Реальные комментарии файла — каждый группирует маршруты по бизнес-смыслу, а не пересказывает вызов `Post`/`Get`:

```go
// Задачи
issues := tracker.Group("/issues")
issues.Post("/", h.CreateIssue, rbac.RequirePermission(rbac.PermTaskCreate, rbacSvc))

// JQL-поиск задач
issues.Post("/jql", h.SearchIssuesJQL, rbac.RequirePermission(rbac.PermProjectView, rbacSvc))

// Связи задача ↔ тред мессенджера (PROD-03)
issues.Get("/:issueKey/message-links", h.ListIssueMessageLinks, ...)
```

`// Связи задача ↔ тред мессенджера (PROD-03)` — не «регистрируем маршрут» (очевидно из кода), а объясняет **зачем** эта группа маршрутов существует (кросс-модульная фича, ссылка на тикет PROD-03), что не считывается из одной строки `issues.Get(...)`.
</good-example>

<bad-example>

Гипотетическая избыточная версия того же файла (антипример, НЕ из репозитория — так писать нельзя):

```go
// Регистрируем POST маршрут для создания задачи
issues.Post("/", h.CreateIssue, rbac.RequirePermission(rbac.PermTaskCreate, rbacSvc))
// Регистрируем GET маршрут для получения списка задач
issues.Get("/", h.ListIssues, rbac.RequirePermission(rbac.PermProjectView, rbacSvc))
// Регистрируем GET маршрут для получения одной задачи по ключу
issues.Get("/:issueKey", h.GetIssue, rbac.RequirePermission(rbac.PermProjectView, rbacSvc))
```

Каждая строка комментария пересказывает HTTP-метод и путь, которые уже видны в вызове. Это шум: 20 таких строк в файле с 40+ маршрутами не добавляют ни одного бита новой информации и будут игнорироваться при чтении.
</bad-example>

**Вывод:** комментарий на группу маршрутов — да, если объясняет бизнес-смысл/связь с тикетом; комментарий на каждую строку маршрута — нет, если он лишь называет HTTP-метод.

## 12. Антипаттерны (сводка)

| Нельзя | Почему | Как правильно |
|--------|--------|---------------|
| `// increment counter` | Пересказ кода, шум | Удалить |
| Закомментированный код | Мёртвый груз, путает | Удалить (есть git) |
| `// TODO: fix later` | Вечный, бесполезный | `TODO(HUB-XXX): суть + условие` |
| godoc = имя функции | Не добавляет смысла | Описать контракт/ошибки (см. §4.2) |
| Комментарий врёт коду | Хуже отсутствия | Обновить/удалить в том же коммите |
| `any` без причины | Теряется типобезопасность | Убрать или `// причина` |
| Assert-«эхо» в тесте | Не объясняет ценность | Объяснить инвариант/риск |
| Эмодзи в коде | Запрещено rule 10 | Убрать |
| Комментарий на каждой строке маршрута/CRUD-метода | Шум, пересказ HTTP-глагола | Комментарий на смысловую группу (§11) |
| Английская проза в godoc/TSDoc вне списка исключений §8.1 | Нарушает RU-COMMENTS | Перевести на русский |
| `@Router` не совпадает с реальным путём | Drift API-докой | Синхронизировать при каждом изменении маршрута |
| Комментарий вместо реальной валидации | Ложное чувство безопасности | Добавить код-проверку инварианта |
