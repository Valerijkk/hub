# Hub — Playbook: Дизайн и дизайн-система

> Эталонный playbook для агентов `designer`, `designer-ver`, `fe1`, `fe2`, `fe-ver`.
> Источник истины по дизайн-системе: `frontend/src/app.css`. Правила: `.cursor/rules/30-frontend.mdc`.
> Ограничения ТЗ: `.cursor/rules/60-tz-constraints.mdc` · `docs/tz_constraints.md`.
> Персоны и UX-контекст: `docs/vision_and_scope.md` · `docs/user_needs_analysis_2026.md`.
>
> **Ключевой принцип:** дизайн Hub — это не картинки, а токены. Любой пиксель, цвет, отступ или радиус
> должен ссылаться на переменную из `app.css`. Хардкод цвета `#1a1a1a` — это баг, а не решение.

## 1.1 Общая карта ролей

Дизайн в Hub закрывают три типа агентов, работающих в конвейере:

```
product / ba / sa           designer            designer-ver          fe1 / fe2         fe-ver
    (требования)   ──────►  (дизайн-спека) ────►  (верификация) ───►  (реализация) ───► (верификация UI)
       US / AC              токены + макет        консистентность      React + Shadcn     a11y + Lighthouse
                            состояния + a11y      a11y + responsive     className-only     visual diff
```

| Агент | Маршрутизация | Роль | Артефакт | Читает | Пишет |
|-------|---------------|------|----------|--------|-------|
| `designer` | `inherit` (routed; max effort) | Дизайн-система, макеты, UX-спеки, токены | Дизайн-спека (Markdown), обновления `app.css`-токенов | `vision_and_scope.md`, `30-frontend.mdc`, `app.css`, US/AC от `ba`/`sa` | `.cursor/playbooks/`-совместимые спеки, DESIGN-SPEC.md фазы |
| `designer-ver` | `inherit` (routed; max effort) | Независимая верификация дизайна | Отчёт верификации `verified: true/false` + лог | Спека `designer`, `app.css`, реализацию `fe` | Verification report |
| `fe1`, `fe2` | `inherit` (routed; max effort) | Реализация UI по спеке | React-компоненты, `className`-расширения Shadcn | DESIGN-SPEC, `30-frontend.mdc`, Shadcn `components/ui/*` | `frontend/src/**` |
| `fe-ver` | `inherit` (routed; max effort) | Верификация реализации UI | Отчёт: a11y (axe), Lighthouse, visual, регрессия | Реализацию `fe`, спеку `designer` | Verification report |

> `team-lead` (GPT-5.6 Sol Pro; downstream — catalog-backed routing по
> `team-workflow.md` §1.1) — оркестратор и финальная инстанция приёмки. Он не рисует, но принимает
> дизайн-артефакт целиком после `designer-ver` и `fe-ver`. См. `.cursor/playbooks/team-workflow.md`.
## 1.2 Когда включается `designer`

`designer` подключается **до** `fe`, когда задача содержит любой из триггеров:

- Новый экран / страница / модальное окно, которого нет в текущем UI.
- Новый переиспользуемый компонент (не просто композиция существующих Shadcn).
- Изменение дизайн-системы: новый токен, цвет, spacing-шаг, радиус, тень, состояние.
- Изменение паттерна взаимодействия (навигация, hotkey-контур, плотность).
- Редизайн существующего экрана (например «привести Kanban к макету»).
- Любая задача с явным UX/визуальным acceptance criteria в US.

`designer` **не** нужен для:

- Багфикса верстки без изменения дизайн-контракта (например «кнопка съехала на 2px»).
- Технического рефакторинга компонентов без визуальных изменений.
- Правки текста / i18n без изменения раскладки.

В этих случаях `fe` работает напрямую, а `fe-ver` проверяет отсутствие визуальной регрессии.
## 1.3 Что делает `designer` (обязанности)

1. **Хранит и развивает дизайн-систему** — токены в `frontend/src/app.css`. Любое новое значение
   (цвет, spacing, радиус, тень) добавляется как токен, а не как inline-хардкод в компоненте.
2. **Пишет дизайн-спеки** — текстовые (Markdown) спеки для `fe`, потому что Figma в проекте нет.
   Спека = структура компонентов + токены + состояния + поведение + a11y + edge-cases (см. §6).
3. **Определяет UX-контракт** — иерархия, отступы, плотность, состояния (loading/empty/error),
   микро-взаимодействия, отзывчивость (breakpoints).
4. **Гарантирует доступность на уровне дизайна** — контраст, focus, размеры целей, keyboard-first (см. §5).
5. **Обеспечивает консистентность** — новый экран визуально неотличим от существующих: те же токены,
   те же радиусы, те же тени, та же типографика.
## 1.4 Что делает `designer-ver` (верификация)

`designer-ver` — независимый агент. Он **не** доверяет спеке `designer` на слово, а проверяет её по коду
(`app.css`, `components/ui/*`) и по чек-листам §7. Ставит `verified: true` только когда:

- все токены в спеке существуют в `app.css` (нет выдуманных переменных);
- контраст пар «текст / фон» рассчитан и проходит 4.5:1 (текст) / 3:1 (UI);
- описаны все состояния (default/hover/active/focus/disabled + loading/empty/error);
- заданы breakpoints и mobile-поведение;
- нет запрещённых паттернов (§9): хардкод цветов, inline-стили, `!important`, произвольные отступы.
## 1.5 Передача спеки в `fe` (handoff)

Handoff `designer → fe` — это короткое, понятное сообщение (2–5 предложений) + артефакт-спека. Формат
handoff описан в `.cursor/playbooks/team-workflow.md` §9. Минимум:

```
Что сделано: дизайн-спека экрана "Sprint Backlog" — структура, токены, 5 состояний, a11y.
Что проверить fe: реализовать по DESIGN-SPEC-sprint-backlog.md, только className для Shadcn.
Артефакты: DESIGN-SPEC-sprint-backlog.md (структура + токены + состояния).
Следующий шаг: fe1 верстает список, fe2 — панель фильтров (разные файлы, без конфликтов).
```

### Good / Bad — момент включения `designer`

**Good:** задача «Добавить экран настроек уведомлений» → `designer` пишет спеку с токенами и состояниями
→ `designer-ver` проверяет → `fe` реализует → `fe-ver` сверяет с спекой. Дизайн-контракт зафиксирован
до кода.

**Bad:** `fe` сразу верстает экран «на глаз», подбирая цвета `#191a20` руками. Результат: рассинхрон с
дизайн-системой, `fe-ver` заворачивает, переделка. Потеряно время команды.

### Чек-лист роли (§1)

- [ ] Определён триггер: нужен ли `designer` вообще (§1.2).
- [ ] Загружены `vision_and_scope.md`, `30-frontend.mdc`, `app.css`.
- [ ] Ясен потребитель спеки: `fe1`/`fe2` и как разделить работу без конфликтов.
- [ ] Handoff написан простым языком (2–5 предложений) + приложен артефакт-спека.

## 3.1 Что уже есть в `frontend/src/components/ui/`

> существующих примитивов — предпочтительнее нового компонента.
## 3.2 Золотое правило: только `className`, не трогать Radix

Из `.cursor/rules/30-frontend.mdc` и `60-tz-constraints.mdc`:

> Shadcn компоненты: только `className` изменения, поведение Radix не трогать. Без inline-стилей, без `!important`.

Практически это значит:

- Разрешено: передавать `className` для визуальной подстройки (цвет, отступ, размер токенами).
- Разрешено: добавлять варианты через `cva` в самом компоненте (см. `button.tsx`).
- Запрещено: менять пропсы Radix, отключать `onOpenChange`, переопределять `data-state`-поведение,
  вручную управлять фокусом там, где Radix уже управляет.
- Запрещено: `style={{...}}` поверх дизайн-системы и `!important`.

### Good / Bad — расширение Shadcn

**Good:**

```tsx
// Только className, токены дизайн-системы
<Button variant="secondary" className="w-full mt-4">
  Пригласить участника
</Button>

// Новый вариант — через cva внутри button.tsx (не inline)
// variants.variant.subtle: "bg-[var(--hover)] text-t2 hover:text-t1"
```

**Bad:**

```tsx
// Inline-стиль поверх системы
<Button style={{ backgroundColor: "#5b9cf5", borderRadius: 20 }}>Ок</Button>

// !important, чтобы "перебить" Shadcn
<Dialog className="!bg-black !p-0" />

// Вмешательство в поведение Radix
<DialogPrimitive.Content onEscapeKeyDown={(e) => e.preventDefault() /* ломает UX */} />
```
## 3.3 Варианты через `cva` (class-variance-authority)

Hub задаёт варианты декларативно через `cva`. Пример из `button.tsx`:

```tsx
const buttonVariants = cva("base classes...", {
  variants: {
    variant: {
      default: "bg-gradient-to-br from-[var(--blueS)] to-[var(--blue)] text-white ...",
      destructive: "bg-gradient-to-br from-[var(--redS)] to-[var(--red)] ...",
      outline: "border border-b1 bg-transparent hover:bg-[var(--hover)] ...",
      secondary: "bg-raised text-t2 border border-b1 ...",
      ghost: "hover:bg-[var(--hover)] hover:text-accent-foreground",
      link: "text-primary underline-offset-4 hover:underline",
    },
    size: { default: "h-10 px-4 py-2", sm: "h-9 px-3", lg: "h-11 px-8", icon: "h-10 w-10" },
  },
  defaultVariants: { variant: "default", size: "default" },
});
```

**Правила для новых вариантов:**

- Новый визуальный вариант добавляется **в `variants`**, а не как ад-хок `className` на месте вызова.
- Каждый вариант использует только токены. Никаких HEX.
- Имена вариантов семантические (`destructive`, `subtle`), не по цвету (`redButton`).
- `defaultVariants` обязателен.
## 3.4 Консистентность компонентов

Матрица консистентности, которую держит `designer` и проверяет `designer-ver`:

| Ось | Правило |
|---|---|
| Кнопки | Всегда `<Button>` из Shadcn; primary CTA = `variant="default"`, отмена = `variant="ghost"`/`outline`, удаление = `variant="destructive"`. |
| Поля | Всегда `<Input>`/`<Textarea>` + `<Label>` через `FormField`; высота инпута 42px (`h-[42px]`). |
| Модалки | `<Dialog>` для форм, `<AlertDialog>`/`<ConfirmDialog>` для подтверждений, `<Sheet>` для боковых панелей. |
| Пустые состояния | Всегда `<EmptyState>` (иконка + title + description), не «самодельный» div. |
| Ошибки модулей | Каждый крупный модуль обёрнут `<ErrorBoundary>` (calls, dashboard, tracker, TMS, messenger). |
| Бейджи статусов | `<Badge variant>` или `.badge-*` классы для TMS/трекера (passed/failed/skipped/broken/blocked). |
| Скролл | `<ScrollArea>` для кастомных областей; глобальный скроллбар 5px уже стилизован. |

### Чек-лист компонентов (§3)

- [ ] Проверено, нет ли уже нужного примитива в `components/ui/*`.
- [ ] Расширение только через `className` (токены) или `cva`-вариант.
- [ ] Поведение Radix не изменено; нет `style={}`; нет `!important`.
- [ ] Новые варианты семантически названы и покрывают состояния.
- [ ] Пустые состояния через `EmptyState`, ошибки через `ErrorBoundary`.

# 4. UX-принципы
## 4.1 Иерархия

Пользователь должен за 1–2 секунды понять «что здесь главное». Инструменты иерархии в Hub:

- **Цвет текста:** `--t1` (главное) → `--t2` (вторичное) → `--t3` (метаданные). Не выделяйте всё жирным.
- **Поверхности:** важный блок — на `--card` с тенью `--sh1`; фон — `--base`; акцентная зона — `--raised`.
- **Размер:** один H1/`text-2xl` на экран; секции — `text-lg`; body — `text-sm`.
- **Акцент:** ровно один primary CTA в видимой области. Остальные действия — `secondary`/`ghost`.

### Good / Bad — иерархия

**Good:** на карточке задачи заголовок `text-t1 font-semibold`, статус — бейдж, метаданные (автор, дата)
— `text-t3 text-xs`. Взгляд идёт сверху вниз по важности.

**Bad:** заголовок, статус, автор и дата — все `text-t1 text-sm font-bold`. Всё «кричит», иерархии нет.
## 4.2 Консистентность

Одинаковые вещи выглядят и ведут себя одинаково во всех модулях (tracker, messenger, TMS, calls,
dashboard). Кнопка «Удалить» везде `destructive` + `ConfirmDialog`. Дата везде в одном формате.
Пустое состояние везде `EmptyState`. Это снижает когнитивную нагрузку профи-пользователя.
## 4.3 Обратная связь (feedback)

Каждое действие пользователя получает немедленный отклик:

| Действие | Ожидаемый feedback |
|---|---|
| Клик по кнопке | `active:scale-[.96]` + переход в loading при async |
| Async-операция | Спиннер/`disabled` на кнопке, оптимистичное обновление через TanStack Query |
| Успех мутации | Toast (`--z-toast`), инвалидация запроса, обновление UI |
| Ошибка | Toast с текстом + `request_id`; поле — красная граница + сообщение |
| Наведение | hover-состояние (см. §2.9) |
| Drag (Kanban) | `cursor: grabbing`, подъём карточки, тень `--sh3` |
## 4.4 Три обязательных состояния данных: loading / empty / error

Любой экран, показывающий данные, обязан описать все три:

- **Loading:** скелетоны (`animate-shimmer`) в форме будущего контента, **не** центрированный спиннер
  на весь экран (кроме первичной загрузки). Скелетон повторяет layout.
- **Empty:** `<EmptyState icon title description>` с понятным следующим шагом («Создайте первую задачу»).
  Не показывать пустую таблицу без объяснения.
- **Error:** `<ErrorBoundary>` для краша модуля + inline-ошибка для частичных сбоев + toast с `request_id`.
  Всегда есть действие «Повторить».

### Good / Bad — состояния данных

**Good:** список задач: при загрузке — 6 скелетон-строк; пусто — EmptyState с кнопкой «Создать задачу»;
ошибка — «Не удалось загрузить. Повторить» + request_id в тексте.

**Bad:** при загрузке — белый экран; пусто — просто ничего; ошибка — компонент «падает» без ErrorBoundary,
рушит весь модуль.
## 4.5 Микро-взаимодействия

Тонкие анимации создают ощущение «живого» интерфейса, но не мешают:

- Вход контента: `animate-fade-in-up` / `kanban-enter` / `dash-enter` (каскад с задержками 80/160ms).
- Hover-подъём карточек/кнопок на 1–3px.
- Typing-индикатор в мессенджере (`.typing-dot`), speaking-ring в звонках.
- Не анимируйте то, что пользователь читает/редактирует. Не зацикливайте отвлекающие анимации.
## 4.6 Отзывчивость (mobile-first, breakpoints)

Tailwind breakpoints (используются в проекте):

| Префикс | min-width | Типичное использование |
|---|---|---|
| (base) | 0 | Мобайл: одна колонка, bottom navigation (US-C05) |
| `sm:` | 640px | Крупный телефон |
| `md:` | 768px | Планшет: две колонки, инпут `md:text-sm` |
| `lg:` | 1024px | Ноутбук: сайдбар + контент |
| `xl:` | 1280px | Десктоп: многоколоночные дашборды |
| `2xl:` | 1536px | Широкий десктоп |

**Правила:**

- Базовые классы = мобайл. Расширения — через `md:`/`lg:`. Не наоборот.
- Kanban на мобайле — упрощённый (одна колонка, свайп), не «сжатый десктоп».
- Модалки на мобайле часто становятся `Sheet` (bottom/side). Таблицы — горизонтальный скролл или карточки.
- Цели нажатия на мобайле ≥ 44×44px (см. §5.5).
## 4.7 Плотность интерфейса для профи-пользователей

Hub — рабочий инструмент для команд 10–50, а не лендинг. Персоны (Алексей-dev, Мария-QA-lead,
Дмитрий-teamlead) проводят в нём часы и ценят информационную плотность и скорость:

- Компактные строки списков/таблиц; много данных на экран без «воздуха ради воздуха».
- Клавиатура — первый класс: Ctrl+K (глобальный поиск), Ctrl+N (новая задача), hotkeys в списках.
- Массовые операции (bulk actions), фильтры (JQL), сохранённые представления.
- Плотность **не** отменяет доступность: цели нажатия и контраст остаются в норме (§5).

### Good / Bad — плотность

**Good:** таблица задач: строка 40px, шрифт `text-sm`, hover подсвечивает строку, клик открывает панель,
клавиши ↑/↓ навигируют. Плотно и быстро.

**Bad:** каждая задача — огромная карточка на пол-экрана с `p-8`. QA-инженер видит 3 задачи вместо 30,
скроллит бесконечно.

### Чек-лист UX (§4)

- [ ] Ясная визуальная иерархия, один primary CTA в зоне видимости.
- [ ] Паттерны консистентны с другими модулями.
- [ ] Есть feedback на каждое действие (hover/active/loading/toast).
- [ ] Описаны loading (скелетон), empty (`EmptyState`), error (`ErrorBoundary` + toast + retry).
- [ ] Микро-взаимодействия уместны и не мешают чтению.
- [ ] Mobile-first: базовые классы мобильные, breakpoints добавляют десктоп.
- [ ] Плотность соответствует профи-аудитории, но не в ущерб a11y.

# 5. Доступность (WCAG 2.2 AA)

Целевой уровень — **WCAG 2.2 AA** (G-05, NFR-16) *(2026: переход с 2.1 — WCAG 2.2 стал ISO/IEC 40500:2025, EN 301 549 переходит на него; 2.2 обратно совместим с 2.1)*. Ниже — операционализированные критерии для дизайна. Заметки перехода: критерий 4.1.1 Parsing упразднён; Magic Link уже удовлетворяет 3.3.8 Accessible Authentication (нет когнитивного теста).
## 5.1 Контраст: 4.5:1 (текст) и 3:1 (UI)

- **Текст обычного размера:** контраст с фоном ≥ **4.5:1**.
- **Крупный текст (≥ 18px bold / ≥ 24px):** ≥ **3:1**.
- **Нетекстовые UI-элементы** (границы инпутов, иконки-действия, focus-ring): ≥ **3:1** с фоном.

`designer` обязан рассчитать контраст ключевых пар и вписать в спеку. Ориентиры по токенам:

| Пара (dark) | Назначение | Требование |
|---|---|---|
| `--t1 #f2f3f5` на `--card #191a20` | Основной текст на карточке | ≥ 4.5:1 (проходит) |
| `--t2 #9da0a8` на `--base #0d0e12` | Вторичный текст | ≥ 4.5:1 (проверять) |
| `--t3 #a1a7b3` на `--card` | Метаданные/placeholder | граничный — не использовать для важного текста |
| `--primary` на `--primary-foreground` | Текст на кнопке | ≥ 4.5:1 |

> Правило: `--t3`/`--t4` — только для второстепенной информации и placeholder. Важный контент (то, что
> пользователь обязан прочитать) — `--t1`/`--t2`.
## 5.2 Focus-индикаторы

- Глобальный `*:focus-visible { outline: 2px solid var(--primary); outline-offset: 2px; }` — база.
- Интерактивы дополнительно несут `focus-visible:ring-2 ring-ring ring-offset-2`.
- Focus **виден всегда** при навигации с клавиатуры. Никогда не `outline: none` без замены на видимый ring.
- Порядок фокуса логичен (сверху вниз, слева направо), соответствует визуальному порядку.
## 5.3 Не только цветом

Информация не передаётся **исключительно** цветом (WCAG 1.4.1):

- Статус теста: цвет **+** текст/иконка (passed «✔ Passed» зелёным, failed «✖ Failed» красным).
- Ошибка поля: красная граница **+** текст ошибки под полем, а не только красная рамка.
- Приоритет задачи: цветная полоса **+** подпись/иконка.

### Good / Bad — не только цветом

**Good:** бейдж «Failed» = красный фон (`--gR`) + иконка + слово «Failed». Дальтоник поймёт по тексту.

**Bad:** статус показан только цветной точкой без подписи — неразличимо при цветовой слепоте.
## 5.4 Клавиатура (keyboard-first)

- Всё, что кликается мышью, доступно с клавиатуры (Tab/Shift+Tab, Enter/Space, Esc для закрытия).
- Radix-примитивы дают клавиатурное поведение из коробки — **не ломать** его (см. §3.2).
- Кастомные интерактивные элементы: `role`, `tabindex`, обработка `onKeyDown` (Enter/Space).
- Модалки: focus-trap (Radix Dialog), Esc закрывает, возврат фокуса на триггер.
- Глобальные hotkeys: Ctrl+K (поиск), Ctrl+N (новая задача) — документируются в `docs/wiki/SHORTCUTS.md`.
## 5.5 Размеры целей нажатия

- **WCAG 2.2 — 2.5.8 Target Size (Minimum):** любая интерактивная цель ≥ **24×24px** (или имеет 24px-зону с учётом зазора до соседей) — это новый обязательный AA-минимум *(2026: переход с 2.1)*. Особое внимание — иконочным кнопкам и плотным тулбарам.
- Минимальная интерактивная цель: **44×44px** на touch (WCAG 2.5.5 / AAA-ориентир, но берём как норму мобайла).
- Десктоп-плотность допускает меньше, но клик-зона (padding) остаётся комфортной (≥ 32px высоты строки) и никогда не опускается ниже 24px-минимума 2.5.8.
- Иконки-кнопки: `size="icon"` = `h-10 w-10` (40px) — на мобайле увеличивать до 44px.
- Соседние цели разделены достаточным зазором, чтобы избежать промахов.
## 5.6 Screen-reader

- Каждое поле имеет `<Label>` (видимый или `sr-only`), связанный с инпутом.
- Иконки-кнопки без текста — `aria-label`.
- Изображения/аватары — осмысленный `alt`.
- Динамические сообщения (toast, ошибки валидации) — в `aria-live` регионах.
- Заголовки — семантические `h1..h6` в правильной вложенности, не «div, стилизованный под заголовок».
- Landmark-роли: `nav`, `main`, `aside` для структуры страницы.
## 5.7 Новые критерии WCAG 2.2 (2026: переход с 2.1)

- **2.5.7 Dragging Movements (AA):** любое действие, выполняемое перетаскиванием, обязано иметь альтернативу без drag. Для Hub критично: **Kanban DnD** — перемещение карточки должно быть доступно и через меню/кнопки (например, «Переместить в колонку…» в контекстном меню карточки), не только перетаскиванием. То же для сортировки списков и resize-панелей.
- **2.5.8 Target Size (Minimum) ≥ 24×24px:** см. §5.5.
- **2.4.11 Focus Not Obscured (Minimum, AA):** элемент в фокусе не должен быть полностью перекрыт другим контентом. Проверять sticky-заголовки, закреплённые панели и тосты: при Tab-навигации фокусируемый элемент обязан оставаться хотя бы частично видимым (учитывать `scroll-padding` под sticky-хедер).
- **3.3.8 Accessible Authentication (AA):** вход без когнитивного теста — Magic Link Hub удовлетворяет из коробки.
- **3.3.7 Redundant Entry / 3.2.6 Consistent Help:** не запрашивать повторно уже введённые в этом процессе данные; точка помощи — в одном и том же месте на всех страницах.

### Чек-лист a11y (§5)

- [ ] Контраст текста ≥ 4.5:1, крупного ≥ 3:1, UI-элементов ≥ 3:1 (рассчитано в спеке).
- [ ] Focus виден для всех интерактивов, порядок логичен.
- [ ] Информация не только цветом (иконка/текст дублируют).
- [ ] Полная клавиатурная навигация; Radix-поведение сохранено.
- [ ] Цели нажатия ≥ 24×24px везде (WCAG 2.2 — 2.5.8); ≥ 44px на touch; комфортные клик-зоны на десктопе.
- [ ] Labels/aria-label/alt/aria-live заданы; семантические заголовки и landmarks.
- [ ] WCAG 2.2 (2026): drag-действия имеют альтернативу без drag (2.5.7); фокус не перекрыт sticky-панелями (2.4.11).
