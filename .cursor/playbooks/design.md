# Hub — Playbook: Дизайн и дизайн-система

> Эталонный playbook для агентов `designer`, `designer-ver`, `fe1`, `fe2`, `fe-ver`.
> Источник истины по дизайн-системе: `frontend/src/app.css`. Правила: `.cursor/rules/30-frontend.mdc`.
> Ограничения ТЗ: `.cursor/rules/60-tz-constraints.mdc` · `docs/tz_constraints.md`.
> Персоны и UX-контекст: `docs/vision_and_scope.md` · `docs/user_needs_analysis_2026.md`.
>
> **Ключевой принцип:** дизайн Hub — это не картинки, а токены. Любой пиксель, цвет, отступ или радиус
> должен ссылаться на переменную из `app.css`. Хардкод цвета `#1a1a1a` — это баг, а не решение.

# 1. Кто и когда: роли дизайна

## 1.1 Общая карта ролей

Дизайн в Hub закрывают три типа агентов, работающих в конвейере:

```
product / ba / sa           designer            designer-ver          fe1 / fe2         fe-ver
    (требования)   ──────►  (дизайн-спека) ────►  (верификация) ───►  (реализация) ───► (верификация UI)
       US / AC              токены + макет        консистентность      React + Shadcn     a11y + Lighthouse
                            состояния + a11y      a11y + responsive     className-only     visual diff
```

| Агент | Маршрутизация | Роль | Артефакт | Читает | Пишет |
|-------|---------------|------|----------|--------|-------|
| `designer` | `inherit` (routed; max effort) | Дизайн-система, макеты, UX-спеки, токены | Дизайн-спека (Markdown), обновления `app.css`-токенов | `vision_and_scope.md`, `30-frontend.mdc`, `app.css`, US/AC от `ba`/`sa` | `.cursor/playbooks/`-совместимые спеки, DESIGN-SPEC.md фазы |
| `designer-ver` | `inherit` (routed; max effort) | Независимая верификация дизайна | Отчёт верификации `verified: true/false` + лог | Спека `designer`, `app.css`, реализацию `fe` | Verification report |
| `fe1`, `fe2` | `inherit` (routed; max effort) | Реализация UI по спеке | React-компоненты, `className`-расширения Shadcn | DESIGN-SPEC, `30-frontend.mdc`, Shadcn `components/ui/*` | `frontend/src/**` |
| `fe-ver` | `inherit` (routed; max effort) | Верификация реализации UI | Отчёт: a11y (axe), Lighthouse, visual, регрессия | Реализацию `fe`, спеку `designer` | Verification report |

> `team-lead` (GPT-5.6 Sol Pro; downstream — catalog-backed routing по
> `team-workflow.md` §1.1) — оркестратор и финальная инстанция приёмки. Он не рисует, но принимает
> дизайн-артефакт целиком после `designer-ver` и `fe-ver`. См. `.cursor/playbooks/team-workflow.md`.

## 1.2 Когда включается `designer`

`designer` подключается **до** `fe`, когда задача содержит любой из триггеров:

- Новый экран / страница / модальное окно, которого нет в текущем UI.
- Новый переиспользуемый компонент (не просто композиция существующих Shadcn).
- Изменение дизайн-системы: новый токен, цвет, spacing-шаг, радиус, тень, состояние.
- Изменение паттерна взаимодействия (навигация, hotkey-контур, плотность).
- Редизайн существующего экрана (например «привести Kanban к макету»).
- Любая задача с явным UX/визуальным acceptance criteria в US.

`designer` **не** нужен для:

- Багфикса верстки без изменения дизайн-контракта (например «кнопка съехала на 2px»).
- Технического рефакторинга компонентов без визуальных изменений.
- Правки текста / i18n без изменения раскладки.

В этих случаях `fe` работает напрямую, а `fe-ver` проверяет отсутствие визуальной регрессии.

## 1.3 Что делает `designer` (обязанности)

1. **Хранит и развивает дизайн-систему** — токены в `frontend/src/app.css`. Любое новое значение
   (цвет, spacing, радиус, тень) добавляется как токен, а не как inline-хардкод в компоненте.
2. **Пишет дизайн-спеки** — текстовые (Markdown) спеки для `fe`, потому что Figma в проекте нет.
   Спека = структура компонентов + токены + состояния + поведение + a11y + edge-cases (см. §6).
3. **Определяет UX-контракт** — иерархия, отступы, плотность, состояния (loading/empty/error),
   микро-взаимодействия, отзывчивость (breakpoints).
4. **Гарантирует доступность на уровне дизайна** — контраст, focus, размеры целей, keyboard-first (см. §5).
5. **Обеспечивает консистентность** — новый экран визуально неотличим от существующих: те же токены,
   те же радиусы, те же тени, та же типографика.

## 1.4 Что делает `designer-ver` (верификация)

`designer-ver` — независимый агент. Он **не** доверяет спеке `designer` на слово, а проверяет её по коду
(`app.css`, `components/ui/*`) и по чек-листам §7. Ставит `verified: true` только когда:

- все токены в спеке существуют в `app.css` (нет выдуманных переменных);
- контраст пар «текст / фон» рассчитан и проходит 4.5:1 (текст) / 3:1 (UI);
- описаны все состояния (default/hover/active/focus/disabled + loading/empty/error);
- заданы breakpoints и mobile-поведение;
- нет запрещённых паттернов (§9): хардкод цветов, inline-стили, `!important`, произвольные отступы.

## 1.5 Передача спеки в `fe` (handoff)

Handoff `designer → fe` — это короткое, понятное сообщение (2–5 предложений) + артефакт-спека. Формат
handoff описан в `.cursor/playbooks/team-workflow.md` §9. Минимум:

```
Что сделано: дизайн-спека экрана "Sprint Backlog" — структура, токены, 5 состояний, a11y.
Что проверить fe: реализовать по DESIGN-SPEC-sprint-backlog.md, только className для Shadcn.
Артефакты: DESIGN-SPEC-sprint-backlog.md (структура + токены + состояния).
Следующий шаг: fe1 верстает список, fe2 — панель фильтров (разные файлы, без конфликтов).
```

### Good / Bad — момент включения `designer`

**Good:** задача «Добавить экран настроек уведомлений» → `designer` пишет спеку с токенами и состояниями
→ `designer-ver` проверяет → `fe` реализует → `fe-ver` сверяет с спекой. Дизайн-контракт зафиксирован
до кода.

**Bad:** `fe` сразу верстает экран «на глаз», подбирая цвета `#191a20` руками. Результат: рассинхрон с
дизайн-системой, `fe-ver` заворачивает, переделка. Потеряно время команды.

### Чек-лист роли (§1)

- [ ] Определён триггер: нужен ли `designer` вообще (§1.2).
- [ ] Загружены `vision_and_scope.md`, `30-frontend.mdc`, `app.css`.
- [ ] Ясен потребитель спеки: `fe1`/`fe2` и как разделить работу без конфликтов.
- [ ] Handoff написан простым языком (2–5 предложений) + приложен артефакт-спека.

# 2. Дизайн-система Hub

## 2.1 Два имени одного и того же: `--hub-*` и реальные токены

В правиле `.cursor/rules/30-frontend.mdc` дизайн-система описана **семантическими** именами вида
`--hub-surface-raised`, `--hub-text-primary`, `--hub-border`. Это удобная для чтения ментальная модель.

В реальном коде (`frontend/src/app.css`) те же токены реализованы **краткими** именами: `--raised`,
`--t1`, `--b1`. Обе нотации описывают одну систему. Таблица соответствия — источник истины при написании
спеки и при верстке.

> **Правило для `designer`:** в спеке допускается писать семантические `--hub-*` имена для читабельности,
> но **обязательно** рядом указывать реальный токен из `app.css`. `fe` в коде использует **только реальные**
> токены/утилиты (`bg-raised`, `var(--raised)`, `text-t1`), потому что именно они существуют в теме.

### Таблица соответствия — Surfaces (поверхности)

| Семантика (`--hub-*`) | Реальный токен | Utility-класс | Light | Dark | Назначение |
|---|---|---|---|---|---|
| `--hub-surface-void` | `--void` | `bg-void` | `#ffffff` | `#08090b` | Самый глубокий фон (за всем) |
| `--hub-surface-base` | `--base` | `bg-base` / `bg-background` | `#f8f9fa` | `#0d0e12` | Базовый фон приложения (body) |
| `--hub-surface-raised` | `--raised` | `bg-raised` | `#f1f3f5` | `#141519` | Приподнятые блоки, secondary, muted |
| `--hub-surface-card` | `--card` | `bg-card` | `#ffffff` | `#191a20` | Карточки, поповеры-контент |
| `--hub-surface-input` | `--input` | `bg-[var(--input)]` | `#f1f3f5` | `#1e2028` | Поля ввода |
| — | `--sidebar` | `bg-sidebar` | `#1a1d21` | `#0b0c0f` | Сайдбар (всегда тёмный) |

## 2.2 Цветовая система (семантические цвета)

Семантические цвета заданы отдельно и имеют «сильный» (`S`) вариант для градиентов и hover. Значения
различаются в light/dark для сохранения контраста.

| Токен | Light | Dark | Утилита в коде | Назначение |
|---|---|---|---|---|
| `--blue` / `--blueS` | `#3b7ee0` / `#2563eb` | `#5b9cf5` / `#3b7ee0` | `var(--blue)` | Primary / info, ссылки |
| `--purple` / `--purpleS` | `#8b6ff0` / `#7c3aed` | `#a78bfa` / `#8b6ff0` | `var(--purple)` | TMS, warning-акцент |
| `--green` / `--greenS` | `#22c088` / `#16a34a` | `#34d399` / `#22c088` | `var(--green)` | Success, passed |
| `--amber` | `#d97706` | `#fbbf24` | `var(--amber)` | Warning, greeting |
| `--red` / `--redS` | `#ef4444` / `#dc2626` | `#f87171` / `#ef4444` | `var(--red)` | Destructive, failed, critical |
| `--orange` | `#ea580c` | `#fb923c` | `var(--orange)` | High priority, broken |
| `--gray` | `#6b7280` | `#6b7280` | `var(--gray)` | Neutral, skipped |

**Accent (акцент пользователя).** `--primary` по умолчанию = `--blue`, но переопределяется атрибутом
`data-accent="red|blue|green|purple|orange"` на корне (см. `app.css`, US-C03). Поэтому:

- Для интерактивных primary-элементов используйте `--primary` / `text-primary` / `bg-primary`,
  а не жёстко `--blue`. Тогда элемент подхватит выбранный пользователем accent.
- Для статических семантик (success/error/warning) используйте конкретный цвет (`--green`, `--red`).

### Good / Bad — использование цвета

**Good:**

```tsx
// Primary CTA — подхватывает accent пользователя
<Button variant="default">Создать задачу</Button>

// Статичная семантика ошибки
<span className="text-[var(--red)]">Тест упал</span>
```

**Bad:**

```tsx
// Хардкод HEX вместо токена — не переключится тема/accent
<button style={{ background: "#3b7ee0" }}>Создать</button>

// Primary через жёсткий blue — игнорирует data-accent пользователя
<div className="bg-[#5b9cf5]">...</div>
```

## 2.3 Тёмная тема (source of truth)

Dark-тема в Hub — не «инверсия» light, а **основной** режим (макеты рисовались тёмными). Правила:

- Тема переключается классом `.dark` на корне документа. Токены переопределяются внутри `.dark {}`.
- Никогда не пишите цвет «только для тёмной темы» хардкодом — используйте токен, у которого уже есть
  значение в обоих режимах.
- Поверхности идут по нарастанию «высоты»: `--void` < `--base` < `--raised` < `--card` < `--input`.
  Более «высокая» поверхность — светлее в dark, что создаёт ощущение слоёв без границ.
- Тени в dark сильнее (`--sh*` с высокой alpha), потому что тёмный фон гасит мягкие тени.
- Есть плавный кроссфейд при переключении темы (200ms, `--ease`) — не ломайте его inline-переопределением
  `transition: none`.

### Good / Bad — тёмная тема

**Good:** карточка задаётся `bg-card` — в light станет `#ffffff`, в dark `#191a20` автоматически.

**Bad:** `className="dark:bg-[#191a20] bg-white"` — дублирует то, что уже решает токен `--card`, и
расходится при следующем изменении палитры.

## 2.4 Типографика

| Параметр | Значение | Источник |
|---|---|---|
| Sans-serif | `Inter, -apple-system, BlinkMacSystemFont, "Segoe UI", sans-serif` | `--sans` |
| Monospace | `JetBrains Mono, ui-monospace, monospace` | `--mono` |
| Base font-size | `14px` | `body` в `app.css` |
| Base line-height | `1.5` | `body` |
| Заголовки | `font-semibold tracking-tight` | `@layer base h1..h6` |
| Сглаживание | `antialiased`, `optimizeLegibility` | `body` |

Шкала размеров (Tailwind) — используйте утилиты, а не произвольные `text-[13px]` без причины:

| Утилита | Размер | Применение |
|---|---|---|
| `text-2xl` | 24px | Заголовок карточки (`CardTitle`) |
| `text-xl` | 20px | Заголовок секции |
| `text-lg` | 18px | Подзаголовок |
| `text-base` | 16px | Крупный body (в input по умолчанию, `md:text-sm`) |
| `text-sm` | 14px | Основной body в приложении |
| `text-xs` | 12px | Метаданные, подписи |
| `text-[11px]` | 11px | Бейджи (см. `badge.tsx`) |

**Правила:**

- Вес: `font-bold` для кнопок/бейджей (см. `button.tsx`, `badge.tsx`), `font-semibold` для заголовков,
  `font-medium` для акцентных подписей, обычный — для body.
- `tracking-tight` только на заголовках. Не «сжимайте» body-текст.
- Не более 3 весов на экране. Иерархия строится размером + весом + цветом (`--t1`/`--t2`/`--t3`),
  а не десятком разных кеглей.

## 2.5 Spacing (отступы)

Hub использует Tailwind spacing-шкалу (шаг 4px). Разрешённые значения — по шкале, произвольные
`p-[13px]` запрещены без обоснования.

| Утилита | px | Типичное применение |
|---|---|---|
| `gap-1` / `p-1` | 4 | Иконка + текст вплотную |
| `gap-2` / `p-2` | 8 | Внутри бейджа, мелкие группы |
| `gap-3` / `p-3` | 12 | Поля ввода, кнопки |
| `gap-4` / `p-4` | 16 | Стандартный внутренний отступ карточки (Kanban card = 16px) |
| `p-6` | 24 | `CardHeader` / `CardContent` (Shadcn) |
| `gap-8` / `p-8` | 32 | Разделение секций |
| `py-12` | 48 | Пустые состояния (`EmptyState`) |

**Правила плотности:** Hub — инструмент для профи-команд (10–50 человек), которые проводят в нём часы.
Плотность выше, чем в consumer-приложениях. Стандартная высота строк списков компактна, но не в ущерб
целям нажатия (см. §5.5).

## 2.6 Радиусы

| Токен | Значение | Утилита | Применение |
|---|---|---|---|
| `--r1` | 6px | `rounded-[var(--r1)]` | Мелкие элементы, `sm` |
| `--r2` | 8px | `rounded-[var(--r2)]` | Кнопки, инпуты (base) |
| `--r3` | 12px | `rounded-[var(--r3)]` | Карточки Kanban, средние блоки |
| `--r4` | 16px | `rounded-[var(--r4)]` | Крупные карточки (`Card`), виджеты |
| `--pill` | 100px | `rounded-full` | Бейджи, чипы, аватары |

> Также замаплены на Tailwind: `--radius-sm=--r1`, `--radius-md=--r2`, `--radius-lg=--r3`, `--radius-xl=--r4`.
> В спеке указывайте `--r2`/`--r4`, а не «8px», чтобы `fe` использовал токен.

## 2.7 Тени и glow

| Токен | Light | Dark | Применение |
|---|---|---|---|
| `--sh1` | `0 1px 3px rgba(0,0,0,.08)` | `0 1px 3px rgba(0,0,0,.5)` | Карточка в покое (`shadow-sm`) |
| `--sh2` | мягкая двойная | усиленная | Hover карточки, поповер (`shadow-md`) |
| `--sh3` | `0 12px 40px` | сильная | Kanban hover, модалка (`shadow-lg`) |
| `--sh4` | `0 24px 80px` | максимальная | Крупные overlay (`shadow-xl`) |

**Glow-фоны** (полупрозрачные заливки для «свечения» и бейджей):

| Токен | Назначение |
|---|---|
| `--gB` | Blue glow — info-бейдж, primary hover-свечение |
| `--gP` | Purple glow — TMS, warning-бейдж |
| `--gG` | Green glow — success-бейдж |
| `--gR` | Red glow — destructive-бейдж |

**Специальные glow-утилиты (`app.css`):** `.btn-glow`, `.logo-glow`, `.hover-pulse`. Кнопка `default`
уже несёт `shadow-[0_0_20px_rgba(91,156,245,0.25)]` — не дублируйте glow сверху.

### Good / Bad — тени

**Good:** `<Card>` уже содержит `shadow-sm → hover:shadow-md`. Дизайнер указывает «состояние hover:
подъём на 2px + `--sh2`» — это ровно то, что делает компонент.

**Bad:** спека требует `box-shadow: 0 10px 30px #000` хардкодом — рассинхрон с `--sh*`, тень будет
слишком жёсткой в light-теме.

## 2.8 Easing и анимации

| Токен | Кривая | Применение |
|---|---|---|
| `--ease` | `cubic-bezier(0.25,0.1,0,1)` | Базовые переходы (цвет, фон, граница) |
| `--spring` | `cubic-bezier(0.175,0.885,0.32,1.1)` | Кнопки, карточки, вход элементов |
| `--bounce` | `cubic-bezier(0.34,1.56,0.64,1)` | Игривые микро-взаимодействия |

Готовые keyframes/утилиты в `app.css`: `animate-fade-in`, `animate-fade-in-up`, `animate-shimmer`
(скелетоны), `animate-dropdown-in`, `animate-scale-in`, `animate-pulse-online`, `kanban-enter`,
`dash-enter`, `msg-enter-x`, `login-form-animate`.

**Длительности:** 150ms — hover/цвет; 200ms — кнопки/тема; 260–280ms — карточки; 400–500ms — вход
контента. Дольше 500ms — только для декоративных фонов (login mesh 20s).

**Reduced motion:** `app.css` содержит `@media (prefers-reduced-motion: reduce)`, который гасит все
анимации до 0.01ms. Не переопределяйте это `!important`-ом в компонентах.

## 2.9 Состояния (hover / active / focus / disabled)

Каждый интерактивный элемент обязан описывать 5 состояний. Базовые паттерны из компонентов Hub:

| Состояние | Паттерн (из `button.tsx` / `input.tsx` / `card.tsx`) |
|---|---|
| default | Базовый фон/граница токенами |
| hover | Подъём `hover:-translate-y-px`, усиление тени, `hover:brightness-110`, граница `--b2` |
| active | `active:scale-[.96]` (кнопки), `active:scale-[1.02]` (Kanban card) |
| focus | `focus-visible:ring-2 focus-visible:ring-ring focus-visible:ring-offset-2`; инпут: `focus-visible:border-[rgba(91,156,245,0.3)]` + мягкий ring-shadow |
| disabled | `disabled:pointer-events-none disabled:opacity-50` |

Глобальный focus-контур задан в `app.css`: `*:focus-visible { outline: 2px solid var(--primary); outline-offset: 2px; }`. Это база доступности — не удаляйте.

### Good / Bad — состояния

**Good:** спека для кастомной кликабельной строки списка: default `bg-transparent`, hover `bg-[var(--hover)]`,
focus — глобальный ring (наследуется), active — `bg-[var(--active)]`, disabled — `opacity-50 + pointer-events-none`.

**Bad:** описан только default и hover. `fe` не знает, как выглядит focus → клавиатурная навигация
невидима → `fe-ver` заворачивает по a11y.

### Чек-лист дизайн-системы (§2)

- [ ] Все цвета/поверхности/границы — токены из `app.css` (нет HEX-хардкода).
- [ ] Primary-элементы используют `--primary` (подхватывают accent), статусы — конкретные семантики.
- [ ] Радиусы из `--r1..--r4`/`--pill`; тени из `--sh1..--sh4`; glow из `--gB/gP/gG/gR`.
- [ ] Типографика: `--sans`/`--mono`, ≤3 веса, иерархия размером+цветом.
- [ ] Spacing по 4px-шкале Tailwind.
- [ ] Для каждого интерактива описаны 5 состояний.
- [ ] Учтён `prefers-reduced-motion`, тема dark — основная.

## 3.2 Золотое правило: только `className`, не трогать Radix

Из `.cursor/rules/30-frontend.mdc` и `60-tz-constraints.mdc`:

> Shadcn компоненты: только `className` изменения, поведение Radix не трогать. Без inline-стилей, без `!important`.

Практически это значит:

- Разрешено: передавать `className` для визуальной подстройки (цвет, отступ, размер токенами).
- Разрешено: добавлять варианты через `cva` в самом компоненте (см. `button.tsx`).
- Запрещено: менять пропсы Radix, отключать `onOpenChange`, переопределять `data-state`-поведение,
  вручную управлять фокусом там, где Radix уже управляет.
- Запрещено: `style={{...}}` поверх дизайн-системы и `!important`.

### Good / Bad — расширение Shadcn

**Good:**

```tsx
// Только className, токены дизайн-системы
<Button variant="secondary" className="w-full mt-4">
  Пригласить участника
</Button>

// Новый вариант — через cva внутри button.tsx (не inline)
// variants.variant.subtle: "bg-[var(--hover)] text-t2 hover:text-t1"
```

**Bad:**

```tsx
// Inline-стиль поверх системы
<Button style={{ backgroundColor: "#5b9cf5", borderRadius: 20 }}>Ок</Button>

// !important, чтобы "перебить" Shadcn
<Dialog className="!bg-black !p-0" />

// Вмешательство в поведение Radix
<DialogPrimitive.Content onEscapeKeyDown={(e) => e.preventDefault() /* ломает UX */} />
```

## 3.3 Варианты через `cva` (class-variance-authority)

Hub задаёт варианты декларативно через `cva`. Пример из `button.tsx`:

```tsx
const buttonVariants = cva("base classes...", {
  variants: {
    variant: {
      default: "bg-gradient-to-br from-[var(--blueS)] to-[var(--blue)] text-white ...",
      destructive: "bg-gradient-to-br from-[var(--redS)] to-[var(--red)] ...",
      outline: "border border-b1 bg-transparent hover:bg-[var(--hover)] ...",
      secondary: "bg-raised text-t2 border border-b1 ...",
      ghost: "hover:bg-[var(--hover)] hover:text-accent-foreground",
      link: "text-primary underline-offset-4 hover:underline",
    },
    size: { default: "h-10 px-4 py-2", sm: "h-9 px-3", lg: "h-11 px-8", icon: "h-10 w-10" },
  },
  defaultVariants: { variant: "default", size: "default" },
});
```

**Правила для новых вариантов:**

- Новый визуальный вариант добавляется **в `variants`**, а не как ад-хок `className` на месте вызова.
- Каждый вариант использует только токены. Никаких HEX.
- Имена вариантов семантические (`destructive`, `subtle`), не по цвету (`redButton`).
- `defaultVariants` обязателен.

## 3.4 Консистентность компонентов

Матрица консистентности, которую держит `designer` и проверяет `designer-ver`:

| Ось | Правило |
|---|---|
| Кнопки | Всегда `<Button>` из Shadcn; primary CTA = `variant="default"`, отмена = `variant="ghost"`/`outline`, удаление = `variant="destructive"`. |
| Поля | Всегда `<Input>`/`<Textarea>` + `<Label>` через `FormField`; высота инпута 42px (`h-[42px]`). |
| Модалки | `<Dialog>` для форм, `<AlertDialog>`/`<ConfirmDialog>` для подтверждений, `<Sheet>` для боковых панелей. |
| Пустые состояния | Всегда `<EmptyState>` (иконка + title + description), не «самодельный» div. |
| Ошибки модулей | Каждый крупный модуль обёрнут `<ErrorBoundary>` (calls, dashboard, tracker, TMS, messenger). |
| Бейджи статусов | `<Badge variant>` или `.badge-*` классы для TMS/трекера (passed/failed/skipped/broken/blocked). |
| Скролл | `<ScrollArea>` для кастомных областей; глобальный скроллбар 5px уже стилизован. |

### Чек-лист компонентов (§3)

- [ ] Проверено, нет ли уже нужного примитива в `components/ui/*`.
- [ ] Расширение только через `className` (токены) или `cva`-вариант.
- [ ] Поведение Radix не изменено; нет `style={}`; нет `!important`.
- [ ] Новые варианты семантически названы и покрывают состояния.
- [ ] Пустые состояния через `EmptyState`, ошибки через `ErrorBoundary`.

# 4. UX-принципы

## 4.1 Иерархия

Пользователь должен за 1–2 секунды понять «что здесь главное». Инструменты иерархии в Hub:

- **Цвет текста:** `--t1` (главное) → `--t2` (вторичное) → `--t3` (метаданные). Не выделяйте всё жирным.
- **Поверхности:** важный блок — на `--card` с тенью `--sh1`; фон — `--base`; акцентная зона — `--raised`.
- **Размер:** один H1/`text-2xl` на экран; секции — `text-lg`; body — `text-sm`.
- **Акцент:** ровно один primary CTA в видимой области. Остальные действия — `secondary`/`ghost`.

### Good / Bad — иерархия

**Good:** на карточке задачи заголовок `text-t1 font-semibold`, статус — бейдж, метаданные (автор, дата)
— `text-t3 text-xs`. Взгляд идёт сверху вниз по важности.

**Bad:** заголовок, статус, автор и дата — все `text-t1 text-sm font-bold`. Всё «кричит», иерархии нет.

## 4.2 Консистентность

Одинаковые вещи выглядят и ведут себя одинаково во всех модулях (tracker, messenger, TMS, calls,
dashboard). Кнопка «Удалить» везде `destructive` + `ConfirmDialog`. Дата везде в одном формате.
Пустое состояние везде `EmptyState`. Это снижает когнитивную нагрузку профи-пользователя.

## 4.3 Обратная связь (feedback)

Каждое действие пользователя получает немедленный отклик:

| Действие | Ожидаемый feedback |
|---|---|
| Клик по кнопке | `active:scale-[.96]` + переход в loading при async |
| Async-операция | Спиннер/`disabled` на кнопке, оптимистичное обновление через TanStack Query |
| Успех мутации | Toast (`--z-toast`), инвалидация запроса, обновление UI |
| Ошибка | Toast с текстом + `request_id`; поле — красная граница + сообщение |
| Наведение | hover-состояние (см. §2.9) |
| Drag (Kanban) | `cursor: grabbing`, подъём карточки, тень `--sh3` |

## 4.4 Три обязательных состояния данных: loading / empty / error

Любой экран, показывающий данные, обязан описать все три:

- **Loading:** скелетоны (`animate-shimmer`) в форме будущего контента, **не** центрированный спиннер
  на весь экран (кроме первичной загрузки). Скелетон повторяет layout.
- **Empty:** `<EmptyState icon title description>` с понятным следующим шагом («Создайте первую задачу»).
  Не показывать пустую таблицу без объяснения.
- **Error:** `<ErrorBoundary>` для краша модуля + inline-ошибка для частичных сбоев + toast с `request_id`.
  Всегда есть действие «Повторить».

### Good / Bad — состояния данных

**Good:** список задач: при загрузке — 6 скелетон-строк; пусто — EmptyState с кнопкой «Создать задачу»;
ошибка — «Не удалось загрузить. Повторить» + request_id в тексте.

**Bad:** при загрузке — белый экран; пусто — просто ничего; ошибка — компонент «падает» без ErrorBoundary,
рушит весь модуль.

## 4.5 Микро-взаимодействия

Тонкие анимации создают ощущение «живого» интерфейса, но не мешают:

- Вход контента: `animate-fade-in-up` / `kanban-enter` / `dash-enter` (каскад с задержками 80/160ms).
- Hover-подъём карточек/кнопок на 1–3px.
- Typing-индикатор в мессенджере (`.typing-dot`), speaking-ring в звонках.
- Не анимируйте то, что пользователь читает/редактирует. Не зацикливайте отвлекающие анимации.

## 4.6 Отзывчивость (mobile-first, breakpoints)

Tailwind breakpoints (используются в проекте):

| Префикс | min-width | Типичное использование |
|---|---|---|
| (base) | 0 | Мобайл: одна колонка, bottom navigation (US-C05) |
| `sm:` | 640px | Крупный телефон |
| `md:` | 768px | Планшет: две колонки, инпут `md:text-sm` |
| `lg:` | 1024px | Ноутбук: сайдбар + контент |
| `xl:` | 1280px | Десктоп: многоколоночные дашборды |
| `2xl:` | 1536px | Широкий десктоп |

**Правила:**

- Базовые классы = мобайл. Расширения — через `md:`/`lg:`. Не наоборот.
- Kanban на мобайле — упрощённый (одна колонка, свайп), не «сжатый десктоп».
- Модалки на мобайле часто становятся `Sheet` (bottom/side). Таблицы — горизонтальный скролл или карточки.
- Цели нажатия на мобайле ≥ 44×44px (см. §5.5).

## 4.7 Плотность интерфейса для профи-пользователей

Hub — рабочий инструмент для команд 10–50, а не лендинг. Персоны (Алексей-dev, Мария-QA-lead,
Дмитрий-teamlead) проводят в нём часы и ценят информационную плотность и скорость:

- Компактные строки списков/таблиц; много данных на экран без «воздуха ради воздуха».
- Клавиатура — первый класс: Ctrl+K (глобальный поиск), Ctrl+N (новая задача), hotkeys в списках.
- Массовые операции (bulk actions), фильтры (JQL), сохранённые представления.
- Плотность **не** отменяет доступность: цели нажатия и контраст остаются в норме (§5).

### Good / Bad — плотность

**Good:** таблица задач: строка 40px, шрифт `text-sm`, hover подсвечивает строку, клик открывает панель,
клавиши ↑/↓ навигируют. Плотно и быстро.

**Bad:** каждая задача — огромная карточка на пол-экрана с `p-8`. QA-инженер видит 3 задачи вместо 30,
скроллит бесконечно.

### Чек-лист UX (§4)

- [ ] Ясная визуальная иерархия, один primary CTA в зоне видимости.
- [ ] Паттерны консистентны с другими модулями.
- [ ] Есть feedback на каждое действие (hover/active/loading/toast).
- [ ] Описаны loading (скелетон), empty (`EmptyState`), error (`ErrorBoundary` + toast + retry).
- [ ] Микро-взаимодействия уместны и не мешают чтению.
- [ ] Mobile-first: базовые классы мобильные, breakpoints добавляют десктоп.
- [ ] Плотность соответствует профи-аудитории, но не в ущерб a11y.

# 5. Доступность (WCAG 2.2 AA)

Целевой уровень — **WCAG 2.2 AA** (G-05, NFR-16) *(2026: переход с 2.1 — WCAG 2.2 стал ISO/IEC 40500:2025, EN 301 549 переходит на него; 2.2 обратно совместим с 2.1)*. Ниже — операционализированные критерии для дизайна. Заметки перехода: критерий 4.1.1 Parsing упразднён; Magic Link уже удовлетворяет 3.3.8 Accessible Authentication (нет когнитивного теста).

## 5.1 Контраст: 4.5:1 (текст) и 3:1 (UI)

- **Текст обычного размера:** контраст с фоном ≥ **4.5:1**.
- **Крупный текст (≥ 18px bold / ≥ 24px):** ≥ **3:1**.
- **Нетекстовые UI-элементы** (границы инпутов, иконки-действия, focus-ring): ≥ **3:1** с фоном.

`designer` обязан рассчитать контраст ключевых пар и вписать в спеку. Ориентиры по токенам:

| Пара (dark) | Назначение | Требование |
|---|---|---|
| `--t1 #f2f3f5` на `--card #191a20` | Основной текст на карточке | ≥ 4.5:1 (проходит) |
| `--t2 #9da0a8` на `--base #0d0e12` | Вторичный текст | ≥ 4.5:1 (проверять) |
| `--t3 #a1a7b3` на `--card` | Метаданные/placeholder | граничный — не использовать для важного текста |
| `--primary` на `--primary-foreground` | Текст на кнопке | ≥ 4.5:1 |

> Правило: `--t3`/`--t4` — только для второстепенной информации и placeholder. Важный контент (то, что
> пользователь обязан прочитать) — `--t1`/`--t2`.

## 5.2 Focus-индикаторы

- Глобальный `*:focus-visible { outline: 2px solid var(--primary); outline-offset: 2px; }` — база.
- Интерактивы дополнительно несут `focus-visible:ring-2 ring-ring ring-offset-2`.
- Focus **виден всегда** при навигации с клавиатуры. Никогда не `outline: none` без замены на видимый ring.
- Порядок фокуса логичен (сверху вниз, слева направо), соответствует визуальному порядку.

## 5.3 Не только цветом

Информация не передаётся **исключительно** цветом (WCAG 1.4.1):

- Статус теста: цвет **+** текст/иконка (passed «✔ Passed» зелёным, failed «✖ Failed» красным).
- Ошибка поля: красная граница **+** текст ошибки под полем, а не только красная рамка.
- Приоритет задачи: цветная полоса **+** подпись/иконка.

### Good / Bad — не только цветом

**Good:** бейдж «Failed» = красный фон (`--gR`) + иконка + слово «Failed». Дальтоник поймёт по тексту.

**Bad:** статус показан только цветной точкой без подписи — неразличимо при цветовой слепоте.

## 5.4 Клавиатура (keyboard-first)

- Всё, что кликается мышью, доступно с клавиатуры (Tab/Shift+Tab, Enter/Space, Esc для закрытия).
- Radix-примитивы дают клавиатурное поведение из коробки — **не ломать** его (см. §3.2).
- Кастомные интерактивные элементы: `role`, `tabindex`, обработка `onKeyDown` (Enter/Space).
- Модалки: focus-trap (Radix Dialog), Esc закрывает, возврат фокуса на триггер.
- Глобальные hotkeys: Ctrl+K (поиск), Ctrl+N (новая задача) — документируются в `docs/wiki/SHORTCUTS.md`.

## 5.5 Размеры целей нажатия

- **WCAG 2.2 — 2.5.8 Target Size (Minimum):** любая интерактивная цель ≥ **24×24px** (или имеет 24px-зону с учётом зазора до соседей) — это новый обязательный AA-минимум *(2026: переход с 2.1)*. Особое внимание — иконочным кнопкам и плотным тулбарам.
- Минимальная интерактивная цель: **44×44px** на touch (WCAG 2.5.5 / AAA-ориентир, но берём как норму мобайла).
- Десктоп-плотность допускает меньше, но клик-зона (padding) остаётся комфортной (≥ 32px высоты строки) и никогда не опускается ниже 24px-минимума 2.5.8.
- Иконки-кнопки: `size="icon"` = `h-10 w-10` (40px) — на мобайле увеличивать до 44px.
- Соседние цели разделены достаточным зазором, чтобы избежать промахов.

## 5.6 Screen-reader

- Каждое поле имеет `<Label>` (видимый или `sr-only`), связанный с инпутом.
- Иконки-кнопки без текста — `aria-label`.
- Изображения/аватары — осмысленный `alt`.
- Динамические сообщения (toast, ошибки валидации) — в `aria-live` регионах.
- Заголовки — семантические `h1..h6` в правильной вложенности, не «div, стилизованный под заголовок».
- Landmark-роли: `nav`, `main`, `aside` для структуры страницы.

## 5.7 Новые критерии WCAG 2.2 (2026: переход с 2.1)

- **2.5.7 Dragging Movements (AA):** любое действие, выполняемое перетаскиванием, обязано иметь альтернативу без drag. Для Hub критично: **Kanban DnD** — перемещение карточки должно быть доступно и через меню/кнопки (например, «Переместить в колонку…» в контекстном меню карточки), не только перетаскиванием. То же для сортировки списков и resize-панелей.
- **2.5.8 Target Size (Minimum) ≥ 24×24px:** см. §5.5.
- **2.4.11 Focus Not Obscured (Minimum, AA):** элемент в фокусе не должен быть полностью перекрыт другим контентом. Проверять sticky-заголовки, закреплённые панели и тосты: при Tab-навигации фокусируемый элемент обязан оставаться хотя бы частично видимым (учитывать `scroll-padding` под sticky-хедер).
- **3.3.8 Accessible Authentication (AA):** вход без когнитивного теста — Magic Link Hub удовлетворяет из коробки.
- **3.3.7 Redundant Entry / 3.2.6 Consistent Help:** не запрашивать повторно уже введённые в этом процессе данные; точка помощи — в одном и том же месте на всех страницах.

### Чек-лист a11y (§5)

- [ ] Контраст текста ≥ 4.5:1, крупного ≥ 3:1, UI-элементов ≥ 3:1 (рассчитано в спеке).
- [ ] Focus виден для всех интерактивов, порядок логичен.
- [ ] Информация не только цветом (иконка/текст дублируют).
- [ ] Полная клавиатурная навигация; Radix-поведение сохранено.
- [ ] Цели нажатия ≥ 24×24px везде (WCAG 2.2 — 2.5.8); ≥ 44px на touch; комфортные клик-зоны на десктопе.
- [ ] Labels/aria-label/alt/aria-live заданы; семантические заголовки и landmarks.
- [ ] WCAG 2.2 (2026): drag-действия имеют альтернативу без drag (2.5.7); фокус не перекрыт sticky-панелями (2.4.11).

# 6. Формат дизайн-спеки для передачи `fe` (без Figma)

## 6.1 Почему текстовая спека

В Hub нет Figma. Дизайн-контракт живёт как **Markdown-спека** (`DESIGN-SPEC-<screen>.md`) плюс, при
необходимости, HTML-мокап через `gsd-sketch`. Текст — это то, что `fe` может точно реализовать, а
`designer-ver`/`fe-ver` — проверить.

## 6.2 Обязательные разделы спеки

Каждая дизайн-спека содержит ровно эти разделы:

```
# DESIGN-SPEC: <название экрана / компонента>

## 1. Контекст
- Связанные US/AC: US-Mxx, ...
- Персона и сценарий: кто и зачем открывает экран
- Точка входа / выхода (роут, откуда попадает пользователь)

## 2. Структура (layout)
- ASCII-схема раскладки (см. 6.3)
- Дерево компонентов: какие Shadcn-примитивы и в какой вложенности
- Сетка/колонки, breakpoints поведение

## 3. Токены
- Поверхности: какие --void/--base/--raised/--card/--input где
- Текст: --t1/--t2/--t3 по элементам
- Границы, радиусы (--rN), тени (--shN), spacing (шкала)
- Акцент: где --primary, где статичные семантики

## 4. Состояния
- default / hover / active / focus / disabled для каждого интерактива
- loading (скелетон), empty (EmptyState текст), error (сообщение + retry)

## 5. Поведение
- Что происходит по клику/вводу/drag
- Async: оптимистичные обновления, инвалидация запросов
- Навигация, hotkeys, фокус-менеджмент

## 6. Доступность
- Контраст ключевых пар (рассчитан)
- aria-*, labels, порядок фокуса, keyboard-map
- Цели нажатия

## 7. Edge-cases
- Длинный текст / переполнение
- 0 / 1 / много элементов
- Оффлайн / медленная сеть
- Права (RBAC): что видит Viewer vs Owner

## 8. Разбивка для fe (кто что делает)
- fe1: <файлы/компоненты>
- fe2: <файлы/компоненты>
- точки синхронизации
```

## 6.3 Пример ASCII-схемы раскладки

Раскладку описывают ASCII-диаграммой — она однозначна и не требует Figma:

```
+--------------------------------------------------------------+
| PageHeader (sticky, page-header-blur)                        |
|  [H1 text-2xl t1]              [Filter chips] [+ Button pri.] |
+--------------------------------------------------------------+
| Toolbar: [Search input h-42] [Tabs] [View toggle]            |
+------------------+-------------------------------------------+
| Sidebar (aside)  | Content (main)                            |
| bg-sidebar       |  Card grid (gap-4)                        |
| w-64 lg: only    |  +----------+ +----------+ +----------+   |
|                  |  | Card r4  | | Card r4  | | Card r4  |   |
|                  |  | sh1      | |          | |          |   |
|                  |  +----------+ +----------+ +----------+   |
|                  |  EmptyState (py-12) if no data           |
+------------------+-------------------------------------------+
```

## 6.4 Пример дерева компонентов

```
<ErrorBoundary>
  <PageHeader>
    <h1 className="text-2xl font-semibold text-t1">Sprint Backlog</h1>
    <Button variant="default">+ Задача</Button>   // Ctrl+N
  </PageHeader>
  <div className="flex gap-4">
    <aside className="hidden lg:block w-64">
      <FilterPanel />                              // fe2
    </aside>
    <main className="flex-1">
      {isLoading && <SkeletonList count={6} />}    // animate-shimmer
      {isEmpty && <EmptyState icon={Inbox} title="Пусто" description="Создайте задачу" />}
      {isError && <InlineError onRetry={refetch} />}
      {data && <IssueList items={data} />}         // fe1
    </main>
  </div>
</ErrorBoundary>
```

## 6.5 GSD-инструменты дизайна

`designer`/`fe` используют GSD-скиллы для дизайна:

| Скилл | Когда | Что даёт |
|---|---|---|
| `gsd-sketch` | Быстрый набросок нового экрана | Одноразовый HTML-мокап, мульти-вариант, до фиксации спеки |
| `gsd-sketch-wrap-up` | После sketch | Упаковывает находки в persistent skill |
| `gsd-ui-phase` | Фаза с фронтендом | Генерирует UI-SPEC.md (дизайн-контракт фазы) — база для DESIGN-SPEC |
| `gsd-ui-review` | После реализации | Ретроспективный 6-pillar visual-аудит реализованного UI |

Поток: `gsd-sketch` (варианты) → зафиксировать DESIGN-SPEC → `fe` реализует → `gsd-ui-review` / `fe-ver`.

### Good / Bad — спека

**Good:** спека содержит все 8 разделов, ASCII-раскладку, дерево компонентов с конкретными Shadcn,
рассчитанный контраст и разбивку fe1/fe2. `fe` реализует без вопросов.

**Bad:** спека — «сделать красиво как в Linear, тёмная тема». Нет токенов, нет состояний, нет edge-cases.
`fe` домысливает, результат непредсказуем, `designer-ver` не может верифицировать.

### Чек-лист спеки (§6)

- [ ] Присутствуют все 8 разделов.
- [ ] Есть ASCII-раскладка и дерево компонентов с конкретными Shadcn-примитивами.
- [ ] Все токены названы (реальные из `app.css`).
- [ ] Описаны состояния (5 интерактивных + loading/empty/error).
- [ ] Рассчитан контраст, задан keyboard-map и aria.
- [ ] Перечислены edge-cases и RBAC-видимость.
- [ ] Работа разбита между fe1/fe2 без пересечения файлов.

# 7. Верификация дизайна (`designer-ver`)

`designer-ver` — независимая нейросеть, проверяющая артефакт `designer` по коду и чек-листам. Не ставит
`verified: true` без прохождения всех блоков ниже. Итог — отчёт с явными PASS/FAIL по пунктам.

## 7.1 Блок «Консистентность токенов»

- [ ] Каждый токен из спеки существует в `frontend/src/app.css` (grep по имени переменной).
- [ ] Нет HEX-хардкода вместо токена (кроме обоснованных исключений вроде статусных `.badge-*`).
- [ ] Primary-элементы используют `--primary` (accent-aware), а не жёсткий `--blue`.
- [ ] Радиусы из `--r1..--r4`/`--pill`; тени из `--sh1..--sh4`; glow из `--gB/gP/gG/gR`.
- [ ] Spacing по 4px-шкале; нет произвольных `p-[13px]` без причины.

## 7.2 Блок «Доступность»

- [ ] Контраст пар «текст/фон» рассчитан и ≥ 4.5:1 (текст) / ≥ 3:1 (крупный/UI).
- [ ] Focus-индикаторы описаны и видимы; глобальный `focus-visible` не удалён.
- [ ] Информация не только цветом (есть текст/иконка-дубликат).
- [ ] Полный keyboard-map; Radix-поведение не изменено.
- [ ] Цели нажатия ≥ 44px (touch); labels/aria/alt заданы.

## 7.3 Блок «Отзывчивость»

- [ ] Заданы breakpoints и поведение на mobile/tablet/desktop.
- [ ] Mobile-first: базовые классы мобильные.
- [ ] Модалки/таблицы имеют мобильную стратегию (Sheet / карточки / горизонтальный скролл).
- [ ] Нет фиксированных ширин, ломающих узкие экраны.

## 7.4 Блок «Соответствие дизайн-системе»

- [ ] Использованы существующие Shadcn-примитивы, где возможно.
- [ ] Расширение только `className`/`cva`; нет `style={}`/`!important`.
- [ ] Пустые состояния через `EmptyState`, ошибки через `ErrorBoundary`.
- [ ] Экран визуально консистентен с соседними модулями.
- [ ] Учтён `prefers-reduced-motion`; dark-тема — основная и корректна.

## 7.5 Формат отчёта `designer-ver`

```
# DESIGN-VER: <экран> — <дата HH:MM>

verified: false            # true только при 0 FAIL

## Токены:        PASS/FAIL (детали)
## a11y:          PASS/FAIL (контраст-таблица)
## Responsive:    PASS/FAIL
## Дизайн-система: PASS/FAIL

## Findings
- [CRITICAL] ...
- [HIGH] ...
- [MINOR] ...

## Вердикт
- Причина отказа / условия для verified: true
```

> `verified: true` ставится только при отсутствии CRITICAL/HIGH и приложенном обосновании. Иначе спека
> возвращается `designer` с конкретными findings. См. цикл верификации `team-workflow.md` §7.

### Чек-лист `designer-ver` (§7)

- [ ] Пройдены все 4 блока (токены, a11y, responsive, дизайн-система).
- [ ] Контраст рассчитан, а не «на глаз».
- [ ] Findings классифицированы (CRITICAL/HIGH/MINOR).
- [ ] Вердикт с явным `verified: true/false` и датой.

# 9. Антипаттерны дизайна

Сводная таблица запрещённых паттернов. Любой из них — основание для FAIL у `designer-ver`/`fe-ver`.

| # | Антипаттерн | Почему плохо | Правильно |
|---|---|---|---|
| 1 | Хардкод цвета (`#191a20`, `rgb(...)`) | Не переключается тема/accent, рассинхрон с палитрой | Токен: `bg-card`, `var(--raised)`, `text-t1` |
| 2 | Inline-стиль поверх системы (`style={{background:...}}`) | Обходит дизайн-систему, не тематизируется | `className` с токенами |
| 3 | `!important` в CSS/классах | Ломает каскад, было 56 случаев (Phase 8 вычистил) | Правильная специфичность через токены/утилиты |
| 4 | Произвольные отступы (`p-[13px]`, `mt-[7px]`) | Ломает визуальный ритм 4px-сетки | Шкала Tailwind (`p-3`, `p-4`) |
| 5 | Недоступный контраст (важный текст на `--t3`) | < 4.5:1, нечитабельно, нарушает WCAG AA | Важный текст на `--t1`/`--t2` |
| 6 | Изменение поведения Radix (пропсы, focus, data-state) | Ломает a11y и UX Shadcn/Radix | Только `className`, поведение не трогать |
| 7 | Информация только цветом (точка без подписи) | Недоступно при цветовой слепоте (WCAG 1.4.1) | Цвет + иконка/текст |
| 8 | `outline: none` без замены | Пропадает focus, невозможна клавиатурная навигация | Оставить `focus-visible` ring/outline |
| 9 | Несогласованные компоненты (свой div вместо `EmptyState`) | Визуальный рассинхрон между модулями | Переиспользовать примитивы `components/ui/*` |
| 10 | Жёсткий `blue` вместо `--primary` для primary CTA | Игнорирует выбранный accent пользователя | `variant="default"` / `bg-primary` |
| 11 | Дублирование `dark:`-хардкода поверх токена | Расходится при смене палитры | Использовать токен с готовыми light/dark |
| 12 | Спека без состояний/edge-cases | `fe` домысливает, непредсказуемый результат | Полная спека по §6.2 |
| 13 | Отключение анимаций `!important` (ломает reduced-motion) | Конфликт с `prefers-reduced-motion` политикой | Полагаться на глобальный media-query |
| 14 | Новый компонент вместо композиции существующих | Раздувает библиотеку, рассинхрон | Проверить `components/ui/*`, композировать |
| 15 | Цели нажатия < 44px на mobile | Промахи, недоступно для touch | ≥ 44×44px, зазоры между целями |

### Финальный чек-лист design.md

- [ ] Все цвета/поверхности/границы/радиусы/тени — токены из `app.css`.
- [ ] Shadcn расширен только `className`/`cva`; Radix не тронут; нет `style`/`!important`.
- [ ] 5 состояний + loading/empty/error для каждого интерактивного экрана.
- [ ] WCAG AA: контраст, focus, не-только-цвет, keyboard, цели нажатия, aria.
- [ ] Спека полная (8 разделов), верифицирована `designer-ver`.

# Приложение C. Рецепты по компонентам Shadcn

Для каждого частого примитива — как правильно расширять и типичный good/bad.

## C.1 Dialog (модальная форма)

**Назначение:** формы, требующие фокуса пользователя (создание задачи, приглашение).

**Good:**

```tsx
<Dialog open={open} onOpenChange={setOpen}>
  <DialogContent className="max-w-lg">
    <DialogHeader>
      <DialogTitle className="text-xl text-t1">Новая задача</DialogTitle>
      <DialogDescription className="text-t2">Заполните поля ниже</DialogDescription>
    </DialogHeader>
    <form className="flex flex-col gap-4">
      <FormField label="Заголовок"><Input /></FormField>
      <FormField label="Описание"><Textarea /></FormField>
    </form>
    <DialogFooter>
      <Button variant="ghost" onClick={() => setOpen(false)}>Отмена</Button>
      <Button variant="default" type="submit">Создать</Button>
    </DialogFooter>
  </DialogContent>
</Dialog>
```

**Bad:** переопределять `onEscapeKeyDown`/`onPointerDownOutside` без причины (ломает ожидаемое закрытие),
или ставить `!p-0 !bg-black`. Отмена не должна быть `type="submit"`.

## C.2 Select (выпадающий список)

**Good:** статусный select с cva-вариантами цвета по значению, только `className`. Radix управляет
клавиатурой (стрелки, typeahead) — не дублируйте `onKeyDown`.

**Bad:** самодельный `<div>`-дропдаун вместо `<Select>` — теряется клавиатура и a11y.

## C.3 DropdownMenu (меню действий)

**Good:** меню «...» действий строки таблицы; пункты `DropdownMenuItem`, деструктивные — `text-[var(--red)]`;
разделитель `DropdownMenuSeparator`. `align="end"`.

**Bad:** popover c ручными кнопками вместо `DropdownMenu` — нет roving-tabindex и Esc.

## C.4 Tooltip

**Good:** тултип на icon-only кнопке дополняет (не заменяет) `aria-label`. Задержка появления из Radix.

**Bad:** класть в тултип критичную информацию, доступную только по hover (недоступно с клавиатуры/touch).

## C.5 Command (Ctrl+K)

**Good:** глобальный поиск US-M07 через `Command`; группы результатов (Задачи/Люди/Проекты/Файлы),
user-scope фильтрация на бэке; Enter открывает, стрелки навигируют.

**Bad:** рендерить все сущности без серверной user-scope фильтрации (нарушение NF-03) и без виртуализации.

## C.6 Sheet / Popover

**Good:** `Sheet` для боковых панелей (детали задачи, фильтры), `Popover` для лёгких контекстных
поповеров (выбор даты, emoji). На mobile Sheet — `side="bottom"`.

**Bad:** использовать `Dialog` там, где нужен неблокирующий `Popover`, — лишний оверлей и focus-trap.

## C.7 Форма (FormField + Label + Input/Textarea)

**Good:** каждое поле в `FormField` c `<Label>`; ошибка под полем текстом + красная граница; кнопка
submit `type="submit"`, отмена `type="button"`.

**Bad:** placeholder вместо label (исчезает при вводе, недоступно screen-reader); ошибка только цветом рамки.

### Чек-лист рецептов (Прил. C)

- [ ] Выбран правильный примитив под задачу (Dialog vs Sheet vs Popover vs DropdownMenu).
- [ ] Расширение только `className`/`cva`; Radix-поведение сохранено.
- [ ] Форма: label + сообщение об ошибке текстом + корректные `type`.
- [ ] Icon-only кнопки имеют `aria-label` (+ Tooltip как дополнение).

# Приложение E. A11y-рецепты по паттернам

## E.1 Форма

- Каждое поле: `<Label htmlFor>` + `<Input id>`; обязательные — с `aria-required`.
- Ошибка: `aria-invalid` + `aria-describedby` на текст ошибки; текст, не только цвет.
- Группировка связанных полей: `<fieldset>` + `<legend>`.

## E.2 Модалка/Sheet

- `role="dialog"` (Radix), `aria-labelledby` на заголовок, `aria-describedby` на описание.
- Focus-trap внутри, Esc закрывает, фокус возвращается на триггер (Radix из коробки — не ломать).

## E.3 Таблица/список

- Семантическая `<table>` c `<th scope>` или ARIA grid для интерактивных.
- Навигация ↑/↓; выделенная строка — `aria-selected`; сортировка — `aria-sort`.
- Виртуализация не должна ломать порядок чтения screen-reader.

## E.4 Меню/дропдаун

- `DropdownMenu` даёт `role=menu`/`menuitem`, roving tabindex, typeahead — не дублировать вручную.
- Деструктивные действия визуально (цвет + иконка) и по тексту отличимы.

## E.5 Тосты/уведомления

- Контейнер тостов — `aria-live="polite"` (ошибки — `assertive`).
- Тост не исчезает слишком быстро для чтения; критичный — с кнопкой действия/закрытия.

### Чек-лист a11y-рецептов (Прил. E)

- [ ] Формы: label+ошибка текстом+aria-invalid.
- [ ] Модалки: labelledby+focus-trap+Esc+возврат фокуса.
- [ ] Списки/таблицы: семантика+клавиатура+aria-selected/sort.
- [ ] Меню: нативное поведение Radix сохранено.
- [ ] Тосты: aria-live, достаточное время, действие.

| Класс | Назначение |
|---|---|
| `.btn-glow` | Свечение primary-кнопки (уже в variant=default) |
| `.logo-glow` | Свечение логотип-бейджа |
| `.hover-pulse` | Пульс CTA при hover |

## H.4 Статусные бейджи (TMS/трекер)

Классы `.badge-passed/.badge-failed/.badge-skipped/.badge-broken/.badge-blocked` имеют отдельные значения
для light и dark (light — насыщенные HEX, dark — glow-токены). Это осознанное исключение из «только
токены»: статусы тестов имеют фиксированную семантику цвета. Новые статусы добавляйте тем же паттерном
(`.badge-<name>` + `.dark .badge-<name>`), а не inline.

### Good / Bad — модульные классы

**Good:** карточка задачи = `<div className="kanban-card kanban-card-high">` — весь визуал и hover уже
описаны, priority-бордер оранжевый через `--orange`.

**Bad:** вручную собирать градиент, hover и бордер карточки в компоненте — дубль `app.css`, рассинхрон.

# Приложение I. Глоссарий и FAQ

## I.1 Глоссарий

| Термин | Значение |
|---|---|
| Токен | CSS-переменная дизайн-системы (`--card`, `--t1`), единственный источник значений |
| Surface | Поверхность-фон по «высоте»: void<base<raised<card<input |
| Accent | Пользовательский primary-цвет (`data-accent`), подхватывается через `--primary` |
| cva | class-variance-authority — декларативные варианты компонента |
| Glow | Полупрозрачная цветная заливка/свечение (`--gB/gP/gG/gR`) |
| Дизайн-спека | Markdown-контракт экрана (8 разделов), заменяет Figma |
| DoD | Definition of Done — критерии готовности артефакта |
| a11y | Accessibility, целевой уровень WCAG 2.2 AA (2026: переход с 2.1) |

## I.2 FAQ

**Нужен новый цвет — что делать?** Добавить токен в `app.css` (`:root` + `.dark`), затем использовать его.
Не хардкодить HEX в компоненте.

**Shadcn-компонент выглядит не так, как в спеке — можно поправить пропсы Radix?** Нет. Только `className`
или новый `cva`-вариант. Если нужен другой поведенческий контракт — это задача для `arch`/`fe` с
согласованием, а не правка на месте.

**Как показать состояние загрузки?** Скелетоны `animate-shimmer` в форме контента. Полноэкранный спиннер —
только для самой первой загрузки приложения.

**Placeholder вместо label — ок?** Нет. Label обязателен (может быть `sr-only`), placeholder — подсказка,
не замена подписи.

**Как проверить контраст?** Рассчитать соотношение для пары «текст/фон» по значениям из `app.css`
(см. Приложение G) и вписать в спеку. `designer-ver` перепроверяет.

**Тёмная или светлая тема — что основное?** Тёмная (макеты рисовались тёмными). Но обе обязаны работать —
используйте токены с готовыми значениями в обоих режимах.

**Можно `!important`?** Нет. Phase 8 вычистил 56 случаев. Новые запрещены (`60-tz-constraints.mdc`).

# Приложение J. Онбординг нового дизайн-агента (первые 5 шагов)

Если ты `designer`/`designer-ver`/`fe` и впервые открываешь дизайн-задачу Hub — выполни по порядку:

   текст (t1→t4), границы (b1→b3), радиусы, тени, семантические цвета и accent-механику.
